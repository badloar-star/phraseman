## 0. Вердикт

Планы 00–08 исполнимы, взаимосогласованы и защищены от главных ловушек
(купленный доступ ≠ знание, голосовая неуверенность ≠ ошибка ученика, immutable
контент, fail-closed). **Исполняем как архитектурный закон** с поправками ниже.

утверждённая владельцем эволюция планов ПОСЛЕ их написания: формат юнита
**12 сессий × (7–9 карточек)** в зонах understand → use → master с угасанием

плюс готовые контракты звёзд/ворот/evidence/delayed/content-studio и рабочая
E1-генерация в админке. Планы и модуль не противоречат — модуль уточняет
структуру юнита. Ревизия стыкует их явно (см. R-01).

## 2. Поправки (R-##). Каждая: что в доке → что делаем → почему

### R-01 · Юнит = 12 сессий; звёздный слот = сессия ⚠️ требует владельца
Доки 03/05/06: эпизод = 8–9 узлов графа, ровно **8** gate-слотов × 3 звезды = 24.
Утверждённый позже формат: **12 сессий** × 7–9 карточек (understand/use/master).
DecisionRegistry (08 §6.2) это уже параметризует (`gateEligibleSlotsPerEpisode`).
**Рекомендация:** слот = сессия → 12 слотов × 3 = **36/юнит**; карточки сессии
агрегируются в 0–3 звезды сессии по критериям 05 (завершил / качество / без
подсказки); кривая ворот и минимумы пересчитываются пропорционально той же
формулой (55%→65%, минимумы 21–26/36). Экономика 05 сохраняет смысл, числа —
новая версия registry v2. Альтернатива (8 слотов поверх 12 сессий) создаёт
кривой маппинг «слот ≠ то, что открывается с карты» — не рекомендую.

### R-02 · Network-voice governance НЕ строим в пилоте
04/06 §3.2 — огромный слой consent/egress/deletion/minors для СЕТЕВОЙ обработки
голоса. Решение владельца: распознавание ТОЛЬКО on-device, аудио не сохраняется.
→ В пилоте нет сетевого голосового трафика вообще: строим только on-device путь
(`speaking_recognition_options` + `speaking_word_match`) + typed fallback.
Схемы остаются дискриминированными (on-device вариант `VoiceReleaseRequirements`),
network-ветка подключится, если Club-capstone войдёт в объём. Экраны с обещанием
сетевой обработки — не показываем (решение §3.2 хендовера).

### R-03 · Delayed-probe scheduler — контракты да, сервер нет
05/06: durable mastery только через server-timing receipts в окне D+3…D+7.
Контракты уже в модуле (`delayed_probe.ts`, `delayed_receipts.ts`). Серверный
scheduler в пилоте E1 не строим; durable-claims в UI не показываем. По докам
delayed НИКОГДА не блокирует ворота — ничего не теряем. Волна после главы 1.

### R-04 · Single-admin режим вместо maker-checker
08: reviewer ≠ author, 4 permission-роли, waivers с экспирацией. Владелец один.
→ Роли и receipts остаются В СХЕМЕ; в пилоте один UID владельца имеет все права,
каждый approve пишет receipt с reason (audit сохраняется). Non-waivable список 08
соблюдаем ПОЛНОСТЬЮ (это защита от брака, не бюрократия); waivable-предупреждения
показываются с однокнопочным acknowledge вместо полной waiver-модели.

### R-05 · Device-preview гранты не блокируют seal в пилоте
08 §13: два one-use гранта iOS+Android до publish. В пилоте: web-превью
(с подписью «структурный предпросмотр») + ручная проверка в Metro. Механизм
грантов — после пилота. Web-превью НЕ помечается как runtime parity (закон 08).

### R-06 · Checkpoint: контракт сразу, реализация после E1
Схемы checkpoint-контракта проектируем в юните с первого дня (иначе переделка),
сам экран/логика E8 — отдельной волной.

### R-07 · Монетизация — новый слой, которого в доках нет
Free 3 сессии/день + Plus (план-вплетение, безлимит, скидка на буст, полный
Mistake Lab) — решения D12–D14. Оформляем как `EntitlementPolicy` рядом с gate
policy в DecisionRegistry-стиле (versioned, не хардкод в компонентах), пейволл —
существующий стек. Access Boost из 05 без изменений.

### R-08 · Аналитика: минимальный набор сразу, DTS-7 позже
07 требует большой каталог + ITT-когорты. Пилот: 6 событий в существующий
`trackEvent` (path_viewed, episode_started/completed, activity_attempted,
star_best_updated, gate_viewed) по правилам each-event-serves-a-decision.
Полный DTS-7/эксперименты — когда появится когорта (R3+ этап 07).

### R-09 · Rollout-манифест позже, сейчас ENABLE_DEV_TOOLS
07 §2 capability manifest — перед когортой R3. В пилоте гейт — dev-флаг (A4).

### R-10 · Моушн: два регистра (решение F23)
Осознанное отклонение от 04: церемонии финала 1.5–2.5с со скипом, конфетти-физика,
полёты с трейлами, комбо — В НАГРАДАХ. Ошибки — строго по 04: без тряски, без
карающих эффектов, feedback-токены 120–240мс. Пер-карточный цикл — «живой»
(решение §3.1: ответ → Проверить → inline вердикт → авто-дальше). Reduced motion
и freeze/layout-контракты — без исключений.

### R-11 · Доставка E1: bundled fallback + Storage authenticated read
Решение E22 = рекомендация 06 §7.3. Полный seal→activate→rollback поток — при
переходе к главе 1; для пилота E1 достаточно staging-паблиша тем же пайплайном
(`vertical_slice` по 08 и так lab/staging-only).

### R-12 · Reference Evidence Pack: макеты на tier-B/C + скрины Kimi
08 §10.5 требует first-hand capture ДО UI. Собран web-research (tier B/C,
2026-07-26) + скрины поставки Kimi. First-hand запись экрана Duolingo с
устройства владельца — желательна, но не блокирует HTML-макеты (они и есть
наш собственный дизайн); блокирующим остаётся только distinctiveness-gate 04
(не копировать композицию/персонажей/подписи — проверяю на каждом макете).
