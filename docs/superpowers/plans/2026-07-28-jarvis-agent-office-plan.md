# Phraseman «Джарвис» — утверждённый план реализации

> План фиксирует решения владельца. Он не запускает сервисы, не выдаёт секреты и не меняет production.

**Цель:** создать управляемого продуктового и инженерного помощника, который принимает сообщения владельца из Telegram или админки, превращает сигналы из приложения в доказательные решения, а после явного согласования может подготовить ветку, тесты, draft PR, merge или deploy.

**Базовая архитектура:** Cloud Run orchestrator получает только redacted, ограниченные evidence packets из Firebase. Cloud Tasks обеспечивает очередь и retries. Решения хранятся как audit-able объекты в Firestore. Существующий Telegram-канал репортов и живая панель `admin/v2/legacy.html` — два интерфейса одной серверной очереди. GitHub App создаёт ветки и draft PR в изолированном runner; merge/deploy допустимы лишь после отдельного одноразового approval владельца, привязанного к точному PR SHA и окружению.

## Утверждённые принципы

- Режимы: выключен → наблюдение → совет → подготовка → исполнение.
- В Telegram и админке можно писать обычным текстом: задавать вопросы, давать задачи и добавлять ограничения к активным задачам.
- Решения, статусы, вопросы, PR и approvals дублируются в Telegram и админке; серверный журнал задачи — источник истины.
- Merge/deploy возможны только после отдельного owner approval; деньги, доступ, auth и Firestore Rules никогда не переходят в автоматическое исполнение.
- Approval привязан к owner Telegram user/chat, живёт 15 минут и одноразовый; для merge/deploy он содержит точный PR SHA, target environment, health gate и rollback plan.
- Модель не получает PII, секреты и полный текст репортов; Telegram получает только безопасные проекции.
- GitHub App может иметь широкие права, но policy engine и tool allowlist остаются обязательными даже при таких правах.
- Начальный бюджет: €50/месяц; €1 на стандартную задачу и €5 на глубокую задачу.

## Пользовательский опыт

Примеры сообщений владельца:

- «Проверь падение retention за неделю» — создаёт задачу анализа.
- «Почему выросли ошибки оплаты?» — возвращает доказательный ответ с источниками.
- «Подготовь PR для исправления» — создаёт ограниченную задачу и просит approval до записи.
- «Не трогай paywall» — добавляет ограничение к текущей задаче.

Команды: `/status`, `/brief`, `/tasks`, `/stop`, `/approve <код>`, `/reject <код>`.

## Фазы

### Фаза 0 — политика и изоляция

Threat model, роли owner/admin/read-only, redaction, 90-дневный retention, kill switch, бюджет, allowlist инструментов и перечень запрещённых областей.

**Готово, когда:** опасная операция и browser-доступ к приватным агентным данным блокируются тестами.

### Фаза 1 — наблюдатель в живой админке

Перенести безопасные проекции существующего Agent Office в `admin/v2/legacy.html`; собрать bounded агрегаты `error_reports`, `user_reports`, health и audit; показать свежесть, confidence, источники, empty/error states и daily digest без модели как fallback.

**Готово, когда:** неполные данные никогда не становятся ложными нулями, а прямого Firestore-доступа из браузера нет.

### Фаза 2 — советник, Telegram и текстовый диалог

Добавить структурированное решение: факт, гипотеза, 2–3 варианта, рекомендация, риск, стоимость, метрика успеха и rollback. Реализовать text-to-task, question-to-answer, уточнения контекста, одноразовые approve/reject, quiet hours, rate limit и audit trail.

**Готово, когда:** повторный callback не меняет состояние; каждая задача одинакова в Telegram и админке; расход виден владельцу.

### Фаза 3 — подготовка кода

GitHub App с подтверждёнными владельцем широкими правами, isolated runner, policy-based tool allowlist, secret scan, тестовые gates и draft PR. В Telegram и админке отправляется PR summary: diff, тесты, риск, стоимость, rollback.

**Готово, когда:** PR не может обойти проверки или policy engine, несмотря на широкие GitHub-права.

### Фаза 4 — merge и deploy по разрешению владельца

После review Джарвис выполняет merge или deploy только для указанного PR SHA и окружения, подтверждённых отдельным owner approval. Changed SHA, истёкший approval, плохой health или отсутствие rollback немедленно отменяют исполнение.

**Готово, когда:** результат и audit receipt дублируются в Telegram и админке. Firestore Rules, auth, деньги, права и удаление остаются ручными.

### Фаза 5 — голос и визуальная оболочка

Голосовой briefing запускается вручную, имеет текстовый дубль и лимит 3 минуты/день. Визуализация поддерживает reduced-motion и 2D fallback; тяжёлый 20k WebGL particle swarm идёт только после отдельного performance gate.

### Фаза 6 — эксперименты

Предложения A/B-тестов с control group, заранее заданной метрикой, stop rule и rollback; rollout более 5% требует нового approval.

## Не входит в MVP

- Merge, push в `main` или production deploy без отдельного approval владельца для конкретного SHA/окружения.
- Изменение Firestore Rules, auth, цен, платежей, refunds, банов, VIP и прав доступа.
- Автоматическая отправка пользователям сообщений.
- Передача PII, секретов или полного содержания репортов в модель/Telegram.
- Полный 3D-интерфейс и автостарт голоса.

1. Подтверждено: MVP — наблюдение + советы + Telegram approvals + текстовый диалог.
2. Подтверждено: использовать текущий Telegram-канал репортов и расширить его до диалога с владельцем.
3. Подтверждено: бюджет и Secret Manager policy.
4. Подтверждено: широкие права GitHub App, но policy engine и отдельный approval перед каждой внешней операцией.
5. Подтверждено: merge/deploy возможны после approval, привязанного к PR SHA, окружению, health gate и rollback plan.
6. До старта нужно назначить owner Telegram ID и список production environments, затем подготовить исполнимые TDD-планы Фаз 0–2.
