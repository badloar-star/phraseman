# Admin v2 YouTube Analytics Design

## Цель

Добавить в Admin v2 отдельный read-only инструмент `Аналитика → Видео YouTube`, который показывает, как пользователи взаимодействуют с YouTube-разделом Phraseman:

- клики по кнопке видео на главной;
- открытия каталога;
- выбор конкретного видео;
- реальные запуски встроенного плеера;
- активное время просмотра;
- достижение 25%, 50%, 75% и 95% ролика;
- нажатия на открытие конкретного видео или канала во внешнем YouTube.

Инструмент не раскрывает список аккаунтов и не хранит персональную историю просмотров. Уникальность считается по анонимному Firebase `user_pseudo_id` и в интерфейсе называется «анонимные экземпляры приложения», а не «люди», «аккаунты» или гарантированно постоянные установки. Переустановка приложения или сброс идентификатора может создать новый экземпляр.

## Границы и честные определения

- «Просмотр» начинается только при состоянии YouTube-плеера `PLAYING`.
- Активное время растёт по настенным секундам только пока плеер играет. Пауза, buffering, фон приложения и перемотка не увеличивают время.
- Глобальный `viewCount`, полученный из YouTube-фида, не смешивается с поведением внутри Phraseman.
- `Linking.openURL()` подтверждает только нажатие и передачу ссылки операционной системе. Метрики называются «Нажали открыть видео» и «Нажали открыть канал», а не «перешли», «посмотрели» или «подписались».
- После открытия внешнего YouTube приложение не видит длительность просмотра, подписку или дальнейшие действия.
- Учитываются только анонимные экземпляры приложения, давшие согласие на необязательную аналитику.
- Исторические данные до выпуска версии с новыми событиями восстановить нельзя.
- Firebase Analytics BigQuery export обновляется не в реальном времени. Экран обязан показывать время свежести данных.
- При нормальной работе JS-таймера аварийное завершение обычно теряет не более одного номинального 10-секундного интервала checkpoint. OS suspension, остановка WebView или задержка таймера могут привести к большей потере; жёсткая 10-секундная гарантия не заявляется.

## Выбранная архитектура

Использовать существующий путь:

`React Native → consent-gated Firebase Analytics → BigQuery export → admin-only callable → Admin v2`.

Не создавать сырой поток просмотров в Firestore: он увеличит стоимость записей, усложнит приватность и продублирует уже существующее аналитическое хранилище.

Не использовать YouTube Analytics API как основной источник. Он подходит для общей статистики канала, но не доказывает, что конкретный просмотр пришёл из Phraseman. Возможная сверка с ним остаётся отдельной будущей интеграцией.

## Событийный контракт

Каждое событие отправляется только после согласия на аналитику. Каноническое поле сессии — существующее `session_id`; дополнительный `product_session_id`, который автоматически добавляет общий Firebase helper, рассматривается только как совместимый alias и не создаёт вторую модель сессий.

Обязательные поля всех девяти событий:

- `schema_version`;
- `event_id` для дедупликации;
- `session_id`;
- `channel_id`;
- `source` из конечного allowlist;
- платформа, версия приложения и build — через существующий аналитический контекст.

Обязательные поля по типу события:

- `youtube_home_entry_click` и `youtube_catalog_open`: общие поля, без `video_id` и `playback_id`;
- `youtube_video_select`, `youtube_player_ready` и `youtube_external_video_open`: общие поля + `video_id`, без обязательного `playback_id`;
- `youtube_playback_start`, `youtube_playback_checkpoint` и `youtube_playback_end`: общие поля + `video_id` + `playback_id`;
- `youtube_channel_open`: общие поля; `video_id` добавляется только для `source=player`, `playback_id` не обязателен.

События:

1. `youtube_home_entry_click` — нажатие кнопки видео на главной.
2. `youtube_catalog_open` — каталог действительно открыт.
3. `youtube_video_select` — выбрана карточка конкретного видео.
4. `youtube_player_ready` — встроенный YouTube-плеер готов.
5. `youtube_playback_start` — впервые получено состояние `PLAYING` для `playback_id`.
6. `youtube_playback_checkpoint` — накопительный снимок активного времени и позиции; отправляется по интервалу, при паузе и уходе приложения в фон.
7. `youtube_playback_end` — завершение попытки при конце ролика, выходе с экрана, внешнем открытии или ошибке. Отзыв согласия является privacy-исключением: попытка очищается локально без terminal-события, потому что после закрытия consent gate новые аналитические события запрещены.
8. `youtube_external_video_open` — нажато открытие конкретного видео во внешнем YouTube.
9. `youtube_channel_open` — нажато открытие канала; `source=catalog|player`.

Checkpoint содержит только ограниченные аналитические поля:

- `active_watch_ms` — накопительное активное время;
- `position_ms` — текущая позиция;
- `duration_ms` — длительность ролика;
- `max_position_permille` — максимальная достигнутая позиция 0–1000; это диагностическое поле, перемотка учитывается;
- `end_reason` для terminal-события из allowlist.

Название видео не отправляется как свободный пользовательский текст. Админская таблица сопоставляет `video_id` с доверенным названием каталога или ограниченным аналитическим измерением, нормализованным на сервере.

Все события и поля регистрируются в существующем `app/product_analytics_event_catalog.ts`. Этот каталог остаётся единым источником истины для event names, warehouse, metric IDs и allowlist полей. Отдельный `youtube_analytics_contract.ts` отвечает за построение и проверку payload, но не создаёт параллельный реестр событий. Тест каталога должен отклонять неизвестные/запрещённые поля и дубли metric IDs.

## Измерение встроенного плеера

Текущий embed уже использует `enablejsapi=1`. `buildLingmanEmbedHtml()` переводится на официальный YouTube IFrame Player API:

`YT.Player → onReady/onStateChange/getCurrentTime/getDuration → ReactNativeWebView.postMessage`.

React Native принимает сообщения только ожидаемой версии и типа, проверяет числовые границы и игнорирует неизвестные поля. Сам WebView не получает возможности вызывать произвольные нативные действия.

Один `playback_id` живёт от первого `PLAYING` до конца ролика, выхода с экрана, внешнего открытия, отзыва согласия или ошибки. Пауза и временный фон не создают новую попытку; возобновление продолжает тот же `playback_id` и не отправляет второй start.

Активное время считается по настенным часам во время `PLAYING`, а не по разнице `getCurrentTime()`, чтобы перемотка вперёд не считалась просмотром. Checkpoint отправляется каждые 10 секунд воспроизведения и немедленно при pause и background. Terminal snapshot отправляется при ended, выходе, внешнем открытии или ошибке. При отзыве согласия попытка очищается локально без отправки terminal snapshot и любых других аналитических событий.

Повторная доставка безопасна: checkpoint накопительный, а BigQuery сначала берёт `MAX(active_watch_ms)` по составному ключу `(user_pseudo_id, playback_id, video_id, schema_version)`, затем суммирует попытки. Внутри попытки `video_id` и `channel_id` обязаны оставаться неизменными; конфликтующая строка считается invalid и не попадает в метрики. Повторные callback не должны создавать второй `youtube_playback_start` для того же составного ключа.

## Backend и права

Создать отдельные модули, не увеличивая уже крупный `admin_product_analytics.ts`:

- `app/youtube_analytics_contract.ts`;
- `functions/src/admin_youtube_analytics_core.ts`;
- `functions/src/admin_youtube_analytics.ts`;
- `admin/v2/scripts/pages/youtube-analytics.js`.

Callable `adminYoutubeAnalytics`:

- требует Firebase Auth admin claim и следует существующей серверной политике `ENFORCE_APP_CHECK`; строгое App Check enforcement включается только после настройки и проверки App Check-провайдера для Admin web;
- использует семантическое право `analytics.read`;
- право получают `owner`, `admin` и `analyst`;
- принимает период 7, 28 или 90 дней, платформу `all|ios|android`, необязательные `videoId` и `channelId`;
- использует date-pruned BigQuery scan, event-name allowlist, `maximumBytesBilled`, bounded response и кэш 10 минут;
- не возвращает `user_pseudo_id`, UID, имя или сырые события.

## Агрегация

BigQuery:

1. фильтрует только YouTube-события и выбранный период;
2. отклоняет неизвестные версии схемы;
3. дедуплицирует по `event_id`;
4. собирает одну попытку по `(user_pseudo_id, playback_id, video_id, schema_version)` и проверяет неизменность канала/видео;
5. берёт максимальные накопительные значения попытки;
6. возвращает только агрегаты.

### Точные определения показателей

- **Событийные клики/открытия** — количество дедуплицированных событий соответствующего типа.
- **Анонимные экземпляры** для шага — `COUNT(DISTINCT user_pseudo_id)` среди валидных событий этого шага в выбранном периоде и фильтрах.
- **Попытка просмотра** — один валидный составной ключ `(user_pseudo_id, playback_id, video_id, schema_version)` с `youtube_playback_start` и `active_watch_ms > 0`.
- **Суммарное активное время** — сумма финального `MAX(active_watch_ms)` всех валидных попыток.
- **Среднее, p50 и p90 времени** — распределение финального `active_watch_ms` по попыткам просмотра, не по людям и не по паре «экземпляр × видео».
- **Анонимные экземпляры со стартом конкретного видео** — distinct `user_pseudo_id` среди попыток этого `video_id`.
- **Накопили ≥25/50/75/95% длительности** — число валидных попыток, где `MIN(active_watch_ms, duration_ms) / duration_ms` достигло порога. Это пороги накопленного активного времени, а не доказательство просмотра уникальных отрезков и не максимальная позиция. Перемотка сама по себе порог не повышает; повтор одного отрезка увеличивает активное время и поэтому может повысить порог.
- **Воронка** — distinct пары `(user_pseudo_id, session_id)` выбранного периода. Каждый следующий шаг учитывается только если он произошёл после предыдущего в той же сессии; для шагов после выбора должны совпадать `channel_id` и `video_id`. Число на следующем шаге не может превышать предыдущий шаг. Процент шага равен `current_step_pairs / previous_step_pairs`; первая ступень показывает абсолютное значение без процента перехода.
- **Таблица видео** — та же семантика, сгруппированная по `channel_id, video_id`; её время/процентили считаются по попыткам, уникальность — по `user_pseudo_id`.
- **Временное окно** — события фильтруются по UTC timestamp в полуинтервале `[from, to)`. Попытка относится к окну и UTC-дню своего валидного start; для неё учитываются checkpoint/end до `to`. Незавершённая попытка использует последний доступный checkpoint и остаётся помеченной как незавершённая.
- **Дневной тренд** — клики относятся к UTC-дню события, а запуски и активное время попытки — к UTC-дню `youtube_playback_start`.

Основные показатели:

- клики с главной;
- открытия каталога;
- выборы видео;
- готовые плееры;
- запуски воспроизведения;
- анонимные экземпляры приложения со стартом;
- суммарное активное время;
- среднее, p50 и p90 активного времени;
- попытки, накопившие активное время не меньше 25%, 50%, 75% и 95% длительности;
- нажатия открытия видео и канала;
- дневной тренд;
- таблица по `video_id`;
- воронка `главная → каталог → выбор → старт → 25% → 75%`.

Качество данных:

- время последнего доступного события;
- события без обязательных полей для своего типа;
- исключённые дубли;
- terminal-события без найденного старта;
- неизвестные версии схемы;
- доля событий, прошедших валидацию;
- состояние `ready|empty|partial|error`.

## Admin v2 UI

Инструмент получает отдельный route `#youtube-analytics` и mount point `youtube-analytics-panel`. Ссылка на него находится в текущем аналитическом хабе `#analytics`, который открывается из области «Деньги / Аналитика». Новый route добавляется в `SUB_ROUTES`, но не в `ADMIN_SECTIONS`, поэтому восьмой раздел главной навигации не появляется. Экран следует `docs/design/ADMIN_UI_BIBLE.md` и текущей палитре Admin v2.

Структура:

1. Заголовок «Аналитика видео YouTube» и короткое объяснение измерений.
2. Единая строка фильтров: период, платформа, канал, видео и одна главная кнопка «Обновить данные».
3. Компактные KPI: клики с главной, запуски, анонимные экземпляры со стартом, активное время, среднее время по попыткам, нажатия открытия канала.
4. Линейный график запусков и времени по дням с доступной табличной альтернативой.
5. Воронка с абсолютными значениями и процентами между этапами.
6. Сортируемая таблица видео.
7. Блок «Что мы можем измерить» со свежестью, напоминанием «учитываются только согласившиеся экземпляры» и ограничениями точности. Процент охвата согласия не показывается: выбранный источник не содержит допустимого знаменателя из отказавшихся экземпляров.

Таблица видео показывает:

- название и YouTube ID вторым уровнем;
- выборы;
- запуски;
- анонимные экземпляры со стартом;
- активное время;
- среднее, p50 и p90;
- попытки, накопившие ≥25/50/75/95% длительности;
- внешние открытия видео.

UX-требования:

- спокойный data-dense layout без декоративного video hero;
- понятные русские названия вместо внутренних ключей;
- SVG-иконки, без emoji;
- tooltip для управляющих элементов;
- видимый keyboard focus и логичный Tab order;
- цвет не является единственным сигналом;
- таблица остаётся читаемой в компактном режиме;
- отсутствие горизонтального скролла всей страницы;
- проверки на 375, 768, 1024 и 1440 px;
- состояния loading, empty, partial и error;
- при ошибке обновления сохраняется последний успешный snapshot с предупреждением.

## Ошибки и деградация

- Недоступный IFrame API не блокирует просмотр видео; аналитика молча пропускает недоступные события, а плеер сохраняет текущий fallback.
- Ошибка отправки Firebase Analytics не влияет на навигацию или воспроизведение.
- Ошибка BigQuery возвращает безопасное состояние источника, без сырого текста инфраструктурной ошибки в UI.
- Empty state объясняет, что данные появятся после выпуска версии и очередного BigQuery export.
- Partial state показывает доступные агрегаты и отдельно перечисляет неполные источники.

## Проверка

- Unit-тесты чистого контракта и нормализации сообщений WebView.
- Тесты учёта active time: play, pause, buffering, seek, resume, ended, background и повторные callback.
- Проверка red/green для дедупликации и `MAX(active_watch_ms)` на составной ключ `(user_pseudo_id, playback_id, video_id, schema_version)`.
- Unit-тесты BigQuery request parsing и response shaping.
- Контрактные тесты Admin v2 для route, callable bridge, mount point, состояний и доступности.
- `node --check` для модулей Admin v2.
- Сфокусированный Functions build/test.
- Ручной сценарий на iOS и Android: play/pause/seek/fullscreen/background/external.
- Проверка отказа от аналитики: YouTube-события не отправляются.
- Проверка размеров 375/768/1024/1440 px.

## Критерии приёмки

- Один реальный запуск не удваивается повторными callback.
- Пауза, buffering, background и перемотка не увеличивают активное время.
- По каждому видео доступны выборы, старты, анонимные экземпляры, суммарное/среднее/p50/p90 время по попыткам и пороги накопленного активного времени 25/50/75/95%.
- Клики канала разделены по источнику.
- Без аналитического согласия события не отправляются.
- Внешнее открытие нигде не называется подтверждённым переходом или просмотром.
- Интерфейс объясняет, что 10 секунд — номинальный checkpoint-интервал, а OS suspension или остановка WebView могут увеличить потерю при аварийном завершении.
- Запрос ограничен периодом, allowlist событий, кэшем и `maximumBytesBilled`.
- Экран доступен только ролям с `analytics.read`.
- Loading, empty, partial и error не разрушают геометрию экрана и не скрывают последний успешный snapshot.
- Новая аналитика не меняет существующую работу YouTube-кнопки, каталога, встроенного плеера и внешних ссылок.

## Вне текущего объёма

- список конкретных аккаунтов или персональная история просмотров;
- подтверждение подписки на YouTube-канал;
- измерение просмотра после ухода во внешний YouTube;
- восстановление исторических данных;
- OAuth-интеграция с YouTube Analytics API;
- real-time отчёт через Firestore.
