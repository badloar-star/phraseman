# ТЗ (после релиза): серверная очистка брошенных гостевых аккаунтов

Governance-ID: TG-AF94830E945A
Status: Proposed — после релиза 2.0.0 (запрос координатора 10.10 23:05). Кода нет; деплой только владельцем.
Owner: сессия 1 · ЯДРО (сервер); удаление по кнопке — сессия 5 (§AA-36)

## Outcome

Гость, который удалил приложение или перестал им пользоваться, не оставляет на сервере данные навсегда. Через
понятный срок бездействия сервер сам удаляет данные гостя — тем же путём, что и ручное удаление аккаунта.

**Что не входит:** удаление гостя по кнопке «Удалить аккаунт». Его чинит сессия 5 (§AA-36: замок гостю, запасной
`accountDeleteMine`, телефон стирается сразу, сервер дожимается фоном).

## Scope

- Новая плановая функция `guestRetentionSweep` (functions/src/guest_retention_sweep.ts), раз в сутки, ночью UTC.
- Кандидат — пользователь, у которого **одновременно**:
  - нет привязанного входа: нет записей `auth_links/*` на этот stable_id, а Firebase Auth-пользователь анонимный
    (`providerData.length === 0`);
  - нет активной подписки, покупки, пожизненного доступа и VIP: entitlement-поля пустые или истекли;
  - нет непогашенных монетных операций и споров: открытых возвратов, chargeback, неоплаченных заказов;
  - `last_active_at` старше срока бездействия.
- **Срок бездействия:** 400 дней — больше года, чтобы годовой цикл (каникулы, сезонная учёба) не задел живых людей.
  Окончательное значение решает владелец; кандидаты на обсуждение — 365 / 400 / 540 дней.
- **Удаление** идёт через существующую цепочку `account_delete_job` (та же полнота, те же коллекции, тот же журнал),
  но **без 14-дневной отсрочки**: восстанавливать гостя нечем, у него нет входа.
- **Лимит за запуск:** не больше 200 удалений. Остаток — в следующие сутки. Каждое удаление — отдельная задача
  с идемпотентным id `guest-retention:<stableId>`, повторный запуск её не дублирует.
- **Журнал:**
  - каждое решение пишется в лог с префиксом `[GUEST-RETENTION]`: кандидат, причина пропуска, результат;
  - итог запуска (найдено / удалено / пропущено по причинам) — в `admin_log` и в департамент Джарвиса (счётчик);
  - PII в логи не попадают: только количества и хэш stable_id.

## Architecture

1. Выборка — только индексированным запросом с `limit`:
   `users where last_active_at < now − срок orderBy last_active_at limit 500`. Нужен одиночный индекс по
   `last_active_at` (составной не нужен).
2. Для каждого кандидата проверки делаются в порядке «дешёвые сначала»:
   1. entitlement-поля из того же документа — без лишнего чтения;
   2. `auth_links` по stable_id — 1 запрос с `limit(1)`;
   3. Firebase Auth `getUser` — без Firestore-стоимости;
   4. открытые денежные записи — 1 запрос с `limit(1)`.
3. Подходящих отдаём `enqueueAccountDeletion({ reason: 'guest_retention', graceMs: 0 })` — тот же код, что у ручного
   удаления.
4. **Выключатель:** remote-флаг `guest_retention_enabled`, по умолчанию `false`. Есть режим «сухого прогона»
   `dryRun`: только считает и пишет журнал, ничего не удаляет. Первую неделю после выкладки — только сухой прогон.

## Security and privacy

- Удаляются только гости без входа и без денег — у таких людей нет способа вернуть данные, и они ничего не потеряют.
- Политика конфиденциальности уже честная. Раздел 19: «We do not promise automatic deletion after a fixed inactivity
  period unless such a deletion job is implemented and active». **До включения правка не нужна.**
- **При включении** (до выкладки) в раздел 19 добавить строку:
  - «Guest accounts (no Google or Apple sign-in) with no purchases and no activity for 400 days are deleted
    automatically, using the same process as account deletion.»
  - Число — то, что выберет владелец. Синхронизировать legal:sync.
- Детские данные не затрагиваются отдельно: правило одно для всех гостей.

## Technical debt

- `last_active_at` пишется не всеми старыми клиентами. Гость без этого поля **не** удаляется: «неизвестно» не значит
  «неактивен». Таких считаем в журнале отдельно.

## Стоимость Firestore (оценка)

Цены — порядок величины для multi-region; точные цифры по региону проекта сверить перед выкладкой.

| Статья | Ориентир |
|---|---|
| Сухой прогон | ≈ 500 чтений выборки + ≤ 2 чтения на кандидата ≈ 1 500 чтений/сутки ≈ 45 000/месяц |
| Удаление одного гостя | ≈ 30–80 удалений документов (users и подколлекции, индексы имён, лидерборд, ссылки) |
| При лимите 200/сутки | ≈ 6 000–16 000 удалений/сутки — центы в сутки по прайсу удалений |
| Итог | Шум на фоне обычной синхронизации |

- Холодный старт функции раз в сутки бесплатен по сути: минимум инстансов 0.

## Verification

- Юнит-тесты на отбор:
  - гость с подпиской, гость с привязкой, гость с открытым возвратом, гость без `last_active_at` — не удаляются;
  - брошенный гость — удаляется.
- Тест идемпотентности: двойной запуск не создаёт второй задачи.
- Тест лимита: 201-й кандидат уходит на следующий запуск.
- Сухой прогон на проде — неделя: счётчики видны в админке до включения удаления.

## Rollback

- Флаг `guest_retention_enabled = false` — функция ничего не делает.
- Удалённое не возвращается. Поэтому сухой прогон и выключатель по умолчанию обязательны.
