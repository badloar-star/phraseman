# Task packet: награда за просмотр 70 % видео, серверная и экономическая часть («1 · Ядро», 05.11.2026)

Только проект. Кода и деплоя нет до ОК владельца на макет. Клиентский план: `video-full-reward-plan-2026-11-05.md` («8 · Моменты»).

## Outcome
+500 монет за полный просмотр каждого видео, один раз навсегда на пару (uid, videoId). Решения владельца: награда при просмотре 70 % длительности; дневного предела нет; воскресного ×2 нет.

## Scope
- Сервер: `functions/src/coin_wallet_policy.ts` (новый источник кошелька `video_full`), тест `functions/src/coin_wallet_policy.test.ts`.
- Клиент (файлы Ядра): `app/level_spin_star_grants.ts` (`levelSpinStarOperationAmountV1`: обход множителя Супер-воскресенья для `videofull_`, как для `chapterexam_`), запись активности в `PRACTICE_RUNE_ACTIVITIES` делают Моменты.
- Документ экономики: этот файл служит ECONOMY-документом до решения, куда его переносить (в `docs/` файла ECONOMY.md нет, есть папка `docs/economy`).

## Architecture
1. Формат операции: `requestId = videofull_<40 hex>`, где hex = sha1(uid | videoId). Один ключ на пару, поэтому повтор, двойной тап и повторный просмотр дают тот же ключ. Кошелёк уже идемпотентен по requestId.
2. Сервер принимает `videofull_` только с суммой РОВНО 500 и promotionEligibility gameplay. Любая другая сумма отклоняется (как у chapterexam, где РОВНО 20).
3. Множитель Супер-воскресенья для `videofull_` не применяется (клиентский обход, иначе 1000 отклонятся сервером и зависнут в очереди).
4. Принцип «телефон решает, сервер хранит» (замок владельца 22.10): сервер не пытается судить, досмотрел ли человек. Он хранит факт по requestId и проверяет только структуру.
5. Мягкая проверка правдоподобия, НЕ блокирующая: интервал между двумя наградами за видео меньше 0,6 × длительности предыдущего видео по серверному времени помечается как аномалия. Награда при этом выдаётся. Длительность клиент присылает в операции не нужно: хватит метки времени сервера и справочной длительности из каталога видео, если она известна; иначе проверка пропускается с логом причины.
6. Лог аномалий `[VIDEO-REWARD]` (uid-хэш, videoId, интервал, причина, решение) для админки. Жёсткая защита (блокировка, потолок) только по накопленным данным и по слову владельца.

## Антифарм-оценка
500 монет это половина цены ранга (1000). Без дневного потолка один бот с накрученными событиями плеера соберёт монеты за весь каталог за минуты. Ограничивает только число видео в каталоге: конечная сумма = 500 × число видео. Это принятый владельцем риск. Следить по метрике «наград за час на пользователя»; порог для первого оповещения предлагаю 10 наград за час.

## Определение «до конца» (для Моментов)
Из плана Моментов, с моей стороны добавлю: `ended` одному не верить. Рекомендуемое правило: накопленные непрерывно сыгранные секунды не меньше 70 % длительности (владелец 05.11: порог 70 %, не 100 %; ended одного недостаточно и не обязателен), перемотка вперёд не засчитывается, пауза не копится. Для видео без известной длительности и для лайвов не начислять, писать причину.

## Security and privacy
Сервер сохранит videoId просмотренных видео и время награды. Это данные активности, их нужно добавить абзацем в политику конфиденциальности до релиза (раздел о данных активности) и в стирание при удалении аккаунта (спецификация account_delete и Джарвис, если он читает кошелёк).
