## 0. Главное за минуту

1. **Почти всё лежит только на телефонах.** На сервере легаси-спинов практически нет:
   `level_spin_credits` — **1 документ на всю базу**, `level_spin_results` — **0**, пользователей с
   ненулевым `progress.level_reward_spin_balance` — **1** (из 5 447 документов `users`).
   Значит, миграция выполняется **на телефоне**, а число затронутых людей и предметов **с сервера
   не посчитать** (NOT_RUN: данных нет на сервере физически).
2. **Сейчас в рабочей ветке спины уже «заморожены»:** экран спина удалён (PM-046, `5c98ac424`),
   все функции выдачи возвращают «ничего не выдано» (PM-047), `claimLocalLevelSpin` /
   `claimLocalLevelSpinWithRunes` вызвать больше неоткуда. Накопленные кредиты спинов лежат у людей
   мёртвым грузом до миграции.
3. **Подарки уровня и выигранные призы спина живут 72 часа** (`GIFT_TTL_MS`, `LOCAL_RESULT_TTL_MS`).
   Долгоживущих вещей три: **кредиты спинов (без срока)**, **неполученные подарки «Дневного пути»
   (без срока)** и **зависший платный спин** (оплачен рунами, приз не забран).
4. **Ожидаемая ценность одного спина по каталогу v7 — ~80 / ~130 / ~140 монет** (скромная /
   средняя / щедрая оценка призов). ~76% её дают косметика и жемчуг; прямых рун в среднем всего ~5.
   Платный спин стоил **300 рун** — примерно вдвое дороже ожидаемой ценности.
5. Рекомендация программы — **вариант «Средне»**: бесплатный спин = 130 монет (ровно ожидаемая
   ценность), платный = не меньше 300, жемчуг ×10 (D15), руны 1:1, Plus-дни не конвертируются, а
   **включаются**.

## 4. Предлагаемые таблицы компенсации (сводка — полная таблица в §7)

| Предмет | Скромно | **Средне (рекомендация)** | Щедро |
|---|---|---|---|
| Бесплатный кредит спина | 50 | **130** | 300 |
| Платный спин с незабранным призом | max(300; ценность приза) | **max(300; ценность приза)** | 300 + ценность приза |
| Руны в подарке/призе | N | **N** | N |
| Жемчуг в подарке/призе | N×10 | **N×10** | N×10 |
| Plus-дни | включить | **включить** | включить |

Обоснование:
- **Скромно**: спин ≈ 60% ожидания — отражает то, что часть призов (XP, подсказки) в 2.0 ничего не
  стоит. Минимум всё равно не ноль: D51 говорит «превращаются в монеты».
- **Средне**: спин = его ожидаемая ценность; никто не теряет в среднем, никто не получает
  непропорционально. Не раздувает экономику рангов (D34: сначала пересмотреть цену, а не
  раздавать бонусы).
- **Щедро**: каждый спин засчитан как купленный (300). Человек с 20 спинами сразу получает 6 000
  монет — это 3 ранга (1 000 + 2 000 + 3 000). Риск: обесценит первые ранги для самых активных.
  Вариант разумен, если владелец хочет «жест благодарности»; тогда предлагаем **потолок 20 спинов
  на человека** (указать это отдельной строкой при утверждении).

Правило D51 «купленное за руны — не меньше цены» выполнено во всех трёх вариантах: платный спин
никогда не даёт меньше 300.

## 5. Спецификация миграции

### 5.1 Где выполнять

**На телефоне.** Данные п.1–5 существуют только там; сервер их не видит. Зачисление — через
существующий рунный журнал `enqueueLevelSpinStarGrant` (телефон пишет операцию в свой журнал,
outbox досылает на сервер в `levelSpinStarGrant` → `users/{uid}/star_operations/{operationId}`).
Новых функций, коллекций и кронов не нужно.

Модуль (предложение): `app/gifts_to_coins_migration.ts`, вызов из `app/_layout.tsx` рядом с
`settleRetiredLevelUpModalDebt` (прецедент такой же разовой миграции —
`app/level_up_modal_retirement_migration.ts`).

**Когда:**
- НЕ на холодном старте (инцидент 22.09: работа на старте = 7 сборок мусора и 6+ с тормозов).
  Запуск через `InteractionManager.runAfterInteractions` + ~15 с после первого кадра;
- только когда `captureAccountGeneration().phase === 'active'` и есть `stableId`;
- **и повторно при каждой активации аккаунта** (смена аккаунта, восстановление из локальной
  копии): у выключенных аккаунтов на устройстве лежат спрятанные копии инвентаря, которые вернутся
  позже. Поэтому метка «сделано» — **на аккаунт**, а не «первый запуск 2.0».

### 5.2 Алгоритм (журнал упреждающей записи, WAL)

Ключ: `gifts_to_coins_v1:<encodeURIComponent(owner)>` — **добавить в `ACCOUNT_LOCAL_KEY_PREFIXES`**
(`app/cloud_sync.ts`), чтобы метка путешествовала вместе с инвентарём при смене аккаунта и
очистке. Иначе вернувшаяся копия инвентаря без метки = двойная выплата.

```
phase: 'planned' | 'plus_applied' | 'credited' | 'retired' | 'done' | 'blocked'
manifest: { items: [{ key, source, giftId|kind, amount, coins }], totalCoins, catalogVersion, tableVersion }
migrationHash: sha256(owner + tableVersion + sorted(item.key:coins))   // заморожен в WAL
```

1. **Вход.** Прочитать WAL. `done` → выход (лог `skip reason=already_done`). `blocked` → выход,
   повтор не чаще раза в сутки.
2. **Флаг.** Удалённый флаг `gifts_to_coins_enabled` (существующий remote config); `false` → выход
   (лог `skip reason=flag_off`). Нужен как рубильник до выпуска исправления.
3. **Опись (только если WAL пуст).** Под `withAccountTransitionLock` прочитать СЫРЫЕ ключи п.1–5
   (не через `loadPendingLevelGiftInventory` — он удаляет просроченное при чтении), посчитать
   монеты по утверждённой таблице, записать WAL `planned` одним `setItem`. Если WAL уже есть —
   **брать manifest из WAL**, опись не пересчитывать (иначе повтор после сбоя даст другую сумму).
4. **Plus-дни.** Для каждого незабранного `plus_days_*`: применить существующим путём
   (`applyGift` → `applySpinPlusForOccurrence`; он идемпотентен по квитанции эффекта). Уже
   действующий Plus не трогаем. Сбой → предмет остаётся, WAL не двигается, повтор при следующем
   запуске; **в монеты Plus не превращаем никогда**. → `plus_applied`.
5. **Зачисление.** Сумма раскладывается на номиналы `stars_2000/1000/500/250/100/50/20/10`
   (жадно, как `runeGiftIds` в `daily_journey_gift_activation.ts`). Для i-го номинала:
   `enqueueLevelSpinStarGrant({ requestId: 'g2c1_' + hash.slice(0,32) + '_' + i, lane: 'base',
   giftId, promotionEligibility: 'excluded_compensation' }, { syncNow: false })`.
   `excluded_compensation` — чтобы компенсация не умножалась «Супер-воскресеньем» и не шла в очки
   недели лиги (D37: очки = заработанные монеты). → `credited`.
6. **Списание предметов** (только после `credited`):
   - п.1: `credits = []`, `issuedLevels`/`issuedCreditIds` **сохранить** (иначе старый код
     заново начеканит спины за те же уровни);
   - п.2/п.3: занятия журнала → `claimed: true`; платный зависший чек закрыть существующим
     `acknowledgeLocalLevelSpin(requestId)` — он переносит рунное списание в outbox и только потом
     удаляет конверт. **Outbox и `level_spin_star_operation_v1:*` платных спинов не удалять** — это
     запись о списании 300 рун;
   - п.4: удалить уровни из `unclaimed_level_gifts*` и штампы; кэш счётчика подарков = 0;
   - п.5: не трогать ключи (модуль удаляется целиком), статус хранится в WAL;
   - снять `level_reward_spin_pending_reveal_v1`;
   - **отменить локальный пуш** «подарок сгорит через 6 часов»: `syncGiftExpiringNotification(null)`.
   → `retired`.
7. **Финал.** `done` + `syncPendingLevelSpinStarGrants` в фоне. Никаких окон, тостов, «полёта
   монет» (D51 «молча»; правило CLAUDE.md: durable — сама награда, празднование не durable).
   Баланс в шапке просто показывает новое число.

### 5.3 Идемпотентность

| Сценарий | Почему не будет двойного начисления |
|---|---|
| Сбой/убийство приложения на любом шаге | manifest и hash заморожены в WAL → те же `requestId` → `enqueueLevelSpinStarGrant` видит существующую операцию (`level_spin_star_operation_v1:*`) и не пишет вторую |
| Повтор на сервере | `star_operations/{operationId}` + отпечаток запроса → сервер отвечает `replayed:true` |
| Переустановка | AsyncStorage стёрт вместе с предметами — нечего конвертировать повторно |
| Смена аккаунта / возврат спрятанной копии | WAL — account-local, путешествует вместе с инвентарём (п.5.2) |
| Два устройства | Инвентарь спинов локален на каждом устройстве — это разные предметы, оба конвертируются. Если manifest совпал байт-в-байт (одинаковые кредиты за уровни) — одинаковый hash, сервер схлопнет. Частичное совпадение кредитов за одни и те же уровни **будет оплачено дважды** — так же, как сегодня их можно было прокрутить на обоих устройствах. Принимаем сознательно (UNKNOWN, как быстро локальная проекция второго устройства сверится с сервером — проверить в реализации) |

### 5.4 Офлайн

Вся миграция локальная. Операции зачисления ложатся в существующий outbox и досылаются, когда
появится сеть. Баланс на телефоне обновляется сразу (оптимистично), сеть догоняет фоном.

### 5.5 Смена аккаунта во время миграции

Каждый шаг проверяет `isCurrentAccountGeneration(token, owner)`; при смене — выход без отката
(WAL остаётся), продолжение при следующей активации этого владельца. Глобальные ключи п.2 и п.4
(`level_reward_spin_gift_journal_v1`, `unclaimed_level_gifts*`) принадлежат активному аккаунту:
они входят в `LEVEL_UP_ACCOUNT_LOCAL_KEYS` и при смене аккаунта уходят в его локальную копию.

### 5.6 Битые данные

`normalizeState` бросает `local_spin_state_corrupt` на битом состоянии. Миграция **не превращает
битое в ноль**: пишет WAL `blocked` с причиной, сырые ключи не трогает (для поддержки), остальные
источники мигрирует. Повтор — раз в сутки.

### 5.7 Логи `[GIFTS-TO-COINS]`

Через `DebugLogger` (переживает перезапуск) + `console.log` в Metro. Без имён, только внутренний id.

```
[GIFTS-TO-COINS] start owner=<id> gen=<n> trigger=<cold_start|account_activate> walPhase=<none|planned|…>
[GIFTS-TO-COINS] skip reason=<already_done|flag_off|identity_not_ready|blocked_backoff> …
[GIFTS-TO-COINS] source=spin_credits count=<n> from=<state_key|balance_cache> coinsEach=<x>
```

### 5.8 Откат

- **До выпуска / в первые дни:** рубильник `gifts_to_coins_enabled=false` останавливает новые
  миграции, уже прошедшие не трогает.
- **Зачисленные монеты не забираем.** Это деньги человека; обратное списание — только отдельным
  решением владельца и отдельной компенсирующей операцией.
- **Код:** откат релиза не возвращает предметы — они списаны. Поэтому WAL с manifest хранится
  ≥ 90 дней: по нему поддержка видит, что было и сколько выдано.
- **Даунгрейд до 1.x** невозможен через стор (D30: 1.6.x не выпускается). Если кто-то поставит
  старую сборку вручную, старый код увидит пустые кредиты и `issuedLevels` — повторно не начеканит.

### 5.9 Серверные легаси-спины (п.10)

1 кредит у 1 человека. Отдельную серверную миграцию не писать. Предложение: вручную из
админки начислить этому человеку компенсацию по той же таблице (1 предмет) либо принять как
пренебрежимое. Функции `levelRewardSpinStatus/Claim/Acknowledge/Delivery/EnrollV1` клиент больше не
вызывает — их снятие с деплоя отдельный вопрос владельцу (D32: удаление серверных функций).

### 5.10 Порядок относительно других миграций

- **До миграции жемчуга (D15/PM-058)** или независимо от неё: жемчуг из подарков **зачисляем сразу
  монетами ×10**, в жемчужный кошелёк не кладём. Тогда порядок миграций не важен.
- **До PM-069** (руны → монеты): компенсация лежит в рунном журнале и переедет вместе с ним.
  PM-069 обязан учитывать операции с `requestId` `g2c1_*`.

## 6a. Риски, найденные по ходу (для PM-047/048)

- 🔴 **Молчаливые нули после PM-047.** Функции выдачи спинов возвращают `false`, а вызывающие места
  реагируют по-разному: задания (`quests_client.ts`) — сервер засчитал награду «спины», клиент
  ничего не дал, просто лог; награда админа с `spins` (`report_reward_bundle.ts`) бросает
  `report_reward_spins_failed` → событие никогда не помечается применённым и повторяется при каждом
  запуске; «Дневной путь» со спином на каждом заходе в «Подарки» пишет ошибку автоклейма. Пока эти
  источники обещают спины, после миграции они создают новые непогашаемые долги. Их нужно убрать
  вместе с обещанием (PM-047), а не оставлять «выдать ноль».
- 🔴 **Истечение при чтении.** `loadPendingLevelGiftInventory` удаляет просроченные подарки прямо в
  момент чтения. Если оставить экран «Подарков» жить до миграции, часть подарков сгорит у тех, кто
  зайдёт на экран. Миграция обязана читать сырые ключи.
- 🟡 **Реферальная рулетка даёт жемчуг** (`prizeKind:'pearls'`) — после удаления жемчуга (D15) приз
  надо перевести на монеты. Не D51, но та же волна.
- 🟡 **Разные курсы жемчуга в коде**: аватар за руны = жемчуг ×80, а D15 = ×10. В таблице выше
  косметика оценена по D15 (×10), иначе один аватар стоил бы 7 200 монет.
