## Явные кандидаты на замену

1. **`app/app_messages.ts` — все 3 листенера (строки 1652, 1673, 1704).**
   Это глобальная и персональная лента объявлений/сообщений + состояния
   прочитанности. Ни один из трёх кейсов не требует «увидеть без перезахода»:
   это не чат и не live-статус. Уже есть локальный SWR-кеш
   (`readCachedSnapshot`/`writeCachedSnapshot`) и событие
   `app_messages_local_changed` — инфраструктура для one-shot+кэш уже
   наполовину построена, конвертация дешёвая.
   - **Оценка экономии:** это ТРИ параллельных постоянно открытых
     collection-подписки, живущих (судя по коду и комментарию про Android
     OOM) всё время, пока приложение открыто у активного пользователя,
     плюс переподписка на каждый reconnect/смену сети. Каждая подписка
     оплачивается как минимум одним чтением на документ при первом снапшоте
     (до 3 × `APP_MESSAGES_BACKGROUND_FETCH_LIMIT` документов) и повторно
     на каждое любое изменение в коллекции — включая изменения ДРУГИХ
     пользователей в глобальной ленте (`app_messages`), которые пересылают
     новый снапшот всем открытым клиентам. При росте базы пользователей
     это кратный (на количество одновременно открытых сессий) трафик на
     каждую публикацию нового сообщения. Замена на one-shot при
     старте/входе в приложение убирает и постоянно открытые каналы, и этот
     fan-out.

2. **`app/league_group_boosts.ts:244` (`leaderboard/{uid}`).**
   Подписка существует только чтобы прочитать `groupId` — значение,
   которое меняется крайне редко (смена лиги/группы раз в неделю).
   Постоянная подписка ради одного почти статичного поля — явная
   инерция. Заменить на `get()` при заходе на экран клуба.

3. **`app/league_group_boosts.ts:254` (`league_groups/{groupId}`, буст).**
   Сам буст —「украшение」по собственному комментарию в коде
   (`«буст лиги — украшение, а не критичные данные»`), и `club_screen.tsx`
   уже применяет для остальной таблицы лиги правило «TTL 6 часов, только
   при заходе на экран». Естественно распространить то же правило на буст,
   тем более что `cacheLeagueGroupBoost`/TTL-инфраструктура уже есть в этом
   же файле.

4. **`app/firestore_friend_requests.ts:686` (`subscribeToFriends`, список
   друзей).** Список друзей — редко меняющиеся данные (добавление друга —
   не частое и не мгновенно критичное действие). SWR-кеш на экране уже есть.
   - **Оценка экономии:** `collection.onSnapshot` с `limit(500)` — при
     открытой вкладке «Друзья» это постоянный канал, который переоткрывается
     при каждом входе на вкладку (`friendsRuntimeActive`), и по коду видно,
     что раньше именно этот класс подписок (collection без лимита) ронял
     Android OOM — сейчас лимит есть, но сам факт постоянной подписки при
     каждом открытии вкладки остаётся дороже, чем один `get()` + локальный
     кэш с последующим фоновым рефрешем.

5. **`app/firestore_friend_requests.ts:754` (`subscribeToIncomingRequests`).**
   Та же логика: `where('status','==','pending').limit(200)` — постоянная
   подписка, тогда как «пришла ли новая заявка» вполне может проверяться
   разово при заходе на вкладку/раз в N часов, если только владелец явно не
   хочет видеть мгновенное появление заявки, пока экран уже открыт (это
   единственный аргумент в пользу realtime здесь — уровень «сомнительно»,
   не «явно оставить»).

Ни у одного из пяти кандидатов НЕТ отсутствия `limit()` — сторож
`AGENTS.md → Firestore Thread-Leak Invariant` уже соблюдён везде (везде есть
`limit()`, кроме одиночных `doc()`-подписок, где `limit` не нужен). Поэтому
самая дорогая находка тут — не «листенер без limit на большую коллекцию»
(таких не найдено), а **количество одновременно открытых постоянных каналов
ради данных, которые не нужны мгновенно**: у одного активного пользователя
единовременно могут быть открыты сразу 3 канала `app_messages.ts` + 2 канала
`league_group_boosts.ts` (на экране клуба) + 2 канала
`firestore_friend_requests.ts` (на вкладке друзей) — то есть до 7
одновременных listener'ов, из которых обоснованно realtime только один класс
кейсов (Арена/деньги/удаление аккаунта), не тронутый в этом списке.

## Оставить как есть

- **`app/arena_client.ts:1066` (`useArenaDocument` → очередь матчмейкинга,
  активный матч, live-документ матча).** Прямая суть Арены — live PvP/PvE
  взаимодействие, статус матча обязан обновляться без перезахода экрана.
  Классический обоснованный realtime.
- **`app/remote_account_deletion_monitor.ts:114`.** Защитный канал:
  сервер может стереть аккаунт в любой момент по модерации/юридическим
  причинам, и клиент обязан отреагировать немедленно, а не при следующем
  холодном старте — иначе пользователь продолжит работать с уже
  недействительным идентификатором. Явный прецедент правила
  «безопасность/деньги важнее экономии».
- **`components/PremiumContext.tsx:578` (`access_projection/current`).**
  Платёжный/VIP-статус. В истории проекта уже был баг именно из-за
  рассинхронизации статуса подписки («Plus активирован при каждом входе»);
  канал специально спроектирован с ретраями, бэкоффом и паузой в фоне
  (`AppState`), то есть уже старается быть дешёвым, оставаясь live там,
  где это нужно для денег.
