# Task packet: Шпиль — авто-включение языка после публикации + флаг «снять задание» (PM-287)

Governance-ID: TG-PM287-SPIRE-TASK-FLAG
Status: Planned
Owner: Claude Sonnet 5 session
Related epic/enabler: E25 / PM-287 (docs/phraseman-2.0/registries/tasks.json)

## Outcome

Владелец (T41, D55) принял решение публиковать пулы Шпиля es/de/fr **без
проверки носителем** — значит ошибки в контенте увидят игроки. PM-287
закрывает два условия принятия этого риска:

1. Как только пул языка опубликован через админку (после PM-285, которая уже
   подтвердила чистоту дистракторов), язык становится доступен в Шпиле сам,
   без отдельного ручного шага «включить язык X» где-то ещё.
2. Оператор админки может быстро снять с публикации конкретное задание, на
   которое пожаловался игрок, не откатывая весь пул и без релиза.

Бенефициар — оператор админки (владелец), который реагирует на жалобу за
минуты, и игрок, который перестаёт видеть кривое задание.

## Scope

In scope:
- `functions/src/spire_task_flag_contract.ts` — чистый контрактный модуль:
  документ `config/spire_task_flags_{lang}` (по одному на es/de/fr),
  добавление/снятие флага, список скрытых id для сборщика пакета.
- `functions/src/admin_spire_task_flag.ts` — callable-обёртки
  (`adminSpireTaskFlagList/Add/Remove`) по образцу `admin_spire_config.ts` —
  тот же admin claim + `application.config.write`, тот же audit-лог.
- Регистрация новых callable в `functions/src/index.ts`.
- Документирование контракта «автовключение языка» — какое поле уже решает
  это (`ArenaTargetPublication.ready`/`enabled` в `arena_target_registry.ts`,
  тот же принцип публикации, что использует Арена) и что PM-272 (сборщик
  пакета, ещё не реализован — status "planned") обязан прочитать
  `spireFlaggedTaskIds()` при сборке недельного пакета языка.

Out of scope:
- Сама сборка недельного пакета Шпиля (PM-272) — не реализована в этой
  сессии, только контракт, которым она обязана будет воспользоваться.
- UI кнопки в `admin/v2/legacy.html` — не запрошен явно acceptance PM-287
  (текст просит «возможность», callable уже даёт эту возможность; экран
  админки — отдельная фронтовая работа, не входит в эту маленькую задачу).
- Правки Арены — только чтение (`admin_arena_publication.ts`,
  `arena_target_registry.ts`) как образец.

## Architecture

Текущая граница: у Шпиля уже есть `config/spire_v1` (spire_config_contract.ts)
для чисел без релиза и отдельно Арена хранит `targetPublications.{lang}` в
`config/arena_v1` с полями `enabled`/`ready` — это и есть механизм
«автовключения языка»: как только `adminArenaPublicationActivate` переводит
публикацию языка в `ready: true, enabled: true`, движок Арены сам считает
язык доступным, никакого отдельного тумблера «включить язык X» нет. Шпиль
(PM-272, когда будет реализован) обязан читать ТУ ЖЕ публикацию Арены
(`ArenaTargetPublication` из `arena_target_registry.ts`) как источник
готовности пула — отдельного дубля публикации для Шпиля заводить не нужно,
контент общий (`content/arena-multilingual/generated/{lang}/tasks.jsonl`).
Это и закрывает PM-287-A1: язык «включается сам» потому, что состояние
публикации уже читается из одного места.

Новая граница: добавляется `config/spire_task_flags_{lang}` — отдельный
маленький документ на язык (не расширение `spire_v1`, чтобы частые
add/remove флагов не гоняли транзакцией общий конфиг таймеров/монет и не
конфликтовали с правками владельца в панели). Сборщик пакета (PM-272) читает
этот документ ОДНИМ запросом на язык при сборке и исключает id из
`flagged`. Ничего не мигрирует и не переименовывается.

## Security and privacy

- Authn/authz: та же защита, что у всех admin-callable Шпиля/Арены —
  `ADMIN_SENSITIVE_WRITE_OPTIONS` + `requireAdminAppCheck` (App Check
  НАВСЕГДА не форсируется — пломба `APP_CHECK_SEALED_BY_OWNER_2026_08_17`,
  не трогается) + custom claim `admin: true` + permission
  `application.config.write` (та же роль, что пишет конфиг Шпиля/Арены).
- Input validation: `taskId` — строгий формат (буквы/цифры/`_`/`-`, ≤200
  символов), `reason` обрезается до 400 символов, `flaggedAtMs`/`flaggedByUid`
  валидируются как конечные положительные значения / непустая строка.
  Мусор на входе — честная ошибка `spire_task_flag_invalid_task_id`, не
  тихое игнорирование.
- Personal data: `flaggedByUid` — uid администратора (не игрока), это то же,
  что уже пишется в `admin_log`/audit-записях по всему проекту; PII игрока
  не хранится (жалоба — только текст причины и id задания).
- Audit: каждое добавление/снятие флага пишет `createAuditRecord` в
  `admin_log`, как `adminSpireConfigSet` — видно, кто и когда снял задание.
- Не трогает Арену (только читает для образца) и не трогает `App Check`
  пломбу — оба явных запрета проекта.

  когда добавить кнопку — до или вместе с запуском публикации.

  этой функции — часть объёма PM-272, отмечено в акцептансе и в notes задачи.
