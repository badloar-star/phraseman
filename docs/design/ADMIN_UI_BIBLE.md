# Библия админки Phraseman

Дата: 2026-06-26  
Статус: обязательные правила для будущей переделки `admin/index.html` и всех новых админских экранов.

## Главная мысль

Админка должна быть простой рабочей панелью, а не складом всех функций сразу.

Человек заходит в админку не читать энциклопедию, а быстро понять:

- что сейчас происходит;
- что требует внимания;
- где нужный рычаг;
- что именно произойдет после нажатия;
- как отменить или проверить результат.

Если экран заставляет помнить, где спрятана функция, читать внутренние названия флагов, бояться кнопки или искать действие среди десятков похожих блоков, экран считается плохим.

## Исследовательская база

Эти правила опираются на проверенные UX-принципы:

- Nielsen Norman Group: интерфейс должен поддерживать узнавание, а не память. Поэтому важные действия видны, подписаны и сгруппированы по смыслу.
- Nielsen Norman Group: эстетичный минимализм означает удаление шума, который не помогает текущей задаче.
- Nielsen Norman Group: кнопки должны иметь понятные состояния: обычное, наведение, фокус, нажатие, загрузка, отключено.
- Nielsen Norman Group: иконки почти всегда нуждаются в текстовых подписях, потому что универсальных иконок мало.
- GOV.UK / ONS plain language: тексты должны быть простыми, короткими и понятными даже экспертам.
- Material Design и USWDS: подсказки должны быть конкретными, появляться на hover/focus и объяснять назначение элемента.
- WCAG 2.2: контраст, фокус, размер кликабельных зон и клавиатурная навигация обязательны, а не декоративны.

## Обязательный стиль

Админка Phraseman должна быть:

- простая;
- быстрая;
- светлая;
- спокойная;
- рабочая;
- с четкими категориями;
- с иконками плюс текстом;
- без визуального мусора;
- без наложений поверх контента;
- без огромных полотен настроек;
- без внутренних названий как основного текста;
- понятная человеку без технического контекста.

Это не лендинг и не витрина. Здесь не нужны большие герои, декоративные карточки, случайные градиенты, перегруженные панели и рекламная подача. Это операционный инструмент.

## Ключевые принципы

### 1. Один экран - одна главная задача

Каждая страница должна отвечать на один вопрос.

Хорошо:

- "Обновления приложения"
- "Баннеры в приложении"
- "Технические работы"
- "Пользователь"
- "Пуш-кампании"

Плохо:

- "Control Panel"
- "Remote Config"
- "Misc"
- "Other"
- "Flags"
- "Tools"

Внутреннее техническое название можно показывать мелко вторым уровнем, но не делать его главным заголовком.

### 2. Все лишнее скрыто, но не потеряно

Главный экран показывает только то, что нужно для решения задачи. Редкие, старые и опасные действия уходят в:

- "Дополнительно";
- "Архив";
- "Диагностика";
- "Опасные действия".

Скрыть не значит удалить. Функция остается доступной, но не мешает каждый день.

Перед тем как убрать legacy-вкладку или кнопку из первого уровня, она должна быть записана в migration coverage:

- старый `tab_id`;
- новый раздел из 7 категорий;
- статус `В v2`, `Workflow` или `Fallback`;
- риск;
- безопасный workflow;
- fallback-ссылка, если native-перенос еще не завершен.

После Native completion board в Admin v2 допустимое целевое состояние: `0` fallback. Если функция еще не умеет писать безопасно, она остается в статусе `Workflow`, а не получает прямую кнопку записи.

Перед переносом конкретной legacy-кнопки нужно прогнать button/function audit:

```powershell
node scripts/admin-legacy-button-audit.mjs
```

Кнопка переносится только после проверки текста, tooltip, риска, write-пути, confirm, audit, rollback и нового раздела. Нельзя копировать старый `onclick`, emoji, цвет и расположение без пересмотра.

После button audit нужно проверить реальную функцию за кнопкой. Если `onclick` ведет к функции, которая пишет в Firestore или вызывает Cloud Function, перенос идет через Function transfer board: `native lane`, `guarded write`, `backend contract` или `inspect before move`.

Финальный статус Admin v2: новый интерфейс является основным рабочим входом. Старый `admin/index.html` можно держать только как архивный аварийный доступ для сверки, а не как обычный путь работы.

После functional transfer нужен operational audit: каждая v2-кнопка должна иметь handler, каждый route target должен вести на существующий экран, каждый Firestore source должен быть записан с правами доступа, ошибкой `permission-denied`/`failed-precondition` и понятным empty/loading/error состоянием. Если действие нельзя честно выполнить из браузера по rules, оно остается `guarded` и указывает на server-side flow или Cloud Function.

Перед русификацией или упрощением текстов нельзя делать слепую bulk-замену по исходникам админки. В админке рядом с видимым текстом живут реальные Firestore collection names, object keys, route ids, action ids и CSS class names. Их нельзя переводить.

Правильный порядок:

- сначала прогнать `node scripts/admin-v2-language-audit.mjs`;
- менять видимый текст, `data-tooltip`, empty/loading/error state и заголовки;
- не менять `data-action`, `data-route`, collection names, object keys, query fields, CSS classes и function names;
- после изменения прогнать `node --check` для измененных JS-файлов, action/route audit и language audit.

### 3. Узнавание важнее памяти

Пользователь не должен помнить, где какая кнопка. Интерфейс сам дает подсказки:

- понятные названия разделов;
- иконка рядом с названием;
- активный пункт меню;
- поиск по разделам;
- хлебные крошки;
- короткое описание страницы;
- подсказка на каждой кнопке.

### 4. Любое действие должно объяснять последствия

Перед кликом человек должен понимать:

- кто увидит изменение;
- когда оно применится;
- можно ли отменить;
- опасно ли действие;
- нужен ли релиз приложения;
- есть ли аудит-лог.

Если это нельзя объяснить коротко, действие должно иметь отдельную форму-подтверждение.

### 5. Сначала безопасный черновик, потом публикация

Для всех массовых функций должен быть путь:

1. Создать черновик.
2. Посмотреть превью.
3. Проверить аудит.
4. Опубликовать.
5. Быстро выключить.

Это касается update modal, баннеров, maintenance, push, выгодных предложений, paywall-экспериментов и remote flags.

## Главная структура админки

Главное меню должно иметь не больше 7 крупных разделов.

### 1. Обзор

Для ежедневной проверки.

Показывать:

- активные кампании;
- критические алерты;
- технические работы;
- ручные update modal;
- последние изменения;
- ошибки публикации;
- быстрые ссылки к частым действиям.

Не показывать:

- длинные таблицы;
- внутренние JSON;
- все флаги сразу;
- исторические данные без причины.

### 2. Приложение

Все, что меняет поведение приложения для пользователей.

Подразделы:

- Обновление приложения
- Баннеры
- Технические работы
- Feature flags
- Remote config
- Версии и сторы

### 3. Пользователи

Все про конкретного человека или группу пользователей.

Подразделы:

- Поиск пользователя
- Профиль
- Покупки
- Доступ
- Жалобы и модерация
- История действий

### 4. Деньги

Все, что влияет на оплату и подписки.

Подразделы:

- Подписки
- Paywall
- Выгодные предложения
- Промокоды
- Возвраты
- Revenue-метрики

### 5. Контент

Все уроки, фразы, паки и публикация контента.

Подразделы:

- Уроки
- Фразы
- Паки
- Переводы
- Импорт
- Проверка качества

### 6. Комьюнити

Все социальные и UGC-функции.

Подразделы:

- UGC
- Арена
- Чат
- Жалобы
- Модерация

### 7. Диагностика

Все для проверки, логов и ремонта.

Подразделы:

- Audit log
- Ошибки
- Health
- Тестовые пуши
- Экспорт
- Advanced tools

### Запрет декоративного real-time

В Admin v2 нельзя добавлять отдельную визуальную карту онлайн-пользователей.

Причина: честный real-time online требует отдельной presence-инфраструктуры и создает дополнительные Firebase writes/reads ради декоративного режима. Админка должна оставаться простой, дешевой и рабочей.

Правила:

- не добавлять отдельный раздел визуальной школы, университета или карты онлайн-пользователей;
- не добавлять отдельные presence-документы, realtime-аватары или live-карту ради админского интерфейса;
- активность пользователей показывать только там, где уже есть существующие рабочие источники без нового фонового расхода;
- arena live, league rooms, UGC, app health и campaign health остаются в обычных разделах `Комьюнити`, `Диагностика`, `Кампании`;
- если нужна новая observability-фича, сначала оценить Firebase reads/writes, стоимость, частоту обновления и пользу для принятия решений.
## Навигация

### Левое меню

Левое меню - основной способ навигации на desktop.

Правила:

- только крупные разделы;
- иконка плюс текст;
- активный раздел выделен ясно;
- счетчики только если они реально помогают;
- не больше 7 разделов первого уровня;
- редкие инструменты не попадают в верхний уровень.

### Верхняя панель

Верхняя панель нужна для быстрых глобальных действий:

- поиск;
- текущий статус окружения;
- аккаунт администратора;
- ссылка на аудит-лог;
- аварийные алерты.

Верхняя панель не должна быть вторым меню со всеми вкладками.

### Поиск

Поиск должен искать:

- разделы;
- кнопки;
- remote flags;
- пользователей;
- campaign_id;
- внутренние ключи.

Результат поиска должен показывать человеческое название и технический ключ.

Пример:

- "Показать окно обновления"  
  `manual_update_enabled`

## Страница

Каждая страница строится одинаково.

### 1. Заголовок

Содержит:

- понятное название;
- короткое описание в одну строку;
- статус, если есть активная публикация;
- одну главную кнопку справа.

Пример:

- Название: "Обновление приложения"
- Описание: "Покажи пользователям окно обновления или включи обязательное обновление."
- Главная кнопка: "Показать окно"

### 2. Статус

Сразу под заголовком показывается текущее состояние:

- выключено;
- черновик;
- запланировано;
- активно;
- ошибка;
- завершено.

Статус должен быть понятным по тексту, а не только по цвету.

### 3. Главная форма

На первом экране только основные поля.

Пример для update modal:

- режим;
- campaign_id;
- target build/version;
- заголовок;
- текст;
- кнопка;
- предпросмотр.

Дополнительные языки, аудит и JSON уходят ниже.

### 4. Превью

Для пользовательских кампаний превью обязательно.

Превью должно показывать:

- как увидит пользователь;
- где появится;
- можно ли закрыть;
- что откроется по кнопке;
- кто попадет в аудиторию.

### 5. История

У каждой опасной или массовой функции должна быть история:

- кто изменил;
- что изменил;
- когда;
- старое значение;
- новое значение;
- причина, если она введена.

## Кнопки

### Общие правила

Каждая кнопка должна иметь:

- понятный текст;
- иконку, если это помогает быстро узнать действие;
- tooltip на hover и focus;
- `aria-label`, если кнопка без видимого текста;
- состояние hover;
- состояние focus;
- состояние loading;
- состояние disabled;
- видимый результат после клика.

### Подписи кнопок

Кнопка отвечает на вопрос "что сделать?".

Хорошо:

- "Сохранить"
- "Показать окно"
- "Выключить баннер"
- "Создать черновик"
- "Опубликовать"
- "Открыть аудит"
- "Скопировать ID"

Плохо:

- "OK"
- "Apply"
- "Run"
- "Submit"
- "Flag"
- "Do"
- "Update" без уточнения

Для сложных действий используем глагол плюс объект.

### Типы кнопок

#### Primary

Одна главная кнопка на экран.

Использовать для:

- сохранить;
- опубликовать;
- показать окно;
- создать кампанию.

#### Secondary

Для обычных действий рядом.

Использовать для:

- предпросмотр;
- открыть аудит;
- скопировать;
- проверить.

#### Ghost

Для тихих действий.

Использовать для:

- закрыть;
- отменить;
- свернуть;
- открыть детали.

#### Danger

Только для опасных действий.

Использовать для:

- выключить для всех;
- удалить;
- сбросить;
- заблокировать;
- включить жесткий режим.

Danger-кнопка не должна стоять рядом с обычными кнопками без визуального разделения.

## Подсказки на кнопках

Подсказка обязательна для каждой кнопки.

Она должна появляться:

- при наведении мыши;
- при фокусе с клавиатуры;
- при долгом tap на touch, если это реализуемо.

Подсказка не заменяет текст кнопки. Кнопка все равно должна быть понятной без hover.

### Формула подсказки

Подсказка отвечает на 4 вопроса:

1. Что сделает кнопка.
2. Кого это затронет.
3. Когда вступит в силу.
4. Как отменить или проверить.

Пример:

Кнопка: "Показать окно"  
Подсказка: "Создаст активную кампанию manual update. Пользователи увидят модал обновления после загрузки remote config. Если задан target build, окно исчезнет после обновления. Выключить можно этой же страницей."

Кнопка: "Выключить баннер"  
Подсказка: "Остановит показ текущего баннера для всех пользователей. Уже закрытые пользователи останутся закрытыми по campaign_id. Изменение попадет в audit log."

Кнопка: "Скопировать ID"  
Подсказка: "Скопирует campaign_id в буфер обмена. Ничего в приложении не изменится."

### Очень длинные объяснения

Если объяснение не помещается в нормальный tooltip, использовать help-popover.

Tooltip тогда говорит коротко:

"Показывает подробное описание действия и рисков."

Popover показывает:

- что изменится;
- риски;
- пример;
- как откатить;
- связанные флаги.

## Иконки

Иконки нужны, потому что они ускоряют узнавание. Но иконка без текста часто непонятна.

Правила:

- использовать один набор иконок во всей админке;
- для web-админки предпочтительно Lucide;
- для React Native UI допустим Ionicons, если экран внутри приложения;
- не использовать emoji как UI-иконки;
- в меню всегда иконка плюс текст;
- icon-only кнопки разрешены только в компактных местах и только с tooltip + aria-label;
- размер иконки в кнопке: 16-20 px;
- размер иконки в меню: 18-22 px.

Рекомендуемые иконки:

- Обзор: `LayoutDashboard`
- Приложение: `SlidersHorizontal`
- Обновление: `Rocket`
- Баннеры: `Megaphone`
- Технические работы: `Wrench`
- Пользователи: `Users`
- Деньги: `CreditCard`
- Контент: `BookOpen`
- Комьюнити: `MessageCircle`
- Диагностика: `Activity`
- Аудит: `ScrollText`
- Опасное действие: `TriangleAlert`
- Сохранить: `Save`
- Закрыть: `X`
- Предпросмотр: `Eye`
- Скопировать: `Copy`

## Цвета

Цвета должны помогать понять состояние, а не украшать ради украшения.

### Базовая палитра

- Фон страницы: `#F6F8FB`
- Поверхность: `#FFFFFF`
- Основной текст: `#111827`
- Вторичный текст: `#64748B`
- Граница: `#DDE3EA`
- Primary: `#2563EB`
- Primary hover: `#1D4ED8`
- Success: `#16A34A`
- Warning: `#D97706`
- Danger: `#DC2626`
- Info: `#0891B2`
- Focus ring: `#38BDF8`

### Контраст

Правила:

- обычный текст минимум 4.5:1;
- крупный текст минимум 3:1;
- иконки и границы важных контролов минимум 3:1;
- фокус должен быть видимым;
- цвет не может быть единственным способом понять статус.

На ярко-зеленых, lime и neon-green поверхностях нельзя использовать белый текст. Нужно использовать темный текст, например `#07110A`.

### Статусы

Статус всегда содержит текст плюс цвет.

Хорошо:

- зеленый бейдж "Активно"
- серый бейдж "Выключено"
- желтый бейдж "Черновик"
- красный бейдж "Ошибка"

Плохо:

- только цветная точка;
- только иконка;
- только внутренний ключ.

## Типографика

Основной шрифт: Inter или системный sans-serif.

Правила:

- основной текст не меньше 14 px на desktop;
- поля и кнопки не меньше 14 px;
- заголовки внутри рабочих панелей компактные;
- line-height для текста 1.4-1.6;
- не использовать отрицательный letter-spacing;
- не делать огромные заголовки внутри админских форм.

Размеры:

- H1 страницы: 24-28 px;
- H2 секции: 18-20 px;
- H3 блока: 15-16 px;
- Body: 14-15 px;
- Hint: 12-13 px;
- Button: 14 px.

## Тексты

### Тон

Тон должен быть:

- прямой;
- спокойный;
- без маркетинга;
- без страха;
- без внутренних терминов как основного текста.

### Правила текста

- короткие предложения;
- один смысл в одном предложении;
- глагол ближе к началу;
- технический ключ показывается вторым уровнем;
- если термин сложный, объяснить рядом;
- не использовать капс для обычного текста;
- не писать "просто", "магия", "авто" без объяснения.

### Примеры замен

Плохо: "force_update_enabled"  
Хорошо: "Обязательное обновление"  
Мелко рядом: `force_update_enabled`

Плохо: "manual_update_target_build"  
Хорошо: "Скрыть после версии"  
Мелко рядом: `manual_update_target_build`

Плохо: "promo_banner_enabled"  
Хорошо: "Показать верхний баннер"  
Мелко рядом: `promo_banner_enabled`

Плохо: "Save RC"  
Хорошо: "Сохранить настройки"

## Формы

Форма должна быть понятна до заполнения.

Каждое поле имеет:

- label сверху;
- короткую подсказку под label или под полем;
- placeholder только как пример, не как label;
- ошибку рядом с полем;
- нормальное disabled-состояние.

Порядок полей:

1. Что включаем.
2. Для кого.
3. Когда.
4. Что увидит пользователь.
5. Как остановить.
6. Технические детали.

### Campaign ID

Для всех кампаний обязателен `campaign_id`.

Использовать для:

- manual update modal;
- promo banner;
- maintenance banner;
- выгодное предложение;
- push campaign;
- paywall campaign.

Правила:

- ID понятный: `manual_update_2026_06_26_v154`;
- новое содержание - новый campaign_id;
- закрытия и "показано один раз" хранятся по campaign_id;
- нельзя переиспользовать старый campaign_id для новой кампании.

## Manual update modal

Manual update modal - отдельная функция от старого force-update.

### Поля

Обязательные:

- включено / выключено;
- режим;
- campaign_id;
- target build/version;
- заголовок;
- текст;
- текст кнопки;
- store URLs.

### Режимы

#### Добровольный

Показывается один раз на campaign_id.

Пользователь может закрыть:

- крестиком;
- кнопкой "Позже";
- после нажатия "Обновить".

Повторно не показывается, пока не сменится campaign_id.

#### Обязательный

Не закрывается, пока:

- пользователь не обновится до target build/version;
- или админ не выключит кампанию.

Кнопка открывает App Store / Google Play.

### Как сделать, чтобы окно не появлялось после обновления

Для каждой manual update campaign задается `target build/version`.

Логика:

- если текущая версия ниже target - показываем;
- если текущая версия равна target или выше - не показываем;
- если target пустой в force-режиме - окно будет жить, пока админ не выключит кампанию;
- если target пустой в optional-режиме - окно покажется один раз по campaign_id.

Это главное правило. Нельзя завязывать manual update только на `min_app_version`, потому что это другая функция.

### Превью

Перед публикацией админ должен видеть:

- как выглядит модал;
- какой режим выбран;
- кто увидит;
- когда исчезнет;
- какой store откроется;
- campaign_id.

## Баннеры и плашки

Все верхние плашки должны занимать место в layout. Они не должны перекрывать элементы приложения.

Обязательные правила:

- есть close-кнопка;
- есть swipe-to-dismiss;
- закрытие сохраняется по campaign_id;
- новый campaign_id снова показывает плашку;
- текст короткий;
- действие не мешает чтению;
- плашка не закрывает кнопки и поля.

### Типы плашек

#### Выгодное предложение

Назначение: мягко позвать пользователя к офферу.

Не должно:

- перекрывать навигацию;
- мешать уроку;
- появляться бесконечно после закрытия;
- использовать агрессивный текст.

#### Технические работы

Назначение: предупредить о временной проблеме.

Для мягкого предупреждения:

- можно закрыть;
- можно свайпнуть;
- хранится по campaign_id.

Для жесткой блокировки:

- отдельный full-screen maintenance block;
- понятный текст;
- объяснение, что делать;
- без лишних кнопок.

## Модальные окна

Модал используется только когда:

- нужно подтвердить опасное действие;
- нужно показать важное состояние;
- нужно собрать короткую форму;
- действие нельзя безопасно сделать inline.

Правила:

- понятный заголовок;
- короткий основной текст;
- одна главная кнопка;
- одна вторичная кнопка;
- danger отдельно;
- закрытие очевидно, если режим не force;
- фокус остается внутри модала;
- Escape закрывает только безопасные модалы;
- фон не должен ломать чтение.

## Таблицы

Таблица должна помогать принять решение, а не показывать все поля базы.

Правила:

- только нужные колонки;
- действия справа;
- фильтры сверху;
- поиск сверху;
- пагинация или virtual scroll;
- пустое состояние с объяснением;
- loading-состояние;
- ошибки рядом с таблицей;
- длинные ID сокращать, но давать копирование.

## Карточки

Карточки использовать только для отдельных сущностей или компактных блоков.

Разрешено:

- статус кампании;
- пользователь;
- метрика;
- черновик;
- ошибка.

Запрещено:

- карточка внутри карточки;
- весь экран как набор декоративных карточек;
- огромные отступы ради красоты;
- одинаковые карточки без явной пользы.

Радиус карточек: 8 px или меньше.

## Состояния

У каждого блока должны быть состояния:

- loading;
- empty;
- error;
- success;
- disabled;
- dirty / есть несохраненные изменения.

Нельзя показывать пустую белую область без объяснения.

## Производительность

Админка не должна грузить весь мир сразу.

Правила:

- грузить данные только активного раздела;
- тяжелые таблицы загружать по запросу;
- поиск debounce 250-400 ms;
- большие списки виртуализировать;
- не держать все модалки в DOM без нужды;
- разделить старый монолитный HTML на модули;
- кэшировать справочники;
- показывать skeleton или компактный loading.

Цель:

- первый экран быстро виден;
- навигация мгновенная;
- редкие тяжелые отчеты не тормозят ежедневные действия.

## Безопасность и контроль

Все массовые действия должны иметь защиту:

- preview;
- confirm;
- audit log;
- rollback или быстрый off switch;
- понятное описание влияния;
- ограничение ролей;
- запрет случайного double click.

Опасные действия требуют явного подтверждения.

Пример:

"Да, выключить баннер для всех"

а не:

"OK"

- "Контент на проверке"

### Environment switcher

Нужен видимый переключатель окружения:

- Production
- Staging
- Development

Правила:

- production выделен ясно;
- опасные действия в production требуют stronger confirm;
- staging не должен выглядеть как production;
- environment показывается в верхней панели всегда.

### Rollback center

У админки 2.0 должен быть единый центр отката.

Он показывает:

- последние изменения;
- кто изменил;
- что можно откатить;
- риск отката;
- кнопку rollback;
- preview результата;
- audit после отката.

Rollback должен быть для:

- remote flags;
- campaigns;
- banners;
- maintenance;
- paywall configs;
- content publish;
- manual update modal.

## Responsive

Админка должна работать на desktop и tablet. Mobile не обязан быть идеальным для всех сложных таблиц, но базовые действия должны быть доступны.

Контрольные ширины:

- 375 px;
- 768 px;
- 1024 px;
- 1440 px.

Правила:

- без горизонтального скролла всей страницы;
- меню превращается в drawer;
- таблицы получают компактный режим;
- кнопки не ломают текст;
- поля не вылезают за экран;
- фиксированные панели не перекрывают контент.

## Accessibility

Обязательные правила:

- все кнопки доступны с клавиатуры;
- порядок Tab совпадает с визуальным порядком;
- focus ring видимый;
- icon-only кнопки имеют `aria-label`;
- поля имеют label;
- ошибки связаны с полями;
- цвет не единственный сигнал;
- touch target минимум 44x44 px для важных кнопок;
- анимации уважают `prefers-reduced-motion`.

## Что запрещено

Запрещено:

- новые разделы без категории;
- кнопки без tooltip;
- кнопки без понятного текста или aria-label;
- emoji как иконки интерфейса;
- внутренние ключи как главный UI-текст;
- overlay-плашки поверх контента;
- два главных CTA на одном экране;
- danger-кнопки рядом с обычными без разделения;
- сохранение без явного feedback;
- формы без preview для массовых изменений;
- новые remote flags без человеческого названия;
- длинные страницы без поиска и структуры;
- новый функционал в `Misc`;
- случайные цвета вне палитры;
- декоративные градиенты ради красоты;
- вложенные карточки;
- крупные изменения без audit log.

## Definition of Done для любого нового экрана

Экран считается готовым только если:

- есть понятная категория;
- есть заголовок и короткое описание;
- есть один главный CTA;
- все кнопки имеют tooltip;
- icon-only кнопки имеют `aria-label`;
- все поля имеют label;
- опасные действия имеют confirm;
- массовые действия имеют preview;
- есть loading / empty / error состояния;
- есть audit log для изменений;
- цвета проходят контраст;
- focus виден;
- экран проверен на 375 / 768 / 1024 / 1440 px;
- текст понятен без знания Firebase/Remote Config;
- технические ключи показаны вторым уровнем;
- нет наложения элементов друг на друга.

## Порядок переделки старой админки

### Этап 1. Навигация

Собрать все существующие вкладки в 7 разделов:

- Обзор
- Приложение
- Пользователи
- Деньги
- Контент
- Комьюнити
- Диагностика

### Этап 2. Единые компоненты

Создать единые:

- кнопку;
- tooltip;
- поле;
- select;
- toggle;
- badge;
- modal;
- banner;
- table;
- empty state;
- confirm dialog.

### Этап 3. Самые важные страницы

Сначала переделать:

- Обновление приложения;
- Баннеры;
- Технические работы;
- Пользователи;
- Audit log.

### Этап 4. Убрать мусор с первого уровня

Перенести редкое в:

- Дополнительно;
- Архив;
- Диагностика;
- Advanced.

### Этап 5. Разбить монолит

Старый `admin/index.html` не должен оставаться одним огромным файлом.

Цель:

- страницы отдельно;
- компоненты отдельно;
- config отдельно;
- API отдельно;
- стили отдельно;
- старые функции переносить постепенно без удаления поведения.

## Главный тест

Если ребенок или новый сотрудник смотрит на экран и может сказать:

"Вот что сейчас включено. Вот что будет, если нажать. Вот где отменить."

значит экран хороший.

Если нужно объяснять голосом, где что находится, значит интерфейс еще не готов.
