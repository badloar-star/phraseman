# Project Research Summary

**Project:** Phraseman — Milestone v1.1 (Apple Watch Micro-Repetition)
**Domain:** Native watchOS companion (SwiftUI + WatchConnectivity) embedded in an Expo (CNG) React Native iOS app, with bidirectional phone↔watch sync into an existing pure-TypeScript SRS engine
**Researched:** 2026-06-07
**Confidence:** HIGH on stack/architecture/pitfalls; MEDIUM on feature-niche specifics

## Executive Summary

Phraseman v1.1 adds an Apple Watch micro-repetition surface on top of an SRS engine (`app/active_recall.ts`) that is already done. The watch milestone adds only the wrist-side review UX and a read-only-ish native bridge: React Native remains the sole writer of all SRS state, while the watch is authoritative only for its own swipe *verdicts* (`gotCorrect`, `reviewedAt`), never for phrase *identity*. The expert pattern is unambiguous — React Native does not run on watchOS, so the watch app is pure SwiftUI, the complication is WidgetKit (ClockKit is deprecated), and the only sanctioned phone↔watch transport is Apple's WatchConnectivity (`WCSession`). The recommended stack is `@bacons/apple-targets` (SDK ≥53; project on SDK 54 ✓) to generate a watch target that survives `expo prebuild --clean`, plus `react-native-watch-connectivity@2.0.0` (RN ≥0.76; project on RN 0.81.5 ✓) for the bridge — or a self-written Swift Expo Module mirroring the team's proven `modules/phrase-widget` pattern.

Three findings are decision-critical and must be surfaced before any planning. First, **App Groups do NOT bridge iPhone↔Watch** — they are separate devices with separate containers, so the existing `group.app.phraseman.widget` cannot reach the watch. Phone↔watch is WatchConnectivity ONLY; a NEW App Group (`group.app.phraseman.watch`) is shared only between the watch app and its complication (both on-watch). Second, the **transport choice is split by direction**: phone→watch due-batch via `updateApplicationContext` (latest-wins, ~262 KB limit), watch→phone swipe results via `transferUserInfo` (durable FIFO, survives out-of-range) — NOT `sendMessage`, which silently drops data when the phone is out of range. Third, the **UX call is binary know/don't-know**, not 4-button SM-2 — it maps directly onto the existing `markReviewed(phrase, gotCorrect: boolean)` contract, and 4 targets on a 40mm screen is fat-finger hell.

Two existential risks must gate the phases. (a) `expo prebuild --clean` (and EAS Build, which runs it) wipes any hand-added watch target — Phase 1 must *prove* prebuild survival with an `xcodebuild -list` gate, and account for the `@bacons/apple-targets` issue #175 patch-package caveat (mis-wired watch dependency + missing Embed Watch Content phase). (b) The opaque `phrase` key can silently mutate during the phone→watch→phone round-trip (Unicode NFD/NFC, stray trim/lowercase, plist/JSON edge cases), causing `markReviewed` to no-op with no error — a dedicated round-trip test must be green *before* any SwiftUI work, and a `reviewId` UUID + last-write-wins-by-`reviewedAt` is the minimum-correct sync policy.

## Key Findings

### Recommended Stack

The watch app is pure SwiftUI (RN cannot run on watchOS); the complication is WidgetKit `accessory*` families (ClockKit deprecated since watchOS 9). The watch target is generated by `@bacons/apple-targets`, which keeps Swift source in a top-level `targets/` directory *outside* `ios/` and re-injects the target on every prebuild — the only approach designed to survive CNG. The phone↔watch bridge is `react-native-watch-connectivity@2.0.0` (New-Architecture rewrite) for the fastest path, with a self-written Swift Expo Module mirroring `modules/phrase-widget` as the equally-valid fallback. Version compatibility is verified: SDK 54 ✓, RN 0.81.5 ✓ — see full detail in STACK.md.

**Core technologies:**
- `@bacons/apple-targets@4.0.7`: generates watch + watch-widget Xcode targets during prebuild — only option purpose-built to survive `expo prebuild --clean` (source lives in `targets/`).
- `react-native-watch-connectivity@2.0.0`: JS/TS wrapper over `WCSession` — New-Arch (Fabric/TurboModule) rewrite, requires RN ≥0.76. Fallback: hand-written Swift Expo Module mirroring `modules/phrase-widget`.
- WidgetKit (watchOS 9+ `accessoryCircular`/`accessoryInline`): renders the due-count complication — ClockKit deprecated, do not use.
- SwiftUI (Xcode 16+): the entire watch UI (card stack, swipe) — non-negotiable, RN does not run on watchOS.
- New App Group `group.app.phraseman.watch` + `UserDefaults(suiteName:)`: shares the due-count snapshot between the watch app and its complication ONLY (both on-watch).

**Transport selection (decision-critical):**
- phone→watch due-batch + complication count → `updateApplicationContext` (latest-wins, ~262 KB).
- watch→phone swipe results → `transferUserInfo` (durable FIFO, guaranteed delivery, survives out-of-range).
- `sendMessage` → AVOID as backbone (requires live reachability; loses data when watch is out of range).

### Expected Features

The watch-flashcard niche is thin and under-documented — Anki and Duolingo have *no* watch app; the only real comparable (TangoWrist) is brand-new and unreviewed. The dominant verdict: watch-only review is a friction trap *unless ruthlessly minimal*. Phraseman can own the niche by doing very little, very well. Full landscape in FEATURES.md.

**Must have (table stakes — all P1):**
- Card stack of due-today items, front-only (English phrase) — the core surface.
- Tap-to-reveal locale answer — respects active recall (always-both is an anti-feature).
- Binary swipe grade (right = know, left = don't) → queued `{phrase, gotCorrect, reviewedAt}` — the spec'd contract.
- Haptic confirmation (distinct right vs left) — cheap, high satisfaction on a glanced screen.
- Offline cache + queued merge (last-write-wins) — non-negotiable; watch is routinely out of range.
- Due-count complication with deep-link — the engagement surface.
- "All caught up" / "load cards on phone" empty + done states — makes sessions end gracefully.
- Locale-correct answer rendering (RU/UK/ES already on each item).

**Should have (defer to v1.x):**
- Digital Crown reveal/advance — add once tap flow validated (lower-complexity tap ships first).
- TTS pronunciation via AirPods (pre-rendered/cached) — differentiator, but offline-audio approach unresolved.
- XP/streak echo on watch — ties micro-sessions into existing gamification.

**Defer (v2+):**
- Optional autoplay pacing; opt-in daily reminder (≤1/day); skip/snooze gesture; richer on-watch stats; Android Wear parity (out of scope per PROJECT.md).

**Decisive UX call:** Binary swipe, NOT 4-button SM-2 (HIGH confidence). Ergonomics win outright on a 40mm screen; the engine signature is already `markReviewed(phrase, gotCorrect: boolean)`; mis-grading corrupts schedule worse than a clean binary signal; the rich 4-grade path stays on the phone.

### Architecture Approach

The design mirrors the existing `widget_bridge` sole-writer pattern but **splits the writer rule by direction**: RN is sole writer for all *display* data (due batch, complication count), while the watch is the sole writer for the *swipe queue* it produces and ships up to RN. The phrase-key invariant makes this safe — the watch only ever echoes back the opaque `phrase` string it received; it is authoritative for the verdict, never the identity. The existing `active_recall.ts` and `modules/phrase-widget` are UNCHANGED reference templates. Full contracts in ARCHITECTURE.md.

**Major components (all NEW unless noted):**
1. `app/active_recall.ts` — UNCHANGED. Sole SRS source of truth (`getDueItems`, `markReviewed`, `countDueItemsToday`).
2. `app/watch_sync.ts` — NEW. Builds down-payloads (pure read, no `commitSessionOverflow`); applies up-payloads via `markReviewed` with LWW + idempotency dedup; exposes `sendDueBatch`/`sendComplicationCount`/`applySwipeBatch`/`onSwipeResults`/`startWatchSync`.
3. `modules/watch-bridge` (Expo Module, iOS-only) — NEW. Owns the iPhone-side `WCSession`; `updateApplicationContext` down, emits `onSwipeResults` on `didReceiveUserInfo` up. Mirrors `modules/phrase-widget` structure.
4. watchOS SwiftUI app target — NEW. Card stack, swipe gestures, `WatchSessionManager` (WCSessionDelegate), `WatchStore` (App Group cache + `pendingSwipes.json` offline queue, replay-on-reconnect).
5. Complication extension (WidgetKit) — NEW. Reads `due_count_today` from `group.app.phraseman.watch`; read-only.
6. Expo config plugin + entitlements — NEW. Preserves the watch target across prebuild; declares the new App Group on watch app + complication targets.

**Sync contract essentials:** two versioned (`schemaVersion: 1`) flat payloads; DOWN batch capped at 20–30 cards (well under the 262 KB context limit) with `back` pre-resolved to the user's locale on the phone (watch stays locale-dumb); UP swipe batch carries `{phrase, gotCorrect, reviewedAt}` (+ `reviewId` UUID per pitfalls). Reader-side schema tolerance: unknown version → watch keeps cache, phone drops batch.

### Critical Pitfalls

The top five are gating risks; full set (10 pitfalls + checklists + recovery strategies) in PITFALLS.md.

1. **`prebuild --clean` destroys the watch target** — Store all watch source in top-level `targets/`; use an idempotent config plugin; apply the `@bacons/apple-targets` issue #175 patch-package (mis-wired dependency + missing Embed Watch Content phase); gate with `xcodebuild -list` after every clean prebuild. (Phase 1)
2. **Phrase key silently mutates on round-trip** → `markReviewed` no-ops, no error. Treat `phrase` as opaque in Swift (never trim/lowercase/normalize); write a round-trip test on 20+ representative phrases (spaces, apostrophes, Cyrillic, multi-word) that must be green *before* any SwiftUI work; add a canary WARNING log in `markReviewed` on `!item`. (Phase 2 test; Phase 5 canary)
3. **Wrong WCSession transfer API** — `sendMessage` drops data out of range; `updateApplicationContext` coalesces (loses all-but-last swipe). Use `updateApplicationContext` down, `transferUserInfo` up. Lock this in the module design before Swift is written. (Phase 2)
4. **Offline double-review corrupts SM-2** — same card reviewed on watch (offline) then phone before sync, applied twice. Last-write-wins by `reviewedAt` + `reviewId` UUID idempotency set (cap 500, TTL 48h) + 5s clock-skew tolerance. UUID generated in Phase 3 at swipe time, in the Phase 2 schema, applied in Phase 5. (Phase 5, with upstream dependencies)
5. **App Group entitlements provisioning hell** — `UserDefaults(suiteName:)` nil on device while fine in simulator. Enable the App Group on host app + watch app + watch extension bundle IDs; declare watch targets in `app.json` `appExtensions`; mind EAS issues #40851 (cached profile without App Groups) and #2578 (CLI doesn't auto-provision the watch target); physical-device `UserDefaults` ping is Phase 1's acceptance gate. (Phase 1)

## Implications for Roadmap

Dependencies flow strictly: you cannot test sync without a session; you cannot have a session without entitlements; you cannot keep the watch target without the config plugin. The critical path is **P1 → P2 → P3**, after which P4 and P5 can parallelize.

### Phase 5 (roadmap #5): Config Plugin, Entitlements & Prebuild-Survival Proof
**Rationale:** Hard blocker — nothing downstream survives a rebuild without it; existential risk (a) lives here.
**Delivers:** `@bacons/apple-targets` wired in `app.config.js`; `targets/watch/` + `targets/watch-widget/` scaffolds; idempotent config plugin declaring `group.app.phraseman.watch` on watch app + complication targets; issue #175 patch-package; a "hello world" watch target.
**Avoids:** Pitfall 1 (prebuild wipe — gated by `xcodebuild -list` after `prebuild --clean`), Pitfall 5 (App Group provisioning — gated by on-device `UserDefaults` ping).

### Phase 6 (roadmap): WCSession Native Bridge (`modules/watch-bridge`) + Round-Trip Test + Schema
**Rationale:** The transport contract and the phrase-key safety net must exist before any UI consumes them; existential risk (b) is closed here.
**Delivers:** iPhone-side `WCSession` Expo Module (mirrors `modules/phrase-widget`): `updateApplicationContext` send, `didReceiveUserInfo` → `onSwipeResults` event; the versioned payload schema including `reviewId`; the phrase-key round-trip test (green in CI before Phase 7).
**Uses:** `react-native-watch-connectivity@2.0.0` (or self-written Swift module); WatchConnectivity.
**Avoids:** Pitfall 2 (round-trip test), Pitfall 3 (correct transport API — grep for no `sendMessage` in up-path), Pitfall 6 (activate-before-transfer singleton), Pitfall 8 (payload cap in schema).

### Phase 7 (roadmap): watchOS SwiftUI App (Card Stack, Swipe, Offline Queue)
**Rationale:** Heaviest phase; the on-wrist experience. Depends on session capability (P5) and the bridge counterpart (P6).
**Delivers:** Front-only card stack → tap-to-reveal → binary swipe → distinct haptics; `WatchSessionManager` + `WatchStore` (App Group cache + `pendingSwipes.json`, persist-on-receipt, replay-on-reconnect); `reviewId` UUID generated at swipe time; empty/done states; locale-correct answers.
**Addresses:** All P1 table-stakes features.
**Avoids:** Pitfall 9 (lifecycle/state loss — persistence-first), Pitfall 2 (opaque-id echo in Swift), Pitfall 10 (offline standalone value for App Store review).

### Phase 8 (roadmap): WidgetKit Complication (parallel with Phase 9)
**Rationale:** Small once `WatchStore` write path exists; depends only on the App Group (P5) and watch app (P7).
**Delivers:** `accessoryCircular`/`accessoryInline` due-count reading `group.app.phraseman.watch`; deep-link into the session; `WidgetCenter.reloadAllTimelines()` after write.
**Avoids:** Pitfall 7 (refresh-budget exhaustion — rate-limit reloads, consider `transferCurrentComplicationUserInfo`), Pitfall 10 (standalone glanceable value).

### Phase 9 (roadmap): RN Sync Layer (`app/watch_sync.ts`) — End-to-End Glue (parallel with Phase 8)
**Rationale:** The self-healing round-trip; wired into app-start last, after the round-trip is provable. Depends on the native module (P6).
**Delivers:** `sendDueBatch` (pure read), `sendComplicationCount`, `applySwipeBatch` (LWW + `reviewId` idempotency + clock-skew tolerance), `onSwipeResults`, `startWatchSync`; canary WARNING in `markReviewed`; one app-start call site mirroring `syncWidgetData`.
**Avoids:** Pitfall 4 (double-review SM-2 corruption — the LWW + idempotency lives here), Pitfall 2 (canary assertion).

### Phase Ordering Rationale

- **Strict critical path P5→P6→P7:** entitlements/target must exist (P5) before a session (P6); the session contract and phrase-key safety net must exist (P6) before the SwiftUI UI consumes them (P7).
- **P8 ∥ P9 after P7:** the complication needs only the watch App Group write path (P7); the RN sync layer needs only the native module (P6) — they touch independent surfaces.
- **Risk-gated front-loading:** both existential risks (prebuild wipe, phrase-key mutation) are forced to the earliest phases where they can be *proven* closed with hard gates (`xcodebuild -list`, green CI round-trip test) rather than discovered late.

Phases likely needing `/gsd:research-phase` during planning:

- **Phase 8 (complication):** complication refresh budget behavior under real usage; whether the count updates frequently enough.
- **Phase 7 (v1.x trigger):** offline TTS approach (pre-rendered clips vs watch-local `AVSpeechSynthesizer`) — unresolved, deferred to the audio sub-phase.
- **Phase 9 (sync layer):** clock-skew tolerance value validation under real device drift.

Phases with standard patterns (lighter research):
