## 1) Что видит человек

Кнопка входа в состоянии загрузки (loadingProvider). Подсказка «Вход занимает больше времени. Можно безопасно закрыть
окно…» включается через 8 с от тапа — но 9,7 с из них человек и так в окне Google, поэтому после возврата подсказка
появляется почти сразу. Пустого ожидания без индикации нет. Фоновые 9,7 с — индикатор обновления (CLOUD-REFRESH-UI), Главная
уже доступна.

## 2) Находки (по фактам лога)

1. **Три полных восстановления параллельно.** Три `[BOOT-RESTORE-STEP]` с totalMs 9,5–9,7 с завершились в 28.23/28.24/28.25
   (одно syncMissingDocument=false — swap_restore, два true); страницы карточек читались по 3 раза (en/fr ×3). Дедуп по
   владельцу (peekCloudRestoreInFlight) не склеил их — вероятно, разные виды вызова (detailed false/true) не делят слот. 💸 ×3
   чтений документа пользователя, событий ошибок по 5 языкам и страниц карточек.
2. **stable_link 4,3–4,4 с в каждом восстановлении** — снова ensure_link, хотя swap за мгновение до этого получил
   подтверждённый ответ (`authoritative_link_reused ageMs=4`). Память ответа ensure_link (Ядро 14.10) привязана к поколению —
   после swap поколение новое, и память не переносится.
3. **mistake_events по языкам — последовательно**: en 1125, es 705, fr 716, de 934, it 767 мс ≈ 4,2 с в каждом восстановлении.
4. **ensure_link на входе 3,75 с** — нет серверного замера, из чего он (холодный старт функции или работа). Прогрев перед
   входом пропущен: `[ACC-SPEED] warm skip … throttled sinceLastMs=276638`.

## 3) Предложение (порядок по выгоде/риску)

| # | Что | Выигрыш | Риск для данных |
|---|---|---|---|
| A | Склеить параллельные восстановления после входа в одно (общий слот in-flight для всех видов вызова одного владельца; detailed-вызов ждёт идущий) | фон −2 копии; 💸 ~2/3 чтений восстановления | низкий: то же чтение, один раз |
| B | Перенести подтверждённый ответ ensure_link через swap в новое поколение (тот же stableUid, ageMs < 60 с) | фон −4,3 с; −1 callable | низкий: ответ сервера тот же, проверка stableUid |
| C | mistake_events по языкам — параллельно (Promise.all) или для неактивных языков — после Главной | фон −3 с | низкий: те же данные, порядок применения сохранить |
| D | Логи [ACC-SPEED] с серверной длительностью ensure_link (сервер отдаёт serverMs) + прогрев функций при открытии окна входа без троттлинга 5 мин | вход −? (до 3 с, если холодный старт) | нет |

Не трогаем: само восстановление прогресса (apply/merge), стирание и смену поколения на входе — это граница данных.
Ожидаемо после A+B+C: фон 11,5 с → ~3–4 с, чтения восстановления ×3 → ×1. Вход (6,9 с работы) — после D по фактам.
