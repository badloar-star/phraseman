# Task packet: повтор генерации ника гостя применяет уже зарезервированное имя, без второго вызова сервера

Governance-ID: TG-3D1E2140504C

Owner: 5 · АВТОРИЗАЦИЯ

## Outcome

Если сервер уже зарезервировал ник (nameGenerateAndReserve вернул имя), а применить его не удалось (skip_apply — аккаунт
ещё активируется; поздний ответ), то следующий повтор применяет ТО ЖЕ имя из локальной записи, не вызывая сервер. У гостя
не бывает «＠Neon 39486 → другое имя через ~20 с», и второй резерв на сервере не тратится.

## Разбор (app/nickname_guard.ts resumePendingGeneratedNickname)

- Имя от сервера жило только в памяти вызова; при skip_apply / skip_owner_mismatch оно терялось, флаг
  generated_nickname_pending_v1 оставался → следующий запуск (онбординг, _layout runHeavyInit, повтор 5/15/45 с) снова
  звал сервер.
- Сервер для того же stableUid обычно возвращает прежнее имя (leaderboard.ts ~290), но только если резерв дошёл до
  users.progress и name_index того же uid. Любое расхождение uid (временная личность гостя) даёт новое имя. Клиентская
  запись резерва снимает вопрос и экономит вызов в любом случае.
- Логов прогона с [NICK-GEN] (cc775527c) ещё нет — цепочка будет видна в первом же прогоне Сверки: step=generated source=cached|server.

## Scope

Только app/nickname_guard.ts + тест tests/nickname_guard_reconcile.test.ts.
- После успеха сервера резерв {reservedName, reservedFor} дописывается в флаг pending (под замком смены аккаунта, только
  если флаг ещё есть).
- Повтор: если в флаге есть резерв и reservedFor === текущий владелец (peekStableId) — имя берётся из флага, сервер не
  вызывается.
- Пропуск применения при живом флаге планирует повтор (бюджет прежний: 3 попытки), теперь он бесплатный.

## Architecture

Флаг pending уже стирается при смене аккаунта (cloud_sync.ts:977), поэтому резерв не переживает смену владельца; плюс
явная проверка reservedFor === активный stableId — чужой резерв не применится.

## Security and privacy

Имя хранится локально в уже существующем ключе; в облако флаг не уходит. Логи без имён.

## Verification

(2) резерв другого владельца не применяется → сервер вызывается для нового; прежние тесты reconcile зелёные.
