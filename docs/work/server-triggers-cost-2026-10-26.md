# Серверные триггеры Firestore: что срабатывает и сколько стоит (Ядро, 26.10, бэклог стр. 79 и 107)

Составлено чтением кода `functions/src` (не прод-данных). Цифры объёма — формулой: сколько записей в коллекции за
месяц, столько срабатываний. Прод-счётчики может снять координатор (Cloud Monitoring → «Function invocations» по имени),
без чтений Firestore.

Цены Blaze: вызов функции — $0,40 за 1 млн сверх 2 млн бесплатных + время процессора/памяти; Firestore (eur3) —
чтения $0,06 / 100 тыс., записи $0,18 / 100 тыс.

## Горячие (срабатывают от действий каждого человека)

| Триггер | Коллекция | На одно событие | Где дешевле |
|---|---|---|---|
| `usersWriteRouter` | `users/{uid}` — **любая** запись профиля | 1 вызов; 4 обработчика выходят по сравнению before/after **без чтений** (реферал — только при новом Plus; VIP-сирота — только скрытый профиль с новым VIP; новый пользователь — только создание; push-токен — только смена токена) | Главная цена — число вызовов = число записей в `users/{uid}`. Фильтра по полю у триггеров Firestore нет, поэтому сужать можно только частотой записей клиента: склеивать синхронизацию прогресса (cloud_sync) в реже идущие пачки. Сам триггер уже один вместо двух (29.08) |
| `adminAlertOnCriticalError` + `adminAlertOnAuthFailureSpike` | `app_errors/{id}` — каждая ошибка с телефона | **2 вызова** на один документ; первый всегда кладёт событие в `admin_alert_events` (1 запись) → ещё **1 вызов** `adminAlertDispatchOnCreate` с чтениями очереди/настроек; второй — запись счётчика всплеска только для ошибок входа | Склеить два триггера на `app_errors` в один (как `usersWriteRouter`) — минус 1 вызов на каждую ошибку. Некритичные ошибки идут в дайджест — их можно не класть в очередь по одной, а считать агрегатом |
| `onAppMessageStateWritten` | `users/{uid}/app_message_states/{id}` | 1 вызов; запись `readCount` только если сменился признак «прочитано» | Нормально: без смены — выход без записи |
| `onAppMessageReactionWritten`, `onAppMessagePollVoteWritten` | реакции и голоса на сообщениях | 1 вызов + запись счётчика | Нормально для текущего объёма |
| `notifyOnFriendRequestCreated`, `notifyOnFriendAccepted`, `notifyOnPackCommentCreated` | заявки, друзья, комментарии | 1 вызов + push | Редкие события |
| `adminAlertOnPromoRedemptionCreated` | `users/{uid}/promo_redemptions` | 1 вызов + 1 запись события + 1 вызов диспетчера | Редкие события |

## Цепочка уведомлений админки (каждое событие ×2 вызова)

Любой `adminAlertOn*` (отзывы, жалобы, покупки, баны, рефералы, журнал админа, рассылки, Джарвис, SOC2, сертификаты,
квитанции RevenueCat) пишет 1 документ в `admin_alert_events`, а тот запускает `adminAlertDispatchOnCreate`. Итого на
событие: 2 вызова + 1–2 записи + чтения настроек. Подбор зависших — крон раз в 15 мин (уже удешевлён 17.10 с 1 мин).

## Что предлагаю (по «да» владельца, каждое — отдельная выкладка)

1. **Склеить два триггера `app_errors`** в один маршрутизатор: −1 вызов на каждую ошибку телефона. Риск низкий, код
   обработчиков не меняется.
2. **Реже писать `users/{uid}` с телефона** (пачки синхронизации) — самый крупный рычаг, но это клиент и
   синхронизация; сначала замер числа вызовов `usersWriteRouter` в Cloud Monitoring.
3. Удалить из выкладки заглушку `helpBoardGenerateCompassForTopicDisabled`, когда старые сборки уйдут.

Ничего из этого не выложено и не менялось — страница только для решения.
