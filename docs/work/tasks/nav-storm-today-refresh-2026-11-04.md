## Outcome

Выяснить по коду, что запускает повторные вызовы и ходят ли они в Firestore, и убрать лишние запуски без изменения поведения для человека.

## Разбор (по коду, не по догадке)

- `loadSpireConfig` (`app/spire_config_client.ts:122`) читает ЛОКАЛЬНЫЙ кэш; в Firestore идёт только при возрасте кэша ≥ `SPIRE_CONFIG_REFRESH_MS` (6 ч) или `force`. Строки «из кэша (возраст=…)» — это чтение памяти телефона, не сеть. Firestore-чтений в минуту: ≈0 (до и после).
- `STORY-ANNOUNCE` (`modules/story_events/announcement_fetch_policy.ts`): решение по версии ленты `story_feed_rev` из кэша конфига; сетевой запрос только при смене версии, возрасте ≥ 24 ч или тёплом возврате ≥ 15 мин. Строка `решение` пишется на КАЖДЫЙ вход/возврат — это журнал решения, не запрос.
- `TODAY-TASKS refresh(foreground)` (`hooks/use_today_tasks.ts:158–162`): каждый `AppState 'active'` и каждое монтирование хука запускает обновление набора дня (`primeSpireTabFlag` + `readTodayTaskLiveness` + `refreshTodayTasks`). Всё локальное (AsyncStorage). 42 за 5 мин = 42 возврата `active` + монтирования при ПРОГОНАХ Сверки/dev_state, где каждая копия вкладок `(tabs)` держит свой хук.
- `NAVIGATE`/`TODAY-SETTLE`: следствие тех же возвратов (завершение обновления дня).

## Scope

`hooks/use_today_tasks.ts` (троттлинг возвратов `active`), тест-сторож.

## Architecture

Модульная метка последнего запуска обновления (общая для всех копий хука): возврат `active` не запускает новое обновление, если прошло < 20 с с прошлого запуска для той же пары (язык обучения, флаг Шпиля). Вход (монтирование/смена цели), полночь и смена пары — всегда обновляют. Поздний ответ и так не затирает свежее (`peekTodayTasks() ?? next`). На ранних выходах — лог `[NAV-STORM]`.
