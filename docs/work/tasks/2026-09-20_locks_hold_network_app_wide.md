# Task packet: сеть под замком аккаунта — поиск по всему приложению

Governance-ID: TG-2308FA00FDEB
Status: In progress
Owner: сессия Claude Opus 5 (2026-09-20)

## Outcome

Ни один сетевой вызов не выполняется под замком аккаунта. Покупка диалога
за руны открывается, кнопки на всех экранах не умирают под пальцем.

## Повод

Владелец: «диалоги не открываются и не покупаются» — четыре круга диагноза.
Три моих гипотезы (нехватка рун, вечная очередь, самозахват) оказались
неверны: покупка не доходила даже до первой своей строки.

Корень нашла параллельная сессия, подтверждён логом устройства:

```
[ARENA-OUTBOX-GUARD] lock timeout target=en waited=5012ms — another holder is stuck
(15:32:08 и 15:33:26)
```

`reserveArenaCall` держал замок во время двух сетевых вызовов. Очередь
`withAccountTransitionLock` ждёт предыдущего владельца БЕЗ таймаута, поэтому
пока один ждёт сеть — стоят ВСЕ 231 владелец замка, включая покупку диалога.
Арену починил коммит `5a2fc1eff`.

## Находка этого пакета

Сплошной поиск «сеть под замком» по app/, components/, modules/, hooks/
дал 7 мест. После проверки каждого вручную:

- `app/friend_gift_inbox.ts:51` — **настоящий дефект, тот же класс**.
  Под замком ТРИ сетевые операции: запрос подарков, `users.get()`,
  `batch.commit()`. Вызывается из `GlobalFriendGiftHost` — на КАЖДОМ экране.
- `app/profile_card_system.ts:541` — `httpsCallable` внутри `void (async ...)`,
  то есть не удерживает замок (fire-and-forget). Не дефект.
- `app/level_spin_star_grants.ts:813,832` — `AsyncStorage.setItem`, локально.
  Ложное срабатывание поиска по `.set(`.
- `app/season_pass_gift_inventory.ts:247` — то же, локальная запись.
- `app/level_reward_spins_client.ts:437` — то же, локальная запись.

## Вторая волна поиска («ещё шире», владелец)

Скан расширен с «сеть» на «любая долгая операция под замком»: SQLite,
FileSystem, SecureStore, setTimeout, динамический импорт, аудио, ассеты.

**Найдено и измерено — phone-state (SQLCipher) под замком аккаунта:**

`recoverProjection` (`level_spin_star_grants.ts:813`) первым делом зовёт
`readPhoneStateStarCreditState`, то есть открытие шифрованной базы. Замер
по логу владельца (самое долгое открытие, 12:33:02 → 12:33:07):

```
open:in                                   +0s
step 1/5 файл открыт                      +0s
step 2/5 ключ применён                    +0s
step 3/5 cipher_version                   +0s
step 4/5 integrity rows=0                 +1s   PRAGMA cipher_integrity_check
step 5/5 страница расшифрована            +2s
step 6/6 проба записи через WAL           +2s   OPEN_WRITE_PROBE
                                          ИТОГО 5 секунд
```

За сессию 32 открытия (по одному на запуск приложения — это НЕ утечка,
первоначальное подозрение снято), длительности: 2,2,2,2,3,4,4,5 секунд.

Всё это время держится замок аккаунта, то есть стоят все остальные 231
владелец: покупка диалога, энергия, спины, подарки.

**Что НЕЛЬЗЯ трогать.** `cipher_integrity_check` и `OPEN_WRITE_PROBE` —
защиты от реальных инцидентов 13.09 и 14.09 (ложный успех прагм на файле
под чужим ключом; порча в хвостах WAL). Ускорять открытие за счёт их
снятия запрещено.

**Правильное лечение** — открывать базу ДО захвата замка (как сделано для
сети), а под замком оставлять только работу с уже открытым соединением.
Это отдельная задача: `openRuntimeSession` поднимает всю сессию phone-state
со всеми редьюсерами и мостами, переносить её через границу замка рискованно
без отдельного разбора.

**Ложные срабатывания второй волны:** `getStableId` в 10 местах под замком —
SecureStore + AsyncStorage с кэшем в памяти, не сеть.

## Scope

In scope: `app/friend_gift_inbox.ts` — вынести сеть из-под замка.

Out of scope: сам механизм замка (очередь без таймаута) — отдельная большая
задача; остальные 230 вызовов замка; 25 файлов с логированием только через
DebugLogger.

## Architecture

**Что защищает замок.** Смену поколения аккаунта: пока идёт переход, нельзя
записать локальное состояние от имени прежнего владельца. Для этого нужны
локальные проверки владельца до и после записи — они мгновенные.

**Что НЕ должно быть под замком.** Чтение из Firestore и `batch.commit()` —
они поколение не меняют и длятся сколько угодно на плохой сети.

**Решение.** Чтение подарков и `users.get()` выполняются ДО захвата замка.
Под замком остаются только `AsyncStorage`-записи эффектов и сохранение
подарков в инвентарь. Отметка «прочитано» (`batch.commit()`) выносится ПОСЛЕ
замка.

**Инвариант.** Под замком аккаунта не выполняется ни один сетевой вызов.

## Security and privacy

Данные те же, новых полей и получателей нет. PII наружу не уходит: читаются
собственные документы пользователя. Политику приватности правка не затрагивает.

## Technical debt

Остаётся корневой долг: `withAccountTransitionLock` — очередь без таймаута,
231 вызов. Любой новый код, случайно выполнивший сеть под замком, воспроизведёт
тот же симптом «кнопка не работает». Сторож на этот инвариант пока есть только
для Арены (`tests/arena_lock_no_network_contract.test.ts`).

## Rollback

`git revert` коммита с этой правкой. Риск отката: возвращается зависание
кнопок на каждом экране при плохой сети. Потери данных откат не вызывает —
награда сохраняется в локальный инвентарь до любой сетевой операции.
