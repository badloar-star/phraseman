# Ядро · задача: отзыв токена Sign in with Apple при удалении аккаунта (подготовка, без выкладки) — 25.10

Governance-ID: TG-52D037074BA1

## Outcome
Требование Apple (с 30.06.2022, App Review 5.1.1(v)): приложение с Sign in with Apple при удалении аккаунта обязано отозвать
токены пользователя через REST `appleid.apple.com/auth/revoke`. Сейчас этого нет нигде — ни в functions, ни в приложении.
Координатор 25.10: подготовить задачу (вызов при удалении — и в конце grace, и при «Удалить навсегда сейчас»), без выкладки.

## Факты (только чтение, 25.10)
- Secret Manager: 29 секретов, ключа Sign in with Apple (.p8 / Key ID / Team ID) нет ни под каким именем.
- Клиент: вход Apple нативно (`expo-apple-authentication` ~8.0.8 + `@react-native-firebase/auth` 21.14.0). Код авторизации Apple
  (`authorizationCode`) нигде не сохраняется и не передаётся; `revokeToken` / `revokeAccessToken` не вызываются.
- В установленной RN Firebase 21.14.0 есть `auth().revokeToken(authorizationCode)` с нативной частью для iOS и Android →
  правка клиента — чистый JS, может уйти обновлением по воздуху.
- Firebase сам вызывает Apple `/auth/revoke`, но ему нужен закрытый ключ Apple в настройках провайдера Apple в консоли Firebase
  (Authentication → Sign-in method → Apple → OAuth code flow: Services ID, Apple Team ID, Key ID, private key). Вход Apple на
  Android выключен (нет Services ID), поэтому ключ там, скорее всего, НЕ задан — проверить может только владелец в консоли.

## Scope (предложение)
Вариант 1 (рекомендую) — клиент + Firebase, без своего хранения токенов:
1. Экран удаления, если у аккаунта есть вход Apple: перед постановкой задачи — повторный запрос Apple
   (`AppleAuthentication.signInAsync` без scopes) → свежий `authorizationCode` → `auth().revokeToken(code)`.
2. Потом обычная постановка задачи удаления (вариант Б «Авторизации»: пользователь Auth живёт до конца grace) и кнопка
   «Удалить навсегда сейчас» — тот же отзыв перед немедленным удалением.
3. Отзыв не мешает «передумать»: после отзыва человек может снова войти через Apple — sub в пределах команды тот же, Firebase
   вернёт того же пользователя (вариант Б), и сработает «Восстановить аккаунт?».
4. Сбой отзыва (отмена окна Apple, нет сети, ключ не задан) удаление НЕ блокирует — журнал `[APPLE-REVOKE]` со стадией и кодом,
   удаление идёт дальше (молчаливого отказа нет, но и заложником отзыва человек не становится).
Вариант 2 (не рекомендую) — сервер: при входе менять код Apple на refresh token, хранить его (новые чувствительные данные) и
отзывать воркером в конце grace. Больше данных, больше поверхности атаки, нужен свой ключ .p8 в секретах.

## Architecture
Где: модуль удаления аккаунта на клиенте (зона «5 · ВХОД»), только для аккаунтов с провайдером apple.com. Сервер не меняется.
Журнал: `[APPLE-REVOKE] start / apple_code_ok / revoked / failed stage=… code=…` — без кода авторизации и токенов в журнале.

## Security and privacy
Код авторизации живёт секунды в памяти и уходит только в Firebase; нигде не сохраняется и не логируется. В политику
конфиденциальности — фраза «при удалении аккаунта мы отзываем доступ, выданный через Sign in with Apple» (проверить текущий
текст раздела удаления).

## Technical debt
Для пятерых, у кого удаление уже поставлено и пользователь Auth снят, отозвать токен уже нельзя (нет ни кода, ни пользователя) —
это остаётся как есть.

## Verification
Тест: отзыв вызывается до постановки задачи у Apple-аккаунта, не вызывается у Google/гостя; сбой отзыва не мешает удалению и
пишет [APPLE-REVOKE] failed. Ручная проверка на iPhone — в консоли Apple ID («Приложения, использующие Apple ID») приложение
исчезает после удаления аккаунта.

## Rollback
Откат коммита клиента; сервер не меняется.

## Нужно от владельца
1. Проверить в консоли Firebase, задан ли закрытый ключ Apple у провайдера Apple (без этого revokeToken вернёт ошибку).
   Если нет — создать ключ Sign in with Apple в Apple Developer и вписать в консоль (ключ вводит владелец, сессии его не видят).
2. «Да» на вариант 1 и на исполнителя (зона удаления — «5 · ВХОД»).
