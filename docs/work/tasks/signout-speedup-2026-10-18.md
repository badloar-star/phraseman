1. Финальная копия: сборка страницы сейчас на КАЖДУЮ пару заново сериализует и хеширует всю страницу (чистый JS SHA-256)

   (база страницы + длина каждой пары): страницы и отпечатки байт в байт те же, хеш — один раз на страницу (как и сейчас
   в writePage). Файл: app/cloud_sync.ts saveAccountSwitchEmergencyBackup. Доказательство — стенд
   (scratchpad backup_bench.ts): старый и новый алгоритм дают одинаковые страницы, время до/после.

   владельца — только по слову координатора (граница данных).

## Шаг 2 — пропуск записи документа при полном совпадении (координатор 02:25: ДА)

8 знаков, uid не печатать), при любом сомнении — пишем как раньше.

Реализация:
- Владелец снимка: снимок cloud_last_sync_snapshot_v1 общий и без владельца. Рядом — новый ключ
  cloud_last_sync_snapshot_owner_v1 = sha256(uid). Пишется ОДНИМ multiSet вместе со снимком там, где владелец известен
  (doSyncToCloud, forceSyncToCloud, восстановление из облака при известном stableId поколения); где неизвестен —
  ключ снимается ДО записи снимка (сомнение → запись). Подрезка снимка (resetWipedClientKeys) владельца не меняет.
- Решение (только для выхода, опция skipUnchangedDocWrite в forceSyncToCloud): пропуск, если владелец снимка = sha256(uid),
  каждый отправляемый ключ есть в снимке, hashCanonicalBody(отправляемое) === hashCanonicalBody(тот же набор из снимка),
  совпадают user_avatar/user_avatar_frame, createdAt уже записан, страницы карточек не писались и в документ списки не
  уходят. Любое иное — запись как раньше. Пропуск не обновляет updatedAt/last_active_at в users/{uid}.
- Новый ключ зарегистрирован: guest_clean_classifier SERVICE_KEYS, config/phone-state-legacy-inventory.v1.json,

## Шаг 3 — разбор порядка маркеров выхода (только журнал, без перестановки; координатор: до релиза не трогаем)

Цепочка app/account_switch_quarantine.ts resumeInternal (замер 01:35, мс):
prepared →(push 457 + signOut 18)→ provider_signed_out →(wipe 1302)→ local_data_cleared →(clearStableId 231)→
stable_id_cleared →(ensureAnonymousIdentity 840, сеть)→ anonymous_authenticated → fresh_stable_created → ready →
хвост (clear_marker 165). Маркеры: 6 пар read + write_verified ≈ 350 мс. До цепочки — чтение 3 журналов 416 мс.

Зависимости:
1. Чтение журналов 416 мс — НЕ зависимость: три getItem параллельно, а время съедает занятый JS-поток (в эти же мс
   перемонтируется вкладка «Уроки» по смене поколения — LESSONS-REBUILD 38.60–38.68, HOME-FOCUS-COST 467 мс).
   Ускорение — отложить перерисовку вкладок до конца смены. Порядок маркеров не трогает.
2. push 457 мс → signOut: снятие push-токена требует авторизации старого аккаунта — строго ДО выхода провайдера.
   Можно начать раньше (параллельно с финальной копией), но это меняет сервер ДО точки невозврата: при отмене смены
   токен уже снят. Решение — продуктовое.
3. wipe 1302 мс → clearStableId → новый гость: жёсткая зависимость. Новый анонимный вход берёт stableId; пока старый
   не стёрт, гость привязался бы к старому stableId; маркер anonymous_authenticated проверяет
   currentStable !== ownerStableId. Сетевую часть (signInAnonymously, ~0,8 с) теоретически можно запустить параллельно
   со стиранием, но смена auth будит слушатели onAuthStateChanged при ещё не стёртых данных старого аккаунта — нужен
   отдельный разбор слушателей. После релиза.
4. Маркеры 350 мс: после собственной проверенной записи маркер можно не перечитывать с диска (одна сессия держит
   замок) — ~150–200 мс. Порядок не меняется, но это код точки невозврата — после релиза, с ревью.
5. Внутри стирания: removeKeys 563 мс (2225 ключей), closePhoneState 269, resetMemory 150 — независимы от маркеров,
   ускорение внутри одного шага возможно без перестановки (отдельная задача).

Ожидание после шагов 1–2 (на телефоне не замерено): 6,9 → ~4,4 с (копия ~2,1 → ~0,2; запись документа −0,55). До 3 с —
пункты 1, 3, 4 выше (после релиза), замер «после» — в очереди Сверки.
