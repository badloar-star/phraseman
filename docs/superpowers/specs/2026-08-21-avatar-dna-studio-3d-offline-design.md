# Avatar DNA Studio: офлайн 3D-архитектура

**Статус:** утверждено владельцем 2026-08-21  
**Дата:** 2026-08-21  
**Заменяет:** 2.5D layered-renderer часть прежней спецификации и плана; экономика, владение, локальное сохранение, legacy fallback и социальные consumers сохраняются, но должны быть перепланированы после технического PASS.

## 1. Зафиксированные решения владельца

- Студия работает полностью офлайн после установки приложения.
- Персонаж статичен. Анимируются только кнопки, вкладки, плитки, панели и переходы интерфейса.
- Визуальная цель — тёплый premium stylized 3D из утверждённого референса: цельный объём, мягкий студийный свет, выразительные правдоподобные глаза, кремово-терракотовая палитра.
- Внешность должна глубоко настраиваться: форма головы и лица, глаза, брови, нос, рот, волосы, одежда, головные уборы, капюшоны, маски, очки, аксессуары, фон и будущие категории.
- Нельзя производить отдельное лицо под каждую комбинацию.
- Любой выпущенный элемент обязан быть совместим с любым поддерживаемым персонажем либо иметь явное детерминированное правило конфликта.
- При выборе любого доступного варианта не допускаются spinner, сетевое ожидание, видимое подтормаживание или догрузка модели после нажатия. Отклик плитки и новый avatar preview должны появляться сразу.
- Независимо сгенерированные растровые глаза, носы, рты, волосы и тела забракованы: у них нет общей геометрии, перспективы, света, окклюзии и анатомии.
- Художественный порог зафиксирован двумя owner-reference изображениями от 2026-08-21: только high-quality semi-realistic stylized 3D с человеческой анатомией, цельными веками/глазницами, сформированными носом и губами, фактурными волосами, тканью и тёплым студийным светом.
- Memoji, chibi, low-poly, шарообразные носы, рты-полоски, волосы из примитивов, плоские наклеенные глаза, игрушечные пропорции и дешёвая мобильная карикатура запрещены даже как временный production-вариант.
- Владелец исключил найм 3D-художника, покупку готовой модели и обязательность Blender. Master asset должен быть создан собственным воспроизводимым dev-time pipeline из свободной CC0-топологии и собственных Phraseman-деформаций.
- Ничего визуально хуже owner-reference не выпускается. Технически работающий, но художественно слабый рендер остаётся dev-only прототипом и не заменяет действующий аватар.

## 2. Краткое решение

Использовать одну каноническую 3D-модель `human_v2` с общей топологией лица и тела. Анатомические варианты реализовать через morph targets одной сетки. Волосы, одежду, маски, очки и головные уборы реализовать как совместимые меши, подготовленные на той же модели и прикреплённые к фиксированным костям/anchors.

Студия отображает модель локально через React Native renderer на базе Expo GL и React Three Fiber/Three.js. Рендер работает только по требованию: после загрузки и после изменения DNA, без постоянного цикла кадров.

После сохранения приложение создаёт локальный статичный портрет. Все обычные поверхности приложения — главная, профиль, таблицы, лиги, друзья, Арена — показывают этот портрет через существующий `AvatarView`, а не создают отдельный 3D-контекст.

```text
AvatarDNA
  -> deterministic 3D resolver
  -> morph weights + mesh visibility + materials + camera
  -> local render-on-change in Studio
  -> local portrait snapshot
  -> ordinary image everywhere else
```

## 3. Почему не Rive 2D

Rive не является production fallback-направлением. Он быстрее для первого 2D-прототипа и легче на слабых устройствах, однако требует заранее нарисованных форм и ручных масок. Он не даёт естественной общей глубины носа, губ, глаз, волос, масок и капюшонов, визуально уводит продукт в 2.5D и поэтому не проходит утверждённый Art P0. Технический FAIL текущего GL runtime разрешается оптимизацией или выбором другого локального 3D runtime, но не снижением художественного контракта.

## 4. Runtime-контур React Native

Целевой стек прототипа:

- Expo SDK 54 / React Native;
- `expo-gl` как нативная GL-поверхность;
- `@react-three/fiber/native` как React renderer;
- `three` для GLB, morph targets, материалов, камеры и света;
- `expo-asset` для статически bundled GLB/текстур;
- существующий Reanimated только для интерфейсных micro-interactions;
- локальный snapshot GL framebuffer для портрета.

Проект уже содержит `expo-gl`, `three` и `@react-three/fiber`, а также ограниченный P0 scaffold. Их наличие подтверждает только возможность runtime-контура; оно не является художественным PASS и не разрешает выпуск тестовой геометрии.

## 5. Каноническая модель `human_v2`

`human_v2` является собственным Phraseman-деривативом, а не прямым MakeHuman runtime asset. Dev-time pipeline берёт только CC0 base mesh/targets с зафиксированной версией и checksum, применяет собственный Phraseman style target, материалы, anchors и ограничения, после чего экспортирует самодостаточный versioned GLB. Код MakeHuman под AGPL, его UI и его Python runtime в приложение не включаются.

### 5.1 Геометрический контракт

- Одна neutral base mesh для головы, шеи и видимой верхней части тела.
- Все анатомические morph targets имеют одинаковое число и порядок вершин с base mesh.
- Morph targets выражают безопасные дельты, а не заменяют всю голову.
- Одновременно смешиваемые морфы ограничиваются проверенным диапазоном весов.
- Глаза используют единые sockets/anchors; допустим размер/наклон в безопасном диапазоне, но eyeball не покидает глазницу.
- Зубы, язык и внутренняя полость рта не входят в v1 статичного портрета.

Начальные семейства морфов прототипа:

- `head_width`;
- `jaw_shape`;
- `nose_width` и `nose_projection`;
- `eye_size` и `eye_spacing`;
- `mouth_width` и `lip_fullness`.

Прототипу не требуется полный каталог. Он проверяет три выразительно различимых face presets, собранных из этих безопасных морфов.

### 5.2 Сменные меши

- Волосы, одежда, капюшоны, маски, очки и аксессуары авторятся на той же neutral модели.
- Каждый меш имеет типизированные anchors, coverage zones и conflict metadata.
- Головной убор может скрыть `hair.front`, `hair.top` или всю причёску, но выбранная причёска остаётся в DNA и автоматически возвращается после снятия предмета.
- Капюшон является составным предметом: outer hood + optional inner hair cap + coverage rule.
- Несовместимая комбинация не исправляется случайным масштабированием в runtime. Она блокируется asset validator до публикации либо разрешается явным deterministic rule.

### 5.3 Материалы

- Цвет кожи, радужки, волос и tintable одежды задаётся параметрами материалов, а не отдельной геометрией.
- Все материалы используют один утверждённый light rig и ограниченную палитру roughness/metalness.
- Текстуры объединяются в небольшие атласы; v1 избегает уникальной 2K-текстуры на каждый предмет.

## 6. Avatar DNA и resolver

Существующий versioned `AvatarDNA` сохраняется как концепция, но `rigId` меняется на `human_v2`, а resolver перестаёт выдавать 2D draw order. Он выдаёт:

```ts
type Avatar3DRenderPlan = {
  morphWeights: Readonly<Record<string, number>>;
  visibleMeshIds: readonly string[];
  hiddenZones: readonly string[];
  materialParams: Readonly<Record<string, string | number>>;
  cameraPreset: 'portrait' | 'studio';
  backgroundId: string;
};
```

Resolver остаётся чистым, детерминированным и тестируемым без GL. Одинаковые DNA + manifest всегда дают одинаковый render plan и render key.

## 7. Экран Студии

### Визуальный контракт владельца — 2026-08-21

Утверждённый целевой экран — мобильная Studio из концепта `exec-b133fdb2-d23f-46a7-b1a1-2a559321c165.png`:

- Вверху — back, заголовок `Студия персонажа`, undo и redo.
- Основную верхнюю часть занимает один крупный, статичный, цельный stylized 3D-персонаж по пояс: тёплая кожа, выразительные естественные глаза, реалистично малый нос, нормальные губы, фактурные волосы и одежда. Никаких Memoji-пропорций, отдельных сгенерированных частей лица, пустого preview или технической маркировки.
- Ниже portrait — ряд из пяти вкладок с иконками: `Основа`, `Лицо`, `Волосы`, `Образ`, `Сцена`; выбранная вкладка выделена терракотовой мягкой карточкой.
- Контент вкладки — ясные секции (например, `Форма лица`, `Брови`, `Глаза`) и компактная сетка вариантов. Плитки показывают подготовленные превью одного канонического рига, а не независимые изображения частей тела.
- Внизу — закреплённая терракотовая кнопка `Сохранить персонажа`.
- Визуальный язык: cream background, cocoa typography, terracotta primary action, тонкие тёплые тени, мягкие rounded cards; зелёный применяется только к успешным состояниям с тёмным foreground.

Этот концепт является визуальной целью, а не production-asset и не разрешает использовать его как bitmap-аватар в приложении.

Структура:

1. Верхняя панель: закрыть, название, undo, redo.
2. Постоянный крупный hero с персонажем и переключателем `Портрет / По пояс`.
3. Пять основных вкладок: `Основа`, `Лицо`, `Волосы`, `Образ`, `Сцена`.
4. Контекстные подкатегории.
5. Одна виртуализированная сетка вариантов.
6. Нижняя фиксированная кнопка сохранения.

Правила UX:

- минимальная touch-зона 44×44;
- выбранное состояние определяется не только цветом;
- все icon-only controls имеют accessibility label;
- интерфейсные реакции занимают 150–300 мс и используют только transform/opacity;
- reduced motion применяет выбор без переходной анимации;
- ярко-зелёные поверхности всегда используют тёмный текст/иконки;
- персонаж, свет и камера никогда не качаются, не моргают и не вращаются автоматически.

Визуальный язык сохраняет тёплый cream/terracotta референс, мягкие объёмные карточки и скругления. Автоматически предложенная learning-indigo палитра не используется, потому что она нарушает уже утверждённую визуальную идентичность поверхности.

## 8. Производительность

- 3D Canvas монтируется только на экране Студии.
- `frameloop="demand"`: новый кадр запрашивается при загрузке, выборе item, смене камеры или размера.
- После стабилизации не должно быть непрерывного render loop.
- **Нулевое ожидание выбора:** до того как Студия примет первый tap, она обязана иметь в памяти GLB, texture atlas, все mesh variants текущего каталога, material instances и скомпилированные shader paths. Нажатие меняет только morph weights, visibility и material values уже созданных объектов.
- **Никакой сети в редакторе:** Studio runtime не выполняет request на выбор item. Любой доступный offline item входит в app bundle или гарантированно предзагружен и проверен до открытия экрана. Элемент, которого нет локально, не показывается как доступный к выбору.
- **Синхронная обратная связь:** выбранная плитка получает visual/a11y state в том же React update. Сам preview должен быть обновлён в следующий запрошенный GL frame; P0 измеряет p95 выбора отдельно на iOS и Android и блокирует масштабирование каталога при заметной задержке.
- Контекст и шейдеры прогреваются на безопасном idle-моменте до первого открытия Studio; первый видимый экран никогда не является прогревочным экраном.
- Прототип использует один GLB, texture atlas не выше 1024 px и ориентир до 60k видимых triangles в режиме `По пояс`.
- Повторяющиеся открытия/закрытия Студии обязаны освобождать геометрию, материалы, текстуры и GL context без роста памяти.
- При ошибке GL приложение сохраняет последний хороший портрет и legacy avatar; пустой аватар запрещён.
- До масштабирования ассетов обязательна проверка минимум на одном реальном iPhone и одном Android, включая более слабый Android-class device.

## 9. Локальный snapshot и использование в приложении

Сохранение выполняется локально в фиксированном порядке:

1. validate DNA и entitlement;
2. resolve render plan;
3. отрисовать portrait camera;
4. сделать snapshot в локальный account-scoped файл;
5. атомарно подтвердить DNA + snapshot metadata;
6. обновить first-frame app snapshot;
7. запустить необязательную синхронизацию.

Сетевой сбой не отменяет локально сохранённого персонажа. Для локального пользователя `AvatarView` предпочитает confirmed local portrait, затем existing custom/level/legacy fallback. Публичная синхронизация и межустройственное восстановление проектируются после PASS прототипа; серверный compositor больше не является условием локальной работы.

## 10. Asset Factory

### 10.1 Источник геометрии и лицензия

- Исходная анатомическая топология и базовые target-дельты берутся только из официального MakeHuman набора, явно опубликованного как CC0.
- Точная upstream-версия, список использованных файлов, SHA-256 и копия применимой лицензии фиксируются в asset provenance manifest.
- Сторонние community assets не наследуют разрешение автоматически: без отдельной подтверждённой CC0-лицензии они запрещены.
- AGPL-код MakeHuman не копируется, не импортируется и не поставляется внутри Phraseman. Pipeline либо читает CC0 asset data собственным конвертером, либо использует MakeHuman исключительно как локальный dev-time инструмент и сохраняет только разрешённый производный output.
- VRoid и аналогичные наборы, запрещающие создание собственного avatar maker, не используются.

### 10.2 Собственный Phraseman authoring pipeline без Blender

- Source of truth — versioned neutral mesh + sparse vertex target data + Phraseman manifests в репозитории, а не `.blend`.
- Собственный Node/Python build tool читает base topology и target offsets, нормализует координаты, собирает morph targets, материалы, anchors и экспортирует GLB/glTF 2.0.
- `phraseman_style_v1` является обязательным morph-слоем поверх анатомической базы. Он фиксирует утверждённые пропорции головы, глазниц, век, носа, губ, скул, челюсти, ушей и шеи до применения пользовательских настроек.
- Мужские и женские варианты используют одну и ту же топологию и разные безопасные наборы весов; они не являются независимо сгенерированными моделями.
- Глаз собирается как согласованная геометрическая система `sclera + iris + pupil + cornea`; веки остаются частью головы и обязаны корректно охватывать eyeball во всех разрешённых морфах.
- Волосы создаются как цельные параметрические меши направленных прядей/крупных локонов с scalp cap и coverage zones. Сферы, капсулы, плоские PNG-пряди и случайный runtime-scale запрещены.
- Одежда и головные уборы строятся от канонических body/head surfaces, используют anchors и собственные corrective targets для крайних разрешённых форм.
- DALL·E/другая генерация допустима только для concept art, палитры и texture ideas; она не производит runtime-геометрию, анатомические части или финальные texture layers.

### 10.3 Автоматические и визуальные проверки

- Каждый build проверяет manifest/schema, provenance, mesh names, topology/vertex order, morph bounds, required anchors, material limits, triangle/texture budgets, missing files, duplicate IDs и immutable hash.
- Валидация отбраковывает самопересечения, выход eyeball из глазницы, разрыв век, hair/scalp penetration, clipping одежды, неразрешённые скрытия и конфликтующие предметы.
- Затем asset проходит визуальную матрицу на утверждённых sentinel face presets, мужской и женской базе, оттенках кожи, причёсках, камерах и конфликтных головных уборах.
- Два фронтальных reference portraits владельца являются нормативным art-direction gate, а не изображениями для встраивания или автоматического трассирования.
- Массовое производство каталога запрещено до одновременного технического и художественного PASS вертикального среза.

## 11. Минимальный технический прототип

Прототип считается успешным только если в реальном приложении работают:

- одна каноническая bust-модель;
- три заметно разных, но корректных face presets через morph targets;
- две причёски;
- одна базовая одежда;
- один составной капюшон, корректно скрывающий нужные зоны волос;
- три оттенка кожи и три цвета волос через материалы;
- камеры `Портрет` и `По пояс`;
- мгновенный выбор без постоянной анимации персонажа;
- заранее прогретый первый preview без loading state;
- локальный portrait snapshot;
- повторное открытие из сохранённого DNA;
- сохранение legacy avatar при любой ошибке 3D.

### Gate P0

PASS требует:

- запуск на iOS и Android;
- отсутствие непрерывного frame loop после стабилизации;
- отсутствие spinner, network request или заметного зависания при смене одного параметра;
- корректные лицо, волосы и капюшон во всех комбинациях прототипа;
- snapshot отображается через обычный React Native image;
- десять циклов открыть/закрыть не приводят к устойчивому росту памяти или crash;
- размер и производительность признаны приемлемыми до расширения каталога.

### Gate Art P0

Art PASS является отдельным обязательным gate и не выводится из зелёных технических тестов. PASS требует двух реальных кадров из приложения — мужского и женского — которые владелец явно принимает относительно reference portraits.

Автоматический FAIL наступает при любом из признаков:

- Memoji/chibi/low-poly/игрушечная или карикатурная стилизация;
- нос, рот, уши, волосы или одежда читаются как геометрические примитивы;
- глаза выглядят наклеенными, не имеют корректных век/глазниц или выходят из лица;
- кожа выглядит как однотонный пластик, волосы — как шлем или набор шаров;
- мужской и женский персонажи не принадлежат одному визуальному семейству;
- качество заметно ниже owner-reference даже при технически корректном GLB.

Текущий code-generated `human_v2_base.glb` из сфер/капсул имеет статус `technical_fixture`, автоматически получает Art FAIL и не может стать production fallback.

Технический FAIL означает остановку массового 3D-asset production и выбор между оптимизацией текущего runtime и другим локальным 3D runtime. Art FAIL означает продолжение ограниченной итерации `phraseman_style_v1` без подключения нового renderer к production surfaces. Ни один FAIL не исправляется переходом к 2.5D или возвратом к независимым PNG-частям.

## 12. Фазы после PASS

1. **P0 — технический spike:** React Native GL, один GLB, морфы, меши, snapshot.
2. **P1 — runtime foundation:** versioned contracts, resolver, storage, lifecycle и fallback.
3. **P2 — полноценная Studio UI:** категории, каталог, undo/redo, accessibility, локализации.
4. **P3 — production starter pack:** расширение морфов и совместимых 3D-предметов с visual QA.
5. **P4 — сохранение и consumers:** local portrait во всех существующих avatar surfaces.
6. **P5 — владение и награды:** immutable catalog, exact grants, no duplicates, economy constitution.
7. **P6 — sync и rollout:** privacy-safe telemetry, recovery, cross-device и постепенный flag rollout.

Прежний 14-task план нельзя исполнять буквально после этого решения: его 2D layer renderer, растровый asset factory и trusted cloud compositor должны быть заменены новым планом реализации утверждённой спецификации.

## 13. Отклонённые пути

- Независимые DALL·E PNG-части — уже доказанно не дают цельного персонажа.
- Генерация готового изображения для каждой комбинации — комбинаторный взрыв и отсутствие настоящего офлайна.
- Серверный финальный render как основной путь — нарушает подтверждённый offline contract.
- Rive 2D/2.5D — не достигает утверждённого 3D-референса и не является production fallback даже после P0 FAIL.
- Постоянная 3D-анимация — не нужна продукту и ухудшает энергопотребление/стабильность.
- Найм 3D-художника — явно исключён владельцем для этого маршрута.
- Покупка готовой модели — явно исключена владельцем; кроме стоимости она не гарантирует единую топологию, права на avatar maker и соответствие стилю.
- Blender как обязательный authoring source — исключён владельцем. Pipeline должен быть воспроизводим из данных и кода без `.blend`.
- VRoid — не соответствует semi-realistic референсу и имеет ограничения на использование его контента в собственных character-creator приложениях.
- AI image-to-3D как master topology — не даёт гарантированного порядка вершин, безопасно смешиваемых morph targets и воспроизводимого качества.
- Процедурная production-модель из сфер, капсул и примитивов — допустима только как technical fixture и всегда проваливает Art P0.

## 14. Утверждённое решение

Владелец утвердил `human_v2`: MakeHuman CC0 topology/targets как dev-time основа, собственный Phraseman authoring/conversion pipeline без Blender, локальный 3D render-on-change в Студии, статичный snapshot во всём остальном приложении и два независимых обязательных gate — Technical P0 и Art P0 — до производства полного каталога.
