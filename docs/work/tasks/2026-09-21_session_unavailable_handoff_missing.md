# «Сессия недоступна / learning_v2_session_ready_handoff_missing» вернулась

Дата: 2026-09-21. Владелец: «ВОТ ТАКОГО НЕ ДОЛЖНО БЫТЬ… УДАЛЯЛ ЖЕ».

## Что показывает экран

`learning_v2_session_ready_handoff_missing` — это НЕ «нет сети» и НЕ «нет
релиза». Это отказ **моста карта → сессия**.

## Как устроен мост

Экран занятия (`app/learning_v2_direct_session_player_v1.tsx`) **сам сессию не
грузит**. Он рассчитывает, что карта заранее всё подготовила и положила
готовый результат в память процесса:

- карта кладёт: `stageLearningV2CourseSessionReadyHandoffV3(handle)`
  (`app/learning_v2_course_released_session_client_v3.ts:1397`), ключ — `sessionRunId`;
- экран забирает: `consumeLearningV2CourseSessionReadyHandoffV3({courseSessionId, sessionRunId})`
  (`app/learning_v2_direct_session_player_v1.tsx:384`).

Не нашёл по ключу → `setLoadFailed(true)` + этот код (строка ~858). Никакого
запасного пути нет **намеренно**: «Production sessions enter only with the map's
fully prepared handoff».

Мост односторонний и одноразовый: `consume` **удаляет** запись, а карта хранит
максимум 8 записей.

## Две точки входа на экран

1. `app/learning-v2/lesson/[id].tsx:1060` — кладёт handoff ВСЕГДА;
2. `app/(tabs)/lessons.tsx:3197` — кладёт **только `if (ready.handle)`**.

В (2) `handle` может быть `null` намеренно — при дев-разблокировке
(`lessons.tsx:2763`). Эта ветка согласована: `learningV2DevUnlockAllActive`
сам под `__DEV__`, и экран принимает `previewMode` тоже под `__DEV__`.
**Проверено — это ложный след, чинить там нечего.**

## Что сделано в этот заход (по правилу «сперва логи»)

Гадать запрещено, поэтому правок логики НЕТ. Поставлена трассировка на ОБА
конца моста, единый префикс `[V2-HANDOFF]`:

- `[V2-HANDOFF] stage` (клиент, при укладке) — под каким `sessionRunId` карта
  положила готовое и какие ключи лежат в мосту;
- `[V2-HANDOFF] consume` (экран, при заборе) — какой `sessionRunId` пришёл
  маршрутом, спрашивали ли мост вообще, что получили и какие ключи были в мосту
  в этот момент; плюс `runtimeMode/previewMode/previewOrigin/runKind/урок/сессия`.

Провал моста дополнительно уходит в `DebugLogger` (переживает перезапуск) —
владелец ловит это на телефоне, а не в бандлере.

Добавлена `peekLearningV2CourseSessionReadyHandoffKeysV3()` — только чтение
ключей, ничего не потребляет.

## Что покажут логи (как читать)

Один grep по `[V2-HANDOFF]`:

- **есть `consume`, но НЕТ `stage`** → карта не готовила сессию (путь запуска
  прошёл мимо подготовки);
- **`stage` и `consume` есть, но `sessionRunId` РАЗНЫЕ** → ключи разошлись:
  маршрут ушёл с одним id, а мост заполнен другим;
- **`askedBridge: false`** → маршрут пришёл вообще без `sessionRunId`/`id`
  (мост даже не спрашивали);
- **`stagedKeys` пустой при живом `stage`** → запись вытеснена лимитом в 8 или
  съедена чужим `consume`.

## Побочная находка: сторож УЖЕ был красный

`tests/learning_v2_direct_intro_gate_contract.test.ts` падает и на чистом HEAD,
**до** любых моих правок. Его регулярка требует, чтобы от
`Promise.all([prepared, modalExit])` до `sessionRunId: ready.sessionRunId` было
не больше 1800 символов; сейчас там 2133 — код между ними разросся.

То есть контракт моста **перестал охраняться раньше**, и возврат бага мог
пройти незамеченным. Чинить надо сторожа (сделать проверку не зависящей от
расстояния в символах), а не растягивать лимит.

Отдельно: `npx jest` по этому файлу убивается SIGTERM по памяти; проверка
прогоняется `npx tsx tests/...` — она чисто текстовая.

## ПРОВЕРЕНО НА ЭМУЛЯТОРЕ 2026-09-22

Владелец: «у тебя есть эмулятор — вот и проверяй всё». Прошёл путь сам:
Pixel_8 + Metro 8081, вход Уроки → **Новые уроки** → карта Learning V2 →
«Глава 1, Сессия 1» → «Начать».

**Мост исправен. Цепочка сходится:**

```
[V2-HANDOFF] stage   {"sessionRunId":"0dd94632…","stagedKeys":["0dd94632…"]}
[V2-HANDOFF] consume {"routedSessionRunId":"0dd94632…","askedBridge":true,"got":true}
```

Ключи совпали, `got: true`. Занятие открылось полностью (интро «Смысл»,
объяснение, вопрос с вариантами, сердечки, «Дальше»). Повторный вход после
выхода крестиком — тоже `got: true`. Экрана «Сессия недоступна» не возникло
ни разу.

### Но по дороге нашёлся НАСТОЯЩИЙ баг — занятия не запускались вообще

Тап по «Начать» не открывал ничего. Причина из logcat:

```
recoverEnergySessionOperations is not a function (it is undefined)
[ENERGY-START] отказ: энергия не прочиталась — экран покажет «отменено»
```

Функция в `app/energy_session_operation_ledger.ts:1149` объявлена **без
`export`**, хотя `components/EnergyContext.tsx:43` её импортирует. Любое
занятие со стоимостью энергии не стартовало. Починено (коммит `854ff8e6f`),
проверено вживую: после правки занятие идёт.

### Почему это не поймали раньше — важнее самого бага

`tsc` эту ошибку **видит**: `TS2724: has no exported member named
'recoverEnergySessionOperations'`. Но полная проверка **падала по памяти на
4 ГБ** (`FATAL ERROR: JavaScript heap out of memory`), и `grep` по пустому
выводу выглядел как «ошибок нет». Я сам в этот капкан попал в прошлом заходе
и написал «типы чистые».

**Правило: проверку типов гонять только с `NODE_OPTIONS=--max-old-space-size=8192`
и смотреть КОД ВОЗВРАТА, а не пустоту вывода.** С 8 ГБ печатается 238 ошибок
(остальные — чужие незакоммиченные правки других сессий).

### Вывод по исходной задаче

Экран `learning_v2_session_ready_handoff_missing` на текущем коде
**воспроизвести не удалось** — мост работает. Скорее всего владелец снимал его
до одной из вчерашних починок (был и второй источник той же надписи — последний
кадр при выходе). Диагностика `[V2-HANDOFF]` оставлена: если экран вернётся,
причина будет видна одним grep, без повторного расследования.

Осталось незакрытым: сторож `learning_v2_direct_intro_gate_contract` по-прежнему
красный (лимит 1800 против факта 2133) — класс бага не охраняется.
