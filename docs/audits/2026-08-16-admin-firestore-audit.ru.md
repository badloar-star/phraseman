## 0. Что уже автоматизировано

Всего в проекте **345 правил коллекций**. То есть примерно каждая седьмая охраняет данные, которые никто не пишет и не читает.

**Что это стоит.** Хранение в Firestore дешёвое, но данные там лежат годами. Точную цифру без консоли не сказать — но это тот случай, когда неизвестный расход тянется бесконечно.

**Что делать.** Не удалять сразу: сначала подтвердить нулевую активность запросом в проде. Правила снести, коллекции оставить закрытыми — как уже сделано для агентов.

## 2. Числа, которые никуда не ведут

Дашборд, на который посмотрели и закрыли, — это несделанный алерт.

### Серийные возвращатели — детектор есть, сигнала нет

`admin/v2/legacy.html:24328` — код уже помечает покупателей с двумя и более возвратами, в интерфейсе есть фильтр «только серийные».

Алерт `cancelRefundSpike` существует, но проверял лично: он ловит **всплеск за час**, а серийный возвращатель — это один человек с двумя возвратами за месяцы. Разные вещи.

Механизм алертов готов, нужен ещё один тип. **~2-3 часа.**

### Жалобы «непонятно объяснили»

Комментарий в самой админке признаёт: «жалоба сама не отключает кэш: админ вручную жмёт „Убрать из кэша“». Три и более жалобы на одну фразу — достаточный сигнал, чтобы убрать её автоматически и уведомить. **~4-6 часов.**

### Остальное без действия

Воронка онбординга (в коде помечена «данные не меняются»), статистика вариантов оплатного экрана без алерта на провал варианта, реферальная панель только с выгрузкой в файл.

## 3. Ручная работа, которая повторяется

| Что | Как часто | Можно ли |
|---|---|---|
| Одобрение пользовательских наборов карточек | Часто | AI-черновик решения — по образцу того, что **уже работает** для идей пользователей |
| Весь недельный цикл турниров: генерация → ревью → публикация → расписание | Еженедельно | Автопубликация при прохождении проверок качества, ручное вмешательство только по флагам |
| Разбор жалоб пользователь-на-пользователя | Часто | Частично — приоритизация и черновик |
| Выдача премиума вручную при сбое | Реже | Уже есть автопуть, ручной остаётся резервом |

Самое дорогое здесь — **турниры**: полный операционный цикл каждую неделю, где генерация уже автоматизирована, а всё остальное руками.

## 4. Что говорит индустрия про «агента, который знает бизнес»

Ресерч дал одну идею, которая заметно сильнее остальных.

### Дерево метрик

Сейчас департамент может сказать «выручка упала». С деревом он скажет, **в какой ветке**: выручка = активации × конверсия × средний чек; активации = новые + вернувшиеся.

Индустриальный стандарт для вопроса «почему упало» — не модель, гадающая по цифрам, а связка: детерминированный расчёт раскладывает метрику по составляющим, а модель только объясняет результат человеческим языком.

Прямая цитата из практики: *«AI never calculates your KPIs — core metrics run on governed SQL»*. Источники: [Metric tree — Mixpanel](https://mixpanel.com/blog/metric-tree/), [Tellius](https://www.tellius.com/resources/blog/ai-powered-root-cause-analysis-from-what-happened-to-why-in-60-seconds) — ПОДТВЕРЖДЕНО.

**Оценка: 4-6 часов.** Не нужен новый сервис — достаточно описать в коде, из чего состоит каждая метрика.

### Процедуры расследования

Внутренний инструмент Meta работает не так, что модель свободно бродит по данным, а по записанным процедурам: «проверить журнал → проверить деплои за N часов → сверить схему событий». В их примере агент проследил падение метрики до конкретного деплоя, изменившего схему.

Для двух-трёх частых типов инцидентов расписать такую процедуру. **~6-8 часов.**

### Знание о бизнесе как папка текстовых файлов

Не база данных и не граф, а `knowledge/*.md` в формате «заголовок → что сейчас верно → детали → история изменений». Департаменты читают выборочно по теме.

Это ровно тот приём, который у вас **уже работает** для контент-конвейеров и памяти между сессиями. Осталось применить к знанию о продукте. **~4-5 часов.**

### Урок, который стоит запомнить

Основатель Base44 (продукт продан за $80M) выключил своего бота поддержки **через две недели**: понял, что жалобы должен читать сам, иначе теряет связь с реальными проблемами продукта.

Вывод для Джарвиса: автономность должна быть **разной по департаментам**. Поддержка — докладывает. Платежи и безопасность — наоборот, им ежедневного крона может быть мало, там нужен событийный триггер.

## 7. Чего делать не надо

- **Не автоматизировать разбор поддержки полностью.** Урок Base44 плюс данные: доверие к AI в сложных запросах — 13.6%, предпочтение живого человека выросло до 85%. Ваша схема с черновиками и кнопкой — уже правильная.
- **Не строить граф знаний и семантический слой.** Для вашего масштаба это избыточно; текстовые файлы дают то же самое и читаются человеком.
- **Не удалять мёртвые коллекции без проверки в проде.** Правила снести можно, данные — только после подтверждения.
