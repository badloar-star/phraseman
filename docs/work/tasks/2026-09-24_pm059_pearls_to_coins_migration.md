## Outcome

У каждого аккаунта (включая скрытые/дополнительные) весь текущий баланс жемчуга молча,
без окон, через ~18 с после старта или активации аккаунта превращается в монеты
(= руны до PM-069) по курсу 1 жемчуг = 10 монет. После миграции баланс жемчуга = 0,
в журнале аккаунта лежит юридический след (сумма, курс, когда, id операций).
Успех: повтор, офлайн, смена аккаунта, два устройства и параллельная миграция подарков
не дают ни двойной выплаты, ни потери жемчуга без монет.

## Scope

In scope:

- `app/shards_system.ts` — новый экспорт `commitShardBalanceMigrationDebit` (списание через неизменяемый журнал жемчуга с квитанцией);
- `app/remote_flags.ts` — выключатель `pearls_to_coins_enabled` (дефолт true);
- `app/cloud_sync.ts` — префиксы WAL и квитанции в account-local;
- `app/_layout.tsx` — ленивый запуск планировщика рядом с миграцией подарков;
- серверная строка-итог `functions/src/pearls_to_coins_report.ts`, экспорт в `functions/src/index.ts`, правило `firestore.rules` — БЕЗ деплоя;
- `tests/pearls_to_coins_migration.test.ts`.

Out of scope: удаление хранилища/экрана жемчуга (PM-060), компенсация бустов (D58), PM-069 (руны → монеты),
админ-панель для строки-итога, деплой functions/rules.

## Architecture

Текущее: жемчуг живёт в клиентском неизменяемом журнале (`client_shard_operation_ledger`), проекция `shards_balance`.
Монеты = рунный кошелёк (`level_spin_star_grants`, outbox + дедуп по requestId).

Поток: снимок баланса B и якоря журнала (ревизия + id головы) под замками → план в WAL (B, монеты = B×10,
номиналы stars_*, детерминированные ключи от owner+якорь+B) → списание РОВНО B одной операцией журнала жемчуга
(квитанция пишется до корня операции) → зачисление номиналов в кошелёк, прогресс после каждой операции →
done + история → строка-итог на сервер.

Инварианты: списание раньше зачисления (жемчуг живой и тратится; обратный порядок дал бы двойную выплату при
«не хватает»); списанное всегда доезжает монетами (план заморожен, флаг не останавливает после списания);
никогда не списывается больше, чем оплачено; «не хватает» = ничего не списано → перепланирование.

## Security and privacy

Нового сбора данных нет: строка-итог содержит только внутренний id аккаунта, числа и время (как у gifts_to_coins).
Сервер проверяет вход (resolveStableUidForAuth), пишет только callable, коллекция закрыта правилом (чтение — админ).
App Check не включается (пломба). Privacy policy не затронута: жемчуг и монеты уже внутриигровые валюты.

## Technical debt

- Accept temporarily: два устройства с РАЗНЫМ состоянием журнала жемчуга, мигрирующие до синхронизации, получат
  разные ключи → двойные монеты (жемчуг уйдёт в долг при слиянии). Владелец: программа 2.0; пересмотр при PM-069;
  потолок — сумма одного баланса на аккаунт, случаи видны по двум строкам истории/отчётам.
- Contain: баланс > 200 000 жемчуга (>1000 операций) не мигрирует автоматически, лог `too_large` → поддержка.
- Accept temporarily: серверная функция отчёта не задеплоена — до деплоя отчёты копятся (до 20 попыток) и сдаются.

## Rollback

Выключатель `pearls_to_coins_enabled=false` в remote_config останавливает НОВЫЕ планы; уже списанное
доезжает монетами (иначе потеря денег). Код можно откатить, данные не теряются: WAL и квитанции остаются,
монеты уже в рунном журнале. Необратимость списания закрыта прямым восстановлением: план в WAL и квитанции.
