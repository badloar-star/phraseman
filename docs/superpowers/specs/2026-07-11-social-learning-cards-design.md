# Phraseman Social Learning Cards — дизайн системы

Дата: 2026-07-11
Статус: согласовано в диалоге, ожидает просмотра записанной спецификации

## 1. Цель

Создать постоянную систему двухслайдовых учебных каруселей для русскоязычной аудитории Phraseman в Instagram, TikTok, Facebook и YouTube.

Каждая публикация должна за 30 секунд ответить на вопрос «почему мне стоит установить Phraseman сейчас» и вести пользователя на официальный сайт `https://knowlyapps.com/`.

Главное позиционирование: Phraseman учит не изолированным словам, а живым английским фразам в контексте, помогает тренировать произношение и превращает практику в короткую ежедневную систему прогресса.

## 2. Аудитория и голос

- Основной уровень: A1–A2.
- Основной возраст: 20–50 лет.
- Язык коммуникации: русский; учебный материал — английский с выбранными русскими пояснениями.
- Тон: дружелюбный, простой и взрослый. Для ошибок и мифов допустима умеренная дерзость без унижения ученика.
- Контент не должен выглядеть как детское приложение или сухой учебник.

## 3. Архитектура

Система объединяет два слоя.

### 3.1. Производственное ядро `social-learning-cards`

Отдельный модуль отвечает за:

1. редакционный manifest;
2. DALL-E-промпты;
3. импорт и разрезание AI-атласов;
4. программную типографику;
5. сборку двух слайдов;
6. создание платформенных подписей и UTM-ссылок;
7. визуальные и структурные проверки;
8. экспорт готового пакета.

Модуль переиспользует существующие механизмы идентификаторов кампаний, UTM, Publer и проверок, но не меняет поведение старого `viral-carousel-engine`.

### 3.2. Административная оболочка

Отдельный раздел админки управляет очередью, статусами, импортом готовых manifest-файлов, связью с опубликованными постами и аналитикой. Перед изменением `admin/index.html` реализация обязана следовать `docs/design/ADMIN_UI_BIBLE.md`.

Админка не вызывает OpenAI API и не получает OpenAI-ключи.

## 4. Контракт публикации

Каждая публикация состоит ровно из двух квадратных JPG-файлов 1080×1080.

### 4.1. Слайд 1 — самостоятельная учебная ценность

- крупный английский заголовок;
- небольшое русское пояснение темы;
- сетка 3×3 для девяти коротких элементов или 2×3 для шести длинных фраз;
- белый или очень светлый фон;
- единый художественный стиль внутри карточки;
- одна однозначная иллюстрация на один учебный элемент;
- отсутствие логотипа, рекламы и CTA Phraseman;
- текст накладывается кодом, а не генерируется внутри изображения.

В пилоте разведочно используются две типографические гипотезы:

- четыре карточки содержат только английские подписи;
- три карточки содержат английские подписи и небольшой русский перевод.

Из-за одновременного различия рубрик и визуальных стилей этот пилот не доказывает причинное влияние языка подписей. Он только выбирает кандидата для отдельного парного A/B-теста. Причинный тест должен использовать две версии одной темы при одинаковых стиле, рубрике, времени и поверхности публикации.

### 4.2. Слайд 2 — мост к установке

- верхняя часть продолжает визуальный язык первого слайда;
- нижняя часть показывает реальный экран Phraseman, связанный с темой;
- контекстная польза меняется для каждой публикации;
- постоянный CTA:

> Установи Phraseman бесплатно
>
> Первый урок — через 30 секунд
>
> Ссылка в профиле

- пакет содержит ссылку вида `https://knowlyapps.com/?utm_source=<platform>&utm_medium=<surface>&utm_campaign=slc_pilot_01&utm_content=<content_id>`.

## 5. Пилот из семи публикаций

Пилот проверяет семь рубрик:

1. тематическая лексика;
2. готовые фразы для ситуации;
3. фразовые глаголы;
4. типичные ошибки русскоязычных;
5. похожие слова и различия;
6. простая мини-грамматика;
7. произношение или естественные замены учебниковых выражений.

Темы ранжируются по трём источникам:

- статистика собственных социальных аккаунтов;
- актуальные открытые тренды;
- визуальная выразительность и примеры, утверждённые владельцем продукта.

Процесс согласования:

1. утвердить семь тем и тексты;
2. произвести одну полную тестовую карусель;
3. после её визуального одобрения произвести остальные шесть.

## 6. DALL-E-процесс

Изображения создаются только встроенным генератором DALL-E в Codex. Проектный OpenAI API, `OPENAI_API_KEY` и любые локальные вызовы image API запрещены.

Для одной публикации:

1. формируется точное задание на 6 или 9 ячеек;
2. DALL-E создаёт единый атлас 2×3 или 3×3 без текста;
3. атлас сохраняется в файловый пакет и разрезается кодом;
4. каждая ячейка проверяется отдельно;
5. только слабые ячейки перегенерируются индивидуально;
6. типографика, заголовок и переводы добавляются программно;
7. финал проверяется при мобильном размере отображения.

Сначала производится только одна тестовая карусель. После её утверждения оставшиеся шесть создаются строго по одной: каждый DALL-E-результат немедленно экспортируется в игнорируемый файловый каталог, сверяется с checkpoint и только затем начинается следующая карточка. Большая серия в одном Codex-сеансе запрещена. При росте контекста работа продолжается в новом или скомпактированном сеансе после проверки сохранённых файлов. Исходники, атласы и промежуточные кропы не помещаются в `assets/images/**` и не входят в bundle приложения.

Внутри одной карточки персонаж и стиль постоянны. Для эмоций, действий и состояний допустим один повторяющийся герой. Для животных, еды и предметов используются прямые предметные иллюстрации.

Семь пилотных визуальных направлений: editorial illustration, мягкий 3D, реалистичная предметная иллюстрация, взрослый комикс, акварель, cinematic lifestyle и ретро-постер. Запрещены копирование живых художников, защищённые персонажи и детская стилизация, снижающая взрослое восприятие продукта.

## 7. Пакет результата

Для каждого `content_id` конвейер сохраняет:

- `slide_01_learning.jpg`;
- `slide_02_install.jpg`;
- исходный DALL-E-атлас и заменённые ячейки;
- финальные промпты;
- `manifest.json`;
- четыре адаптированные подписи;
- alt-текст;
- UTM-ссылки;
- отчёт проверок.

Материалы сохраняются в файловых каталогах проекта и не передаются большими base64-пакетами в историю Codex.

## 8. Платформенные подписи

Смысловое ядро едино, окончания адаптируются:

- Instagram и TikTok: короткий вопрос/крючок и «ссылка в профиле»;
- Facebook: активная UTM-ссылка в первом абзаце;
- YouTube: короткое описание и активная ссылка там, где формат её поддерживает.

Поверхности пилота: Instagram carousel post, TikTok Photo Mode, Facebook multi-photo post и YouTube Community image post. До экспорта проверяется фактическая поддержка двух квадратных изображений, сохранение порядка слайдов и доступность выбранной поверхности для подключённого аккаунта. Если YouTube Community image post недоступен или не поддерживает нужную последовательность, документированный fallback — один квадратный Community-пост с первым слайдом и CTA/ссылкой в тексте; он маркируется как отдельная поверхность и не сравнивается напрямую с двухслайдовыми каруселями.

ManyChat не используется в пилоте. Главный путь всегда ведёт напрямую к установке.

Публикация выполняется вручную после визуальной проверки. Первая версия конвейера не отправляет посты автоматически.

## 9. Админский рабочий процесс

Статусы карточки:

`Идея → Текст готов → Ждёт DALL-E → Изображения готовы → Проверка → Готово к публикации → Опубликовано → Собирает данные → Оценено`

Для карточки хранятся:

- `content_id`;
- `revision` и аудит изменений;
- тема, рубрика и уровень;
- учебные элементы;
- визуальный стиль;
- пути к файлам;
- подписи и UTM;
- идентификаторы или URL публикаций для каждой платформы;
- доступные метрики Publer;
- переходы на сайт;
- итоговые оценки.

Разделы админки:

1. очередь;
2. карточка публикации с двумя превью;
3. импорт пакета;
4. привязка публикаций;
5. результаты;
6. победители.

## 10. Publer и аналитика

Publer используется для получения доступных метрик отдельных постов, включая охват, реакции, комментарии, репосты, клики и другие показатели, которые возвращает конкретная социальная сеть.

Секрет Publer хранится в Firebase Secret Manager или существующем эквивалентном серверном хранилище секретов. Он не должен попадать в клиентский bundle, manifest, логи, отчёты или сообщения об ошибках. Серверная функция требует аутентификацию и проверяет административную роль до любого запроса. Она валидирует post ID/URL и разрешает только заранее настроенные социальные аккаунты, применяет таймауты, ограничение частоты запросов и возвращает клиенту безопасные сообщения без сырого ответа провайдера.

До реализации проверяется доступность Publer API на текущем тарифе. Если API недоступен, импорт статистики должен поддерживать безопасный ручной CSV/XLSX-файл без блокировки остального конвейера. Импорт принимает не более 5 MB и 10 000 строк, только фиксированную схему столбцов, расширения `.csv`/`.xlsx` и соответствующие MIME-типы, запрещает XLSM и макросы, нейтрализует формулы, не принимает произвольные файловые пути и сначала работает в preview/dry-run. Применение данных требует отдельного подтверждения администратора.

Победители определяются по двум независимым оценкам:

- учебная ценность: сохранения и репосты относительно охвата;
- коммерческая ценность: переходы на корневую страницу официального сайта, для которых будет расширен текущий контракт `siteStatsTrack` и клиентского beacon, чтобы передавать нормализованные `utm_source`, `utm_medium`, `utm_campaign` и `utm_content`.

Текущие `site_stats/daily_*` и `site_stats/totals` продолжают хранить только общие счётчики. UTM-разбивка не добавляется динамическими полями в эти документы. Для неё вводится отдельная ограниченная агрегация `site_stats_content_daily/{date}_{tupleHash}` с полями `date`, `source`, `medium`, `campaign`, `contentId`, разрешёнными счётчиками событий и `updatedAt`. `tupleHash` детерминированно строится на сервере из нормализованной комбинации, поэтому клиент не управляет путём документа.

Сервер принимает только разрешённые типы событий из существующего `EVENT_FIELDS`. UTM нормализуются в нижний регистр, ограничиваются 64 символами и форматом `[a-z0-9_-]+`. `source` и `medium` дополнительно проверяются по allowlist поддерживаемых платформ и поверхностей; неизвестные, пустые или слишком длинные значения отбрасываются из UTM-разбивки, но не ломают общий счётчик события. В UTM-агрегацию разрешены только идентификаторы кампании и контента — персональные данные, пользовательский текст, email, UID, IP и параметры устройства не сохраняются.

Форматная проверка дополняется серверным реестром известных кампаний и опубликованных карточек. Пара `campaign + contentId` создаёт или обновляет content-агрегат только если она существует в реестре, имеет опубликованную активную ревизию и разрешает указанную платформу/поверхность. Неизвестная пара обновляет только прежние totals/daily и никогда не создаёт `site_stats_content_daily`. Реестр может безопасно кэшироваться с ограниченным TTL, но серверное хранилище остаётся источником истины; клиент не может зарегистрировать или активировать пару через beacon.

Старые beacon-события без UTM остаются полностью совместимыми и обновляют прежние totals/daily-счётчики. Новая ветка использует существующее ограничение частоты запросов и не должна ослаблять его. Focused-тесты покрывают: нормализацию, неизвестные и слишком длинные значения, отсутствие UTM, разрешённые типы событий, корректное разделение totals и content-агрегации, детерминированный ключ и rate limiting. Отдельные тесты подтверждают, что известная опубликованная пара создаёт/обновляет агрегат, неизвестная пара не создаёт документ, а перебор множества валидных случайных ID не увеличивает число content-документов.

Карточная атрибуция по `utm_content=<content_id>` считается точной только на поверхностях с уникальной кликабельной ссылкой конкретного поста. В Instagram и TikTok общая ссылка в профиле не позволяет честно связать клик с одной карточкой: там админка показывает метрики конкретного поста из Publer, а переходы и установки — агрегатно по кампании и явно указанному временному окну после публикации. Эти значения маркируются как корреляция, а не атрибуция. Полная Android/iOS-атрибуция проектируется отдельным вторым улучшением после пилота.

## 11. Проверки и отказоустойчивость

Конвейер должен останавливать экспорт, если:

- количество элементов не равно 6 или 9;
- английские элементы или переводы дублируются;
- подпись не помещается без чрезмерного уменьшения;
- изображение отсутствует или имеет неверный размер;
- DALL-E-ячейка содержит читаемый случайный текст;
- иллюстрация неоднозначна или не соответствует значению;
- второй слайд не содержит тематического экрана, CTA или content_id/UTM в manifest;
- файлы платформенного пакета неполны.

Автоматические нормы финального файла:

- ровно 1080×1080 пикселей;
- JPEG в sRGB/RGB, без альфа-канала;
- safe area не менее 48 пикселей от каждого края;
- заголовок не меньше 56 px, английская подпись не меньше 34 px, русский перевод не меньше 24 px;
- заголовок — не более двух строк, подпись элемента — не более двух строк на каждом языке;
- контраст текста и фона не ниже WCAG AA 4.5:1;
- целевой размер одного JPG — не более 1.5 MB без заметных артефактов.

После автоматических проверок обязательна ручная визуальная проверка в масштабе мобильного экрана. Чек-лист: однозначность смысла каждой ячейки, отсутствие случайного текста и анатомических/предметных дефектов, отсутствие обрезки, корректность английского и русского, использование реального актуального экрана Phraseman, читаемый CTA и правильный порядок двух слайдов. Экспорт и статус `Готово к публикации` запрещены, пока не пройдены автоматическая и ручная проверки.

Ошибки сохраняются в отчёте проверки. Исходники не удаляются. Каждый `content_id` имеет неизменяемые ревизии (`revision=1,2,...`) и аудит изменений. Повторный запуск в пределах черновой ревизии идемпотентно обновляет её артефакты, не создавая дублей. Ревизии со статусом `Опубликовано`, `Собирает данные` или `Оценено` не перезаписываются: изменение создаёт новую ревизию, сохраняя старые файлы, связи с постами и статистику.

## 12. Этапы реализации

### Этап 1 — производственное ядро и пилот

- схема manifest;
- очередь семи тем;
- шаблоны 6 и 9 элементов;
- DALL-E handoff;
- сборка двух слайдов;
- проверки;
- платформенные подписи и UTM;
- одна тестовая публикация, затем остальные шесть.

### Этап 2 — административная оболочка и аналитика

- очередь и карточка публикации;
- импорт manifest;
- привязка опубликованных постов;
- защищённая интеграция Publer или ручной импорт;
- точные переходы сайта по `utm_content=<content_id>` только для постов с уникальной кликабельной ссылкой; для Instagram/TikTok — агрегаты кампании во временном окне с явной пометкой «корреляция»;
- таблица результатов и победителей.

## 13. Критерии приёмки

- Создан отдельный конвейер, не изменяющий существующие форматы.
- Пилот содержит семь уникальных двухслайдовых квадратных каруселей.
- Все учебные изображения созданы встроенным DALL-E в Codex без OpenAI API.
- Каждый первый слайд читаем на телефоне и не содержит рекламы.
- Каждый второй слайд показывает тематический экран Phraseman и утверждённый CTA.
- Каждый пакет содержит четыре подписи, UTM и полный manifest.
- Все структурные и визуальные проверки проходят.
- Финалы соответствуют файловым, типографическим, safe-area и контрастным нормам; ручной чек-лист подписан до статуса `Готово к публикации`.
- Пакет проверен на Instagram carousel, TikTok Photo Mode, Facebook multi-photo и YouTube Community либо использует документированный YouTube fallback.
- Админка импортирует пакет, показывает статус и связывает карточку с доступной аналитикой.
- Publer-функция проверяет аутентификацию, административную роль, allowlist аккаунтов и не раскрывает секреты; ручной импорт проходит preview/dry-run и проверки файла.
- Тестовый переход с `utm_content=<content_id>` увеличивает общий счётчик и правильную запись `site_stats_content_daily`, после чего эта агрегированная запись доступна админке; событие без UTM продолжает работать без создания content-записи.
- Только зарегистрированная опубликованная пара `campaign + contentId` создаёт content-агрегат; неизвестные и перебираемые валидные ID не увеличивают число документов.
- Публикация остаётся ручной.
- Существующие функции приложения, админки и старого карусельного движка не удаляются и не отключаются.

## 14. Вне первой версии

- автоматическая публикация;
- ManyChat;
- вызов DALL-E или OpenAI API из админки;
- массовое производство до оценки пилота;
- точная кроссплатформенная атрибуция установок;
- автоматическое добавление новых учебных материалов в приложение.
