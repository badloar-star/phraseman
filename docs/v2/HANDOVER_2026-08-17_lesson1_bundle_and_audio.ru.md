## 3. Что было исправлено за эту сессию — по порядку, с причиной и коммитом

Все коммиты на ветке `feature/referral-roulette`, автор `Claude

только ПОСЛЕ того, как предыдущий убрал маскирующую его ошибку — это была
цепочка, не список независимых проблем.

### 3.1 App Check блокировал ЛЮБОЙ вызов чтения курса

Обе читающие функции (`learningV2CourseActiveCatalogGetV1`,
`learningV2CourseReleasedSessionGetV3`) требовали токен App Check, которого
нет в дев-сборке (`app/app_check_init.ts` не активирует debug-провайдер без
переменной окружения). Ответ — 401, экран показывал «Сессия недоступна» /
«NOT FOUND».

**Решение владельца — App Check запломбирован НАВСЕГДА во всём проекте**, не
только для Learning V2. Коммит `a36ad0450`. Пломба:
`functions/src/callable_options.ts` (маркер
`APP_CHECK_SEALED_BY_OWNER_2026_08_17`), все флаги захардкожены в `false`,
переменные окружения `ENFORCE_APP_CHECK*` больше не читаются. Сторож:
`functions/src/app_check_sealed.test.ts` — ломает сборку при попытке вернуть
энфорс. **Полный запрет теперь и в CLAUDE.md**, раздел «⛔ APP CHECK
ЗАПЛОМБИРОВАН НАВСЕГДА». НЕ ПРЕДЛАГАЙ включить App Check ни для чего в этом
проекте. Если где-то найдёшь требование App Check — заводи отдельную сессию
на снятие, не трогай походя.

### 3.2 Пути пакетов сессий расходились между публикатором и индексом

Публикатор (`functions/src/content_factory/learning_v2_publish_authored_course_v1.ts`)
писал пакет сессии по пути `learning-v2/course-session-packages/<releaseId>/01.json`
(плоский, вручную составленный), а индекс релиза вычислял путь КАНОНИЧЕСКОЙ
функцией `learningV2CourseSessionPackageObjectPathV1` в
`modules/learning-v2/runtime/course_lesson_release_index_v1.ts:271` —
`sha256(releaseId)/lesson-01/sessions/01/<отпечаток>/<хеш>.json`. Файлы лежали
не там, где их искал индекс. Исправлено: публикатор теперь зовёт ТУ ЖЕ
функцию, что и индекс — разойтись физически не могут. Часть коммита `4dc57dec4`.

### 3.3 Тип содержимого без charset

Закрепление индекса релиза сверяет `contentType` файла и требует
`application/json; charset=utf-8`, а писатель хранилища
(`functions/src/content_factory/artifact_storage.ts:46`) по умолчанию
пишет `application/json` без charset. Четыре поля из пяти совпадали, пятое
рубило весь курс с `metadata_mismatch`. Исправлено передачей явного
`contentType` в вызове `writeImmutableObject`. Часть коммита `4dc57dec4`.

### 3.4 Пакет сессии собирался НЕВЕРНО — 5 ключей вместо 40

Самая серьёзная моя собственная ошибка. Мой же конвертер
(`modules/learning-v2/content/source/session_package_from_shard_v1.ts`)
клал пять детей (`intro`, `learner`, `evaluatorCapsule`, `evaluatorSidecar`,
`auxiliary`) ТЕЛАМИ прямо в пакет. Контракт
(`modules/learning-v2/runtime/course_session_release_package_v1.ts`) требует
обёртку из ~40 полей (`ROOT_KEYS`, строка 135), где каждый ребёнок — ССЫЛКА
на отдельный файл со своим хешем/размером/generation, а не тело. Чтение
падало с `learning_v2_course_session_release_package_invalid`. Исправлено:
публикатор теперь пишет пятерых детей ПО ОТДЕЛЬНОСТИ, собирает их
закрепления, строит обёртку каноническим строителем
`materializeLearningV2CourseSessionReleasePackageV1`. Часть коммита `4dc57dec4`.

### 3.5 packageFingerprint считался неверно (хеш файла ≠ хеш тела контракта)

`packageFingerprint` в контракте — это `hashCanonicalBody(тело без самого
поля packageFingerprint)`, а НЕ хеш всего записанного JSON-файла. Публикатор
подставлял хеш файла в оба места (путь объекта И поле в индексе), они
физически разные числа. Чтение падало на
`v2_course_released_session_package_join_mismatch`. Исправлено: отпечаток
теперь берётся ИЗ САМОГО собранного пакета (`packageBody.packageFingerprint`),
а не считается заново. Отдельный коммит (после `4dc57dec4`, до
`07dfb7e16` — точный хэш не зафиксирован в этом файле, смотри `git log -p`
на `learning_v2_publish_authored_course_v1.ts` около времени 14:00-14:20).

### 3.6 Капсула оценщика собиралась вручную — единственный ребёнок не через строитель

`evaluatorCapsule` в конвертере лепился вручную объектом `{schemaVersion,
courseSessionId, introAnswers, answers}` — единственный из пяти детей,
собиравшийся НЕ через `materialize...` функцию. Контракт
(`modules/learning-v2/runtime/course_session_evaluator_capsule_child_v1.ts`)
требует `entries`/`entryCount` и восемь полей полномочий, плюс
криптографические ОБЯЗАТЕЛЬСТВА (хеш+соль) вместо открытых ответов внутри
файла. Чтение падало с
`learning_v2_course_session_evaluator_capsule_child_invalid`. Исправлено
(коммит `07dfb7e16`), три под-дефекта нашлись по цепочке при исправлении:
  - `card.contentItem.targetText` не существует, нужно `acceptedAnswers`;
  - соль должна быть 64-значным хешем (`saltFor()`), не голым id;
  - интро-вопросы капсулы получали `family: 'listen_choose'`
    (→ `inputKind: 'choice_token'`), а `createLearningV2CourseSessionDeviceRunV1`
    (`modules/learning-v2/runtime/course_session_device_run_v1.ts:316`) ЖЁСТКО
    требует `inputKind: 'text'` для первых трёх записей капсулы — заменено на
    `family: 'phrase_builder'` с текстом правильного варианта.
  - `auxiliaryChild.entries` для интро-слотов использовал `card.cardId`
    (`card-episode-01-s01-01`), а остальные дети — `page.question.questionId`
    (`...:intro-q-1`) — РАЗНЫЕ строки для того же слота, из-за чего
    `sameOrder`-проверка в device_run падала. Исправлено: `auxiliary`
    переопределяет `interactionId` на `questionId` для первых трёх записей.

### 3.7 Число фраз в сессии — 12 не проходило контракт, поднято до 15

Контракт требует 14–18 заданий (`profile: standard`) в пакете. 12 фраз
(3 вопроса интро + 9 карточек практики) давали РОВНО 12 заданий. Владелец
выбрал поднять содержание до 15 (раздел 2, ключевые решения). Три агента
(при лимите «не более 3») дописали по 3 фразы в каждую из 10 сессий.
Коммиты: расширение фраз объединено с `4dc57dec4` и последующими правками
(см. раздел 9 — часть НЕ ЗАКОММИЧЕНА до сих пор).

Вместе с этим пришлось поднять:
  - `LEARNING_V2_SESSION_CARD_PURPOSES` с 12 до 15 записей в
    `modules/learning-v2/content/generator_session_shard.ts` (коммит `58c18c3e8`,
    туда же добавлены `retrieval_practice`, `near_transfer`,
    `independent_check` как продолжение кривой нагрузки);
  - `validateLearningV2GeneratedSessionShardV1` жёстко требовал
    `input.cards.length !== 12` — валидатор НИГДЕ не вызывается в цепочке
    публикации (проверено grep), поэтому раньше это молчаливое расхождение
    не всплывало, но это была дыра в контракте. Заменено на
    `LEARNING_V2_SESSION_CARD_PURPOSES.length`, коммит `58c18c3e8`.
  - в публикаторе `interactionIds` собирался только из карточек практики
    (9 штук), а контракт требует ТРИ ВОПРОСА ИНТРО ПЕРВЫМИ + карточки —
    добавлено `introInteractionIds` из тела `intro`-ребёнка перед
    остальными. Часть коммита `4dc57dec4` / последующих.

### 3.8 Урок 1 запускается из бандла — без единого сетевого запроса

Главная задача сессии. `modules/learning-v2/content/source/authored_sessions_v1.ts`
уже месяцами содержал 10 написанных сессий, но НИ ОДИН файл приложения их не
импортировал — проигрыватель `app/learning_v2_direct_session_player_v1.tsx`
всегда шёл через `loadCurrentLearningV2CourseReleasedSessionV3` →
облачная функция `learningV2CourseReleasedSessionGetV3` (композитный релиз с
отдельным аудио-слоем, которого нет — падал бы всегда).

Добавлена функция `bundledLearningV2CourseSessionMaterialV3` в
`app/learning_v2_course_released_session_client_v3.ts` (около строки 751) —
если для `lessonOrdinal===1` есть локальный шард с таким `sessionOrdinal`,
строит материал СИНХРОННО из `authoredLearningV2SessionShards()` +
`buildSessionChildBodiesFromShard`, без единого сетевого вызова. Подключена
ПЕРВОЙ СТРОКОЙ в `loadCurrentLearningV2CourseReleasedSessionV3` — сеть для
написанных сессий не трогается вовсе. Аудио-ребёнок собирается ПУСТЫМ
(`interactions: []`, строка ~779) — озвучки в бандле нет, и это осознанно
(раздел 8, аудио ещё не сгенерировано).

При сквозной проверке (`createLearningV2CourseSessionDeviceRunV1` — РЕАЛЬНАЯ
функция, запускающая сессию на устройстве, не изолированная проверка одного

## 8. Генерация аудио — исследовано, НЕ начато

Владелец подтвердил через AskUserQuestion:
  - **Полный контракт**: 4 голоса на каждое произносимое СЛОВО внутри каждой
    карточки, не только на целую фразу.
  - **Место хранения**: Firebase Storage (контракт `objectPath` этого прямо
    требует), НЕ бандл приложения.
  - Оплата подтверждена явно («да, запускай»), но САМА ГЕНЕРАЦИЯ НЕ
    ЗАПУЩЕНА — работа была прервана требованием сначала вывести весь контент
    и сделать макет для правок (раздел 0, п. 9-10 требований). **НЕ трать
    деньги на аудио, пока владелец не увидел и не одобрил финальный текст
    через макет** — правки текста ПОСЛЕ генерации означали бы генерировать
    заново, то есть тратить деньги дважды.

### Контракт аудио — точные факты, проверенные в коде

Голоса (ровно четыре, фиксированные ID):
`modules/learning-v2/contracts/voice_playback_policy_v1.ts:3-8`:
```ts
export const V2_REQUIRED_VOICE_IDS = Object.freeze(["ash", "onyx", "nova", "coral"] as const);
```
Политика воспроизведения (та же файл, строки 10-22): случайный перебор без
повтора одного голоса подряд (`local_shuffled_round_robin`,
`exhaustAllVoicesBeforeRepeat: true`), НЕ запрос к серверу при каждом
воспроизведении (`serverRequestPerPlayback: false`), НЕТ удалённого
TTS-фолбэка во время сессии (`remoteTtsFallbackDuringSession: false`) — то
есть ВСЕ 4 варианта должны быть заранее сгенерированы и лежать в Storage,
рантайм не может дозвать TTS на лету.

Структура файла на карточку —
`modules/learning-v2/runtime/course_session_audio_child_v1.ts`:
```ts
interface LearningV2CourseSessionAudioSelectableV1 {  // строка 31-44
  selectableId, audioTargetId, wordId, wordOrdinal, visibleTextHash,
  files: readonly [File, File, File, File];  // РОВНО 4, по одному на голос
  selectableFingerprint;
}
interface LearningV2CourseSessionInteractionAudioV1 {  // строка 46-59
  interactionId, taskVoiceGroupFingerprint,
  fullPhraseFiles: [File,File,File,File] | null,  // 4 файла на ВСЮ фразу целиком
  selectables: LearningV2CourseSessionAudioSelectableV1[],  // + по 4 файла на КАЖДОЕ слово
  interactionAudioFingerprint;
}
```
Каждый файл (`LearningV2CourseSessionAudioFileV1`, строки 21-29):
`voiceId, objectPath, contentHash, objectGeneration, byteSize,
contentType: "audio/mpeg", fileFingerprint`. Лимит на файл — 64 КБ (строка
16, `LEARNING_V2_COURSE_SESSION_AUDIO_FILE_MAX_BYTES_V1`), на весь
аудио-ребёнка сессии — 4 МБ (строка 14-15).

Какие карточки вообще требуют аудио — не все:
`modules/learning-v2/content/generator_session_shard.ts:160-165`:
```ts
const AUDIO_FAMILIES = new Set(['listen_choose', 'sound_contrast', 'listen_build_dictation', 'scripted_repeat_compare']);
```
Проверено подсчётом (одноразовым тестом, результат ниже, не переносился в
постоянный код): из 150 карточек (10 сессий × 15) — **70 карточек требуют
аудио**, **65 уникальных английских текстов** нужно озвучить (некоторые
фразы повторяются между сессиями намеренно, интервальное повторение).
Список семейств по всем 150 карточкам:
```
listen_choose: 20, speed_match: 20 (без аудио), phrase_builder: 40 (без аудио),
sound_contrast: 5, context_gap_grammar: 20 (без аудио),
scripted_repeat_compare: 20, listen_build_dictation: 25
```
Это только ЦЕЛЫЕ ФРАЗЫ. Полный контракт требует ЕЩЁ по 4 файла на каждое
СЛОВО внутри этих 70 карточек — точное число слов не подсчитано в этой
сессии, нужно посчитать перед стартом генерации (примерно ×3-5 к 65 —
итоговый объём файлов может быть 250-350 уникальных текстов × 4 голоса =
1000-1400 файлов, оцени точнее перед тратой денег).

   нужно СКАЧИВАТЬ на первом открытии сессии (Storage, не бандл, — это
