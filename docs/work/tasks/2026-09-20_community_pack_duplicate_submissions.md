## Outcome

Владелец нажимает «Сделать публичным» на своём наборе сколько угодно раз — в админке
(«Наборы сообщества» → «Заявки») остаётся РОВНО ОДНА заявка на этот набор, и в ней
лежит последняя версия карточек. Сегодня три нажатия дали три одинаковых заявки
«My phrases verbs» (12:31, 12:44, 12:49), и владелец не понимает, какую одобрять.

Успех измеряется так: повторная публикация того же локального набора не увеличивает
число документов в `community_pack_submissions`, а обновляет `payload` существующего.

## Scope

In scope:
- `app/community_packs/publishLocalPack.ts` — единственная точка публикации
  (через неё идут оба экрана: `app/community_pack_create.tsx` и
  `app/flashcards_collection.tsx`).
- `app/community_packs/localAuthorPacks.ts` — поля `cloudPackId` / `publicationKey`,
  если потребуется разделить «id заявки» и «id опубликованного набора».
- Трассировка `[UGC-PUBLISH]` по правилу «сперва логи».

Out of scope:
- Серверная функция `communitySubmitPackForReview` — её идемпотентность корректна,
  ломает её клиент. Сервер не трогаем.
- Админка `admin/v2/legacy.html` — три висящие заявки владелец закрывает вручную
  (одну одобрить, две отклонить), автоматической схлопывалки не делаем.
- Логика правки уже опубликованного набора (ветка `updatePackId` на сервере).

## Architecture

Текущая граница (сломанная): сервер возвращает `{ submissionId }` — идентификатор
документа в коллекции `community_pack_submissions`. Клиент на строке 86 записывает
его в поле `cloudPackId`, которое по контракту хранит идентификатор документа в
ДРУГОЙ коллекции — `community_packs`. Две разные коллекции, один слот хранения.

Последствие — цепочка из трёх звеньев:
1. телефон отправляет `updatePackId` = id заявки;
2. сервер не находит такой набор в `community_packs`, сбрасывает `updatePackId`
   и уходит в ветку создания (functions/src/community_packs.ts:522-535);
3. ветка создания защищена идемпотентностью по `submissionKey`, но клиент на
   шаге 1 перезаписал `publicationKey`, поэтому ключ каждый раз новый и защита
   не срабатывает → `tx.create` нового документа.

Намеченная граница: `cloudPackId` заполняется ТОЛЬКО реальным идентификатором
опубликованного набора. Идентификатор заявки туда не попадает никогда.
`publicationKey` — стабильный на всё время жизни локального набора; он и есть
ключ идемпотентности, который склеивает повторные нажатия в одну заявку.

Инвариант: `publicationKey` меняется единственный раз — при отзыве публикации
(`withdrawLocalAuthorPack`), где новая публикация намеренно начинается с нуля.

## Security and privacy

Авторизация не меняется: вызов остаётся авторизованным, `authorStableId` по-прежнему
проверяется сервером через `resolveStableUidForAuth`. Новых полей, новых сторонних
сервисов, новых разрешений и новых персональных данных нет — правка только перестаёт
записывать в локальное поле чужой идентификатор. Privacy policy обновления не требует.

Побочный положительный эффект: меньше мусорных документов в модерации — меньше
поверхности для случайной публикации не того содержимого.

## Technical debt

- Pay now: смешение двух идентификаторов в одном поле `cloudPackId`. Устраняется
  внутри этой задачи — id заявки туда больше не пишется.
- Pay now: немая обработка ошибки публикации (`if (__DEV__) console.warn`) —
  в релизе причина отказа не видна вообще. Лог причины остаётся навсегда,
  по правилу «запрет немого catch».
- Contain: уже испорченные телефоны (в `cloudPackId` лежит id заявки). Граница —
  самолечение при первой же публикации: значение распознаётся как id заявки и
  отбрасывается. Условие выхода — когда в проде не останется старых записей,
  проверку можно снять; до тех пор она стоит.
- Accept temporarily: нет серверного сторожа «один автор + один submissionKey =
  одна заявка» на уровне правил Firestore. Владелец: эта же сессия. Дата ревью:
  при следующей задаче по UGC. Потолок влияния: дубли возможны только если клиент
  снова начнёт слать разный ключ. Покрывается тестом-контрактом.

## Rollback

Правка чисто клиентская и не мигрирует данные: откат — вернуть прежние строки в
`publishLocalPack.ts`. Уже созданные заявки и опубликованные наборы не затрагиваются,
купленные наборы и доступы не зависят от этого поля. Потери данных при откате нет;
вернётся лишь прежнее поведение с дублями.
