# Быстрый и бесшумно надёжный «Разбор промаха»

**Дата:** 2026-08-08  
**Статус:** на подтверждении владельца

## Цель

После успешного получения «Разбора промаха» кнопка «Объяснить проще» должна открывать уже готовый текст без второго пользовательского ожидания. Если модель вернула текст, который не прошёл валидатор, этот текст нельзя показывать или публиковать в кэш: сервер бесшумно повторяет генерацию ограниченное число раз, а существующий клиентский фоновый retry продолжает восстанавливать временные сбои без error-состояния в UI.

## Рассмотренные варианты

1. **Одна генерация возвращает полный и простой варианты — выбранный вариант.**
   - Плюсы: один вызов провайдера на нормальном холодном пути, оба текста согласованы, «Объяснить проще» открывается из готового кэша.
   - Минусы: требуется надёжно разделить два текста и расширить ответ callable.

2. **Две генерации запускать параллельно.**
   - Плюсы: почти не меняются существующие промпты.
   - Минусы: двойная стоимость и два независимых отказа; полный разбор ждёт более медленную генерацию.

3. **После полного разбора фоном запрашивать ELI5.**
   - Плюсы: не задерживает первый текст.
   - Минусы: быстрый тап всё ещё может попасть в незавершённую вторую генерацию; сохраняется двойной вызов провайдера.

Выбран вариант 1 как единственный, который убирает вторую генерацию и второе ожидание одновременно.

## Контракт и совместимость

Callable `explainMistake` сохраняет существующие поля `text`, `variant`, `fromCache`, `model` и `remainingQuota`. В ответ добавляются необязательные поля:

```ts
fullText?: string;
eli5Text?: string;
```

- Для `variant: 'full'` нормальный холодный путь генерирует bundle из двух частей и возвращает `text === fullText`, одновременно передавая `eli5Text`.
- Для `variant: 'eli5'` сохраняется существующий контракт `text === eli5Text`.
- Старые клиенты игнорируют новые поля и продолжают работать.
- Старые кэш-записи, где есть `full`, но нет `eli5`, продолжают обслуживаться существующим ленивым ELI5-путём.
- Текущий явный UI-триггер, consent-логика и транспортный фоновый retry не меняются в этой итерации.

## Серверный поток

### Холодный `full`

1. Сервер читает общий кэш и берёт существующий full-lock.
2. Один запрос к модели просит вернуть две явно размеченные секции: полный разбор и простое объяснение. Формат использует детерминированные маркеры, а не JSON mode, чтобы не зависеть от поддержки `response_format` выбранной runtime-моделью.
3. Парсер требует ровно две непустые секции и удаляет служебные маркеры.
4. Языковой валидатор независимо проверяет обе секции.
5. При успешной проверке обе секции одним cache-write публикуются как `ready`.
6. Биллинг учитывает суммарные токены всех попыток, включая забракованные валидатором.

### Validator-retry

- Максимум три попытки в одном callable: первая генерация плюс два внутренних повтора.
- Внутренний повтор разрешён только для брака результата: неверный язык, отсутствующая/повреждённая секция или другой детерминированный output-validation failure.
- Сетевые ошибки, timeout и ошибки провайдера не размножаются этим циклом; они уходят в уже существующий транспортный retry.
- Auth, permission, quota и invalid-argument никогда не повторяются.
- Забракованный текст не возвращается клиенту и не записывается как `ready`.
- Только после исчерпания трёх внутренних попыток запись получает `rejected`; существующий клиент остаётся в loading и продолжает фоновое восстановление согласно cache TTL/backoff.

### ELI5 для старого кэша

Если `full` уже существует, но `eli5` отсутствует, сервер использует текущий отдельный ELI5 prompt с теми же максимум тремя validator-попытками. Это переходный путь; новые full-cache miss сразу заполняют оба поля.

## Клиентский поток

1. `callExplainMistake(...variant: 'full')` получает `fullText` и, при наличии, `eli5Text`.
2. Клиент сохраняет full и ELI5 под их существующими локальными cache keys.
3. `useMistakeExplain` переводит inline-карточку в `ready` и одновременно подготавливает ELI5 state как `ready`.
4. Нажатие «Объяснить проще» открывает модалку с готовым текстом и не вызывает сеть.
5. Если ответ пришёл от старой версии сервера без `eli5Text`, сохраняется текущий ленивый сетевой путь.

## Одновременные запросы и кэш

- Full-lock остаётся единственным владельцем bundle-генерации.
- Bundle cache-write публикует `full`, `eli5`, `status: 'ready'` и очищает оба pending-маркера атомарно одним `set(..., { merge: true })`.
- Отдельный ELI5-lock остаётся для старых кэш-записей и старых клиентов.
- Проигравший конкурентный запрос опрашивает кэш и принимает bundle, опубликованный победителем; дублирующая генерация не запускается.

## Наблюдаемость

Структурированные серверные логи содержат только технические поля, без ответа ученика и текста объяснения:

- `variant`
- `fromCache`
- `generationAttempts`
- `validatorRejects`
- `bundleGenerated`
- `durationMs`

Содержимое промпта, пользовательского ответа и сгенерированных текстов в логи не добавляется.

## Тестирование

TDD-покрытие должно доказать:

1. Холодный full делает один provider-call, возвращает два текста и кэширует оба.
2. Последующий ELI5 читается из кэша без provider-call.
3. Два первых ответа, отклонённых валидатором, бесшумно заменяются третьим валидным ответом.
4. После трёх отклонений ни один забракованный текст не возвращается и не публикуется как `ready`.
5. Provider/network/auth/quota errors не проходят через validator-retry.
6. Клиент сохраняет оба локальных варианта и подготавливает ELI5 state.
7. Ответ старого сервера без `eli5Text` сохраняет ленивый ELI5 fallback.
8. Одновременные full-запросы не создают дублирующую bundle-генерацию.

## Критерии приёмки

- После готового нового full-разбора «Объяснить проще» не выполняет сетевой запрос.
- На нормальном холодном пути выполняется одна генерация провайдера вместо двух последовательных.
- Ни один текст, забракованный валидатором, не показывается пользователю и не становится ready-cache.
- Validator-retry ограничен тремя попытками и не повторяет неповторяемые ошибки.
- Старые клиенты и старые неполные кэш-записи остаются совместимыми.
- Целевые тесты клиента и Functions проходят; TypeScript-сборка Functions проходит.

## Вне текущей итерации

- Перенос функции из `us-central1` ближе к Firestore `eur3`.
- Изменение `minInstances`.
- Замена модели или A/B качества моделей.
- Изменение consent UX, первого UI-триггера или политики бесшумного транспортного retry.
- Общая перестройка лимитов и платёжных гейтов.
