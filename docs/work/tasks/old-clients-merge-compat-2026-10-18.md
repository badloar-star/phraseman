# Старые сборки 1.x и отказ серверного слияния `authMergeStableAccounts` (18.10)

Только чтение. Составил «9 · САЙТ» для Ядра по заданию координатора.

Ядро добавляет серверный отказ слияния гостя в существующий аккаунт (правило владельца 2), но только для новых клиентов. Здесь — как поведут себя старые сборки из стора.

**Какая версия считается старой.** Последняя версия 1.x в git — **1.6.24, сборка 130, коммит `af76518ac`** (22.09, «chore(релиз): версия 1.6.24, сборка 130»). Следующая сборка уже 2.0.0 (`6969eff3e`, 10.10). Тегов релизов в репозитории нет. Какая именно сборка опубликована в сторах, git не говорит — в документах я не нашёл подтверждения «1.6.24 в продаже». Ниже всё проверено по коду `af76518ac`. Ветки входа в 1.6.2x менялись мало, но если в сторе 1.6.22–1.6.23, этот разбор стоит перепроверить на их коммитах (`6c02e4088`, `add09e9ff`).

## 1. Когда 1.6.24 вызывает `authMergeStableAccounts`

Вызов один — `mergeStableAccountsViaServer` в `app/cloud_sync.ts:2779-2804` (по `af76518ac`).

**Запрос:** `{ stableIdA, stableIdB }`, ничего больше. Ожидание — 12 с (`STABLE_AUTH_LINK_TIMEOUT_MS`).

**Как клиент понимает ответ:**
- Любая ошибка — HttpsError, таймаут или сеть — превращается в `null`: catch на :2800-2803 молчит, пишет только в `__DEV__`.
- Ответ без `ok: true` клиент тоже считает неудачей (`merge?.ok`).

**Прогрев.** `warmAuthSignInCallables` (`cloud_sync.ts:2381`) шлёт `{ warmup: true }` без входа, троттл 10 мин. **Ветку прогрева на сервере сохранить** — иначе каждое открытие окна входа на старой сборке даст ошибочный вызов. Вызов бесплатный по смыслу, но засоряет журнал.

**Где вызывается** — `app/auth_provider.ts` в `af76518ac`:

| # | Ветка | Строки | Условие вызова | Кого сливает |
|---|---|---|---|---|
| 1 | `merged_swap_to_remote` | :2485-2596, вызов :2520-2522 | (а) провайдер уже привязан к другому stable (`auth_links/{providerUid}.stable_id ≠ local`, :2283-2288, ветка remote :2329-2384), **или** (б) сервер на `ensureStableAuthLink(local)` вернул другой канонический stable (:2468-2473). **И** нет маркера передачи провайдера (`providerHandoffMarker`), **и** на телефоне есть значимые данные (`hasMeaningfulLocalAccountData`) | `(локальный stable, удалённый stable)` |
| 2 | `merged_keep_local` | :2598-2650, вызов :2609 | Ветка есть, но **в 1.6.24 её никто не назначает** (поиском по `kind: 'merged_keep_local'` присваиваний не найдено, только тип :2301) | Мёртвый код |

**Где слияния НЕТ** — то есть главный случай правила 2, «гость с прогрессом входит в чужой существующий аккаунт»:
- **Гость с прогрессом, существующий аккаунт.** `linkWithCredential` падает с `credential-already-in-use`. Дальше `isLocalAnonymousIdentityProvenCleanForCredentialHandoff()` (:2124). При `!localClean && !postCompletionHandoff` клиент возвращает **`account_switch_required`** (:2155-2165) — до любого слияния.
- **Гость пустой, или метка «свежий гость после смены» (`postCompletionHandoff`).** Создаётся `providerHandoffMarker` (:2137), значит `preserveLocalProgress = false` (:2487-2489), значит **слияние не зовётся** (:2520-2522 → `null`).

**Вывод по (1).** Старая сборка зовёт слияние только в редких случаях (а) и (б), когда локальный и удалённый stable принадлежат **одному человеку**:
- переустановка, после которой в Keychain остался другой stable;
- оборванный прошлый вход;
- провайдер без маркера передачи.

Классический «гость → чужой аккаунт» до слияния не доходит.

**Для Ядра.** Отказ надо ставить только на «чужого гостя», а не на «оба stable доказанно мои» (ветка XP-merge, где оба привязаны к одному auth uid). Иначе старые сборки потеряют легитимное слияние своих двух копий.

## 2. Что увидит человек на 1.6.24, если сервер откажет

| Как сервер откажет | Что сделает клиент 1.6.24 | Что увидит человек | Прогресс |
|---|---|---|---|
| Быстро бросит `HttpsError` (любой код) **или** вернёт `{ ok: false, … }` | `merge` = `null` или не `ok` → перечитывает якорь `ensureStableAuthLinkForStableIdDetailed(remote, …, { requireAuthoritative: true })` (:2528-2536) → при `ok` берёт `canonical = remote` → `quiesce` → стирает локальное → `setStableId(remote)` → догрузка B в фоне (:2547-2575) → `result: 'merged_devices'` | **Обычный успешный вход в B**, без текста ошибки. Шторка закрывается, через несколько секунд виден прогресс B | Гость не слит в B. До стирания его прогресс уже отправлен в облако под старым stable (presync, :2494-2506), поэтому он не уничтожен, но на экране его больше нет — висит в старом документе без владельца. По смыслу это «вход без слияния» — то, что и нужно правилу 2 |
| Отказ **после** перечитывания якоря, якорь не авторитетен (`!ok`) | `return { result: 'error', error: 'merge_pending' }` (:2534-2535) **до** стирания | Красная строка: заголовок «Не получилось», текст **«Не получилось войти. Попробуй позже.»** (`components/RegistrationPromptModal.tsx:1188-1199` по `af76518ac`) | Локальный прогресс цел. Но Firebase уже держит сессию провайдера B при локальном A. Следующий тап упирается в `account_switch_required` (:2005-2014) — **мягкий тупик**, выход только через «Сменить аккаунт» в Настройках. Это не следствие отказа слияния, а сбой перечитывания якоря |
| Сервер **держит** вызов дольше 12 с (медленный отказ) | Клиент ждёт до 12 с (`withTimeout`), потом `null` → дальше как в первой строке | 12 с колечко на кнопке, потом вход в B | Как в первой строке |
| Presync перед слиянием упал (нет сети) | `throw` в :2504 → catch :2589-2595 → `error: 'swap_<message>'` | «Не получилось войти. Попробуй позже.» | Цел, вход отменён. Не зависит от отказа слияния |

**Вывод по (2).** Отказ на сервере старую сборку **не ломает**, если он быстрый, а исход сводится к «вход в B без слияния».

**Требования к отказу:**
- **Отвечать сразу.** Бросать `HttpsError('failed-precondition', 'merge_refused_guest')` или возвращать `{ ok: false, reason: 'merge_refused_guest' }` — для 1.6.24 это одно и то же.
- **Не держать вызов до таймаута.** Иначе человек 12 с смотрит на колечко.
- **Не портить `auth_links` и якорь.** Перечитывание якоря сразу после отказа (:2528) должно вернуть `ok` и удалённый stable. Если отказ хоть как-то трогает якорь, старая сборка уйдёт в `merge_pending` и мягкий тупик.

## 3. Как отличить новый клиент от старого

**Что уже есть:**
- 1.6.24 шлёт ровно `{ stableIdA, stableIdB }` (`cloud_sync.ts:2793-2797` по `af76518ac`).
- Текущий клиент шлёт `{ stableIdA, stableIdB, ...anonMergeNonceField('merge', [a, b]) }` (`app/cloud_sync.ts:2741-2748`). Поле `anonMergeNonce` появляется **не всегда**, а только когда есть свежая метка анонимного владения. Как признак версии оно **ненадёжно**: его отсутствие не значит «старый клиент».
- App Check как признак не годится: клиентский App Check снят (пломба 2026-08-17).
- Версию приложения callable сам не передаёт: в `request` её нет.

**Рекомендация:**
- Новый клиент добавляет **явное поле** в запрос `authMergeStableAccounts`, например `{ …, clientMergeContract: 2 }`. Сервер включает отказ слияния гостя **только при `clientMergeContract >= 2`**, а без поля оставляет прежнее поведение.
- Строгих проверок, которые отвергнут лишнее поле, в обработчике 1.6.24 нет — поле добавляет только новый клиент, старому ничего не нужно.
- Альтернатива без признака: включить отказ для всех. По разбору (2) старая сборка его переживёт — вход в B без слияния. Но тогда отказ заденет и легитимные слияния двух копий одного человека, ветки (а) и (б) из раздела 1. Поэтому лучше с полем.

## Коротко для Ядра

- 1.6.24 зовёт слияние редко: две копии одного человека, без маркера передачи. Гость с прогрессом в чужой аккаунт до слияния не доходит — останавливается на `account_switch_required`.
- Быстрый отказ сервера в 1.6.24 выглядит как обычный вход в B без слияния. Текста ошибки нет, прогресс гостя остаётся в облаке под старым stable.
- Опасно только: медленный отказ (12 с колечко) и любое касание якоря/`auth_links` при отказе (`merge_pending` → мягкий тупик).
- Признак нового клиента — новое явное поле `clientMergeContract`. Наличие `anonMergeNonce` признаком не считать.
- Ветку прогрева `{ warmup: true }` не трогать.
