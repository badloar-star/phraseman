# Смоук-аудит Phraseman на вылеты — 2026-06-21

## Как проверяли

Это статический смоук-аудит исходного кода (без запуска на реальном устройстве или эмуляторе): код приложения был разбит на 12 функциональных зон, по каждой искались паттерны runtime-крашей в фазе рендера React — итерации/деструктуризация потенциально `undefined`-значений, небезопасный `JSON.parse`, разбор route-параметров, чтение контекста без guard. Каждая предполагаемая находка проходила адверсариальную верификацию: цепочка от источника «грязных» данных до места падения прослеживалась вручную по реальным строкам кода, и находка засчитывалась только при подтверждённой достижимости. Динамические сценарии (реальные нажатия, сетевые ответы, повреждённый AsyncStorage на живом устройстве) НЕ воспроизводились — выводы основаны исключительно на чтении кода.

Покрытие: ~335 файлов `.tsx` (142 экрана + 193 компонента). В приложении один-единственный глобальный `ErrorBoundary` (`app/_layout.tsx`), обёрнутый снаружи всего стека провайдеров: он ловит ошибки только фазы рендера/lifecycle, показывает дружелюбную заглушку с кнопкой «Попробовать снова» и шлёт отчёт в Crashlytics. Локальных (гранулярных) ErrorBoundary вокруг отдельных экранов/модалок НЕТ — любой render-краш роняет фоллбэк на весь экран. Асинхронные ошибки (промисы/таймеры/хендлеры) boundary не ловит — для них есть отдельный глобальный `onunhandledrejection` (`app/_layout.tsx`).

Все 12 зон были проверены, ни одна не упала по rate-limit — перепроверять из-за недоверенного покрытия ничего не требуется.

> **Личная перепроверка автора (после аудита):** единственная подтверждённая находка ниже прослежена вручную по коду (`loadLeagueState` → `applyLeagueOpen` → `setGroup(state.group)` без `?? []` → `[...group]` в рендере) и подтверждена как реальная, но низкого риска. См. раздел ниже.

## Подтверждённые крах-риски (по убыванию серьёзности)

### [низкий] app/club_screen.tsx:834 — ClubScreen (тело рендера)

- **Что упадёт:** весь экран «Лиги» — `[...group].sort(...)` бросает `TypeError: undefined is not iterable`, краш ловит глобальный ErrorBoundary и показывает фоллбэк на весь экран.
- **Когда (trigger):** при входе в раздел Лиги состояние читается через `loadLeagueState()` (`app/league_engine.ts:508`), которая делает `JSON.parse` и возвращает результат без санитизации поля `group`. Если сохранённый в AsyncStorage объект состояния лиги не содержит `group` (частичная/повреждённая запись, дающая валидный JSON-объект вида `{leagueId, weekId}`), то `applyLeagueOpen` выполняет `setGroup(state.group)` = `undefined` (`app/club_screen.tsx:614`, здесь нет `?? []`), и в рендере деструктуризация `[...group]` падает. Инициализация стейта защищена (`app/club_screen.tsx:405` — `?? []`), поэтому на старте краха нет — только после загрузки битого кэша.
- **Сниппет:**
```ts
const sortedGroup = [...group].sort((a, b) => b.points - a.points);
```
- **Фикс (1 строка):** в `applyLeagueOpen` заменить `setGroup(state.group)` на `setGroup(state.group ?? [])` (либо санитизировать `group` в `loadLeagueState`).

> Severity низкий потому, что все штатные писатели состояния (`saveLeagueState`, фолбэк, удалённые результаты) ВСЕГДА кладут поле `group`, а суффикс ключа состояния изолирует старые схемы. Остаётся только редкий случай повреждённой частичной записи.

## Что НЕ нашли / зоны без рисков

- **Контекст-провайдеры безопасны:** большинство контекстов созданы с дефолтным значением, а не `null` (`PremiumContext`, `AchievementContext`, `StudyTargetContext`, `ThemeContext`, `EnergyContext`, `LangContext`) — `useContext` вернёт дефолт даже без провайдера. Контексты с `null`-дефолтом fail-soft: `OverlayArbiter` возвращает заглушку, `NoEnergyModal` уже делает `if (!ctx) return`.
- **JSON.parse в `_layout.tsx` защищён** локальными `try/catch` (login_bonus, level-up queue, leaderboard cache).
- **Порядок провайдеров корректен:** ErrorBoundary стоит снаружи всех провайдеров и не использует тему/контекст в фоллбэке (хардкод цвета), поэтому переживёт даже краш `ThemeProvider`/`LangProvider`.
- **Зоны tabs-core, lessons, personal-plan, cards-collectibles, premium-paywall, ai-dialog-compass, quizzes, settings-profile, components-modals-2** — подтверждённых render-крашей не выявлено. В trainer, components-modals-1 и arena часть кандидатов была отсеяна как ложные при верификации (защищённая инициализация / недостижимый путь).

## Рекомендации

- **Санитизировать на границе данных:** функции загрузки состояния (`loadLeagueState` и аналоги) после `JSON.parse` должны нормализовать форму объекта — массивы по умолчанию `[]`, обязательные поля с дефолтами, а не доверять типу возврата.
- **Дефолты для async-стейта:** любой `setState`, принимающий значение из распарсенного кэша/ответа, должен иметь `?? []` / `?? {}` для коллекций, которые потом итерируются или деструктурируются в рендере.
- **Локальные ErrorBoundary вокруг тяжёлых/независимых экранов** (Лиги/Арена, ИИ-диалог, квизы, модалки апгрейда): сейчас любой их краш роняет фоллбэк на всё приложение — гранулярная изоляция оставит остальную навигацию рабочей.
- **Защита route-параметров:** ввести единый хелпер-нормализатор для `useLocalSearchParams`/`useGlobalSearchParams` (параметры — это `string | string[] | undefined`); любой `parseInt`/индексация/`JSON.parse` над сырым параметром без нормализации = потенциальный render-краш. Это ~20 вхождений в 10+ экранах — точечно не проверены.
- **Греп `JSON.parse` по экранам отдельно:** в `_layout.tsx` они защищены вручную, но незащищённый `JSON.parse` в render-пути любого другого экрана — главный системный риск; стоит проверить адресно.
- **Тесты на «битый кэш»:** добавить юнит-тесты, прогоняющие загрузчики состояния через частичные/повреждённые JSON-объекты, чтобы ловить отсутствие дефолтов до релиза.
