# Чтения Firestore на холодном старте — R1 (аудит по коду, 12.10.2026)

Автор: сессия «1 · Ядро». Источник: код ветки `feature/referral-roulette` на 12.10 (после bd3e11bd3) и архивные
журналы сборщика ([MEM-TICK] 11–12.10). Эмулятор не использовался. Точные числа на устройстве даст строка
`[MEM-TICK] firestoreReadsByCaller` из журнала Сверки.

**Главный вывод.** До первого кадра Главной сеть почти не нужна: Главная рисуется из снимка, а тяжёлый старт
(`runHeavyInit`, восстановление из облака при включённом `boot_restore_defer_enabled`) идёт ПОСЛЕ кадра Главной
(`runAfterHomeFirstFrame`, `_layout.tsx:1837`). Дорого не «до кадра», а **каждый холодный старт без TTL**:
документ `users/{uid}` читается до 3 раз, а входящие сообщения — тремя запросами до 80 документов, без всякого
срока жизни. Плюс «Настройки» на каждом возврате.

Факт из журнала (metro_003901.log, старый счётчик без вызывающих): первые 7 с — `users:3`, к 13 с — ещё
`query:3, users:1`. Это совпадает с таблицей: три чтения `users` (восстановление, бан, рассылка/привязка) и
три запроса входящих.

### «Настройки» (к журналу Сверки)

| Что | Метод | Срок жизни | Повтор |
|---|---|---|---|
| Входящие (те же 3 запроса × 80, что #7) | 3× query | **30 с** (`settings.tsx:348`) | при каждом входе в «Настройки» и возврате из фона, если прошло >30 с |
| `getLinkedAuthInfo` → **весь** `users/{stableId}` ради поля `linkedAuth` | get | нет: уход с вкладки ставит «грязно» (`settings.tsx:654–658`) | **при каждом возврате** в «Настройки» (`:649–652`) |

Это и есть кандидат на «users/query каждые 30–60 с»: любое переключение активности вкладки (фокус, фон,
оверлей) повторяет оба чтения. Подтвердит или опровергнет `firestoreReadsByCaller`.

## Три самые дешёвые правки (предложение, без выкладки)

1. **Входящие: убрать `force` на каждом холодном старте и 30 с в «Настройках».** Метку «уже форсили для
   stableId» хранить в AsyncStorage (как `lastBackgroundRefresh`), `force` — только при настоящем входе в
   аккаунт; холодный старт и «Настройки» — общий TTL 6 ч (`APP_MESSAGES_FOREGROUND_MIN_INTERVAL_MS` уже есть).
   Экономия: до **240 чтений на каждый запуск** и до 240 на каждый заход в «Настройки». Правка — 2 файла,
   ~10 строк; снимок на экране не меняется (он уже из кэша).
2. **Один `users/{uid}` на старт вместо трёх.** Проверка бана берёт поле `banned` из документа, который
   восстановление (#4) уже прочитало, а не читает его заново; TTL кэша бана 30 мин → 6 ч (бан — редкое
   событие; отказывает ли сервер забаненному сам — по коду не проверено, решение за владельцем). Рассылка (#6) при `premiumAudience≠all` берёт доступ из
   локального состояния PremiumContext, а не из документа. Экономия: 1–2 полных чтения `users` на запуск.
3. **«Настройки»: строка аккаунта без чтения `users`.** Показывать `linkedAuth` из снимка Настроек и Firebase
   Auth (`providerData` — 0 чтений), а документ читать только по событию `auth_provider_linked` и не чаще раза
   в 6 ч; уход с вкладки больше не помечает «грязно». Экономия: 1 полное чтение `users` на каждый заход.

Попутно (не входит в тройку): эффект рассылки (#6) перезапускается при каждой смене `studyTarget` — вызов
сервера повторяется в течение одного старта; и в `fetchPendingGlobalBroadcastModal` немой `catch { return null }`
(`global_broadcast_modal.ts:438`) — по правилу «сперва логи» туда нужна строка с причиной.

Влияние на скорость: все три правки убирают работу из окна сразу после первого кадра (сеть + разбор до 240
документов на JS-потоке), то есть ускоряют первые секунды Главной и вход в «Настройки», а не замедляют.
Optimistic UI не затрагивается: экраны и так рисуются из снимков.
