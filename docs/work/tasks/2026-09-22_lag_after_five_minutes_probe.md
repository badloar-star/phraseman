## Outcome

Владелец 2026-09-22: «после 5 минут в приложении и переходов по разным разделам
оно начало лагать/тормозить». Сборка — TestFlight (релиз), не дев.

**Симптом НОВЫЙ и отличается от вчерашнего.** 21.09 жалоба звучала «всё лагает,
причём ВЕЗДЕ» — постоянная медленность с первой секунды, под неё построен замер
`perf_release_probe.ts` (всплески перерисовок внутри экрана). Сегодня описано
НАРАСТАНИЕ: сначала нормально, через 5 минут начинает. Счётчик рендеров такое
не видит по построению — он считает внутри одного экрана и обнуляет окно
каждую секунду.

Успех этого пакета — **НЕ починка, а факты с устройства**: замер, который
различает две взаимоисключающие версии нарастания, плюс закрытие найденных
неограниченных кэшей.

Критерий: после прохода владельца по разделам в журнале отладки есть ряд строк
`[PERF-RELEASE] хранилище через N мин`, по которому видно, растёт ли индекс
ключей за сессию и дорожает ли полный скан.

## Scope

In scope:
- `app/perf_release_probe.ts` — новая функция `probeStorageGrowth(reason)`:
  размер индекса хранилища, время полного скана, прирост с начала сессии и с
  прошлого замера. Не чаще раза в минуту, пишет только при медленном скане,
  заметном приросте или каждый пятый замер (опорная точка ряда).
- `app/_layout.tsx` — вызов замера на смене раздела через
  `InteractionManager.runAfterInteractions` (после анимации перехода).
- `app/arena_client.ts` — граница у `viewerSeatCache` (растёт на каждый матч).
- `app/collectibles/svg_gray.ts` — граница у `grayCache`. ВАЖНО: проверка
  показала, что `grayscaleSvg` НЕ ВЫЗЫВАЕТСЯ НИОТКУДА (единственное вхождение
  по всем .ts/.tsx — сам файл). Модуль мёртвый, на лаги не влияет; граница
  поставлена «на вырост», и это ЗАПИСАНО в комментарии, чтобы следующая
  сессия не приняла файл за причину. Удаление мёртвого кода — отдельная
  задача (сторож массового удаления блокирует такие коммиты).
- `app/practice_rune_settlement.ts` — **главная находка**. Функция
  `flushStalePracticeRuneSettlements` делает ПОЛНЫЙ скан индекса
  AsyncStorage и вызывается при входе в ЛЮБУЮ из семи активностей
  (`hooks/usePracticeRunes.ts:323`) и при каждой смене `sessionKey` внутри
  них — то есть буквально на каждом переходе между разделами, что и описал
  владелец. Добавлен потолок частоты: скан пропускается только когда прошлый
  подтвердил ПУСТУЮ очередь и прошло меньше 5 минут.

СОЗНАТЕЛЬНО ВНЕ ОБЛАСТИ:
- **Чистка реестра осколков.** Владелец разрешил удалять «только заведомо
  завершённые» записи, но проверка кода показала: реестр осколков — НЕ набор
  независимых записей, как у энергии, а **непрерывная цепь с ревизиями**
  (`client_shard_operation_ledger.ts:806-813`). Состояние перестраивается
  подряд, код требует ревизии строго `1,2,3…` без пропусков и совпадения
  `balanceBefore === предыдущий balanceAfter`, иначе бросает
  `client_shard_root_chain_gap`. Удаление любой старой операции ломает цепь и
  стоит человеку его осколков. Правильное решение — свёртка цепи в
  контрольную точку, механизма для неё в коде НЕТ. Это отдельная задача с
  деньгами, делать её заодно с замером нельзя. Потолок 4096
  (`:800`) остаётся зафиксированной отложенной ПОЛОМКОЙ.
- Правки 20+ мест с полными сканами `getAllKeys` — до получения ряда замеров.
  Вчерашний круг показал, чем кончается починка по статической догадке.
- Разбиение `HomeScreen` (5192 строки) — правило владельца
  `feedback_never_rewrite_screen_wholesale`.

## Architecture

Границы не меняются, новых зависимостей нет.

`probeStorageGrowth` живёт в памяти процесса (`storageProbeState`), на диск и в
сеть ничего не пишет, сбрасывается вместе с остальными счётчиками при смене
аккаунта (`resetReleasePerfCounters`). `AsyncStorage` импортируется динамически
внутри функции — модуль замера не должен тянуть хранилище в синхронный бандл
первого кадра.

Замер обязан РАЗЛИЧИТЬ две версии, иначе бесполезен:
- индекс растёт за сессию → виноват рост (чинить чистку/кэш);
- индекс стабилен, а сканы долгие → виноват накопленный за месяцы размер базы
  (чинить кэшем поверх скана).
Один снимок на это не отвечает — отвечает только ряд, поэтому пишутся и
абсолютное число, и обе дельты.

Границы кэшей ставятся по образцу уже принятого в проекте FIFO-вытеснения
(`course_accordion_map_model_v1.ts:111`), новый механизм не вводится.

**Инвариант досылки рун, который НЕЛЬЗЯ нарушить.** Очередь досылки — это
деньги: локальный баланс уже начислен, серверу осталось догнать. Поэтому
потолок частоты устроен несимметрично:
- скан ПРОПУСКАЕТСЯ только если прошлый нашёл очередь полностью пустой
  (`synced === 0 && pending === 0 && keys.length === 0`);
- любой непустой результат СТИРАЕТ отметку — следующий заход сканирует снова;
- постановка в очередь (`markPracticeRuneSettlementPending`) стирает отметку
  немедленно, иначе новая запись ждала бы досылки до пяти минут;
- очередь пополняется только в этом же процессе, поэтому отметка в памяти
  процесса не может разойтись с диском.
Итог: досылка не может потеряться, экономится только повторный скан там, где
искать заведомо нечего — самый частый случай у обычного игрока.

## Security and privacy

Персональных данных не добавляется, не хранится и не передаётся. Замер пишет
только числа (количество ключей, миллисекунды) и имя раздела; содержимое
ключей не читается, значения не логируются. В Firestore не уходит — severity
строго `warning`, как у существующего замера. Privacy policy обновления не
требует.

## Technical debt

- **Реестр осколков без чистки и со свёрткой, которой нет.** Disposition:
  **Contain** — зафиксировано здесь как отложенная ПОЛОМКА (на 4096 записях
  исключение вместо баланса). Owner: владелец. Exit condition: отдельная
  задача на контрольную точку цепи, до достижения потолка у реальных
  аккаунтов.
- **20+ мест с полным `getAllKeys`** на путях навигации. Disposition:
  **Contain** — ждут ряда замеров. Exit condition: данные с телефона.
- **Нет сторожа на полные сканы хранилища** — новые `getAllKeys` добавляются
  незамеченными, так их и накопилось 20+. Disposition: **Accept temporarily.**
  Exit condition: сторож после того, как станет ясно, какие сканы допустимы.
- **Табы не размонтируются** (`react-freeze`, `ENABLE_TAB_FREEZE`): накопления
  внутри таба живут до перезапуска приложения. Disposition: **Accept** — это
  осознанное решение против нагрева, менять его нельзя. Следствие: кэши
  обязаны иметь границы сами, на размонтирование рассчитывать нельзя.

## Verification

- Прямой разбор изменённых файлов (тяжёлые прогоны владелец запретил в этом
  заходе; jest/tsc не запускались).
- Замер не выполняется чаще раза в минуту — проверяется ранним выходом по
  `STORAGE_PROBE_MIN_INTERVAL_MS`.
- Замер не ломает навигацию: вызов отложен до конца анимации перехода,
  ошибка ловится и пишет причину (немой catch запрещён).
- Ручная проверка владельцем: пройти по разделам 5–10 минут, открыть журнал
  отладки, прислать строки `[PERF-RELEASE]`.
- Границы кэшей: вытеснение по FIFO, старое значение пересчитывается при
  повторном обращении — корректность не зависит от попадания в кэш.

## Rollback

Обратимо одним `git revert`. Замер — чистое добавление, на данные, экономику и
выданные права не влияет; после отката просто нет строк в журнале. Границы
кэшей меняют только объём памяти: при вытеснении значение пересчитывается тем
же кодом, формат данных на диске не затрагивается, миграций нет.
