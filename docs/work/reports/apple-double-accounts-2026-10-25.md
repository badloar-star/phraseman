# «Двойники» Apple у владельца — разбор (5 · ВХОД, 25.10.2026)

Изучение без правок кода и без записей в прод. Прод — только чтение: список пользователей Firebase Auth (бесплатно) и
точечные чтения документов. В отчёте только числа и да/нет, без uid и почт. Записи владельца: **A** (users от 11.10)
и **B** (users от 24.10).

## Короткий ответ

**Это не смена Apple ID и не другой клиент Sign in with Apple. Это удаление аккаунта A, после которого 14-дневное
«передумать» оказалось недостижимым.**

1. 23.10 в 09:16 UTC — последний вход в A (Apple, iOS).
2. 23.10 в 09:17:48 по A создана задача удаления: `account_deletion_jobs`, статус `queued`, решение «не гость»
   (`sign_in_provider_apple.com`), срок через 14 дней. В ту же секунду сервер **удалил пользователя Firebase Auth** аккаунта A:
   `functions/src/account_delete.ts`, шаг `auth_release` после `enqueue`.
3. 23.10 в 09:18:08, через 20 секунд, — вход Apple снова. Пользователя Firebase с этим Apple ID уже нет, поэтому Firebase
   создал **нового** пользователя B (сейчас у него Apple + Google). Для B заведена новая запись users.
4. «Разные providerUid» — это не идентификатор Apple. В наших `auth_links` и `linkedAuth` поле `providerUid` хранит
   **uid пользователя Firebase** (`functions/src/auth_identity.ts`: `providerUid: authUid`). Он и должен отличаться:
   старый пользователь удалён, новый создан. Идентификатор Apple (sub) у A сравнить уже нельзя — пользователь A удалён.
5. Окно «Восстановить аккаунт?» не появилось и не появится. Статус удаления (`accountDeleteStatusMine`) и восстановление
   (`accountDeleteRestoreMine`) ищут задачу по `accountDeleteJobId(authUid)` **вошедшего** пользователя. Метки
   `account_deletion_auth_markers` тоже лежат по authUid. У B uid новый, его задачи нет → «удаления нет» → обычный вход
   в новую пустую запись.

**Итог:** обещание владельца от 31.08 («14 дней на передумать, при входе — Восстановить аккаунт?») для аккаунтов
Google/Apple не работает никогда. Пользователя Auth снимаем сразу, а восстановление привязано к его uid.

## Как у нас сопоставляются записи

- **Вход → запись users** — только по uid Firebase. `resolveStableUidForAuth`:
  1. живая `auth_links/{authUid}`;
  2. карта `account_id_index`;
  3. `linkedAuth.providerUid == authUid`;
  4. запрошенный с телефона stable id — только если его владелец этот же uid (иначе `stable_id_mismatch`, телефон
     заводит новую личность).
- **По почте не склеиваем НАМЕРЕННО** — это защита от захвата чужого аккаунта.
- Единственное исключение — `authAppleLinkByVerifiedEmail` (18.10). Он привязывает apple.com к аккаунту с той же
  подтверждённой почтой Google, у которого Apple ещё нет. Если у аккаунта уже другой Apple — отказ `account_has_other_apple`.
  К удалённым аккаунтам не применяется.

## Что происходит при смене способа входа

- **Привязать Google к аккаунту Apple** (или наоборот) — тот же пользователь Firebase, всё сохраняется: прогресс, монеты, Plus.
- **Войти другим провайдером или другим Apple ID, когда пользователя нет** (удалён, или это другой человек) — новый
  пользователь Firebase, новая пустая запись. Прогресс, монеты и админская выдача Plus (`users/{stable}.progress.premium_plan
  = admin_grant`) остаются в старой записи.
- **Plus из магазина** восстанавливается кнопкой «Восстановить покупки»: он привязан к аккаунту магазина.
- **У пары владельца** в обеих записях полей Plus (`premium_plan`, `premium_expiry`, `admin_premium_override`) **нет**, и в
  `admin_log` по этим записям ничего не найдено. Где была админская выдача — нужно уточнить: возможно, на другую запись.
- Прогресс в обеих записях есть: 762 и 773 ключа progress.

## Предложение — как не терять Plus и прогресс

**1. Починить «передумать» для Google/Apple (главное).** Сделать это отдельной задачей, под ревью безопасности.
- При постановке задачи удаления запоминать хэши личностей провайдера из токена: `sha256(providerId + ':' + sub)` из
  `firebase.identities` — Apple sub, Google sub. Почта не используется. Хэши хранить в задаче и в индексе
  `account_deletion_provider_index/{hash}` → jobId. Никакой лишней PII: только хэш, который и так проверяется подписью
  провайдера.
- При входе (`authEnsureStableLink`) смотреть индекс по хэшам личностей нового пользователя: одно точечное чтение на
  провайдера. Есть живая задача в grace → ответ «аккаунт в удалении» → телефон показывает «Восстановить аккаунт?».
- Согласие → `accountDeleteRestoreMine` по задаче из индекса: снимает задачу и перепривязывает `auth_links/{новый uid}`
  к старой записи users. Пустая запись нового входа становится сиротой без данных.
- Доказательство владения — тот же Apple/Google sub, проверенный Firebase. Не почта, поэтому захват невозможен.
- Стоимость Firebase: +1 запись при удалении, +1–2 точечных чтения на вход. Сканов нет.
- Альтернатива — не удалять пользователя Auth до конца grace, а `disabled: true`. Хуже: отключённый пользователь вообще
  не входит (`auth/user-disabled`), значит, нужен неавторизованный путь восстановления. Плюс споры с правилами Apple
  про «удаление сразу».

**2. Случай владельца (A → B).** Только по «да» владельца, это запись в прод.
- Вариант 1 — админская починка: снять задачу удаления A, перепривязать вход B к записи A, запись B оставить сиротой.
  Прогресс B за 23–25.10 при этом не переедет.
- Вариант 2 — оставить B и заново выдать Plus на B через «Пульт».
- Задача удаления A сейчас в grace. Через 14 дней (≈06.11) воркер **безвозвратно** сотрёт A — решить нужно до этого срока.

**3. Остальные 4 задачи в grace.** После починки п.1 эти люди смогут «передумать» при входе. До починки — никто из них
не сможет.
