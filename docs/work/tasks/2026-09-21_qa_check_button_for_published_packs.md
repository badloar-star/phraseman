# Кнопка проверки ИИ у опубликованных наборов

Governance-ID: TG-3316629FE833
Governance-ID: TG-74F42AEED627
Дата: 2026-09-21

Запрос владельца: «вкладка Наборы… я там должен иметь возможность исправлять
так же через ИИ все наборы», «на кнопке активные… там нет кнопки проверить и
исправить». На вопрос про объём: «То же самое, что у заявок».

## Диагноз

Вкладка «Активные наборы» наполняется (проверено: 6 опубликованных наборов,
запрос админки их возвращает). Кнопки проверки там нет по простой причине:
`enhanceCards` (`legacy.html:56519`) обходит ТОЛЬКО `cp-submissions-list` —
список заявок. У опубликованных наборов свой список `cp-active-list` и свои
кнопки (`data-cp-active-open` / `-revision` / `-remove`).

То есть механизма там никогда не было, а не «сломался».

## Outcome

В каждой строке опубликованного набора появляется та же кнопка проверки, что
у заявок. Панель открывается в режиме «опубликованный набор»:
1. «Проверить» → находки ИИ (тот же `adminCommunityPackQaReview`);
2. «Поставить поля на место» — когда поля перепутаны;
3. применение правок идёт через `adminCommunityPackApplyQaFixesToPublished`,
   который двигает реестр дублей той же транзакцией;
4. публикации НЕТ: набор уже в каталоге, правки применяются на месте.

## Scope

### Правится
- `admin/v2/legacy.html`:
  - `enhanceCards` обходит оба списка (заявки и активные наборы);
  - `getRow` умеет отдавать и опубликованный набор (`_communityActivePacksCache`);
  - панель различает режим: заявка или опубликованный набор;
  - `applyFixesAndPublish` для опубликованного зовёт `...ToPublished` и НЕ
    публикует (набор уже в каталоге).

### НЕ трогается
- `functions/src/*` — серверная функция для опубликованных уже написана и
  задеплоена (`adminCommunityPackApplyQaFixesToPublished`).
- Существующие кнопки строки набора («Открыть», «JSON», «На доработку»,
  «Снять с продажи») остаются как есть.

## Architecture

Один механизм на оба списка, а не второй его экземпляр: `enhanceCards`
получает список источников `[{listId, attr, kind}]`. Режим (`submission` |
`published`) хранится в черновике панели и определяет:
- какой callable зовётся при применении правок;
- нужен ли шаг публикации (для опубликованного — нет).

`getRow` сначала ищет в кэше заявок, затем в кэше активных наборов. Порядок
важен: у заявки-правки и набора может совпадать id (`editTargetPackId`),
и заявка в очереди приоритетнее — её решение перезапишет набор.

## Security and privacy

Доступ прежний: обе callable admin-only, `enforceAppCheck: ENFORCE_APP_CHECK_OPENAI`.
В OpenAI уходит только содержимое карточек — `authorStableId`/uid/email не
отправляются (сторожится тестом). Privacy policy правок не требует.

## Technical debt

Кэш активных наборов, как и кэш заявок, не обновляется сам — после применения
правок его нужно перезагружать (`loadActiveCommunityPacks(true)`), иначе
повторит историю с протухшими карточками из
`2026-09-21_qa_stale_cache_after_swap.md`.

данных не менялись; откат возвращает прежний список без кнопки.
