# Runtime, приоритеты и очередь

## Сначала существующая система
В `app/app_resume_policy.ts` уже есть coalescing queue с ключом, cancel и serial drain [C04]. `app/_layout.tsx` имеет несколько bootstrap/preload систем [C03]. Это не доказательство, что они все лишние; это карта точек аудита. Задача — оставить один понятный контракт исполнения, не ещё один framework поверх существующих.

## Предлагаемая иерархия работ
P0: немедленная реакция UI и минимальная локальная гидратация активного экрана. P1: подтверждённое действие пользователя, сохранение результата, критическая авторизация/entitlement. P2: локальное восстановление и запрос необходимых данных активного экрана. P3: отложенная синхронизация, flush и локальное обслуживание. P4: необязательный prefetch и диагностика. Это предложенные приоритеты, которые надо сопоставить с реальным кодом; не утверждение, что такие очереди уже реализованы.

Не помещать всю сеть в длинную глобальную последовательную цепь: это создаст head-of-line blocking. Конкурентность ограничивать отдельно для сетевых загрузок, дисковых записей и аудио. Общий durable write path имеет приоритет над prefetch. Нужны дедупликация, fairness, deadline, cancellation, retry с пределом и владелец результата. Цифры лимитов выставить после baseline, не по вкусу.

## Карточка job
`id`, `featureOwner`, `codePath`, `trigger`, `scope(account/locale/screen)`, `priority`, `dedupeKey`, `ttl`, `maxConcurrent`, `timeout`, `retryLimit`, `cancelOn`, `reads/writes/bytes`, `cpu/memory`, `observableErrors`, `keep/remove/archive`, `auditSHA`. Шаблон в registries; нет job без регистрации. На микроправку кнопки обычно пишется «существующий job не меняется, новых нет», а не запускается новый фоновый pipeline.

## Старт и возврат
Первый полезный экран не должен ожидать достижения/ауры/спины/league/background AI. Не грузить packs неактивного V2 на холодном старте. Не выполнять сеть в module evaluation. Account generation и нужная восстановительная защита сохраняются. При смене аккаунта/языка/экрана запросы не применяют старый результат. Отменённый UI consumer не уничтожает обязательную durable запись.

Кешированный экран показывается вместе с честным состоянием freshness. Ошибка не превращается в вечный skeleton и не скрывается для «премиального» вида. Empty и unavailable различаются. Возврат из фона оставляет время касанию/первому кадру; задержки 900/2500ms в просмотренном коде не объявляются идеальными без измерения.

## Измерения
Release build на реальном слабом телефоне; одинаковый сценарий/сеть/данные, несколько запусков и p50/p95. Метрики: cold/warm start до действия, resume, tap-to-feedback, навигация, scroll, peak memory, pending jobs, JS/native/assets bytes. Кандидатные регрессионные пороги задаются отдельно после baseline, не скрываются под обещанием «летает». Dev Metro bundling 34 секунды и runtime startup 2 секунды — разные измерения.

## Очистка bundle
Инвентаризировать static/dynamic imports, router auto-discovery, native packages, embedded assets и manifests. Выключенный flag не гарантирует исключение. Архивы Макса и генераторов вне release roots. Удаление большого временного файла из git не доказывает уменьшения установленной сборки. Нельзя удалять библиотеку анимации, если она ещё обслуживает нужную навигацию.

Сравнивать production/release сборки в одинаковых условиях; developer overhead не принимать за пользовательский baseline. Официальный обзор React Native отдельно рассматривает JS и UI frame rate и рекомендует release-проверки [W12]. Конкретные пороги устанавливаются по фактическим устройствам, а не переносятся из комментариев старого кода.
