## 2. Архитектура опоры под капотом (файлы и их роль)

### 2.1. Приём почты
- **`functions/src/support_inbox.ts`** (~6800+ строк после правок сессии) —
  главный файл всего конвейера. Читает почту через IMAP, классифицирует,

  отправляет письмо через SMTP.
- Коллекция Firestore: `support_inbox` (документ на письмо).
- Триггер: `supportInboxOnNewMail` — Cloud Function `onDocumentCreated` на
  `support_inbox/{messageDocId}`.
- IMAP-опрос входящих: крон `gmailSupportPullCron` (см. `index.ts`).

### 2.2. Классификация риска

  возвращает `'safe' | 'billing' | 'account' | 'legal' | 'privacy' | 'safety' | 'security'`.
  Регулярки на ключевые слова (RU/EN/ES). См. строки ~14, ~112.
- Специальные быстрые маршруты (bypass модели, готовый текст):
  - `isPremiumAlternativePaymentQuestion` / `buildPremiumAlternativePaymentReply`

  - `isPaymentCountryQuestion` / `buildPaymentCountryReply` — **НОВОЕ**,

### 2.3. Текст вопроса без цитат — `supportIssueText()`
- **`functions/src/support_inbox.ts`**, строки ~330 (объявление функции).
- **КРИТИЧНО ПОНИМАТЬ**: письмо клиента в Gmail может содержать ВСЮ
  историю переписки в виде `>`-цитат. Замер на реальном письме показал
  **472 строки, 461 из них (98%) — цитаты**, новый вопрос — 544 символа
  из 14817. Слова из старых цитат («Plus», «оплата», «Россия») ловились
  классификатором риска и уводили ответ не по теме.
- `supportIssueText(doc)` = `subject + '\n' + (stripQuotedTail(bodyText) || bodyText)`
  — откат к полному телу, если после чистки текста не осталось (письмо
  состояло из одной цитаты целиком).
- **Заведено 16 мест** в `support_inbox.ts`, где раньше строился текст
  вопроса напрямую (`${doc.subject}\n${doc.bodyText}`) — все переведены на
  `supportIssueText()`. Если добавляешь новое место, где нужен текст вопроса
  для классификации/поиска по коду — **обязательно используй эту функцию**,
  не собирай строку заново.
- Используется в `classifySupportRisk()`, `retrieveSupportRepositoryContext()`,
  `isPremiumAlternativePaymentQuestion()`, `renderOwnerStyleForIssue()` и др.

### 2.4. Отсечение цитат — `stripQuotedTail()`
- **`functions/src/support_owner_style.ts`**, строка 44.
- Изначально писалась ТОЛЬКО для чистки писем владельца из Sent (для
  обучения), потом (см. 2.3) стала общей утилитой и для входящих писем
  клиентов через `supportIssueText`.
- Распознаёт 4 формата обрыва цитаты:
  1. Строка начинается с `>`.
  2. Шапка Gmail RU/EN/ES вида «вт, 11 авг. 2026 г., 23:20 Имя <почта> писал:»
     — регулярка на ХВОСТ строки (`писал:|wrote:|escribió:`), не на начало,
     потому что русская шапка начинается с дня недели, а не с даты.
  3. Второй вид шапки БЕЗ слова «писал», Gmail иногда обрезает на адресе:
     «вт, 11 авг. 2026 г., 23:20 Имя <почта>:» — найдено на РЕАЛЬНОМ письме
     из прода, синтетический тест этого не ловил.
  4. `-- Original Message --` / `-- Пересылаемое сообщение --`.

- **`functions/src/support_owner_style.ts`** — чистый модуль (без Firestore).
- **`functions/src/support_inbox.ts`**, строки ~1228–1439 — Firestore-обёртка.
- **ПОЛНАЯ ЦЕПОЧКА (проверена чтением кода строка за строкой в этой сессии):**

  1. **Крон `gmailSupportOwnerReplyDetectionCron`** (`functions/src/index.ts`,

  3. `fetchOwnerSentRepliesViaImap()` (`support_inbox.ts:1228`) — открывает
     папку `[Gmail]/Sent Mail` через IMAP, читает письма после checkpoint UID
     (`imapSentLastUid` в `admin_config/support_inbox`), парсит заголовки
     `In-Reply-To`/`References`, применяет `stripQuotedTail()` к телу.
  4. Для каждого письма: `candidateOpenThreadDocIdsForOwnerReply()`
     (`support_inbox.ts:401`) — сопоставляет `In-Reply-To`/`References` с

  5. **ДВЕ операции на каждого кандидата, порядок важен:**
     - `closeOpenThreadForOwnerReply(db, candidateId)` — если тред ещё

       после этого бот НИКОГДА не отвечает в этом разговоре, см. 2.6).
     - `rememberOwnerStyleExample(db, candidateId, reply.bodyText)` —
       вызывается **ДО проверки, закрылся ли тред** (`didClose`). Комментарий
       в коде на строке ~1330 объясняет: «ответ владельца ценен как образец
       голоса НЕЗАВИСИМО от того, был ли тред ещё открыт». Значит учится
       даже на письмах, которые владелец закрыл вручную раньше или на
       которые уже ответили.
  6. `rememberOwnerStyleExample()` (`support_inbox.ts:1414`):
     - Читает документ `support_inbox/{messageDocId}`.
     - **⚠️ НАЙДЕННЫЙ, НО НЕ ИСПРАВЛЕННЫЙ ДЕФЕКТ** (строка 1425):
       ```ts
       const question = `${message.subject ?? ''}\n${message.bodyText ?? ''}`.trim();
       ```
       Это НАПРЯМУЮ конкатенация полей, БЕЗ вызова `supportIssueText()` /
       `stripQuotedTail()`. Если письмо клиента, на которое отвечал владелец,
       само содержало длинную цепочку цитат — «вопрос» в сохранённом примере
       обучения будет содержать эти цитаты как часть вопроса. Не критично
       (это только контекст в промпте, не факт, который уходит клиенту),
       но нарушает принцип «одна точка правды для текста вопроса», который
       был наведён во всём остальном файле. **См. раздел 6, пункт про
       доработку.**
     - `isUsableOwnerStyleExample()` (`support_owner_style.ts:77`) — фильтр:
       ответ 80–1800 символов, вопрос ≥20 символов, не автоответ/пересылка.

       `SUPPORT_OWNER_STYLE_COLLECTION`, `support_inbox.ts:1348`), ключ
       документа = `messageDocId` (идемпотентно при повторном прогоне).
  7. **Чтение при генерации нового ответа** — `renderOwnerStyleForIssue()`
     (`support_inbox.ts:1373`):
     - Кэш на 30 минут в памяти инстанса (`OWNER_STYLE_CACHE_TTL_MS`).
     - Читает до 60 последних примеров (`OWNER_STYLE_KEEP_LIMIT`), сортировка
       `orderBy('savedAtMs', 'desc')`.
     - `selectOwnerStyleExamples()` (`support_owner_style.ts:111`) — отбирает
       топ-5 (`OWNER_STYLE_EXAMPLE_LIMIT`) БЛИЗКИХ ПО ТЕМЕ примеров: простое
       пересечение слов ≥4 символов между текстом нового письма и
       `question+answer` каждого примера, при равенстве — более свежий.
       Специально НЕ эмбеддинги/векторный поиск — владелец объяснил, что
       десятки писем не требуют такой инфраструктуры.
     - `renderOwnerStyleExamples()` (`support_owner_style.ts:135`) — рендерит

       и манеру — но НЕ переноси факты, суммы, имена и обстоятельства из

  8. **Единственная точка вставки в промпт** — `support_inbox.ts:929`
     (внутри `buildGroundedReplyResult`, вызывается из
     `buildCouncilReviewedSupportReply`):

     ...

     Проверено грепом по всему файлу — `renderOwnerStyleForIssue` вызывается

## 3. Основная проблема сессии (то, ради чего всё это делалось)

Владелец обнаружил на реальных письмах клиентов серию симптомов, которые
складывались в одну картину: **Джарвис читал письма, но систематически не
понимал их и отвечал не по делу, либо не отвечал вовсе, либо отвечал, но
ответ терялся технически.**

### 3.1. Классы найденных проблем (по возрастанию серьёзности находки)

1. **Молчание вместо ответа.** Причина — я сам записал `admin_config/support_inbox.supportOwnerInstructions`
   НАПРЯМУЮ в Firestore консольным скриптом в предыдущей сессии, в обход
   штатного `adminSupportSaveInstructions`, и не заполнил обязательные поля
   (`promptVersion`, `fingerprint`). `parseSupportOwnerInstructions()` бросал
   исключение на каждом письме → падение в `retry` с кодом
   `support_instructions_unavailable`. **Это моя ошибка, не архитектурная.**
   Исправлено скриптом `scripts/repair_support_owner_instructions.mjs`.

2. **Ответ не по теме (98% письма — цитаты).** Разобрано в разделе 2.3/2.4
   выше. Это архитектурная находка — класс дефекта, а не разовая ошибка.

3. **«Одобрено», но письмо не уходит.** Причина: отпечаток кодовой базы
   (`knowledgeFingerprint`) считался по ВСЕЙ кодовой базе и менялся при
   КАЖДОМ деплое функций (в том числе не связанном с этим письмом). Владелец
   нажимал «Одобрено», но за 10 секунд между подготовкой и подтверждением
   успевал пройти чужой деплой → отпечаток расходился → отправка отменялась
   с кодом `support_knowledge_changed`. **Три нажатия владельца сгорели
   именно так, и виноваты были МОИ ЖЕ деплои в течение того же дня.**
   Исправлено: для промежуточных (`holding`) ответов проверка отпечатка
   пропускается вовсе (они не утверждают фактов о продукте — устаревать
   нечему); для обоснованных ответов добавлен отдельный отпечаток
   `evidenceFingerprint`, считающийся ТОЛЬКО по процитированным фрагментам
   кода, а не по всей базе.

4. **Мёртвые карточки в Telegram** — раздел 2.9 выше.

5. **Заготовка вместо ответа по существу.** Владелец увидел письмо клиента
   Шухрата с вопросом «в какую страну идёт платёж, если оплачу?» — Джарвис
   ответил шаблоном «поднимем вашу покупку, ответит человек» — шаблоном,
   написанным для ЖАЛОБ на списание денег, а не для факта, который известен
   заранее. **Это была ПОСЛЕДНЯЯ капля**, после которой владелец потребовал
   («НЕ ДОЛЖНО БЫТЬ ЗАГОТОВОК!!!!!!») полностью убрать шаблонные тексты
   клиенту и заменить их эскалацией владельцу с полным текстом письма —
   см. коммит `3fb844fe7`, раздел 4.5 и раздел 0 (про рассинхрон с продом).

### 3.2. Общая закономерность, которую стоит держать в голове

Все находки, кроме №1 (моя разовая ошибка) и №3 (тоже отчасти моя ошибка
деплоями), — это случаи, когда **классификатор смотрел на весь текст, а не
на то, что реально спросил человек**, либо когда **техническая проверка
(отпечаток, TTL, номер сообщения) была спроектирована для одной ситуации
(обоснованный факт из кода) и молча ломала другую (промежуточный ответ,
человеческое нажатие кнопки)**. При любой новой находке в этой системе
первым делом стоит спросить: «эта проверка/классификатор смотрит на то,
что реально хотел сказать человек, или на артефакт (цитаты, отпечаток кода,
номер сообщения), который к сути вопроса не относится?».

## 7. Общие уроки этого проекта (не специфично для этой сессии, но важно)

- **Класс бага «расходящиеся копии одной проверки».** Минимум трижды за
  сессию находилась одна и та же логическая ошибка: правило/регулярку/
  проверку копировали в 2–4 места вместо одной общей функции, потом чинили
  ОДНО место и забывали остальные. Явный пример — `isSupportEmailDepartment()`
  в `support_telegram_review.ts`, комментарий там прямо предупреждает: «это
  была ЧЕТВЁРТАЯ копия одного правила». При любой находке в этом коде
  СНАЧАЛА грепать по всему `functions/src/`, есть ли похожий код в другом
  месте, и чинить ОДНОВРЕМЕННО везде или выносить в общую функцию.
- **Регулярки с `\b` не работают с кириллицей в JavaScript.** Дважды за
  сессию (в `FORBIDDEN_ASSERTIONS` и в `GREETING_OPENER`) весь русский
  вариант правила молча не работал из-за внешнего `\b` на всей группе. При
  написании regex с русским и английским текстом — `\b` можно ставить ТОЛЬКО
  вокруг латинских альтернатив, никогда вокруг группы, содержащей кириллицу.
- **Параллельные сессии Claude Code работают в этом же дереве.** Минимум
  дважды за день git-индекс блокировался чужим процессом
  (`.git/index.lock`), и минимум один коммит содержал файлы из чужой
  области (`de13495eb` содержал чужую сборку `learning-v2` под моим
  сообщением коммита — не заметил при коммите). **Перед каждым коммитом
  проверять `git status`/`git diff --stat` на предмет посторонних файлов.**
- **Владелец крайне чувствителен к битым ссылкам и заготовкам.** Оба этих
  класса проблем существовали ГОДАМИ (ссылка `/help` никогда не вела никуда)
  прежде чем он их заметил — стоит на будущее ПРОАКТИВНО грепать любые
  адреса и шаблонные тексты, уходящие клиентам, а не ждать, пока он найдёт
  их сам открыв письмо.
- **Собранный рантайм (`functions/lib/`) НЕ отслеживается в git**
  (`.gitignore:246`) — деплой пересобирает сам. Коммит, который случайно
