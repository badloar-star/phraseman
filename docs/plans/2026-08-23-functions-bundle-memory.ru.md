# Память бандла Functions: почему функции не стартуют. 2026-08-23

## Что случилось

`maxVoiceFinalize` была создана в проде 22.08 и **ни разу не запустилась**:
Cloud Run отклонял каждый старт — `Memory limit of 256 MiB exceeded with
258-277 MiB used`, `STARTUP TCP probe failed`. Деплой при этом рапортовал
успех. Сутки не работали разборы уроков MAX и пост-скан безопасности.

## Корень (замерено, не предположение)

Cloud Functions gen2 при старте **любого** контейнера загружает `index.js`
целиком — со всеми **240 экспортируемыми функциями** и **853 модулями**
бандла, чтобы найти нужную точку входа. Замер:

```
baseline node                         48 МБ
+ firebase-admin                      59 МБ
+ firebase-functions/v2               67 МБ
+ require('lib/functions/src/index')  360-369 МБ   ← старт любой функции
```

То есть **любая** функция с лимитом 256 MiB рискует не стартовать.
`maxVoiceFinalize` просто оказалась первой новой функцией после того, как
бандл перевалил за порог.

## Что сделано

1. `maxVoiceFinalize`: `memory: '512MiB'` (коммит ec5f11e23). Проверено живым
   вызовом: HTTP 401 `auth_required` за 0.5 с — контейнер стартует.
2. `support_repository_context.ts`: снимок 17 МБ (`support_repo_context.json`)
   больше не парсится на верхнем уровне модуля, читается лениво с кэшем
   (коммит 9bf803a0c). Замер импорта модуля: **+40 МБ → +0 МБ**. Тесты
   поддержки 91/91 зелёные.

3. `supportInboxOnNewMail`: память задана явно `512MiB` (коммит 29b127b46).
   Логи 20.08 показали, что она **уже падала** — `Memory limit of 256 MiB
   exceeded with 260-269 MiB used`, причём НЕ на старте, а во время разбора
   письма (`probe succeeded`, затем ошибка). То есть проблема задевала
   обработку писем поддержки ещё до истории с MAX.

Ленивая загрузка снимает 40 МБ, но общий вес бандла остаётся ~340-360 МБ:
его набирают сотни модулей и их зависимости, а не один файл. Поэтому
`256MiB` в этом проекте больше НЕ является рабочим лимитом ни для одной
функции: замер `require(index.js)` даёт 336 МБ RSS даже при
`--max-old-space-size=200`.

## Открытый риск (важно)

**В проекте 33 функции с `memory: '256MiB'`.** Сейчас они работают на старых
образах и не перезапускались, ошибок в логах нет. Но при следующем
передеплое любая из них может не подняться — ровно как `maxVoiceFinalize`.

Проверять после КАЖДОГО деплоя новой/изменённой функции:
```bash
npx firebase functions:log --only ИМЯ --project phraseman-ea0b3 | grep -i "memory limit\|probe failed"
```
и делать живой вызов — «Deploy complete» не означает, что функция работает.

## Варианты лечения (решение владельца)

1. **Поднять память проблемным функциям до 512 MiB по мере необходимости** —
   дёшево в работе, но удваивает цену GB-секунды точечно. Так сделано сейчас.
2. **Разделить `index.ts` на несколько кодбаз** (`firebase.json` → несколько
   записей `codebase`): каждая функция грузит только свой поднабор модулей.
   Радикально решает корень, но это крупный рефакторинг с риском задеть все
   240 функций — отдельной задачей, не попутно.
3. **Проверить `minInstances`-функции особо**: у тёплого инстанса перезапуск
   происходит незаметно, и падение по памяти проявится как «функция пропала».
