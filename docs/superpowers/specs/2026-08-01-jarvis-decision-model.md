# Джарвис v2 — модель решений (проект)

> Проектный документ. Не код, не запуск сервисов, не изменение production.
> Основание: `docs/superpowers/plans/2026-07-28-jarvis-agent-office-plan.md` (утверждённый план владельца).
> Решение владельца 2026-08-01: существующий `agent_office` и `agent_manager` **сносятся**,
> модель решений проектируется **заново**. Первый видимый рубеж — панель в живой админке.

## 1. Зачем заново

Аудит написанного (2026-08-01) показал, что переиспользование невозможно:

| Что заявлено | Что в коде |
|---|---|
| Наблюдение за приложением | `source_adapters.ts:29` — живого читателя Firestore **нет**, коллекторы надо инжектить, «общего внутреннего шва» не существует |
| Структурный совет | Нет. Есть три жёстко зашитых сигнала и один `actionType: 'analysis_prepare'` |
| Диалог текстом в Telegram | Нет. Обработчик принимает **только** `callback_query` вида `ao1:a:<nonce>` |
| Команды `/status` `/brief` `/tasks` `/stop` | Нет |
| Панель в живой админке | Нет. `admin-agent-office.mjs` — 43 строки чистых валидаторов, без UI, и лежит в замороженной админке |
| Один агентный слой | Два: `agent_office` и `agent_manager`, разные ledger'ы, общий вебхук на `ao1`/`am1` |

Ценное, что подтверждено аудитом и переносится **как принцип, не как код**:
fail-closed на неполных данных, запрет прямого браузерного доступа к агентным коллекциям,
одноразовые approval-токены с TTL, отделение owner-привязки от браузерно-редактируемого конфига.

## 2. Границы (из утверждённого плана, не пересматриваются)

- Режимы: `off` → `observe` → `advise` → `prepare` → `execute`.
- Merge/deploy — только по отдельному одноразовому approval на точный PR SHA + окружение.
- Никогда не автоматизируются: Firestore Rules, auth, деньги, права, удаление, рассылки пользователям.
- В модель и в Telegram не уходят PII, секреты и полный текст репортов.
- Бюджет: €50/мес, €1 обычная задача, €5 глубокая.
- Telegram-бот — **тот же**, что шлёт алерты (`ADMIN_ALERT_BOT_TOKEN`). Подтверждено владельцем 2026-08-01.

## 3. Ядро модели: Decision

Единица работы — **решение** (`decision`), а не «кейс» и не «рекомендация». Одно решение
проходит путь целиком и всегда одинаково выглядит в админке и в Telegram.

```
Decision
├─ id, revision, contentHash        — версионирование, защита от гонок
├─ mode                             — режим, в котором решение создано
├─ trigger                          — что его породило: signal | owner_request
├─ question                         — вопрос владельца или название сигнала
├─ evidence[]                       — доказательства (см. §4)
├─ finding                          — ФАКТ: что наблюдается, только из evidence
├─ hypothesis                       — ГИПОТЕЗА: чем объясняется
├─ options[2..3]                    — ВАРИАНТЫ, каждый со своей ценой и риском
├─ recommendation                   — какой вариант и почему
├─ risk                             — что может пойти не так
├─ cost                             — € и время
├─ successMetric                    — по чему поймём, что сработало
├─ rollback                         — как откатить
├─ confidence                       — 0..1, падает при неполных данных
├─ constraints[]                    — ограничения владельца («не трогай paywall»)
└─ status                           — draft → awaiting_owner → approved | rejected | expired
```

**Жёсткое правило:** `finding` не может утверждать ничего, чего нет в `evidence[]`.
Если доказательств не хватает — решение рождается со статусом `insufficient_evidence`,
и это видно и в панели, и в Telegram. Ложный ноль запрещён: отсутствие данных
никогда не рендерится как «0», только как «нет данных».

## 4. Evidence — доказательства

```
Evidence
├─ sourceId          — имя источника (не путь к документу)
├─ state             — ready | empty | partial | error | stale | truncated
├─ observedAtMs      — когда снято
├─ count | null      — null, если состояние не даёт права утверждать число
├─ truncated         — упёрлись ли в лимит
├─ droppedCount      — сколько отброшено (иначе выводы врут)
└─ digest            — безопасная агрегированная проекция, без PII и без текста репортов
```

`digest` — единственное, что уходит в модель и в Telegram. Сырые документы не покидают сервер.

## 5. Источники и как читаются (Firebase-экономия)

Читатель обязан быть **один** — общий внутренний шов, которого в старом коде не было.

| Группа | Коллекции | Правило чтения |
|---|---|---|
| Сигналы качества | `error_reports`, `user_reports`, `app_errors` | `where` по времени + `limit`, инкрементальный курсор |
| Деньги | `paywall_funnel`, `revenuecat_premium_events` | только агрегаты, окно «текущий период vs предыдущий» |
| Активность | `users`, `app_activity` | только счётчики, никогда не выгрузка коллекции |

Обязательно:
- **Снапшот раз в N часов**, не по запросу панели. Панель читает готовый снапшот, а не считает на лету.
- **Курсор** вместо повторного вычитывания окна.
- **Никаких `onSnapshot`** на агентные коллекции ни на сервере, ни в браузере.
- Каждое чтение оставляет `Evidence` с честным `state` — включая `error` и `stale`.

## 6. Диалог: текст → задача

Чего в старом коде не было совсем.

| Владелец пишет | Что происходит |
|---|---|
| «Проверь падение retention за неделю» | новое `Decision`, trigger = `owner_request` |
| «Почему выросли ошибки оплаты?» | `Decision` со `finding` + источниками, без предложения действий |
| «Подготовь PR для исправления» | `Decision` в режиме `prepare`, требует approval до любой записи |
| «Не трогай paywall» | `constraint` добавляется к активному решению, не создаёт новое |

Команды: `/status`, `/brief`, `/tasks`, `/stop`, `/approve <код>`, `/reject <код>`.

Защита диалога:
- только owner user id + приватный чат, всё остальное молча отбрасывается;
- rate limit и quiet hours;
- дедупликация по `update_id` — повторная доставка ничего не меняет;
- свободный текст **никогда** не запускает внешний эффект сам по себе.

## 7. Approval

Наследуем проверенную схему, но пишем заново:
- одноразовый, TTL 15 минут, привязан к owner user/chat;
- содержит `decisionId` + `revision` + `contentHash` — изменилось решение, approval недействителен;
- для merge/deploy дополнительно: PR SHA, окружение, health gate, rollback plan;
- потребление идемпотентно: повторное нажатие не меняет состояние.

## 8. Панель в живой админке

**Только `admin/v2/legacy.html`** — единственная рабочая админка (CLAUDE.md).
Замороженные `admin/v2/index.html`, `admin/v2/scripts/*` не трогаются и не переносятся.

Панель показывает:
- список решений со статусом, свежестью и confidence;
- раскрытое решение: факт → гипотеза → варианты → рекомендация → риск → цена → метрика → откат;
- источники каждого доказательства с честным состоянием;
- kill switch и текущий режим;
- журнал аудита.

Требования к панели:
- данные только через callable, прямого Firestore из браузера нет;
- ленивая загрузка — не утяжелять старт админки (файл уже ~38 600 строк);
- кэш + ручное обновление, без автополлинга;
- **optimistic UI**: approve/reject и kill switch красят состояние мгновенно, откат при ошибке,
  защита от двойного нажатия, поздний ответ не затирает свежее значение;
- empty/error/stale состояния явные, ложный ноль запрещён;
- дизайн по правилам владельца: без обводок контейнеров, без мелких подписей-расшифровок.

## 9. Порядок работ

| Рубеж | Содержание | Готово, когда |
|---|---|---|
| Р0 | Этот документ + TDD-план Фаз 0–2 | План утверждён владельцем |
| Р1 | Новая модель + единый читатель источников, TDD | Тесты: ложный ноль невозможен, неполные данные роняют confidence |
| Р2 | Панель в `legacy.html` на новых данных | Владелец видит реальные решения в живой админке |
| Р3 | Диалог в Telegram (текст + команды + approvals) | Одинаковое состояние в Telegram и админке, повтор не меняет состояние |
| Р4 | Снос старых `agent_office` и `agent_manager` | Функции удалены из `index.ts`, деплой зелёный, Rules сохранены |
| Р5+ | Подготовка кода, merge/deploy по approval | По утверждённому плану, Фазы 3–4 |

**Снос — последним.** Оба слоя экспортируются из `functions/src/index.ts:451-480`;
удаление до готовности нового ломает деплой всех функций.

## 10. Открытые вопросы к владельцу

1. **Owner Telegram ID** (числовой user id + chat id) — без него диалог и approvals не включаются.
2. **Список production environments** — что считается «боевым» в approval на deploy.
3. Какие сигналы владелец хочет видеть первыми: деньги, ошибки, retention — порядок важен для Р1.
