# Миграции, компенсация и работа с Git

## Что нельзя потерять
Собственные карточки/наборы, учебный прогресс, купленный доступ, действующая подписка, реальные остатки, запись pending операции, работы Learning V2 и законсервированные генераторы/Макс. Удаление старого UI не доказывает разрешение удалить всё, что использовало его название.

## Матрица перехода
Жемчуг → остаток ×10 монет один раз. Руны → целевой кошелёк без умножения/двойной записи; точное сопоставление поля после аудита. Старые диалоговые unlocks → grandfathered rights либо явное решение. Старые уроки/оценки → progress и rights без молчаливого ухудшения. Косметика/boosts/card tiers → индивидуальная политика ledger, не автоматическая универсальная 1:10. Энергия 100+/модификаторы → новый state и согласованное разовое заполнение/компенсация. Local scheduled notifications → отменить удалённые типы. Theme/avatar IDs → безопасный coin/default fallback.

## Безопасный rollout
Версия схемы, migration ID/idempotency, dry-run на копии, объём затронутых записей и стоимость. Снимок и восстановление проверены. Релизные флаги/совместимость старого клиента определены ДО записи новых схем. Нет двух неконтролируемых writers старого/нового кошелька. Два устройства, offline queued writes, повтор миграции, downgrade, смена аккаунта, refund и restore проверены.

Rollback кода не всегда откатывает схему. Нужно определить обратимый период, условия запрета downgrade, совместимые readers и план восстановления данных. Purge отложить до прохождения этих gates, но не хранить лишние персональные данные бессрочно.

## Одна каноническая ветка
Цель принимается, способ не разрушительный. Инвентаризация remote/local branches, unique commits, active worktrees, незакоммиченные изменения и PR. Выбрать base по фактическому release/work tree, не по слову master. Нужные изменения перенести/объединить, проверить. Историю законсервированных работ сохранить вне активного release graph, при необходимости в проверенном Git bundle/приватном архиве.

До удаления показать точный список веток, SHA, судьбу уникальных коммитов и проверенный архив. Отдельное подтверждение перед выполнением. Не включать массовую команду удаления в автоматический setup. После — сверить remote/local refs и возможности восстановления. Содержимое архива само по себе не мешает иметь одну активную рабочую ветку.

В этой сессии branches/data/deploy не менялись. Этот пакет не заменяет ledger покупателей и не является выполненной миграцией.

## Консервация Арены и Макса: фактический формат (PM-238)

Статус на 2026-10-02. Это описание того, что УЖЕ сделано (D10, D74, D78, D81, D83 и пломба MAX от 2026-09-04), а не новое действие. Ничего не восстанавливается и не распечатывается: Арена удалена, MAX запломбирован, возврат — только по прямой команде владельца.

### Арена — удалена из релиза, источники в Git
- Клиент (экраны, маршруты, `app/arena_*` 21 файл, `components/arena` 34 файла, хуки, ассеты рангов и звуков) удалён целиком в `efe19ae9d` (общий снимок 2.0, 2026-09-30). Сторож: `tests/d83_arena_client_deleted.probe.ts` (PASS).
- Сервер: реализация (`arena_v2.ts`, `arena_expansion.ts`), надгробия `arena_retired.ts` и все arena-callable/cron/trigger сняты с точки входа деплоя. Живыми остаются только 8 админских функций пула заданий (`adminArenaConfig*`, `adminArenaContent*`, `adminArenaPublication*`): ими питается Шпиль. Сторож: `tests/d74_arena_server_retired.probe.ts` (PASS; 8 экспортов, 17 удалённых модулей).
- Генераторы и пул остались на диске в `functions/src` (`arena_*`, `tournament_*`, `admin_tournament_*`, всего 177 файлов `arena|tournament|max_*`), потому что Шпиль импортирует `tournament_core` и `tournament_pool_publication`. Они не экспортируются как функции: в release graph (деплой и бандл клиента) не входят.
- Клиентские модули Арены, которые нужны Шпилю и Learning V2, перечислены в `KEPT_ARENA_MODULES` пробы D83: `answer_check`, `contract`, `sound_catalog`, `target_registry`.

### MAX — запломбирован, исходники сохранены
- Клиентский MAX удалён (D81): экраны `app/max_*`, флаги, орб, маршруты. Сторож `tests/max_section_sealed_contract.test.ts` (4/4) требует, чтобы клиентского кода MAX не было вовсе.
- Сервер: все функции сняты с деплоя; `functions-max/index.ts` экспортирует только маркер пломбы `MAX_SECTION_SEALED_BY_OWNER_2026_09_04` из `functions/src/max_section_seal.ts`. Кроны, инстансы и расходы OpenAI не работают. Исходники серверной части (`functions/src/max_voice_*`, `max_lesson_reminder_push`) лежат на диске, секретов в них нет.
- Jarvis и кодбаза MAX используют одну пломбу (`maxvoice_department`, `maxvoice_snapshot`).

### Где хранится удалённое и как восстановить (по команде владельца)
- Тег `archive/arena-max-pre-removal-2026-09-30` → `1e2f77929` (родитель `efe19ae9d`): последний коммит, где клиент Арены и клиентский MAX ещё целы. Тег локальный; ссылка защищает коммит от сборки мусора, push тега делает владелец.
- Полное дерево Арены на момент завершения: тег `orbit/snapshot-20260718-arena-complete` (`8f4771b0e`).
- Просмотр без изменения рабочего дерева: `git show 1e2f77929:app/arena_client.ts`, `git ls-tree -r --name-only 1e2f77929 -- components/arena`.
- Восстановление файла: `git restore --source=1e2f77929 -- <путь>` (только по команде владельца и в отдельной сессии).
- Возврат MAX: порядок в шапке `functions-max/index.ts` и `CLAUDE.md` (снять пломбу, раскомментировать экспорты, задеплоить кодбазу `max`, удалить сторож). Перед возвратом исправить причину: 59% звонков заканчивались на нуле секунд.
- Возврат Арены: не планируется (D54, D74, D78, D83 заменяют её Шпилем). Её контракты (`arena_v2_core`, `arena_config_contract`) устарели относительно Шпиля и до возврата требуют отдельного аудита.
