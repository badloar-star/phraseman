# Программа «Бандл-диета»: JS-бандл 55 → 15–20 МБ, APK 165 → ~95 МБ

Дата: 2026-08-24. Владелец: цель — супермалый бандл (10–20 МБ), при этом
пользователь НИКОГДА не видит незагруженный контент: всё прогружается заранее.

## Точка отсчёта (аудит 2026-08-24, замерено по реальным артефактам)

| Компонент release-APK | Вес | Комментарий |
|---|---|---|
| JS-бандл (Hermes) | **55.3 МБ** | норма для RN — 5–10 МБ; раздут контентом в коде |

## Фаза 1 — plan_content_* вон из бандла (−19 МБ JS) 🔜 ГЛАВНАЯ

Инфраструктура УЖЕ ЕСТЬ и включена (`VERIFIED_COURSE_PACK_REMOTE_ENABLED = true`):
`course_pack_remote_loader.ts` (скачивание + дисковый кэш + sha256 + evict),
`plan_content_remote_readiness.ts` (сервер → кэш → bundled-фолбэк),
`course_pack_manifest.ts` (валидация манифеста). Не хватает трёх шагов:

1. **Экспортёр**: скрипт `scripts/export_plan_content_packs.mjs` — читает
   `plan_content_{mitap,gavan,impuls,echo,voyazh}.ts`, пишет пак:
   `manifest.json` (buildCoursePackCacheKey-совместимый) + `index.json` +
   `plans/<plan>/day-NNN.json` (формат уже зашит в rowPathFor:
   `plans/${planId}/day-${NNN}.json`, контент — `{contentHash, content}` под
   `readVerifiedCoursePackDay`).
2. **Выгрузка в Firebase Storage** (`plan-content/<hash>/...`) — по образцу
   ранее использованного upload_plan_audio_to_storage. Storage+CDN, json.gz,
   0 чтений Firestore: клиент качает по манифесту один раз на версию.
3. **Префетч-оркестровка** (чтобы юзер НИКОГДА не увидел дыру):
   - холодный старт: после первого кадра, в idle — `ensureRemoteCoursePack`
     ТОЛЬКО для активного плана пользователя; затем лениво day-rows ±2 дня
     от текущего (каждый ~50 КБ);
   - покупка/выбор плана: сразу фоновый префетч всех дней плана
     (84 × ~50 КБ ≈ 4 МБ, wifi-friendly), тихий прогресс в карточке плана;
   - вход в день: `resolveRemoteOrBundledPlanContentDay` уже отдаёт кэш
     мгновенно; не в кэше → скелет с зарезервированной геометрией (Performance
     Bible) + догрузка одного дня <1 c, ретрай, офлайн-сообщение только когда
     нет НИ кэша, НИ сети;
   - версии: смена манифеста → фоновая догрузка новой версии, старый кэш
     живёт до полной готовности новой (никаких дыр при обновлении контента).
4. **ФИНАЛ (после проверки на устройстве, отдельный коммит-переключатель):**
   выпилить 5 require из `plan_content_registry.ts` → −19 МБ из бандла.
   До этого коммита приложение работает как сегодня (bundled-фолбэк).
   Откат = revert одного коммита.

Риски: офлайн-первый-запуск нового юзера, купившего план до выхода в сеть —
недостижимо (покупка требует сети); повреждённый кэш — уже покрыт sha256+evict.

## Порядок и правила

1. Ф1 экспортёр+выгрузка → проверка на устройстве → финал-коммит. Только потом Ф2.
2. Каждый перенос — коммит-переключатель с мгновенным revert.
3. Сторожа не ослаблять; контракты путей обновлять в том же коммите.
4. Никаких новых таймеров/фоновых циклов: префетч только по событиям
   (старт-idle, покупка, вход на экран) — правило Firebase-экономии.
