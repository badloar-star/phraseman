# Arena: подсчёт очков во время ожидания и живой тайминг соперника

**Дата:** 2026-08-25  
**Статус:** одобрено владельцем по визуальному макету; ожидает финальной проверки spec

## Цель

После последнего ответа экран Арены не должен выглядеть зависшим на последнем
вопросе. Пока готовится итог, игрок сразу видит короткую сцену подсчёта уже
известных локальных очков матча. Победа, поражение или ничья появляются только
следующим состоянием, когда готов согласованный результат.

Сценарный соперник в быстром матче не должен визуально отвечать одновременно с
игроком на каждом задании. Его заранее рассчитанное время ответа остаётся
независимым: иногда отметка и существующий звук соперника появляются до ответа
игрока, иногда — после него.

## Выбранный UX

1. Последний ответ закрывает вопрос без пустого кадра и без обычного spinner.
2. Поверх игрового фона появляется компактная финальная сцена: подпись «Очки
   матча», крупное число от нуля до локального `matchStars` и спокойная
   пульсация статуса сверки.
3. Для ритма используются только существующие Arena SFX (`starFly` / `starLand`)
   с ограниченной частотой; новые аудиофайлы и TTS не создаются.
4. После готовности результата текущий маршрут открывает существующий экран
   победы, поражения или ничьей. Сцена подсчёта не подменяет награды, XP, рейтинг
   или баланс кошелька и не выдумывает серверные значения.
5. При Reduced Motion число сразу принимает итоговое локальное значение,
   декоративное движение отключается, но статус ожидания и последующий исход
   остаются понятны.

Под словом «руны» в исходном запросе зафиксирована визуальная метафора очков
матча. Денежная/кошельковая валюта не начисляется и не показывается заранее.

## Рассмотренные подходы

### A. Финальная сцена внутри текущего экрана матча — выбран

Сцена монтируется в `arena_match` сразу после локальной фазы `finished`. Она
использует уже прогретый фон и известный счёт, поэтому не зависит от сети и не
создаёт ещё один загрузочный экран. Это единственный подход, который убирает
ощущение зависшего последнего вопроса и сохраняет текущий authoritative flow.

### B. Сразу переходить на неполный экран результата

Число можно считать уже в `arena_results`, но quick-результат появляется только
с авторитетной XP-наградой. Ранний неполный экран затем резко заменился бы
`ResultsSequence`; существующие контракты специально запрещают такой скачок.

### C. Оставить последний вопрос и анимировать только HUD

Минимальная правка, но пользователь всё равно видит заблокированный вопрос и
считает приложение зависшим. Визуальная иерархия не сообщает, что матч уже
завершён.

## Архитектура

### Финальный подсчёт

- Новый небольшой Arena-компонент отвечает только за финальную сцену и получает
  `score`, `active`, `reduceMotion` и callback звукового такта.
- Чистая модель подсчёта определяет безопасную последовательность отображаемых
  чисел и ограничивает число звуковых ударов. Нулевой результат остаётся нулём,
  отрицательные/нечисловые значения нормализуются.
- `app/arena_match.tsx` показывает сцену при локальном `finished`, пока переход
  на результат ещё не выполнен. Существующие доставка отчёта, outbox, retry,
  handoff и terminal sync не меняют владельца и продолжают работать параллельно.
- Результат, пришедший очень быстро, ждёт только короткого минимального такта,
  достаточного для чтения финального числа; дополнительной искусственной
  задержки после завершения такта нет.
- Для долгого ожидания число остаётся стабильным, а ненавязчивый статус
  продолжает сообщать, что результат сверяется. Ошибки хранения/доставки
  используют существующие Arena alert-состояния.

### Независимый ответ соперника

- Заранее известный точный tick остаётся в локальной машине с начала задания:
  он нужен для честного расчёта бонуса «ответил раньше» и не является сетевым
  событием.
- Видимость tick отделяется от знания tick. Локальное состояние хранит, какие
  ответы соперника уже разрешено показать. Live tick реального игрока видим
  сразу после прихода; заранее известный exact tick раскрывается по своему
  `raceElapsedMs`.
- Если игрок ответил раньше exact-соперника, его отметка появляется в фазе
  разбора ответа с короткой различимой задержкой, ограниченной длиной reveal.
  Если соперник был быстрее, отметка появляется во время ответа игрока.
- Таймер раскрытия восстанавливается из текущей фазы и монотонного времени.
  Повторный render/resume не создаёт второй tick и второй звук. Будущие задания
  никогда не раскрываются заранее.
- Живой счёт соперника использует только уже раскрытые ticks; внутренняя модель
  награды продолжает использовать полный точный tick. Так UI ощущается живым,
  а расчёт не теряет детерминизм.

## Данные и контракты

- Firestore schema, Rules, экономика, баланс рун/звёзд и Jarvis data contract не
  меняются.
- Формат серверного `opponentTicks` не меняется; используется существующий
  признак `exact` и `raceElapsedMs`.
- Новые пользовательские строки добавляются во все восемь Arena locales через
  `modules/arena/copy.ts`.
- Решение добавляется в `docs/arena/OWNER_DECISIONS.md` поверх текущего журнала.

## Проверки

1. Чистые тесты модели подсчёта: 0, малый и максимальный Arena score, bounded
   число звуковых beats, Reduced Motion.
2. Тесты машины/представления соперника: exact tick скрыт до своего времени,
   появляется до или после игрока по данным плана, live tick видим сразу,
   будущий tick не раскрывается, resume не дублирует раскрытие.
3. Source/UI contract: финальная сцена заменяет последний вопрос в `finished`,
   использует существующий `useArenaSound`, не показывает wallet currency и не
   обходит handoff/result readiness.
4. Узкие Arena Jest-наборы для изменённых модулей, затем обязательный Arena
   gate из защищённого контура с semaphore-слотом, если он запускает тяжёлый
   Jest.

## Самопроверка spec

- Неопределённых `TODO`/`TBD` нет.
- Локальный score и авторитетная награда явно разделены.
- Изменение не удаляет quick `ResultsSequence`, retry/outbox, ранний ranked
  preview или существующие звуки.
- Тайминг реального игрока и заранее подготовленного exact-соперника не
  смешивается.
