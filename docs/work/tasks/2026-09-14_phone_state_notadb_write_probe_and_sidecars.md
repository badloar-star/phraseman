## Факты из логов (не гипотеза)

`.expo/metro-console.log`, запуск 07:57:33–07:57:34, бандл с вчерашней починкой:

```
[PHONE-STATE-DB] open:step 4/5 integrity rows=0
[PHONE-STATE-DB] open:step 5/5 страница данных расшифрована, sqlite_master tables=0, user_version=0
[PHONE-STATE-DB] open:ok
[FC-TRAIN-ENTRY] bootstrap:FAILED за 1348мс — Calling the 'finalizeAsync' function has failed
→ Caused by: Error code 26: file is not a database
```

Ноль строк `recover:verdict` — восстановление снова не вызывалось.

Что это доказывает:

1. Вчерашняя проба (`SELECT count(*) FROM sqlite_master`) ПРОШЛА и вернула 0
   таблиц: главный файл читается как пустая база. Проверка чтения главного
   файла не ловит этот случай в принципе.
2. Падает первая ЗАПИСЬ: `migratePhoneStateSchema` открывает эксклюзивную
   транзакцию и выполняет `CREATE TABLE …` — и получает NOTADB. Запись идёт
   через WAL и журнал, а проба выполнялась ДО `PRAGMA journal_mode = WAL`.
   Значит непригодны хвосты базы — `-wal` / `-shm` / `-journal`, оставшиеся от
   файла под другим ключом.
3. `SQLite.deleteDatabaseAsync` в expo-sqlite 16.0.10 удаляет ТОЛЬКО главный
   файл (`FileManager.removeItem(atPath: path)`, iOS/SQLiteModule.swift:510).
   Даже когда восстановление сработает, хвосты переживут его, и пересозданная
   база унаследует ту же порчу. Класс «механизм есть, данных ему не дали».

## Architecture

- **Пригодность доказывается ЗАПИСЬЮ, а не чтением**, и только ПОСЛЕ
  `DATABASE_CONFIGURATION` (WAL включён). Проба — крошечная служебная таблица
  `phone_state_open_probe` с одной строкой, которая перезаписывается при каждом
  открытии. Запись проходит через WAL и любой горячий журнал, поэтому порча
  хвостов вскрывается внутри `try` и попадает в восстановление.
- **Пересоздание удаляет ВСЁ семейство файлов**: главный файл через
  `deleteDatabaseAsync`, хвосты `-wal` / `-shm` / `-journal` через
  `expo-file-system` по `SQLite.defaultDatabaseDirectory`. Каждое удаление
  логируется, отказ не молчит.
- **Страховочная сеть** в `openRuntimeSession`: если NOTADB всё же всплывёт в
  миграции (любой путь, который я не предвидел), база закрывается,
  пересоздаётся тем же помощником и миграция повторяется один раз. Это и есть
  «проверка по-другому»: вход не может быть заблокирован этим классом ошибки,
  откуда бы он ни пришёл.
- Прежние проверки (cipher_version, integrity) остаются как ранняя диагностика.

## Security and privacy

Новых данных, сервисов и разрешений нет. Удаляются локальные файлы базы,
которые расшифровать невозможно (ключ утрачен) — потери данных сверх уже
случившейся нет. Privacy policy не затрагивается.
