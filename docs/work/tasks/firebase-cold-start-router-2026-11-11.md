# Firebase: единая точка входа против холодных стартов — план, 2026-11-11

Поручение владельца 11.11: «проведи аудит Firebase… где можно сделать намного дешевле и ничего не потерять» → «да, готовь план».
Продолжение `firebase-cost-cut-2026-10-17.md`. Статус: **план, код не написан**.

## 1. Что показали замеры (прод `phraseman-ea0b3`, Cloud Monitoring, 7 суток до 11.11, только чтение)

Выгрузки биллинга нет — суммы ниже посчитаны по публичным тарифам.

**Счёт ≈ 28–30 $/мес, из них ≈ 22 $ — процессорное время функций.** Почти всё это время — холодные старты:

- один холодный старт стоит ≈ 31–43 vCPU-с: ускорение старта Cloud Run даёт 2 vCPU на время старта + 10 с после.
  Проверка формулы `2 × (старт + 10 с)` на трёх функциях: `accountMergeOutboxRetryCron` 6,3 с → 32,6 (факт 31,2);
  `communityMonthStandingsRefresh` 11,6 с → 43,2 (факт 41,3); `accountDeleteRetryCron` 17,0 с → 54 (факт 49,5);
- холодных стартов 7 684 за неделю при 75 410 вызовах — каждый десятый вызов будит функцию;
- всего 254 172 vCPU-с за неделю.

| Группа | Сервисов | Вызовов | Холодных стартов | vCPU-с |
|---|---|---|---|---|
| Вызовы из приложения (callable) | 63 | 53 493 | 5 328 | 177 464 |
| Задания по расписанию | 22 | 7 515 | 993 | 38 027 |

**Почему стартов так много:** 63 пользовательские функции — 63 отдельных сервиса. У каждого трафик редкий, экземпляр засыпает
через ~15 минут, следующий вызов платит за старт. Вместе же трафик плотный: из 672 пятнадцатиминутных окон за неделю пустых
только 12, медиана — 70 вызовов на окно. Один общий сервис почти не засыпал бы.

**Второй факт:** база в `eur3`, 430 из 435 сервисов в `us-central1`; каждое обращение к базе ≈ 120 мс (`callable_options.ts:7`).
Средняя длительность простых вызовов 1,6–2,1 с. Это про скорость для пользователя, не про счёт.

## 2. Решение

Одна функция-маршрутизатор `api` в `europe-west1` принимает `{ name, data }` и передаёт запрос уже существующему
обработчику. Обработчики не переписываются: у callable в firebase-functions 7 есть метод `.run(request)`.

Что это даёт разом:
- **счёт:** 5 328 стартов в неделю → десятки (общий сервис не засыпает);
- **скорость:** сервер рядом с базой — обращение к базе ≈ 120 мс → единицы мс; исчезает ожидание 5–7 с на «пробуждение».

### Сервер
- `api`: `europe-west1`, `cpu: 1`, `concurrency: 80`, `memory: 512MiB`, `timeoutSeconds: 60`, `maxInstances: 10`, `minInstances: 0`.
- Белый список «имя → обработчик». Имя не из списка → `HttpsError('unimplemented', 'router_unknown_name')`, обработчик не вызывается.
- `request.auth`, `request.rawRequest` (IP для лимитов), `request.app` передаются как есть — лимиты и проверки внутри обработчиков работают без правок.
- Ошибки обработчика (`HttpsError`) проходят наружу без изменений.
- На каждый вызов одна строка лога `[API-ROUTER] {name, ms, outcome}` — иначе пропадёт видимость «какая функция сколько стоит»
  (сейчас её даёт разбивка по сервисам).
- Секреты: объединение секретов включённых обработчиков.
- Старые 63 функции в `us-central1` **остаются**: ими пользуются старые сборки приложения. Удалять — когда их трафик уйдёт в ноль.
- Вариант размещения — отдельная кодовая база с коротким индексом (как `functions-english-test`): не трогает общий
  `functions/src/index.ts` и грузит только нужные обработчики, старт легче. Решить на шаге 1 по фактическому размеру.

### Приложение
- Одна точка перехвата вместо правки 77 мест вызова в 59 файлах: приём уже есть в `app/dev_callable_counter.ts`
  (обёртка над `httpsCallable` модуля функций).
- Перехват включается флагом в `remote_config/app` и списком имён оттуда же. Флаг выключен → всё работает как сегодня.
- Откат без релиза: выключить флаг.
- Запасной путь на старую функцию — **только** при ответе `router_unknown_name` (доказано, что обработчик не запускался).
  При таймауте или обрыве сети повтор на старый адрес запрещён: неизвестно, выполнилось ли действие (награды, покупки).
- Optimistic UI не меняется: экраны и локальные обновления остаются прежними, меняется только адрес вызова.

### Что в маршрутизатор НЕ входит (первая очередь)
- ИИ-функции: таймауты до 150 с, 512 МБ, свои секреты и лимиты — отдельный маршрутизатор позже, если замер покажет смысл (360 стартов/нед).
- Вход и слияние аккаунтов (`authEnsureStableLink` и др.): у них уже свой перенос в Европу и свой прогрев.
- Вебхуки оплаты, сайт, админка, триггеры базы.

## 5. Риски и что может сломаться

- **Один сервис на всё:** сбой маршрутизатора задевает все включённые функции разом. Защита — флаг (откат без релиза) и
  старые функции, которые никуда не деваются.
- **Память:** полный бандл занимал ≈ 340 МБ (комментарий `support_inbox.ts:6737`), поэтому 512 МБ и замер на шаге 1.
- **Двойное выполнение:** исключено правилом «запасной путь только при `router_unknown_name`».
- **Потеря разбивки расходов по функциям:** закрывается логом `[API-ROUTER]`.
- **Privacy Policy:** обработка запросов переезжает из США в ЕС. Проверить формулировку о местах обработки данных в политике
  до релиза (правило владельца о данных). Данные и состав сторонних сервисов не меняются.
- **Квота vCPU региона:** `maxInstances: 10 × 1 vCPU` — в пределах лимита; в `europe-west1` сейчас только 5 сервисов.
- **Расхождение кода и прода по ядрам:** в коде у `HOT_CALLABLE_OPTIONS` `cpu: 1`, у `practiceRuneGrant` в проде 0,167.
  Сверить перед любым полным деплоем.
