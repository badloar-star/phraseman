# Джарвис: кнопки подтверждения в Telegram

Действующее руководство по approvals Джарвиса. Заменяет
`agent-office-telegram-approvals.md`, который описывает **снесённый** слой
`agent_office` и формат `ao1` — тот код удалён в Р4 (2026-08-02).

Состояние на 2026-08-02: **работает в бою**, подтверждено владельцем —
нажатие кнопки вернуло «Принято, подтверждено».

## Что где лежит

| Файл | Отвечает за |
|---|---|
| `functions/src/jarvis/approval_token.ts` | Выдача и проверка токена. Чистая логика, без Firestore |
| `functions/src/jarvis/approval_store.ts` | Запись и атомарное погашение в Firestore |
| `functions/src/jarvis/approval_webhook_core.ts` | Логика отказов. Чистая, без сети |
| `functions/src/jarvis/approval_webhook.ts` | HTTP-точка входа. Намеренно тонкая |
| `functions/src/jarvis/approval_audit.ts` | Журнал подтверждений |
| `functions/src/jarvis/telegram_buttons.ts` | Раскладка клавиатуры |
| `functions/src/jarvis/issue_decision_buttons.ts` | Связка «решение → пара кнопок», `hashDecision` |

| `functions/src/jarvis/control.ts` | Свой kill switch Джарвиса (`jarvis_control`) |

Коллекции: `jarvis_approval_tokens` (закрыта полностью),
`jarvis_approval_audit` (admin читает, пишет только сервер),
`jarvis_control` (admin читает, пишет только сервер).

## Модель безопасности

Нажатие кнопки — действие от имени владельца, поэтому токен доказывает три
вещи сразу: **кто** нажал, **что** подтверждается, и что нажатие **свежее**.

1. **В Firestore только SHA-256 хеш nonce.** Сырой nonce живёт лишь в
   `callback_data` на телефоне владельца. Утечка базы не даёт нажать кнопку.
2. **Привязка и к user id, и к chat id.** Пересланное в другой чат сообщение
   не сработает.
3. **TTL 10 минут + одноразовость.** Старое сообщение в истории не становится
   вечно живой кнопкой.
4. **Сравнение хешей через `timingSafeEqual`.** Обычное `===` возвращается тем
   быстрее, чем раньше разошлись строки — по времени ответа хеш подбирается
   посимвольно.
5. **Порядок проверок:** секрет вебхука → личность → и только затем база. Так
   посторонний не нагружает Firestore, подбирая nonce.
6. **Отказ НЕ гасит токен.** Иначе чужой, получив пересланное сообщение,
   «сжигал» бы кнопку владельца простым нажатием — отказ в обслуживании.
7. **Одинаковый ответ всем посторонним.** Не подсказываем, что именно не так.

Полномочия берутся из секрета `JARVIS_TELEGRAM_CONFIG`, **не** из
`admin_config/alerts`: тот документ редактируется из браузера, и кто угодно с
доступом к админке подменил бы получателя и стал бы «владельцем».

## Секрет

```json
{
  "webhookSecret": "<не короче 32 символов, A-Z a-z 0-9 _ ->",
  "ownerTelegramUserId": "<числовой telegram user id>",
  "ownerTelegramChatId": "<id ЛИЧНОГО чата>",
  "selftestEnabled": false
}
```

Задаётся интерактивно, значение не попадает в историю shell:

```bash
firebase functions:secrets:set JARVIS_TELEGRAM_CONFIG --project phraseman-ea0b3
```

Без корректного секрета функция отвечает `404` и не трогает ни Firestore, ни
Telegram — считается невключённой.

`selftestEnabled` открывает проверочную ветку выдачи кнопки. Строго `=== true`:
строка `"true"`, единица и отсутствие поля читаются как «выключено».
**По умолчанию выключена** — лишняя дверь в боевой функции остаётся закрытой.

## Установка вебхука

Делается **вручную**. В коде её нет намеренно: деплой не должен перебивать
вебхук бота, общего с алертами.

```bash
firebase deploy --only functions:jarvisTelegramApprovalWebhook --project phraseman-ea0b3
```

Затем `setWebhook` из защищённой среды: `url` — адрес функции, `secret_token` —
тот же `webhookSecret`, `allowed_updates` — `["callback_query","message"]`.

> ⚠️ `allowed_updates` без `message` заставляет Telegram **молча выбрасывать**
> все текстовые сообщения владельца. На этом уже теряли сообщения: снесённый
> слой оставил `["callback_query"]`, и бот не слышал владельца, пока это не
> нашли вручную.

Проверьте `getWebhookInfo` тем же защищённым способом.

## Проверка после деплоя

Все четыре ответа обязаны совпасть:

| Запрос | Ожидается |
|---|---|
| GET | `405` |
| POST без секрета | `401` |
| POST с секретом, чужой telegram id | `200` + «Эта кнопка не для вас» |
| POST `{"selftest":true}` с верным секретом при выключенном флаге | `404` |

> ⚠️ Сборка: `tsc --noEmit` **не пишет файлы**. После правок обязателен
> `npm run build`, иначе деплой уедет со старым кодом. Проверять по наличию
> изменения в `lib/functions/src/...`, а не по успешному тайпчеку. На этом уже
> обожглись: функция отвечала `200` из старой ветки, а сообщение не уходило.

## Команды из Telegram (2026-08-02)

Вебхук принимает и обычные текстовые сообщения (`allowed_updates` включает
`message`), поэтому три команды работают без отдельной настройки:

| Команда | Что делает |
|---|---|
| `/status` | Одно чтение `jarvis_control`: режим, причина (если выключен), когда был последний суточный прогон и сколько находок в нём было |
| `/stop` | `jarvis_control.mode = 'off'`, причина `«остановлен командой /stop из Telegram»` |
| `/start` | Возвращает `mode = 'observe'` |

Проверка личности та же строгость, что у кнопок: и telegram user id, и chat id
должны совпасть с владельцем — иначе команда молча игнорируется, это не
безобидное чтение, `/stop` меняет состояние системы.

## Аварийная остановка

1. **Быстро и своим рубильником:** отправьте `/stop` в Telegram, или
   вручную установите `jarvis_control/global.mode = 'off'` в консоли
   Firestore. Гасит ТОЛЬКО Джарвиса — отчёты об ошибках из `admin_alerts.ts`
   продолжают идти как обычно (рубильники раздельные, см. `control.ts`).
2. Полностью: удалить вебхук через Bot API из защищённой среды — тогда и
   `/stop` перестанет доходить.
3. Ротация bot token затрагивает **и** admin alerts. Ротация
   `JARVIS_TELEGRAM_CONFIG` — только approvals.

## Что кнопка делает сейчас

Подтверждение записывается в журнал `jarvis_approval_audit` — и отказы тоже:
попытка нажать чужую кнопку это свидетельство, а не повод для тишины.
Действий за нажатием пока нет: департаменты только наблюдают. Кнопки готовы
к моменту, когда действия появятся.

Отклонённый совет (нажали «✕») не появляется в сводке повторно 3 суток
(`REJECTION_MEMORY_MS` в `recent_rejections.ts`) — если проблема не решилась,
Джарвис напомнит снова после этого окна, а не молчит навсегда.

Находки сортируются по важности (`severity.ts`) перед обрезкой до пяти в
сообщении: платежи и безопасность — P0, поддержка — P1, качество/деньги — P2,
рост/контент/фабрика/удержание — P3. Повторы с одинаковым (department,
finding) в рамках одного прогона склеиваются в одну находку.
