# Надёжный локальный поток повышения уровня и подарков

Дата: 2026-07-11

## Цель

Гарантировать на текущем устройстве, что каждое фактическое новое повышение уровня:

- создаёт ровно один entitlement-набор за каждый достигнутый уровень согласно действующим single/dual правилам (один подарок для обычного потока, два — когда применяется Premium dual-flow);
- сохраняет подарок до показа модального окна;
- показывает глобальное окно повышения уровня независимо от текущего экрана;
- не теряется при конкурирующей модалке, сворачивании приложения, перезапуске или временной ошибке локального хранилища;
- отображается в разделе «Подарки» с подписью уровня происхождения.

Изменение распространяется на уже сохранённую очередь ожидания и на все будущие повышения. Оно не выдаёт автоматически подарки за все исторические уровни существующего пользователя.

## Подтверждённые дефекты

1. `levelUp` рендерится нативным `Modal`, но отсутствует в `NATIVE_MODAL_KEYS`. Арбитр может передать ему слот сразу после закрытия другого нативного окна без защитной паузы, из-за чего нативная презентация способна сорваться.
2. Persistent-очередь подтверждается при логическом `levelUpOverlayVisible`, до фактического `Modal.onShow`. Сбой нативной презентации удаляет возможность повторного показа после перезапуска.
3. `xp_manager` запускает `ensureUnclaimedGiftForLevel` без ожидания результата и параллельно для нескольких уровней. Несколько операций read-modify-write могут перетереть подарки друг друга; ошибка записи полностью скрывается.
4. Серверно подтверждённый новый progress event может поставить уровень в очередь без создания соответствующего подарка.
5. Рост XP при обычном cloud restore сам по себе не доказывает новое повышение на этом устройстве: подарок мог быть забран на другом устройстве. Создавать подарок только по такому росту нельзя без синхронизируемого серверного журнала наград.

## Архитектура

### 1. Единый локальный reconciler наград

Новый небольшой модуль принимает диапазон `previousXP -> nextXP` только для фактического начисления или серверно подтверждённого нового progress event.

Для каждого пересечённого уровня он последовательно:

1. проверяет, есть ли подарок в single/dual pending-хранилище;
2. проверяет, был ли подарок уже забран;
3. при отсутствии создаёт и сохраняет подарок;
4. после подтверждённой устойчивой записи добавляет уровень в persistent-очередь модала;
5. после фиксации состояния посылает `level_up_pending`.

Операции сериализуются внутри процесса, чтобы два параллельных источника XP не перетирали один и тот же JSON. Повторный вызов безопасен и не создаёт дубликаты.

Результат для каждого уровня различает состояния:

- `persisted` — новый подарок записан;
- `already_pending` — подарок уже ожидает получения;
- `already_claimed` — подарок уже получен, повторно не создаётся и старое поздравление не восстанавливается;
- `failed` — запись не подтверждена.

При `failed` уровень не добавляется в очередь показа. Если локальное хранилище доступно, сохраняется отдельный durable retry marker; при полном отказе AsyncStorage остаётся in-memory retry до конца текущего процесса. Marker обрабатывается при старте, возврате приложения в active и следующем начислении XP. После завершения процесса во время полного отказа локального хранилища абсолютная локальная гарантия технически невозможна; приложение не должно скрывать такой сбой как успешное сохранение.

Для ремонта существующей очереди переходы фиксированы:

- `persisted` / `already_pending` — уровень остаётся или добавляется в очередь показа;
- `already_claimed` — уровень удаляется из persistent- и in-memory-очереди без старого поздравления;
- `failed` — уровень не показывается и остаётся retry-кандидатом.

### 2. Источники вызова

Reconciler вызывается:

- из `registerXP` для реального локального повышения;
- из обработки серверного результата только когда сервер подтвердил новый progress event и поднял локальный XP выше значения до зеркалирования;
- из ремонта ранее сохранённой `pending_level_up_queue`, чтобы создать отсутствующий подарок перед показом.

Reconciler не вызывается из общего cloud restore только на основании того, что облачный XP выше локального. Это предотвращает повторную выдачу подарка, уже полученного на другом устройстве.

Прямые записи `user_total_xp`, не представляющие новое наградное событие, не должны самостоятельно порождать level-up entitlement.

### 3. Надёжный показ модала

- Добавить `levelUp` в `NATIVE_MODAL_KEYS`, чтобы переход между нативными модалками проходил через существующий безопасный handoff gap.
- Persistent-очередь подтверждать только из `Modal.onShow`, а не из эффекта по логическому состоянию.
- При возврате приложения в `active` перечитывать очередь и retry marker.
- Сохранять текущий принцип арбитра: одновременно показывается только одно крупное окно; level-up ждёт освобождения слота.
- После `onShow` текущий уровень можно удалить из persistent-очереди, а in-memory очередь продолжает удерживать его до завершения цепочки level-up -> подарок.
- Если окно не получило `onShow`, persistent-запись остаётся и будет повторена.

### 4. Подарочный инвентарь

Существующие single/dual pending-записи остаются источником истины для раздела «Подарки». Подпись `Уровень N` сохраняется. Получение подарка остаётся идемпотентным: already-claimed уровень не воскрешается.

Для уже сохранённого pending-уровня без подарка reconciler создаёт подарок до показа модала. Если запись не удалась, модал не обещает несуществующую награду и повторяет попытку позже.

## Миграция и границы

- Не создавать подарки за все уровни от 1 до текущего.
- Не трактовать cloud restore как новое повышение.
- Обработать существующие значения `pending_level_up_queue` и будущие повышения.
- Не добавлять на этом этапе межустройственный pending/claimed ledger.
- Не менять формулу уровня, XP, состав подарков, Premium-логику или тексты раздела «Подарки» кроме необходимых диагностических/доступностных уточнений.
- Не удалять существующие возможности модалов и подарков.

## Ошибки и восстановление

- Ошибка создания или сохранения подарка возвращает `failed`; при доступном локальном хранилище записывается durable retry marker, а при полном отказе сохраняется in-memory retry текущего процесса.
- Ошибка чтения очереди не очищает её.
- Повреждённые элементы очереди фильтруются; валидные положительные уровни сохраняются без дублей.
- Foreground и запуск приложения повторяют незавершённую локальную работу.
- Повторный event или повторный запуск не выдаёт второй подарок.

## Проверки и критерии приёмки

1. Переход `native modal -> levelUp` требует handoff gap.
2. Persistent-уровень не удаляется до `Modal.onShow`.
3. После `onShow` уровень удаляется из persistent-очереди ровно один раз.
4. Перескок нескольких уровней последовательно сохраняет один корректный entitlement-набор для каждого уровня, сохраняя существующие single/dual правила.
5. Параллельные повторные вызовы не создают дубликаты и не теряют записи.
6. `already_claimed` не создаёт pending-подарок и не восстанавливает старое поздравление.
7. `failed` не ставит неподтверждённую награду в очередь показа и создаёт durable retry marker при доступном AsyncStorage либо in-memory retry при его полном отказе.
8. Серверно подтверждённый новый progress event создаёт и подарок, и очередь.
9. Обычный cloud restore более высокого XP не создаёт подарок повторно.
10. Существующая очередь переживает перезапуск и перечитывается при foreground.
11. Раздел «Подарки» показывает награду и её исходный уровень.
12. Узкие тесты XP, инвентаря, арбитра, модала и runtime/performance guards проходят без изменения их ожидаемого поведения.

## Вне текущего объёма

Полная межустройственная гарантия требует account-scoped серверного ledger с детерминированным ключом уровня и состояниями `pending/claimed`. Она должна проектироваться отдельно вместе с Cloud Functions, Firestore rules, восстановлением аккаунта и защитой от повторной выдачи.
