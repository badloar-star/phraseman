## Находки и безопасные направления

### 1. Высокий приоритет: измерить и облегчить именно текущий путь данных Home

Источник: [home.tsx](C:/appsprojects/phraseman/app/(tabs)/home.tsx:2621), [пакетный resolver](C:/appsprojects/phraseman/app/lesson_lock_system.ts:172), [граница готовности статистики](C:/appsprojects/phraseman/app/(tabs)/home.tsx:2774).

Home читает прогресс 32 уроков и last-opened одним `multiGet`, разбирает записи, затем делает `await import('../lesson_lock_system')` и вызывает resolver. В наблюдаемом первом проходе весь этот участок занял 3 610 мс, в следующем — 4 мс. Это сильный кандидат для исследования, но текущая отсечка не различает загрузку/выполнение модуля, ожидание JS-потока, storage и вычисления.

История: 2 сентября `97a8a0442` добавил детализацию после обнаружения медленного последовательного цикла. Пакетный resolver уже зафиксирован в `6ce8e6b4e` 3 сентября; комментарий ссылается на решение владельца 2 сентября. Предлагать заменить старый цикл ещё раз — ошибочный аудит. Проверка доступности нужна, чтобы кнопка «Урок» не вела в ранее запомненный заблокированный урок; сам resolver намеренно ничего не выдаёт и не записывает.

Следующий эксперимент: отдельные отсечки `lessonStorage`, `lessonParse`, `lessonModule`, `lessonResolve`, `freeze+multiplier`, `statsCommitted`, затем именованный хвост лиг/медалей/офферов. Если задержка в загрузке модуля — вынести узкое read-only вычисление из тяжёлого модуля; если в storage — переиспользовать уже прочитанные данные. Сохранить правила доступа, корректные счётчики, account-generation и study-target isolation. Второстепенные эффекты отделять от первого кадра, а не удалять.

### 2. Высокий приоритет: прогрев четырёх вкладок конкурирует с запуском

Источник: [константы прогрева](C:/appsprojects/phraseman/app/(tabs)/_layout.tsx:369), [планировщик](C:/appsprojects/phraseman/app/(tabs)/_layout.tsx:1035), [ранний сигнал Home](C:/appsprojects/phraseman/app/(tabs)/home.tsx:975).

После `app_first_content_ready` ставятся четыре задачи с задержками 0/180/360/540 мс; есть fallback 1 600 мс и idle timeout 400 мс. Задачи вызывают загрузку модулей и монтирование скрытых вкладок. Сигнал Home приходит уже после монтирования, до завершения `loadData`. Планировщик не проверяет root-ready, готовность данных Home или фактическое исчезновение splash. Это подтверждённое пересечение жизненных циклов; его вклад в миллисекундах пока не измерен.

История: агрессивные 0 мс/400 мс зафиксированы snapshot-коммитом `96c32bb97d` 24 августа. Комментарии объясняют цель: избавиться от задержки первого тапа по «Урокам». Freeze сохранять: он останавливает рендеры, но не автоматически все эффекты/подписки.

Безопасная оптимизация: запускать очередь после настоящего первого рабочего кадра, прогревать последовательно с бюджетом времени, отдавать приоритет явному тапу и отменять устаревшую работу при уходе в фон. Проверять одновременно cold-start и первый переход по каждой вкладке. Не отключать прогрев целиком и не переносить весь его расход на первый тап.

### 3. Средний приоритет: повторные локальные чтения и публикации

Источники: [hydratePersonalProgress](C:/appsprojects/phraseman/app/personal_progress_store.ts:73), [app snapshot](C:/appsprojects/phraseman/app/app_snapshot_bootstrap.ts:216), [Home](C:/appsprojects/phraseman/app/(tabs)/home.tsx:2477), [прогрев уроков](C:/appsprojects/phraseman/app/lesson_screen_bootstrap.ts:142), [его запуск](C:/appsprojects/phraseman/app/_layout.tsx:2480).

`hydratePersonalProgress()` вызывается разными стартовыми потребителями; реализация `globalStore.hydrate()` не объединяет одновременные чтения. Root-прогрев отдельно читает 128 ключей состояния 32 уроков, включая те же progress-ключи, которые нужны Home. Он запускается после `setReady` через `InteractionManager`, но не после подтверждённого снятия всех splash gates. Promise.race не отменяет проигравшую фоновую работу.

История: текущий progress store зафиксирован в `05a45451f` 24 августа. Его revision-проверка защищает более новую публикацию от запоздалого результата. Snapshot-гидратация нужна для первого кадра с реальными данными, без скачка 0 → настоящее значение.

Безопасная оптимизация: общий in-flight read в пределах одной генерации аккаунта и источника данных; общий результат чтения progress для Home/прогрева уроков; подробные session/phraseOrder данные остальных уроков читать позже. Нельзя заменить свежую гидратацию вечным кэшем, убрать revision/reset или перенести данные между аккаунтами/языками. Экономия времени требует замера.

### 4. Предыдущая lazy-правка Home не доказывает уменьшения стартовой работы

Источник: [module-scope promise](C:/appsprojects/phraseman/app/(tabs)/_layout.tsx:33), [локальный Metro runtime](C:/appsprojects/phraseman/node_modules/metro-runtime/src/modules/asyncRequire.js:17), [router context](C:/appsprojects/phraseman/router.ctx.js:1).

`const homeScreenModulePromise = import('./home')` выполняется немедленно при оценке tabs layout. `React.lazy` здесь не переносит вызов import до более позднего пользовательского действия. В установленном Metro без split-loader `require.importAll` выполняется до возврата promise — это воспроизведено из настоящего runtime-файла. На одном JS-потоке evaluation не становится параллельным только из-за `import()`.

В DEV добавляется риск ожидания дополнительного bundle fetch; при sync route-discovery Expo Router также вызывает `node.loadRoute()` для маршрутов. Home остаётся маршрутом в `require.context`, который прошлый простой подсчёт статических импортов не описывает.

Метрики «743 → 566 модулей» и «9,73 → 7,56 МБ исходников» не являются измерением release bundle, TTI или экономии RAM. По [документации Metro](https://metrobundler.dev/docs/module-api/), dynamic import разделяет загрузку в development, не уменьшая таким способом release bundle; [Expo](https://docs.expo.dev/router/web/async-routes/) отдельно ограничивает native production async routes.

Правка незакоммичена; заявленная цель — перекрыть загрузку Home с bootstrap. Вместо дальнейшей косметической замены импортов нужен профиль реально выполняемых модулей и более узкий first-screen dependency path. Отдельно оптимизировать dev и релиз.

### 5. Регрессия: восстановление push-расписания читает негидратированную память

Источники: [runSessionChecks](C:/appsprojects/phraseman/app/_layout.tsx:693), [дефолтная память](C:/appsprojects/phraseman/app/notifications.ts:1256), [ежедневное напоминание](C:/appsprojects/phraseman/app/notifications.ts:518).

После удаления bootstrap-гидратации `runSessionChecks` импортирует notifications и сразу читает `getNotifSettingsSnapshot()`. Начальное расписание имеет все дни `enabled:false`. Фактическая загрузка сохранённого расписания теперь остаётся на экране настроек. При включённых уведомлениях и сохранённом расписании по дням холодный запуск может выбрать daily-ветку; она отменяет старые per-day reminders. Изолированная проверка реального фрагмента кода: до hydration `hasPerDay=false`, после чтения сохранённого понедельника `true`.

История: bootstrap-memory контракт документирован и зафиксирован 30 апреля (`20ee88cad2`), чтобы сразу видеть правильные тумблеры. Удаление загрузки в предыдущей оптимизации — незакоммиченная правка. Цель переноса из boot понятна, но зависимость чтение → использование потеряна.

Безопасное исправление до дальнейшей оптимизации: восстановить гарантированное чтение настроек перед выбором режима планирования; можно сделать это после первого экрана, не возвращая тяжёлый notifications-модуль в обязательный bootstrap. Проверить per-day/daily/выключено, отказ разрешений и неизменность времени/категорий. Никаких уведомлений этим аудитом не планировалось.

Дополнительно: [EnergyContext](C:/appsprojects/phraseman/components/EnergyContext.tsx:656) после стартовой загрузки вызывает sync push. И планирование, и отмена лениво импортируют notifications, поэтому модуль всё равно может загрузиться под заставкой. Переносить нужно момент некритичной сверки уведомлений, не готовность энергии и не саму функцию отмены.

### 6. Регрессии/риски: заставка зависит от Home, а ошибки lazy-onboarding скрыты

Источники: [native gate](C:/appsprojects/phraseman/app/_layout.tsx:1545), [fallback](C:/appsprojects/phraseman/app/_layout.tsx:1588), [JS overlay](C:/appsprojects/phraseman/app/_layout.tsx:2918), [onboarding import](C:/appsprojects/phraseman/app/_layout.tsx:1218).

- Новый `homeScreenReady` обязателен глобально, а устанавливается только событием из `HomeScreenHost` в tabs. Если начальный маршрут не монтирует Home, например холодное открытие отдельного экрана по внешней ссылке, сигналу неоткуда прийти. Fallback выставляет только `firstContentReady`; обе заставки при `homeScreenReady=false` остаются. Это проверено на реальных gate-выражениях. Конкретный native deep-link маршрут на устройстве в этом аудите не воспроизводился, поэтому это source-level риск зависания, не заявление о воспроизведении всех ссылок.
- Если `import('../components/onboarding')` отклоняется, catch ничего не делает, а JS splash требует загруженный компонент. Комментарий обещает retry при следующем render, но effect зависит только от `effectiveShowOnboarding`: обычный повторный render retry не запускает. Нужны наблюдаемая ошибка и реальный путь повторной попытки, не пустой экран и не обход onboarding.

Обе правки незакоммичены и введены при предыдущем ускорении ради защиты от пустого первого кадра. Эта цель верная, реализация требует route-aware readiness. История особенно важна: `519de9ff0` от 29 августа уже исправлял вечный splash после сбоя идентичности и обход экрана восстановления. Нельзя снова вводить бессрочную блокировку либо убирать защиту аккаунта ради выхода из неё.

## Что не трогать ради формального сокращения splash

- `ensureFreshPostDeletionIdentity`, recovery/account-generation guards: предотвращают доступ к старым данным и смешение аккаунтов.
- Гидратацию возраста/согласий до соответствующих защищённых эффектов; last-known real-data snapshots и стабильную геометрию первого кадра.
- Правила доступа к урокам, локальные результаты/награды, six-hour league cache, дедупликацию модалок/уведомлений и freeze невидимых экранов.
- 350 мс в bootstrap: это бюджет ожидания, не обязательная пауза. Механическое снижение не устраняет синхронную работу и может ухудшить первый кадр. Текущий budget зафиксирован `51f76a63c` 23 мая.
- OTA и шрифты как «очевидную причину»: конфигурация уже использует `ON_ERROR_RECOVERY`/`fallbackToCacheTimeout:0`, а native fonts встроены через expo-font. DEV имеет отдельную загрузку шрифтов. Это не доказательство отсутствия native/font расходов, но основания просто удалить эти механизмы нет.

## Как проверять следующее ускорение

1. Сначала устранить регрессии настроек и восстановления splash с поведенческими тестами; source-token тесты предыдущей правки проверяют наличие строк, а не запуск приложения.
2. Зафиксировать устройство, build/commit, режим DEV/release-like и начальные данные. Провести отдельно повторный запуск существующего пользователя, новую установку/onboarding, offline и холодную внешнюю ссылку/notification tap. Не очищать пользовательские данные ради замера.
3. Измерять native start → JS/module work → identity/hydration → commit реального первого экрана → снятие native и JS splash → первый обработанный тап. Отдельно считать завершение фоновой синхронизации: оно не обязано быть TTI.
4. Добавить недостающие отсечки Home, загрузки модулей и фонового premount; снять профиль JS до первого рабочего кадра. Измерять одну гипотезу за раз: уроки, очередь прогрева, общие storage reads.
5. Сравнить минимум 10 одинаковых запусков до/после: медиана и худший результат, отдельно cold и warm. Не выдавать JS reload и холодную компиляцию Metro за холодный запуск установленного релиза. Не обещать проценты/секунды до этой серии.
6. Проверить первый тап по вкладкам, реальные цифры без скачка нулей, доступ к урокам, уведомления, энергию, ошибку lazy import, onboarding и смену аккаунта/языка. Ускорение не принимается, если ломает любой из этих сценариев.

Среда разработки тоже перегружена: при начальном осмотре было 101 процесс Node (~14,46 GiB working set суммарно). Это возможный источник нестабильных dev-замеров, но не объяснение скорости установленного релиза. Чужие процессы не завершались, кэши не чистились. Полные Jest/tsc/build не запускались: для read-only аудита использованы узкие проверки; успех сборки или релизное ускорение не заявляются.

## Предварительный допуск — уточнение владельца после аудита

Подход «сначала изменим, потом узнаем, не стало ли хуже» не разрешён. Ранее внесённые правки этим уточнением не считаются автоматически проверенными; откат чужих/общих изменений не выполняется.

### Находки и предложения
