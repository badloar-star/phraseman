# Проверка лишнего ожидания модуля Home до правки приложения

Дата: 12 сентября 2026. Дополнение к [основному аудиту](C:/appsprojects/phraseman/docs/reports/STARTUP_REAUDIT_2026-09-12.md).

## Статус

**Подтверждён механизм лишнего ожидания в изолированном запуске установленного Metro/Expo runtime. Допуска к изменению приложения пока нет.** Влияние на реальный запуск и отсутствие ухудшения других действий не измерены. Исходники приложения не менялись; прогрев, кэши, UI, уведомления и таймеры не менялись.

## Цепочка зависимостей

1. [Корневой layout](C:/appsprojects/phraseman/app/_layout.tsx:127) статически импортирует `repairLessonUnlocksAfterRestore` из `lesson_lock_system`. Этот импорт зафиксирован ещё 30 апреля (`20ee88cad2`): модуль нужен для восстановления прогресса, а не только для Home.
2. [Home](C:/appsprojects/phraseman/app/(tabs)/home.tsx:2661) в `loadData` делает `await import('../lesson_lock_system')`, чтобы получить `resolveLastAvailableLessonId`.
3. Этот вызов зафиксирован 2 сентября в `7aadad13b9` при замене старого последовательного цикла пакетной проверкой. Цель была правильной: убрать десятки чтений и сохранить корректность кнопки последнего урока.
4. Установленный Expo использует собственный `expo/src/async-require/asyncRequireModule.ts`. Он вызывает загрузчик bundle **до** получения уже существующих exports. Предыдущая проверка стандартного Metro runtime имела сходную логику; теперь непосредственно проверен используемый Expo-вариант.
5. `expo/src/async-require/buildAsyncRequire.ts` хранит отдельный кэш promise по URL. Он не проверяет, инициализирован ли требуемый модуль обычным импортом. При первом обращении по данному динамическому URL может начаться лишний запрос, при следующих используется кэш URL.

Это объясняет, почему обычный импорт в root сам по себе не доказывает отсутствие ожидания при первом динамическом импорте из Home. Это пока объяснение механизма, а не доказанная атрибуция всех 3 610 мс из старого dev-лога именно ему.

## Что выполнено без изменения приложения

[Диагностический скрипт](C:/appsprojects/phraseman/.codex-tmp/startup-proof/prove-cached-module-wait.mjs) исполняет установленные Metro module registry и два Expo async-require модуля в изолированной среде Node. Внешний bundle loader заменён управляемой promise — реальной сети и аккаунтов в эксперименте нет.

Проверки:

- Обычная загрузка инициализирует модуль ровно один раз.
- Последующий первый dynamic import инициирует запрос по bundle URL и остаётся незавершённым, пока этот запрос не разрешён, хотя модуль уже инициализирован.
- Чтение кэшированного модуля возвращает тот же объект функции без повторного выполнения фабрики.
- После разрешения bundle promise dynamic import возвращает ту же функцию.
- Повторный dynamic import не добавляет запросов.
- Без split-loader функция также совпадает; этот механизм сетевого ожидания не доказывает проблему native release.

Отдельно исполнены реальные `main_course_access` и тело resolver на 64 входах: уроки 1–32 × два существующих target (`en`, `es`). Все возвращают тот же номер, без чтений хранилища. Это согласуется с решением владельца от 8 сентября открыть основной курс: resolver для этих входов не выполняет прежний цикл чтений. Само решение о доступе не изменялось, функция не удалялась и не обходилась в приложении.

Команда: `node .codex-tmp/startup-proof/prove-cached-module-wait.mjs`.
Результат: EXIT 0; [машинный отчёт](C:/appsprojects/phraseman/.codex-tmp/startup-proof/cached-module-wait-proof.json).

## Границы доказательства

- Управляемая promise не измеряет реальные миллисекунды. Здесь нет заявления об ускорении устройства.
- Ещё не проверены содержимое инициализированного module cache на актуальном iPhone, конкретный dynamic bundle URL, фаза первого запроса и доля storage/JS/render в общей отсечке Home.
- Приложение не перезапускалось и не инструментировалось. Чтение metadata через существующий inspector не удалось: 12 сентября в 11:04 UTC Metro не сообщил подключённый main-JS target Phraseman. [Результат проверки подключения](C:/appsprojects/phraseman/.codex-tmp/startup-proof/lesson-runtime-metadata.json).
- Нет подтверждения, относится ли наблюдаемая пользователем проблема к Metro/dev, установленной сборке без Metro или обоим режимам. Эта разница принципиальна: найденный дополнительный запрос не обосновывает ускорение установленного native-релиза.

## Следующий шаг и критерий допуска

Сначала уточнить режим проблемного запуска и получить подключённое устройство/профиль этой сборки. В dev проверить существующий кэш и факт лишнего bundle-запроса, не изменяя приложение. Для релиза нужны собственные startup-отсечки/профиль: переносить на него dev-вывод запрещено.

Рассматриваемый узкий вариант — в Home обращаться к **уже обязательно загруженному** модулю на том же этапе работы, не меняя resolver, данных, момента прогрева других экранов или кэшей. Пока исходные условия и влияние не подтверждены на целевом запуске, этот вариант не реализуется. Ни общий progress store, ни фоновые очереди не включены в допустимую область правки.

## Находки и предложения

Найден предметный кандидат без идеи «загрузить потом», но его статус — проверенный механизм, не готовая оптимизация. Для продолжения нужна проверка на целевой сборке; отсутствие подключения и неуточнённый режим не заменяются предположением о гарантированной безопасности.
