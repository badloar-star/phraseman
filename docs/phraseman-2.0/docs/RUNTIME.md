# Runtime, приоритеты и очередь

## Сначала существующая система
В `app/app_resume_policy.ts` уже есть coalescing queue с ключом, cancel и serial drain [C04]. `app/_layout.tsx` имеет несколько bootstrap/preload систем [C03]. Это не доказательство, что они все лишние; это карта точек аудита. Задача — оставить один понятный контракт исполнения, не ещё один framework поверх существующих.

## Предлагаемая иерархия работ
P0: немедленная реакция UI и минимальная локальная гидратация активного экрана. P1: подтверждённое действие пользователя, сохранение результата, критическая авторизация/entitlement. P2: локальное восстановление и запрос необходимых данных активного экрана. P3: отложенная синхронизация, flush и локальное обслуживание. P4: необязательный prefetch и диагностика. Это предложенные приоритеты, которые надо сопоставить с реальным кодом; не утверждение, что такие очереди уже реализованы.

Не помещать всю сеть в длинную глобальную последовательную цепь: это создаст head-of-line blocking. Конкурентность ограничивать отдельно для сетевых загрузок, дисковых записей и аудио. Общий durable write path имеет приоритет над prefetch. Нужны дедупликация, fairness, deadline, cancellation, retry с пределом и владелец результата. Цифры лимитов выставить после baseline, не по вкусу.

## Карточка job
`id`, `featureOwner`, `codePath`, `trigger`, `scope(account/locale/screen)`, `priority`, `dedupeKey`, `ttl`, `maxConcurrent`, `timeout`, `retryLimit`, `cancelOn`, `reads/writes/bytes`, `cpu/memory`, `observableErrors`, `keep/remove/archive`, `auditSHA`. Шаблон в registries; нет job без регистрации. На микроправку кнопки обычно пишется «существующий job не меняется, новых нет», а не запускается новый фоновый pipeline.

## Старт и возврат
Первый полезный экран не должен ожидать достижения/ауры/спины/league/background AI. Не грузить packs неактивного V2 на холодном старте. Не выполнять сеть в module evaluation. Account generation и нужная восстановительная защита сохраняются. При смене аккаунта/языка/экрана запросы не применяют старый результат. Отменённый UI consumer не уничтожает обязательную durable запись.

Кешированный экран показывается вместе с честным состоянием freshness. Ошибка не превращается в вечный skeleton и не скрывается для «премиального» вида. Empty и unavailable различаются. Возврат из фона оставляет время касанию/первому кадру; задержки 900/2500ms в просмотренном коде не объявляются идеальными без измерения.

## Измерения
Release build на реальном слабом телефоне; одинаковый сценарий/сеть/данные, несколько запусков и p50/p95. Метрики: cold/warm start до действия, resume, tap-to-feedback, навигация, scroll, peak memory, pending jobs, JS/native/assets bytes. Кандидатные регрессионные пороги задаются отдельно после baseline, не скрываются под обещанием «летает». Dev Metro bundling 34 секунды и runtime startup 2 секунды — разные измерения.

## Очистка bundle
Инвентаризировать static/dynamic imports, router auto-discovery, native packages, embedded assets и manifests. Выключенный flag не гарантирует исключение. Архивы Макса и генераторов вне release roots. Удаление большого временного файла из git не доказывает уменьшения установленной сборки. Нельзя удалять библиотеку анимации, если она ещё обслуживает нужную навигацию.

Сравнивать production/release сборки в одинаковых условиях; developer overhead не принимать за пользовательский baseline. Официальный обзор React Native отдельно рассматривает JS и UI frame rate и рекомендует release-проверки [W12]. Конкретные пороги устанавливаются по фактическим устройствам, а не переносятся из комментариев старого кода.

## Карта и сделанное по коду (сессия ядра, 2026-10-01, PM-211/213/214/215)
Карта строилась по коду и реестру PM-210, без замеров на устройстве. Подтверждённые дефекты и правки:

- **Кэш друзей не принадлежал аккаунту (PM-213).** Один общий ключ без uid, once-промис на процесс, память переживала смену аккаунта; позднее чтение диска прошлого владельца могло лечь в память нового. Теперь `resetFriendsTabSwrWarmForAccountSwitch()` вызывается из стирания данных аккаунта (`app/cloud_sync.ts`), а чтение диска помнит владельца и эпоху сброса и при несовпадении отбрасывается (лог `[FRIENDS-WARM]`).
- **Прогрев друзей ждал первый кадр (PM-211).** Чтение двух ключей и разбор до 240 профилей входили в бюджет 350 мс корня, хотя Главная друзей не показывает. Теперь вызывается после публикации снапшота и не ожидается.
- **Очередь foreground-задач (PM-215).** Serial-очередь не имела потолка на задачу: одна зависшая задача держала все остальные, а отказ глотался пустым catch. Теперь дедлайн на задачу (`FOREGROUND_TASK_DEADLINE_MS`, 10 с — до замера) и лог `[RUNTIME-QUEUE]`.
- **Прогрев арта достижений (PM-213/PM-215).** Качал пачки при свёрнутом приложении и не уступал сети живого занятия. Теперь каждая пачка под арендой «интерактивной тишины сети», в фоне очередь останавливается и забывает URL (повтор по следующему событию, лог `[RUNTIME-PREFETCH]`).

Проверено и признано в порядке (правок не нужно): прогрев озвучки фраз (`hooks/phrase_audio_ahead_prefetch.ts`) — аренда, отмена по фону и аккаунту, 2 воркера, потолок 6 МБ; синхронизация `cloud_sync` гасится перед сменой аккаунта; outbox прогресса/поддержки/отзывов проверяют владельца перед отправкой; общий `AsyncStorage` не получает записей от prefetch (озвучка и арт идут в файловый кэш).

Не принято без замера на устройстве: лимиты параллельности и дедлайн (PM-215-A3), «честное пустое/ошибка» и вечный skeleton на экранах (PM-214, зона «Дизайн»). Сценарии замера — в отчёте сессии.


## Измерение release bundle (PM-216, ядро, 2026-10-02)
Размер репозитория, `assets/` на диске и архива EAS — не размер приложения. Три числа держим раздельно:
- **исходники** (`assets/` на диске) и **архив EAS** (минус `.easignore`) — `node scripts/pm009_asset_bundle_inventory.mjs` → `evidence/PM-009_asset_bundle_inventory.md`; колонка «в бандле» — верхняя граница по статическим `require()` (достижимость Metro не строится). Состояние на 2026-10-02: исходники 107.08 МБ, архив EAS 15.22 МБ, в бандле ≤ 13.86 МБ (501 файл), в архиве но не в бандле 1.37 МБ.
- **JS / assets / native по платформам** — только из релизной сборки: `node scripts/pm216_release_size_report.mjs <каталог expo export> [--ipa файл] [--aab файл]` (скрипт читает готовый результат `expo export`, сам ничего не собирает; native = установочный файл − JS − assets, помечено как оценка). Тяжёлую сборку запускает владелец/CI под светофором.

Кандидаты «в архиве, но не в бандле» (95 файлов, 1.37 МБ) НЕ удалены сознательно: они весят только в архиве EAS, на установленное приложение не влияют; часть привязана к запечатанному MAX и к темам Главной (зона «Дизайн»/решение владельца), а `level-spin-rewards/*` ссылаются тесты и генераторы. Удалять — по D78 с картой потребителей из PM-009 и отдельным решением.

## Регрессионные performance gates (PM-220, ядро, 2026-10-02)
Матрица `config/performance-gates.json`, сторож `tests/pm220_performance_gates.probe.ts`. Пять сценариев: старт, возврат из фона, навигация, скролл, тренировка — у каждого ≥ 2 исходниковых сторожа (уже существующие: `perf_freeze_contract`, `layout_stability_contract`, `startup_*`, `app_resume_policy`, `pm210/pm212` и др.) и ≥ 2 метрики замера на устройстве. «Средний FPS» запрещён как единственное доказательство.
Числовых порогов пока НЕТ: `threshold = null`, пока нет `config/perf-device-baseline.json` (минимум слабый Android + iPhone, release, ≥ 5 запусков, p50/p95). Проба запрещает любое число без baseline, а с baseline — порог строже худшего p95. Снять baseline может только владелец с реальными телефонами.
