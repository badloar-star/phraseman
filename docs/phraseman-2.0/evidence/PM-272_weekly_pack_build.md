### Как это согласовано с PM-275 (`spireReportSteps`)

- Путь: `spire_packs/{lang}/{tier}/{weekId}.json`, ровно тот, который читает
  `spire_progress.ts::resolveExpectedPackHash`.
- `packHash` лежит в **customMetadata** файла (`metadata.metadata.packHash`),
  то есть там, где его ищет `resolveExpectedPackHash`. Формат `sp1_<32 символа base64url>`
  проходит `PACK_HASH_RE` (`[A-Za-z0-9:_-]{8,128}`).
- `weekId` считается от понедельника по UTC (`spireWeekId(spireWeekStartMs)`).
  Совпадает с `getWeekKey(isoDateUtc(now))` на сервере отчётов. Проверено: 24.09 → `2026-W39`,
  вс 27.09 23:00 → `2026-W39`, пн 28.09 00:05 → `2026-W40`.
- Файл недели без `force` **не перезаписывается**. Если пересобрать его посреди недели
  с другим хешем, отчёты с прежним хешем получат `pack_mismatch`.
  Сборка детерминирована: тот же пул даёт тот же хеш, повторный запуск ничего не ломает.

### Схема пакета (TOWER_CONTRACT §4)

```
{ schema:'spire-pack-v1', weekId, lang, tier, packHash, saltId,
  timer:{ baseMsByKind, perFloorDecay, floorMin },
  aboveCloudsCyclesFloors:[11..15], pendingKinds:{listen,dictate,voice},
  source:{ poolVersion, publicationFingerprint, legacyPool, poolTaskCount },
  stats:{ slots, uniqueTasks, reusedAcrossSteps, fallbacks, excludedFlagged },
  floors:[ { floor, guardian, voiceRequired, hardness,
             steps:[ { step, sets:[ { tasks:[publicTask×10], answerFingerprints:[[..]×10] } ×3 ] } ] } ] }
```

По сравнению с черновиком контракта добавлено:
- `saltId`: соль отпечатков вместо `matchId` Арены. Клиент уже ждёт её в
  `SpireStepPlan.saltId` → `arenaAnswerFingerprint(saltId, …)`;
- `aboveCloudsCyclesFloors`: этажи 16+ проходят наборы 11..15 по кругу, отдельного
  контента для них нет;
- `pendingKinds`, `source`, `stats`, `hardness`: служебные поля для честного
  экрана и диагностики.

### Логика плана = Арена без дуэли (A2)

Каждое задание собирается через `toPublicTournamentTask(task, saltId)`. Из
payload вырезаются `explanation`/`wrongOptionReasons`, как в
`arena_duel_v3.ts::arenaPlanTask`. Задание принимается, только если его режим проходит `arenaIsTaskMode`.
Ответы (`correctIndex`, `correctTokens`) в публичную форму не попадают. Отпечатки
лежат отдельным полем набора, параллельно `tasks[i]`.

Пул читается тем же запросом, что `arena_v2.ts::loadArenaTaskPool`, и проходит ту же проверку:
`validateTournamentTaskForNewRoom` / `validateArenaTaskForNewRoom`, сверку публикации и
доказательство Меркла. Индексы Арены уже есть, новых не нужно. Файлы Арены не тронуты.

### Выбор заданий

- **Внутри ступени** (3 набора × 10) задание не повторяется никогда.
- Каждая ячейка «режим × сложность» проходит пакет по своей перемешанной очереди, поэтому
  повтор между ступенями возникает только после её исчерпания.
- Не хватает ячейки (в es `find_oddity:3` = 0) → берётся запасная цепочка: тот же режим с
  соседней сложностью, затем соседний режим «выбора», затем любой.
- Режимы по этажам (§4.4): 1–2 — выбор 8 + пары 2; 3–4, 6–9, 11–15 — выбор 6 + сборка 3 +
  пары 1; Стражи 5/10/15 — выбор 4 + сборка 4 + пары 2.
- Трудность `h = 0.65·tier/11 + 0.3·(floor−1)/14 (+0.1 на 11+, +0.05 Страж)`, средняя
  сложность набора `1 + 2h`. Гранит, этаж 1 — всё лёгкое; Алмаз, этажи 13–15 — всё трудное.
  Внутри набора задания идут от лёгкого к трудному.
- Задания, снятые оператором (PM-287, `config/spire_task_flags_{lang}`), исключаются через
  контракт PM-287 (`parseSpireTaskFlagsDoc` + `spireFlaggedTaskIds`), одно чтение на язык.

| Что | Сколько |

## Открытые вопросы владельцу

1. **es/de/fr сейчас без пакета.** Файлы `content/arena-multilingual/generated/{es,de,fr}`
   проверены по дистракторам (PM-285), но их `manifest.json` = `verdict: BLOCK`,
   `releaseEligible: false`, и контур Арены не опубликован. Сборщик честно пропускает
   язык (`target_contour_not_published`), клиент показывает «скоро» (§4.8). Чтобы языки
   появились в Шпиле, нужна публикация контура через админку Арены (D55/T41 разрешают
   публикацию без носителя). После неё следующий крон (или `adminSpirePackBuild`)
   соберёт пакет сам. Никакой отдельной галки «включить язык» нет (как в PM-287).
2. **Слух/диктант/голос.** По §4.4 на 6–9 нужны «на слух, диктант», а с 11 этажа —
   «голос обязателен». В пакете их нет: `audioUri` не решён (PM-286), голосовые задания
   сняты из пула Арены (`validateTournamentTaskForNewRoom` отвергает `isVoice`). Поэтому
   `voiceRequired: false`, а `pendingKinds` перечисляет недостающее. Решение нужно
   владельцу: звук записанным файлом в Storage или голосом телефона (TTS) → тогда
   611 черновиков PM-286 (только en) смогут войти в пакет.
3. **Шпиль включают посреди недели.** Пока `config/spire_v1.enabled=false`, крон ничего
   не собирает (экономия). После включения нужно один раз вызвать `adminSpirePackBuild`,
   иначе до воскресенья отчёты будут `pack_unknown`. Кнопки в админке пока нет. Вариант:
   собирать и при выключенном Шпиле (≈4000 чтений в неделю впустую) — выбор за владельцем.
4. **Удаление Арены (TOWER §7).** Сборщик читает `arena_v2_config/current` и
   `tournamentTasks`. При удалении Арены как режима эти документы и коллекцию нужно
   сохранить: они входят в список «оставить».
5. **Раскладка режимов и формула трудности** (выбор 8/6/4, сборка 0/3/4, пары 2/1/2;
   веса 0,65/0,3) — мои предложения по §4.4, не решение владельца. Сейчас это
   константы в коде. Если владелец захочет крутить их без релиза, их можно перенести в
   `config/spire_v1`.
