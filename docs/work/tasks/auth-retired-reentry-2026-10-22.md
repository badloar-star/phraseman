# Разбор: повторный вход после окончательного удаления аккаунта (вопрос владельцу №26)

Governance-ID: TG-EA17211A08BE
Status: Анализ (только чтение, код не менялся)
Owner: Ядро (сессия 1), по запросу координатора 22.10; находка — 5 · ВХОД.

## Outcome

Ответ на три вопроса: (1) используется ли список постоянных запретов как бан; (2) что будет, если удалять пользователя Firebase Auth; (3) рекомендация.

## Что на самом деле происходит (уточнение к находке Входа)

- Запрет: `account_deletion_permanent_denials/adel_deny_<sha256(identity)>`. При удалении он ставится на **всё замыкание личности** — основной `authUid`, `stableUid` и все связанные личности (`account_delete_job.ts:313-319`, `cleanIdentityClosure`).
- Вход проверяет запрет по своему Firebase uid: `auth_identity.ts:2057-2059` и `:2094` → `throwIdentityRetired('auth')`.
- Окончательная очистка (после grace) **уже удаляет пользователя Firebase Auth** (`account_delete.ts:2028`, `admin.auth().deleteUser(authUid)`). После этого тот же Google или Apple при новом входе получает НОВЫЙ uid, и старый запрет не срабатывает.
- **Дыра:** удаляется только ОДИН, основной `authUid`. Остальные Firebase-пользователи замыкания остаются живыми, а запрет на них стоит навсегда. Это, например, вход через Apple, привязанный при слиянии с Google, или прежний гостевой uid. Человек входит именно этим способом → тот же uid → `identity_retired` навсегда.
- Вторая причина того же симптома — сбой самого `deleteUser`: инцидент 12.10 «authDeleted=false у всех трёх». Тогда остаётся живым даже основной uid.
- Во время grace (14 дней) отказ задуман: там должен работать сценарий восстановления (`account_delete_restore.ts`). Это не дыра.

## (1) Используется ли список как бан? — НЕТ

Читают его только как ограду «личность удалена», а не как модерацию:
- `account_gate.ts:96-144` — отказ серверных вызовов для удалённой личности;
- `revenuecat_shards.ts:484/574/948` — не начислять Plus и не переносить покупки на удалённую личность;
- `auth_recovery.ts`, `auth_merge.ts` — не восстанавливать и не сливать удалённое;
- `premium_expiry_cron.ts`, `dialogue_v2_*_repository.ts` — не писать данные удалённой личности.
Админка (`admin/v2/legacy.html`) этот список не читает (0 упоминаний). Модерационные баны — отдельный механизм по хешу почты (`replaceBanWithHash`, `account_delete.ts:1584/1995`); они переживают удаление намеренно, и это не трогаем.

## (2) Последствия удаления пользователей Firebase Auth

- **Данные и журналы:** к моменту `deleteUser` всё уже стёрто или обезличено (`deleteUser` идёт последним шагом после надгробия). Удаление Auth-пользователя ничего нового не стирает.
- **RevenueCat:** покупатель регистрируется по `canonicalUserId` = stableUid (`app/revenuecat_init.ts:275`), а не по Firebase uid. Удаление Auth-пользователя RevenueCat не затрагивает.
  - Вернувшийся человек получит НОВЫЙ stableUid. Подписка, оплаченная старым аккаунтом, к нему сама не перейдёт.
  - «Восстановить покупки» вызовет перенос в RevenueCat, но сервер ОТКАЖЕТ: запрет на старом stableUid остаётся (`revenuecat_shards.ts:948-954`, `transferIdentities`).
  - Это отдельное решение владельца: человек удалил аккаунт, но подписка в App Store / Google Play у него могла остаться активной.
- **Рефералы, вводный доступ, подарки:** новый stableUid = новый пользователь. Можно повторно получить вводный 72-часовой доступ и стать «новым» рефералом. Злоупотребление ограничено: удалить аккаунт и ждать 14 дней grace ради 72 часов невыгодно. Но реферальную награду пригласившему стоит проверить на повтор по устройству.
- **Повтор uid:** удалённый Firebase uid никогда не выдаётся повторно, поэтому запрет на нём после удаления безвреден — снимать его не обязательно.

## (3) Рекомендация

**Не снимать запреты, а удалять ВСЕХ Firebase-пользователей замыкания при окончательной очистке.**
- Вместо одного `deleteUser(authUid)` пройти по всем auth-личностям `frozenIdentityClosure`. Каждый `auth/user-not-found` = уже удалён, писать в журнал. Отдельная стадия с курсором, как прочие, чтобы таймаут не потерял хвост.
- Запреты остаются как ограда данных и покупок. На удалённых uid они инертны, на stableUid по-прежнему защищают от «воскрешения» данных и денег.
- Для уже удалённых аккаунтов, у которых живы связанные Auth-пользователи, — разовая дочистка: найти задачи `account_deletion_jobs` со статусом completed, взять замыкание, вызвать `deleteUser` для каждой auth-личности. Только чтение и удаление Auth, без Firestore-данных. Число таких людей — посчитать перед запуском (только чтение); выполнять только по «да» владельца.
- Почему не «снимать запрет»: снятие без удаления Auth-пользователя вернуло бы тот же uid к старым ссылкам auth_links и привязкам, то есть к риску склейки с недочищенным. Удаление Auth-пользователя даёт чистый новый uid, а запрет оставляет защиту на месте.

**Отдельно для владельца (вопрос №26):** подписка, оплаченная до удаления. Сейчас её нельзя перенести на новый аккаунт (запрет на старом stableUid). Варианты:
- (а) так и оставить: удалил аккаунт — подписка привязана к удалённому, а в магазине её можно отменить;
- (б) разрешить перенос подписки с удалённой личности, если перенос инициирован тем же Apple ID / Google-аккаунтом (RevenueCat TRANSFER). Это правка денежного пути, нужен просмотр Ревизора.

## Architecture

См. выше: запрет по замыканию (`account_delete_job.ts:313`), проверка входа (`auth_identity.ts:2094`), удаление Auth только для основного uid (`account_delete.ts:2028`).

## Security and privacy

Рекомендация не ослабляет защиту: запреты остаются, удаляются только учётные записи входа, которые и так должны быть удалены по политике («удаление аккаунта»). Это скорее закрывает долг перед политикой: связанные учётные записи входа сейчас переживают удаление.

## Technical debt

Связанные Firebase Auth-пользователи переживают окончательное удаление — долг перед политикой удаления. Владелец — Ядро + 5 · ВХОД.
