# Раздел админки «Соцсети» + петля обратной связи для генерации фраз

Статус: PLAN (не начато). Дата: 2026-07-06. Владелец: badloar@gmail.com.

## 1. Цель одним абзацем

Отдельный раздел в админке (`admin/index.html`), который раз в день собирает детальную
статистику опубликованных коротких видео с 5 площадок (YouTube, Instagram, Facebook,
Threads, TikTok), связывает каждый пост с конкретной сгенерённой фразой/темой/форматом, и на
основе того, **что реально заходит**, кормит генератор фраз для новых шортсов. Публикация
остаётся на Publer — мы только читаем аналитику и замыкаем петлю обратной связи.

## 2. Ключевая проблема (решается ПЕРВОЙ)

Publer НЕ даёт связку «пост на площадке ↔ наша фраза». Без неё дашборд показывает цифры, но
ИИ не может учиться. Решение — двойное:

- **Маркер-тег.** Студия `lingman-montazher` при экспорте видео знает `phraseId`. Она кладёт в
  конец описания поста незаметный маркер `#pmv_<shortId>`, где `shortId` — короткий код фразы.
  Сборщик статистики парсит этот тег из описания поста через API площадки → восстанавливает
  связку. Работает на всех 5 площадках, от Publer не зависит.
- **Реестр публикаций.** Студия при экспорте пишет документ в Firestore
  `social_publications/{shortId}` c полями: `phraseId, theme, format, lengthSec, lang,
  createdAt, platforms[]`. Это источник истины «что за фраза скрывается за постом» и запасной
  канал матчинга по дате+площадке, если тег вдруг срезан площадкой.

`shortId` — детерминированный короткий хеш от `phraseId` (например, base32 от первых 6 байт
sha1), чтобы тег был компактным и обратимым через реестр.

## 2b. КРИТИЧНО: половина воронки УЖЕ построена (не дублировать!)

В проекте уже есть внутренняя воронка (маркетинговый пайплайн VIRAL / `content/marketing/`):

- **UTM-метки роликов** — `MARKETING_SYSTEM.md §3`: `?utm_campaign=<код_ролика>` (напр.
  `0705_fillerwords`). Квиз `/start/` сохраняет UTM и прикрепляет к заказу.
- **Клики/переходы/показы пейвола** — `functions/src/site_stats.ts` (`siteStatsTrack`):
  считает clicks, checkout_clicks по дням в `site_stats/daily_YYYY-MM-DD`.
- **Триал/оплата привязаны к ролику** — Firestore `web_premium_orders` хранит UTM ролика
  внутри заказа (email, тариф, код, utm).
- **RevenueCat-вебхук уже есть** — `functions/src/revenuecat_shards.ts` ловит события покупок.
- **Раздел админки с воронкой уже есть** — `admin/site.html` (вкладка «🌐 Сайт»): заказы,
  воронка, UTM, статусы.
- **Ловля метки в приложении уже есть** — `app/+native-intent.tsx` вытаскивает `?ref=` из
  deep link (расширяется на `utm`/`pmv` тем же механизмом).

**Вывод:** внутренняя половина воронки (клик→установка→триал→оплата, привязанная к ролику) —
УЖЕ РАБОТАЕТ. Не строить заново. Задача сводится к трём вещам:

1. **Достроить внешнюю половину** — метрики самих площадок (показы/лайки/удержание видео из
   API 5 площадок). Сейчас `site_stats` знает только переходы на сайт, но НЕ то, что было
   внутри соцсети до клика.
2. **Наложение графиков** — свести в один SVG-график с несколькими слоями на одной оси дней:
   `показы видео → клики (site_stats) → триалы/оплаты (web_premium_orders + RevenueCat)`.
   Прямой запрос владельца «наложение нескольких графиков на один».
3. **Унифицировать метку** — свести `utm_campaign` (код ролика) ↔ `phraseId` (генератор) ↔
   `#pmv_<shortId>` (тег в описании) к ОДНОМУ коду ролика, чтобы петля замкнулась
   сквозняком от показа до оплаты.

### Единый код ролика (campaignId)

Единая метка `campaignId` = код ролика, общий для всех слоёв:
- в UTM: `utm_campaign=<campaignId>`
- в теге описания: `#pmv_<campaignId>` (или связан с ним через реестр)
- в реестре студии: `social_publications/{campaignId}` c полем `phraseId`

Формат сохранить совместимым с существующим (`0705_fillerwords` = дата+тема), но добавить в
реестр явную привязку к `phraseId`, чтобы генератор понимал «этот код = эта фраза».

## 3. Модель данных (Firestore)

- `social_publications/{shortId}` — реестр (пишет студия):
  `{ shortId, phraseId, theme, format, lengthSec, lang, createdAt, platforms: string[],
     publerPostIds?: Record<platform,string> }`
- `social_metrics/{shortId}/snapshots/{yyyymmdd}` — суточные срезы (пишет cron-сборщик):
  `{ platform, views, likes, comments, shares, saves, reach, avgWatchPct?, capturedAt }`
  (по одному документу на площадку в день; поля, которых площадка не отдаёт, отсутствуют)
- `social_platform_posts/{platform}/{platformPostId}` — сырое сопоставление
  «пост площадки → shortId», кэш распарсенного тега, чтобы не парсить повторно.
- `social_ranking/current` — агрегат для генератора (перестраивается cron-сборщиком):
  `{ byTheme: {theme -> score}, byFormat: {...}, byLength: {...}, topPhrases: [...],
     worstPhrases: [...], updatedAt, method, sampleSize }`
  score = нормализованная вовлечённость (взвешенная сумма метрик на показ), сглаженная по
  объёму выборки (тема с 1 видео не должна побеждать тему с 20).

Существующие коллекции воронки (НЕ создавать заново, читать как есть):
- `site_stats/daily_YYYY-MM-DD` — клики/переходы/показы пейвола (пишет `siteStatsTrack`).
- `web_premium_orders` — заказы с UTM ролика (email, тариф, код, статус paid).
- RevenueCat-события — через существующий `revenuecat_shards.ts` (при необходимости расширить,
  чтобы фиксировать `campaignId`/источник в момент триала, а не только оплаты).

Новая связка воронки:
- `campaign_funnel/{campaignId}/daily/{yyyymmdd}` — сведённый по дням слой воронки на один
  ролик: `{ views (из social_metrics), clicks (из site_stats), trials, paid, revenue }`.
  Это источник для графика-наложения. Перестраивается тем же cron, что и ranking.

Индексы Firestore добавить в `firestore.indexes.json`. Правила `firestore.rules`: коллекции
`social_*` и `campaign_funnel` — чтение только админам, запись только с бэкенда (functions).

## 4. Сбор статистики (Firebase Functions, TypeScript)

Новый модуль `functions/src/social/` (много мелких файлов, по правилу coding-style):

- `social/secrets.ts` — `defineSecret` для всех токенов (см. §7), паттерн как в
  `admin_daily_digest.ts`.
- `social/youtube.ts` — клиент YouTube Data + Analytics API. Метрики: views, likes, comments,
  avgViewPercentage (удержание), subscribersGained.
- `social/meta.ts` — общий клиент Graph API для Instagram + Facebook (один долгоживущий токен):
  reach, impressions, engagement, saves, shares.
- `social/threads.ts` — Threads Insights API: views, likes, replies, reposts, quotes.
- `social/tiktok.ts` — TikTok Display/Content API: views, likes, shares, comments,
  avgWatchTime. (Активируется после одобрения приложения — см. §7, риск по срокам.)
- `social/collector.ts` — оркестратор: для каждой площадки тянет посты за окно (напр. 30 дней),
  парсит `#pmv_<shortId>` из описания, матчит с реестром, пишет `social_metrics` снапшот.
- `social/ranking.ts` — перестраивает `social_ranking/current` из накопленных снапшотов.
- `social/cron.ts` — `onSchedule` (Firebase scheduler) раз в сутки: collector → ranking.
- `social/admin_api.ts` — `onCall` функции для админки: `socialGetOverview`,
  `socialGetPostDetails`, `socialGetRanking`. Проверка admin, `enforceAppCheck` как в проекте.

Все внешние вызовы — с обработкой ошибок, ретраями и логированием (одна площадка упала — не
роняем остальные; частичный успех фиксируем).

## 5. Раздел админки «Соцсети» (`admin/index.html`)

Новый пункт меню «Соцсети». Содержимое:

- **Сводка сверху:** плитки по площадкам (всего постов, суммарные просмотры, средняя
  вовлечённость, тренд к прошлой неделе).
- **График по дням** (SVG, как уже сделано для OpenAI budget — переиспользовать подход
  series-графика из заметки `phraseman_openai_budget_full_coverage_and_daily_chart`).
- **Таблица постов:** дата, площадки, тема/фраза (из реестра), просмотры, вовлечённость,
  удержание. Сортировка/фильтр по площадке и теме.
- **Топ-контент и провалы:** две колонки — «что лучше всего зашло» / «что не зашло», по темам
  и форматам. Это визуализация `social_ranking/current`.
- **График-наложение сквозной воронки (прямой запрос владельца):** один SVG-график, ось X —
  дни, несколько накладываемых линий-слоёв: `показы видео` → `клики` → `триалы` → `оплаты`.
  Слои можно включать/выключать чекбоксами (наложить любые метрики друг на друга для
  сравнения). Разные шкалы (показы тысячами, оплаты штуками) — двойная ось Y или нормализация,
  переключатель. Фильтр по конкретному ролику (`campaignId`) → та же воронка для одного видео:
  «этот ролик дал X показов → Y кликов → Z триалов → N оплат». Данные из
  `campaign_funnel/{campaignId}/daily`.
- **Привязка «статистика видео ↔ статистика воронки» в таблице:** к каждой строке ролика —
  не только просмотры/лайки площадки, но и колонки клики/триалы/оплаты/выручка (сквозняк). Это
  и есть «привязка статистики к статистике с видео», которую просил владелец.
- Стиль — по правилу дизайна владельца: без обводок контейнеров, тон/градиент, эффекты
  клиппать по радиусу (см. `design_no_borders_tone_only`).

Данные грузятся вызовом `socialGetOverview` при открытии раздела (паттерн автозагрузки как в
`phraseman_admin_sections_autoload_users`).

## 6. Петля в генератор фраз

Генератор (`lingman-montazher` / `scripts/build_lingman_wednesday_*` / промпт-слой):

- Перед генерацией новой пачки фраз читает `social_ranking/current` (через экспорт функции или
  прямой Firestore-доступ студии).
- Подмешивает в промпт компактную сводку: «темы/форматы с высокой вовлечённостью — делай
  больше в эту сторону; вот что не заходит — избегай». Не жёсткий фильтр, а вес/подсказка, чтобы
  не схлопнуть разнообразие.
- Логирует, какой рейтинг был учтён при генерации (для аудита «почему сгенерилось именно это»).

**Главное правило веса:** оплата важнее лайка. Ranking взвешивает не только вовлечённость
площадки, но и КОНЕЦ воронки — триалы и оплаты из `campaign_funnel`. Фраза с 100k просмотров
и 0 оплат для генератора хуже, чем фраза с 20k просмотров и 15 оплатами. `score` =
f(вовлечённость, клики, триалы, **оплаты/выручка**) с наибольшим весом на оплаты. Иначе ИИ
будет гнать «виральное, но не продающее».

Правило: рейтинг — это подсказка, а не диктатура. Разнообразие тем сохраняем (иначе петля
скатится в один формат).

## 7. Чек-лист токенов (делает ВЛАДЕЛЕЦ, я готовлю инструкции)

Отдельный файл: `specs/social-analytics-tokens-checklist.md`. Кратко:

- **YouTube** — Google Cloud проект, включить YouTube Data + Analytics API, OAuth или
  service-account с доступом к каналу. (Проще всего, делаем первым.)
- **Meta (Instagram + Facebook)** — бизнес/creator IG-аккаунт, привязка к FB-странице,
  Meta App, долгоживущий Page Access Token, permissions (instagram_basic,
  instagram_manage_insights, pages_read_engagement).
- **Threads** — Threads API, токен через тот же Meta-флоу.
- **TikTok** — TikTok for Developers app, Login Kit + Data/Display scope; **доступ к аналитике
  выдаётся после ревью приложения — заложить недели ожидания**. TikTok активируем последним.

Все токены — в Firebase secrets (`firebase functions:secrets:set ...`), НЕ в коде.

## 8. Порядок работ (вертикальными срезами)

1. **Фундамент связки + унификация метки:** `campaignId` как единый код ролика, маркер-тег в
   студии, реестр `social_publications` c привязкой к `phraseId`, свести `utm_campaign` к тому
   же коду, правила+индексы Firestore. (Без этого петля не замыкается.) Не требует токенов.
2. **Сквозная воронка из ТОГО, ЧТО УЖЕ ЕСТЬ:** собрать `campaign_funnel` из существующих
   `site_stats` + `web_premium_orders` (+ RevenueCat), сделать график-наложение в админке.
   Это даёт ценность СРАЗУ, даже до подключения API площадок (внешние показы пока пустые).
3. **Сквозной срез на YouTube:** сбор метрик площадки → снапшоты → влить `views` в
   `campaign_funnel` → ranking (с весом на оплаты) → петля в генератор. Доказать «зашло и
   ПРОДАЛО → ИИ учёл».
4. **Тираж на Meta:** Instagram + Facebook + Threads (один токен-флоу).
5. **TikTok:** подключить, когда одобрят приложение.

Каждый срез — атомарные коммиты в общую ветку, деплой functions + hosting, при необходимости OTA.

## 9. Явные риски / ограничения

- **Никакого скрейпинга** страниц площадок — против правил, банится, ломается. Только
  официальные API.
- **TikTok — узкое место по срокам** (ревью приложения).
- **Meta требует бизнес-аккаунты** и корректную привязку IG↔FB-страница.
- Publer-аналитика вторична (агрегированная, без связки с нашей фразой) — используется как
  сверка, не как основной источник.
- Токены — только в secrets; ротация при утечке (правило security.md).

## 10. Критерий готовности (по срезу YouTube)

- [ ] Студия при экспорте пишет реестр и кладёт `#pmv_<shortId>` в описание.
- [ ] Cron-сборщик раз в сутки тянет YouTube-метрики и пишет снапшоты + ranking.
- [ ] Раздел «Соцсети» показывает сводку, график, таблицу постов, топ/провалы.
- [ ] Генератор читает ranking и подмешивает его в промпт (с логом учёта).
- [ ] Правила Firestore закрывают `social_*` от неадминов.
- [ ] Секреты в Firebase secrets, ничего не захардкожено.
