## 🔴 Главная находка: функции в США, база в Европе

- Firestore проекта: `eur3` (Европа, мульти-регион). Проверено: `gcloud firestore databases describe` → `eur3 FIRESTORE_NATIVE`.
- Все функции: `us-central1` (`functions/src/callable_options.ts:3`, `REGION = 'us-central1'`).
- Каждое обращение функции к базе пересекает океан: примерно 100–130 мс туда и обратно вместо 5–10 мс внутри региона.

Журнал запросов прода (`authensurestablelink`, 18.10 09:48–10:07, только чтение) показывает:

Значит, 4–6 с — это не холодный старт, а сама цепочка обращений к базе через океан. Совет Ревизора 3.126 п.1 («`minInstances: 1`») этого не вылечит.

## 1. Функции пути входа: что делают и сколько стоят

Типичный путь для правил 2 и 3. Клиент уже выставил stableId из `link_lookup`, поэтому `linkedStableId === stableId`, ветка `b4` (`auth_identity.ts:2257–2271`). Последовательные обращения к базе:

### `authStampAnonOwnership` — `auth_identity.ts:2750`

Гость (анонимный вход) ставит метку владения своим stableId и получает одноразовый nonce. По этому nonce потом разрешено слияние: смотри вопрос 2. Короткая функция, но тоже ходит в базу через океан.

### `authMergeStableAccounts` — `auth_merge.ts:1680`

Явное слияние двух аккаунтов: `mergeStableAccounts` → `auth_merge.ts:1037`, резерв → `auth_merge.ts:519`, затем `processAccountMergeOutboxJob` синхронно в том же вызове. Переносит прогресс, события ошибок, рефералы (`repointReferralOnMerge`, 1505), записи RevenueCat, звёзды, наборы карточек. Самая тяжёлая функция пути — десятки транзакций.

### Восстановление по коду — `auth_recovery.ts:691, 1081, 1487, 1709, 2052, 2177`

В обычном входе Google/Apple не участвует. В проде мертво с 02.09 (`app_check_required`), подробности — в плане выкладки fe8734d4d.

## 2. Есть ли серверный путь, который переносит прогресс гостя в существующий аккаунт при правиле 2

**Да. Сервер это разрешает, правило 2 держится только на клиенте.**

- `authMergeStableAccounts` → `reserveStableAccountMerge`, `functions/src/auth_merge.ts:603–620`:
  - победитель — аккаунт, которым вызывающий владеет сейчас (существующий Google/Apple);
  - проигравший — гостевой stableId; принимается, если на нём есть анонимная метка владения (`requireAnonLoserClaim`) и клиент прислал её nonce (`verifyAnonMergeClaimNonce`, 613–617);
  - дальше `processAccountMergeOutboxJob` переносит прогресс гостя в существующий аккаунт.
- Сервер не проверяет, был ли целевой аккаунт новым (правило 1) или существующим (правило 2). Для него оба случая — «владелец двух аккаунтов просит слить».
- Клиентская точка вызова, по Ревизору 3.126: `app/auth_provider.ts:3425–3556`. При `preserveLocalProgress = true` идут presync и `mergeStableAccountsViaServer(local, remote)`. После 748ed272f анонимный конфликт с прогрессом получает `account_switch_required` и сюда не доходит. Путь без записи передачи (не анонимный конфликт, наследный reward-merge) остаётся — его достижимость проверяет Авторизация.
- Старые сборки (1.6.x, 2.0 до 748ed272f) этот вызов делают. Сервер им не мешает.

`authEnsureStableLink` прогресс гостя НЕ переносит:
- в ветках `b2–b5` (`auth_identity.ts:2226–2288`) источники — только найденный существующий аккаунт и его прежние id, гостевой stableId туда не попадает;
- `cleanupLegacyAuthIdentityDuplicates` (1442) сводит только документы с тем же `firebaseAuthUid`, то есть того же провайдера. У гостя другой анонимный uid.

Предложение (после «ок» координатора, серверная правка): закрыть правило 2 и на сервере.
- В `reserveStableAccountMerge` отказывать `merge_existing_account_forbidden`, если проигравший — гость с анонимной меткой, а победитель существовал ДО этого входа. Признак — `users/{winner}.createdAt` (или первая привязка `linkedAuth.linkedAt`) раньше `auth_time` вызывающего; точное поле выбрать по данным.
- Правило 1 не задевается: новый аккаунт создаётся в этом же входе, и слияния там нет — гость сам становится аккаунтом через `linkWithCredential`.
- Старые сборки на этот отказ уходят в свою ветку «слияние не удалось». Её поведение для правила 2 надо проверить на 1.6.x до выкладки.

## 3. Что из серверного можно делать ПОСЛЕ показа Главной, фоном

Ответ `authEnsureStableLink` нужен входу только для «кто ты» — какой stableUid. Обязательная часть, без неё нельзя пускать:
- проверки удаления и запрета;
- выбор аккаунта (`resolveStableUidForAuth`);
- проверка владения;
- транзакция привязки `repairIdentityDocumentsAtomically` — пишет `auth_links` и `users`.

Можно после ответа, отдельным заданием (запись в outbox + `onDocumentCreated`, как у `account_merge_outbox`):
- `finishUserIdentityRepairBestEffort`: правка `leaderboard` и уборка дублей (шаг 11);
- `upsertEmailContact` (шаг 12) — учёт почты для рассылок, входу не нужен;
- `enrichMetadataFromAuth` (шаг 4) — нужен только чтобы записать почту в `linkedAuth`. Транзакция пишет то, что прислал клиент, а дописать из Auth можно в задании;
- `restoreBanFromIdentityHash` (шаг 13) — тоже можно: бан ставится флагом в профиле, и клиент увидит его при следующей синхронизации. Но пару секунд забаненный будет внутри. Решение за координатором; по умолчанию оставить в ответе — одно чтение.

Важно: при `cpu gcf_gen1` процессор после ответа не гарантирован. Работа «после return» без задания может не выполниться, поэтому нужен outbox и триггер, а не `void promise`.

Окно вызовов `ensure_link` (шаг 1) можно запускать параллельно с шагами 2–3 и дожидаться перед транзакцией привязки.

## Что ускорить, по убыванию выигрыша

1. **Регион.** Перенести функции входа (`authEnsureStableLink`, `authStampAnonOwnership`, `authMergeStableAccounts`, затем восстановление) в `europe-west1`, рядом с `eur3`.
   - Ожидание: 4–6 с → 0,3–0,6 с на тёплом экземпляре.
   - Старые сборки зовут `us-central1` по имени, поэтому их копии в США оставить до ухода старых сборок, как с `voiceMinuteWalletMine`. Новая сборка зовёт Европу.
   - Нужна клиентская правка региона вызова (Авторизация) и новая сборка.
   - Тот же эффект у ВСЕХ функций проекта: каждая реплика ИИ теперь делает ещё 2–3 обращения к базе на окно вызовов и потолок расходов (+0,3–0,5 с через океан). Перенос горячих функций в Европу — отдельное решение владельца.
2. **Без переноса региона:**
   - память чтений на один вызов: `auth_links`, `users/{id}`, надгробия по одному разу;
   - `Promise.all` для независимых шагов 1–3 и 5–7.
   Ожидание: ~30 → ~12–15 обращений, то есть 4 с → ~1,5–2 с. Правка в `auth_identity.ts`, тесты `auth_identity*.test.ts` (2931 + 446 строк).
3. Уборку и учёт (шаги 4, 11, 12) — в outbox после ответа: −0,5–1,5 с, когда уборка срабатывает.
4. 🟡 Шум журнала: на каждый вызов три строки WARNING «Failed to validate AppCheck token» (`firebase-functions` проверяет присланный старыми клиентами битый токен App Check; энфорс выключен, пломба). Это деньги за журнал и шум. Убрать можно только на клиенте старых сборок — новые токен не шлют. На сервере не трогать: пломба App Check.
5. 🟡 `recoveryHintClientIp` (`auth_identity.ts:2466`) всё ещё берёт ПЕРВЫЙ адрес x-forwarded-for — подделываемый, как было в окнах до c055fd6d9. Перевести на `callerIpFromRawRequest` + `ipRateKey`.
