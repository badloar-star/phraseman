# ТЗ (после релиза): ранг монеты и визитка «Про» — покупка подтверждается сервером

Governance-ID: TG-5594EDE88DF4
Status: Proposed — после релиза 2.0.0 (находка Авторизации §AA-38 C3, запрос координатора 10.10 00:50). Кода нет.
Owner: сессия 1 · ЯДРО (полоса монет). Деньги → тесты + ревью агентом + выкладка владельцем.

## Что сейчас (проверено по коду)

- **Где идёт покупка.** Повышение ранга (app/coin_rank_upgrade_v1.ts) и визитка «Про» (app/profile_card_pro_v1.ts) тратят монеты
  только на телефоне:
  - `prepareRuneSpend` (app/level_spin_star_grants.ts) и ОДИН `AsyncStorage.multiSet` с новым рангом/«Про»;
  - сети нет.
- **Где лежат данные.** Ключи `coin_rank_v1:`, `profile_card_pro_v1:`, `level_spin_star_projection_v1:` — локальные:
  - путешествуют только в резервной копии смены аккаунта на этом же телефоне (app/cloud_sync.ts, `ACCOUNT_LOCAL_KEY_PREFIXES`);
  - в облако не уходят.
- **Что знает сервер.** Книга монет `users/{uid}.stars` + `star_operations` (functions/src/stars_ledger.ts):
  - начисления и подарки;
  - серверные траты (диалоги, Learning V2);
  - про ранг и «Про» — ничего.
- **Публичный ранг.** `coinRank` и `profileCardPro` в публичном профиле присылает телефон;
  functions/src/public_profile_projection.ts проверяет только диапазон / `=== true`.

## Последствия и риск эксплойта

| Сценарий | Что видит человек | Выгода нарушителю |
|---|---|---|
| Переустановка / новый телефон | Ранг и «Про» пропали, потраченные монеты «вернулись» (баланс = серверный) | **Нет**: покупка теряется вместе с тратой. Вред — честному человеку (теряет ранг) |
| Один аккаунт на двух телефонах | На каждом свой локальный учёт трат при общем серверном балансе | **Есть, средний**: одни монеты тратятся дважды (ранг на A, ранг/«Про» на B), обе покупки остаются |
| Подмена снимка профиля | Друзья видят ранг 19 / «Про» без оплаты | **Есть, косметический**: подделка статуса, денег не даёт |

Монеты не покупаются за реальные деньги, поэтому прямого финансового ущерба нет. Это вопрос честности рейтинга
и доверия к рангу. Лиги D162 считают только заработок (earn) и рангом не пользуются, их это не задевает.

**Почему не заплатка сейчас.** Самая быстрая мера — «сервер игнорирует coinRank/profileCardPro из снимка». Она
обнулила бы ранг и «Про» у ВСЕХ честных пользователей в глазах друзей. Монета-аватар — единственный аватар
приложения (D108), так что это видимая регрессия хуже самой дыры.

## Решение

1. **Функция `coinShopPurchase`** — onCall, `HOT_CALLABLE_OPTIONS`, без App Check (пломба). Образец —
   functions/src/ai_dialog_sync_purchase.ts.
   - Действия: `rank_up { expectedFromRank }`, `pro_buy`.
   - Цены — по серверной копии таблицы рангов; клиент цену не присылает.
   - Одна `runTransaction`:
     - `prepareStarOperations` + `commitStarOperations` с операцией класса `spend`;
     - стабильные opId: `coin_rank:<uid>:to_<N>`, `profile_card_pro:<uid>`;
     - тут же запись `users/{uid}.coinShop = { rank, pro, updatedAtMs }`.
   - Ответы:
     - повтор с тем же opId → `already_applied`;
     - `insufficient_coins`;
     - `stale_rank` (expectedFromRank ≠ серверный).
2. **stars_ledger.ts:** причины `coin_rank_upgrade`, `profile_card_pro` → класс `spend` в `STAR_OP_CLASS` и `STAR_OP_SOURCE`.
   - Тест: трата не двигает `earnedTotal`, неделю, сезон, счётчик D162.
3. **Публичный профиль:** `coinRank` и `profileCardPro` сервер берёт из `users/{uid}.coinShop`, значения из снимка
   телефона игнорирует. Включать только ПОСЛЕ переноса (п. 5), иначе — регрессия выше.
4. **firestore.rules:** клиенту запрещена запись поля `coinShop` в `users/{uid}`.
5. **Перенос уже купленного** — разовая функция `coinShopBackfill`.
   - Телефон присылает свою локальную цепочку рангов и флаг «Про».
   - Сервер принимает только непрерывную цепочку от текущего серверного ранга.
   - Списывает её полную цену из серверного баланса теми же opId.
   - Монет не хватает → переносит ту часть, на которую хватает. Остальное отклоняется и пишется в журнал.
   - Так ранг нельзя «напечатать»: без денег на сервере его нет.
   - Локальная трата по перенесённому opId снимается (как у остальных серверно подтверждённых трат), иначе цена
     спишется дважды.
6. **Клиент:**
   - Оптимистично: ранг/«Про» меняются на экране сразу, сеть догоняет.
   - Откат с понятным сообщением при отказе.
   - Защита от двойного тапа — уже есть: `expectedFromRank`, детерминированный opId.
   - Офлайн: покупка ставится в очередь с тем же opId, без второй цены.
   - **При входе** ранг/«Про» восстанавливаются из `users/{uid}`, который синхронизация уже читает — ноль лишних чтений.
7. **Логи:** `[COIN-SHOP]`. Вход (uid-хэш, действие, ожидаемый ранг), каждое ветвление со значением, ответ сервера,
   каждый ранний выход и catch.
8. **Джарвис:** новое поле `users/{uid}.coinShop` занести в `jarvis_data_contract_guard.test.ts` (или явно отметить
   «не читается»). Департамент монет при желании считает число покупок рангов агрегацией `.count()`.

## Стоимость Firebase

- **Покупка:** 1 вызов, 1 транзакция — чтение пользователя + запись пользователя + запись операции.
  Покупки ранга редкие (цена N × 1000 монет).
- **Вход:** 0 дополнительных чтений (`users/{uid}` уже читается синхронизацией).
- **Перенос:** 1 вызов на аккаунт за жизнь.

## Security and privacy

Новых персональных данных нет (ранг уже публичен). Политика конфиденциальности не затрагивается. App Check не включаем.

## Technical debt

До выкладки остаются двойная трата на двух телефонах и подделка публичного ранга — оба риска средние/косметические
и описаны выше.

## Verification

- **Функция:**
  - успех;
  - повтор (идемпотентность);
  - нехватка монет;
  - устаревший ранг;
  - чужой uid;
  - перенос: полная / частичная / отклонённая цепочка.
- **Книга:** трата не двигает earn-счётчики.
- **Правила:** клиент не пишет `coinShop`.
- **Клиент:** оптимистичный показ + откат; восстановление на «втором телефоне» из `users/{uid}`.

## Rollback

- Функцию не вызывать (флаг на клиенте).
- Публичный профиль вернуть к значениям из снимка (п. 3 за отдельным флагом).
