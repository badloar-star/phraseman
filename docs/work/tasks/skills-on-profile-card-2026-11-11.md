## Outcome

Человек, открывший чужую визитку, видит звезду навыков и шесть полосок уровней хозяина по правилам владельца (D207):
я и мои друзья — всегда; посторонний — только если у хозяина визитка «Про»; иначе блока просто нет (ни замка, ни «скрыто»).

Мера успеха этой задачи: правило видимости — одна чистая функция с тестом; блок для визитки — готовый компонент на семи
стилях; передача между людьми спроектирована без единого нового чтения Firestore, а всё, что требует сервера, вынесено
владельцу отдельным пунктом, а не написано втихую.

## Architecture

### Что есть сейчас (разведка, факты из кода)

- Чужая визитка читает ОДИН документ `public_profiles/{uid}` (`app/profile_card_public.ts` → `fetchPublicProfileCard`):
  кэш в памяти 10 минут, склейка одновременных запросов, копия на диске для первого кадра. Из документа берутся
  `profileCardPro`, `profileCardStyle`, `profileCardBio`.
- Стиль «Про» = `resolveProfileCardLook({ pro, style })` (`app/profile_card_styles.ts`): `pro === true` и стиль из шести → стиль, иначе обычная.
- В `public_profiles` клиент писать НЕ может (`firestore.rules`: `allow update/create/delete: if false`). Пишет только
  серверная функция `publicProfileProjectMine` (`functions/src/public_profile_projection.ts`) и только поля из своего
  жёсткого списка: неизвестное поле из запроса она молча отбрасывает.
- Клиент зовёт её из `app/public_profile_snapshot.ts` (`syncPublicProfileSnapshot`): собирает имя, аватар, ранг, «Про»,
  стиль, счётчики; считает `displayHash`; если хэш не изменился — вызова нет вовсе.
- `public_profiles/{uid}` читает ЛЮБОЙ вошедший пользователь (`allow read: if request.auth != null`). Отдельного
  «только друзьям» у этого документа нет.
- Друзья получают данные друг о друге вторым каналом — серверной выдачей `functions/src/friends_profiles.ts`, которая
  читает уже загруженный `users/{uid}.progress` (неделя друга, фраза дня) и отдаёт только принятым друзьям.

### Проект передачи (ни одного нового чтения и ни одной новой записи)

Что передаётся: только шесть уровней — массив из шести целых 0…30 в порядке `SKILL_IDS`
(`listening, speech, vocab, grammar, speed, social`), имя поля `skillLevels`. Очки, прирост за неделю, журнал действий и
дневные счётчики устройство не покидают.

Запись (одна, уже существующая):
1. `syncPublicProfileSnapshot` добавляет `skillLevels` в тот же объект `profile`, который уже уходит в
   `publicProfileProjectMine`. Отдельного вызова нет.
2. Уровни входят в `displayHash`, поэтому вызов происходит только когда уровень действительно изменился.
3. Чтобы рост уровня сам не будил сеть чаще раза в сутки: изменение одних только уровней отправляется не чаще одного раза
   в календарный день (метка дня в том же кэше `public_profile_snapshot_v1:<владелец>`); если вызов всё равно идёт по другой
   причине (имя, ранг, «Про») — уровни едут в нём бесплатно. Повод для отправки — старт приложения и существующие вызовы,
   нового таймера нет.

Чтение (ноль новых):
- Посторонний и друг: `normalizePublicProfileCard` разбирает `skillLevels` из ТОГО ЖЕ документа, который уже прочитан
  для визитки; уровни ложатся в ту же память и ту же дисковую копию, поэтому блок есть в первом кадре.
- Друг хозяина без «Про»: уровни приходят в ТОМ ЖЕ ответе серверной выдачи друзьям, которая уже читает `users/{uid}.progress`.

### Что упёрлось в сервер — НЕ написано, ждёт решения владельца

1. `publicProfileProjectMine` отбрасывает неизвестные поля. Чтобы уровни дошли до чужих, в серверный список нужно добавить
   `skillLevels` (проверка: ровно шесть целых 0…30, иначе поле не пишется) и выложить функцию. Это правка сервера и выкладка.
2. Правило «посторонний без „Про“ не видит» нельзя обеспечить одним скрытием в приложении: документ `public_profiles`
   читает любой вошедший пользователь, значит уровни человека без «Про» технически доступны в обход приложения. Честное
   исполнение правила владельца — сервер пишет `skillLevels` в `public_profiles` ТОЛЬКО при `profileCardPro === true`
   и стирает поле, когда «Про» нет (так же, как уже стирается `profileCardStyle`).
3. Тогда друзьям человека без «Про» уровни должны идти вторым каналом: клиент кладёт те же шесть чисел в свой
   синхронизируемый прогресс (`progress.skills_public_v1`, едет в уже существующей записи прогресса), а
   `friends_profiles.ts` отдаёт их принятым друзьям в уже существующем ответе. Это вторая правка сервера.
4. Уровни — заявление устройства, сервер их не пересчитывает (как и ранг монеты на визитке). Накрутка даёт только
   красивую звезду, наград и прав за уровень нет. Если владелец захочет серверную достоверность — это отдельная работа.

Вопрос владельцу: одобрить пункты 1–3 (две правки сервера + выкладка) или выбрать упрощение «уровни в `public_profiles`
у всех, скрытие только в приложении» (одна правка сервера, но тогда абзац политики обязан честно сказать, что уровни
относятся к публичным полям профиля).

### Инварианты

- Правило видимости живёт в одном месте — `skillsBlockVisible`; визитка и профиль друга не решают сами.
- Нет уровней (не дошли, битые) → блока нет. Нули вместо неизвестного не рисуем: это было бы враньё о человеке.
- Свои навыки на своей визитке — из локального хранилища, сеть не нужна.

## Security and privacy

- Новая категория данных, видимая другим: шесть уровней навыков. Не очки, не история, не время занятий.
- Авторизация: запись — существующая серверная функция с проверкой личности вызывающего; чтение — существующее правило
  `public_profiles`. Новых правил и функций в этой задаче нет.
- Вход извне (`skillLevels` из сети или с диска) проверяется на границе: массив ровно из шести конечных целых 0…30,
  иначе отбрасывается целиком (`parseSkillLevels`).
- Скрытые и удалённые аккаунты: проекция и так не пишется при `identityHidden` и при удалении; документ стирается вместе с аккаунтом.
- App Check не используется и не предлагается. Секретов нет. Во внешние каналы уровни не уходят.
- Политика конфиденциальности: раздел 5 перечисляет поля, видимые другим; уровней навыков там нет → до выкладки
  передачи политику нужно дополнить. Править политику — решение владельца.
