на каком шаге он встал. Кнопки режимов не зависят от его зависания

## Диагноз

Логи устройства 15:06–15:23, ВСЕ строки:
```
[ARENA-HUB] ... homeLoaded=true serverFailure=false ... reportGuard=checking
```
Ни одной строки с `clear` или `blocked` за 17 минут.

`arenaOutboxBlockedByUpdate` делает три шага, и все молчат:
1. `captureAccountGeneration()` — ранний выход, если аккаунт не активен;
2. `withAccountTransitionLock(...)` — очередь БЕЗ таймаута: `await previous`
   ждёт предыдущего владельца бесконечно (`account_generation.ts:184`);
3. `arenaOutboxList(...)` — чтение AsyncStorage.

Весь код обёрнут в `catch { return false }` — немой catch, запрещённый
правилом проекта. Поэтому ни причина, ни шаг неизвестны.

231 вызов `withAccountTransitionLock` без дедлайна в проекте: угадать, кто
держит замок, невозможно. Нужны факты.

## Scope

In scope: `app/arena_client.ts` — `arenaOutboxBlockedByUpdate`:
трассировка каждого шага + предел ожидания замка.

Out of scope: остальные 230 вызовов замка, сам механизм outbox, хаб.

## Architecture

**Трассировка.** Каждый шаг печатает `[ARENA-OUTBOX-GUARD]`: вход (язык,
состояние аккаунта), результат захвата замка, число записей в очереди,
итог. Немой `catch` заменён на `catch` с причиной — правило проекта.

**Предел ожидания.** `withAccountTransitionLock` → `...WithDeadline`
с 5 секундами. Не захватили — возвращаем `false` («блокировки не нашли») и
пишем причину. Это безопасно: гвард запрещает игру только при ПОЛОЖИТЕЛЬНОМ
ответе, а неизвестность теперь не запрещает ничего (4fbaf7e78).

**Инвариант.** Ни одна локальная проверка Арены не ждёт замок бесконечно и
не молчит о причине отказа.
