## Outcome

Владелец: «не работает! фулл аудит исправление причин». Предыдущая гипотеза
(гонка локального и серверного добавления) была НЕВЕРНОЙ — логи показывают, что
`addedByMe: false` стабильно при каждом открытии шторки, включая повторные через
минуты, а не только сразу после добавления. Документ
`community_packs/{packId}/pack_adds/{stableId}` не появляется на сервере НИКОГДА.

Найдены три складывающиеся причины (подтверждены чтением кода и независимым
аудитом):

1. **Транзакция отклоняется целиком.** `firestoreTx.bumpCounter`
   (`packSocialFirestore.ts:97-99`) делает `tx.set(packRef(packId), {...},
   {merge:true})` на документ `community_packs/{packId}`, НЕ прочитав его в этой
   же транзакции. Правило `allow update: if communityPackSocialCountersOnly()`
   опирается на `resource.data`; при непрочитанном документе `set(merge)`
   трактуется как create-or-update, `allow create: if false` — и транзакция
   отклоняется ЦЕЛИКОМ, унося с собой и запись `pack_adds` из `setMembership`.
2. **Локальный дедуп-флаг сжигает единственную попытку.**
   `communityPackActions.ts:83-87`: `markCommunityPackAddCounted(packId)` пишет
   флаг в AsyncStorage и возвращает `true` ДО `registerCommunityPackAddRemote`,
   результат серверного вызова не проверяется, флаг при провале не
   откатывается. После первой же неудачи `firstTime=false` → ранний `return` —
   серверная запись не повторяется НИКОГДА, даже через дни.
3. **Немой catch прятал причину.** `registerCommunityPackAddRemote`
   (`packSocialFirestore.ts:138-140`) — `catch { return NOOP_RESULT }` без
   логирования, нарушение правила проекта «сперва логи». Из-за этого
   `permission-denied` от транзакции был невидим месяцами.

Следствие: `packAddedByMe(packId)` в `firestore.rules` не находит документ →
`allow create` на `pack_comments` не проходит → `firestore/permission-denied`
при отправке отклика. Побочно: `addedCount` не растёт ни у кого, соц-сортировка
каталога работает на нулях.

## Scope

In scope:
- `app/community_packs/packSocialFirestore.ts`:
  • `firestoreTx` — читать документ набора в транзакции перед записью счётчика
    (транзакционное правило Firestore: все чтения до всех записей), и не
    создавать документ, если его нет (`allow create: if false` — писать счётчик
    только в существующий набор);
  • `registerCommunityPackAddRemote` / `setCommunityPackLikeRemote` — заменить
    немые `catch` на логирование причины с префиксом `[PACK-SOCIAL]`
    (код ошибки, packId, userId, длительность), по правилу «сперва логи».
- `app/community_packs/communityPackActions.ts`: `bumpAddedCountOnce` —
  ставить локальный флаг ТОЛЬКО после подтверждённой серверной записи;
  при провале флаг не ставить (или откатить), чтобы следующая попытка
  повторила запись. Логировать ветвления.
- `app/community_packs/packSocial.ts`: `PackSocialTx.bumpCounter` — контракт
  должен позволять реализации сообщить, что документ набора отсутствует
  (иначе чистая функция не сможет отличить «не было» от «записали»).
- Восстановление уже пострадавших устройств: локальный флаг
  `markCommunityPackAddCounted` на телефонах владельца/пользователей уже
  «сожжён» — нужен путь, который заново регистрирует добавление для наборов,
  которые числятся добавленными локально, но не имеют `pack_adds` на сервере.
  Реализуется как страховка в `PackCommentsSheet` (уже добавленное ожидание
  `registerCommunityPackAddRemote` перед отправкой) — теперь оно заработает,
  потому что серверная запись перестанет падать.

Out of scope:
- Изменение `firestore.rules` — правила КОРРЕКТНЫ, они честно отклоняют
  недопустимую запись. Чинится клиент, а не сторож.
- Визуальный редизайн шторки комментариев — отдельная задача.

## Architecture

Структурно не меняется. Транзакция получает недостающее чтение документа
набора; порядок операций приводится к требованию Firestore (reads before
writes). Локальный дедуп-флаг из «оптимистичного» становится
«подтверждающим» — ставится после факта, а не до него.

## Security and privacy

Не затрагивается: правила Firestore не ослабляются, новых данных не
собирается. Наоборот, устраняется обход — счётчик теперь не может быть
записан в несуществующий документ набора.

## Technical debt

Снимается существующий долг (два немых `catch`, нарушавших правило проекта).
Нового долга не вносится.

## Найдено сверх плана (тот же дефект, другие места)

Каскадная проверка показала, что `set(merge)` на НЕпрочитанный документ набора
жил ещё в двух местах `packCommentsFirestore.ts` — то есть отклик не
опубликовался бы даже после починки `pack_adds`:

- `publishPackComment` — писал `commentsCount` через `tx.set(packRef, ...,
  {merge:true})` без `tx.get(packRef)`. Исправлено: чтение набора первым,
  затем `tx.update`.
- `deletePackComment` — тот же дефект на `increment(-1)`. Исправлено так же.
- `togglePackCommentReaction` — НЕ трогали: там `set(merge)` идёт по документу,
  прочитанному в этой же транзакции (`tx.get(ref)`), и бьёт в `pack_comments`,
  где правила разрешают `update`. Дефекта нет.

## Починенные сторожа (охраняли ложь)

- `tests/pack_comments_rules_contract.test.ts` — три ожидания требовали ГОЛОГО
  `== request.auth.uid`, то есть ровно ту формулировку, из-за которой отклики
  не создавались ни у кого. Переписаны на мост `authLinkMapsToUser`, добавлен
  явный запрет возврата сломанной формы.
- `tests/community_pack_like_owner_fix.test.ts` — регулярка сторожила точную
  вёрстку однострочного гарда, сломалась от добавления логов. Переписана на
  проверку факта, а не формы.
- `tests/community_pack_social.test.ts` — добавлены два сторожа класса бага:
  «все чтения до всех записей» и «несуществующий набор → ok:false и ни одной
  записи».
