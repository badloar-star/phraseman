# Telegram-пульс приложения для владельца

## Цель

Сделать в единственной рабочей админке Phraseman (`admin/v2/legacy.html`) настраиваемый центр Telegram-уведомлений, который безопасно и максимально быстро сообщает владельцу о важных событиях приложения. Новый пользователь является обязательным уведомлением. Остальные источники включаются отдельно.

Система должна объединить уже существующие Telegram-алерты и новые источники в один контракт доставки, исключить сознательные дубли, повторять временно неудавшиеся отправки и не переносить в Telegram чувствительные данные.

## Утверждённый выбор владельца

Владелец выбрал 47 событий из HTML-макета.

### Люди и рефералы — мгновенно

- новый пользователь — всегда включён и не имеет выключателя;
- реферальный код применён;
- первый запуск по рефералу подтверждён;
- реферал квалифицирован;
- реферальная награда выдана;
- новый бан или снятие бана.

Термин «реферальный код применён» означает достоверно созданную сервером attribution. Он не должен называться установкой. «Первый запуск по рефералу подтверждён» становится отдельным серверным событием, чтобы не выдавать применение кода за установку.

## Выбранная архитектура

### Единый каталог событий

Все поддерживаемые события объявляются в compile-time каталоге с устойчивым `eventType`, режимом доставки, уровнем важности и разрешёнными полями. Админский конфиг может включать или выключать только заранее объявленные типы. Он не может задавать произвольную коллекцию, поле Firestore или Telegram-шаблон.

Старые имена типов сохраняются при миграции либо однозначно преобразуются в новые. UI, callable нормализации и серверный тип используют один общий каталог, чтобы список переключателей не расходился с серверным whitelist.

### Неизменяемая очередь

Источники не вызывают Telegram напрямую. Они создают server-only документ в `admin_alert_events/{stableEventKey}` через общий `enqueueAdminAlert()`.

Примеры стабильных ключей:

- `user.created:<uid>`;
- `feedback.created:<feedbackId>`;
- `referral.attributed:<attributionId>`;
- `referral.first_launch:<uid>`;
- `revenuecat:<eventId>`;
- `web:<orderId>:paid`;
- `telegram_stars:<chargeId>:paid`;
- `report:<source>:<reportId>`.

Повтор одного исходного webhook или Firestore-trigger не создаёт второе событие. Документ очереди хранит как минимум `eventType`, безопасный payload, `createdAt`, `attempts`, `nextAttemptAt`, lease, `sentAt`, Telegram `messageId` и состояние dead letter.

Один dispatcher читает конфиг, проверяет выбранный тип, строит сообщение только из allowlist-полей и отправляет его через существующий секрет `ADMIN_ALERT_BOT_TOKEN`. Сетевые ошибки, HTTP 429 и 5xx повторяются с backoff и учётом `retry_after`; постоянные 4xx переводят событие в диагностируемое состояние. Периодический recovery-pass подбирает зависшие или отложенные документы.

Telegram не предоставляет идемпотентный ключ для `sendMessage`, поэтому абсолютное exactly-once обещание невозможно при сбое между успешной отправкой и записью `sentAt`. Контракт системы: идемпотентное создание, отсутствие сознательных повторных отправок и at-least-once доставка с максимально узким окном редкого дубля.

### Источники событий

- Новый пользователь подключается как обработчик существующего единого `users/{uid}` write-router; второй горячий триггер на `users` не создаётся. Событие выпускается только при первом создании профиля, а не при миграции или обычном обновлении.
- Оценки читаются из `feedback_entries` только для выбранных типов `lesson`, `vocab`, `dialogue`, `arena_blitz` и `arena_rating`.
- Применение реферального кода, qualification и reward используют существующий жизненный цикл `referral_attributions`.
- Первый запуск по рефералу получает отдельный аутентифицированный серверный receipt после проверки существующей attribution. Клиент не может напрямую записать финальный alert-документ.
- Store-покупки, траялы, продления, отмены, истечения, billing issues и refunds используют авторитетные `revenuecat_premium_events`.
- Web Checkout и Telegram Stars перестают отправлять владельцу параллельные PII-сообщения и вместо этого создают события общей очереди. Клиентские подтверждения покупки сохраняются без функциональных изменений.
- Существующие user/content/idea/explanation/community reports, safety, auth spike, cron и error alerts переводятся на тот же producer/dispatcher без потери текущего поведения.
- Админские действия используют существующий audit trail; одно действие не должно одновременно породить два владельческих сообщения из audit и предметного обработчика.
- Сводки агрегируются отдельно и создают один outbox-документ на временное окно.

### Активность, запуски и завершения уроков

Текущий `app_activity` не является полным источником всей жизни приложения: часть событий зависит от согласия и часть ошибок сэмплируется. Поэтому выбранные сводки не должны притворяться точными на основе неполной выборки.

Для активных пользователей, запусков и завершений уроков вводятся privacy-conscious агрегаты с устойчивым суточным ключом и минимальными счётчиками. Сырые тексты, email, полный UID и device identifiers в Telegram не отправляются. Метрика в дайджесте помечается как оценочная, пока её источник не прошёл проверку полноты.

## Приватность сообщения

В Telegram разрешены только:

- тип события и время;
- платформа, язык, environment и продукт;
- публичный никнейм, если он уже предназначен для отображения;
- последние четыре символа внутреннего идентификатора;
- рейтинг, категория, severity и агрегированная сумма с валютой;
- ссылка на соответствующий защищённый раздел админки.

В Telegram запрещены:

- email, полный UID, Telegram user ID и device ID;
- transaction ID, charge ID, activation code и секреты;
- произвольный текст репорта, письма или пользовательской идеи;
- stack trace, request/context payload и другие неограниченные вложенные поля;
- содержимое голосовых сессий и safety-контент.

Маскирование выполняется до помещения события в очередь. Dispatcher принимает только типизированный безопасный payload и не пересылает произвольный Firestore-документ.

## Админский интерфейс

Изменения выполняются только в `admin/v2/legacy.html`, в существующем разделе Telegram-алертов.

Интерфейс следует утверждённому HTML-макету:

- светлая спокойная поверхность в стиле Admin UI Bible;
- шесть раскрываемых категорий;
- отдельный переключатель для каждого выбранного события;
- неизменяемый включённый переключатель «Новый пользователь»;
- явные метки «Мгновенно» и «Сводка»;
- счётчики выбранных мгновенных событий и сводок;
- кнопки «Рекомендуемый набор», «Выбрать всё» и «Очистить»;
- один главный CTA сохранения;
- preview безопасного Telegram-сообщения;
- touch targets не меньше 44×44 px, видимый focus, контраст не ниже 4.5:1 и поддержка reduced motion.

Настройки сохраняются только существующим аудируемым admin callable с custom admin claim и отдельным permission. Прямая клиентская запись `admin_config/alerts` закрывается правилами. App Check на админских функциях не включается.

## Режимы и защита от шума

- Обязательный `newUser` всегда отправляется при включённом master-канале и не может быть отключён отдельным типом.
- Мгновенные события получают cooldown или агрегацию только там, где уже определён риск всплеска: auth failures, refunds, content reports и повторяющиеся errors.
- Сводки имеют стабильный ключ окна, например `digest:revenue:2026-09-12` или `digest:errors:2026-09-12T14`.
- Событие ниже выбранного уровня важности не должно попадать в Telegram лишь потому, что оно присутствует в коллекции.
- Master-switch полностью останавливает отправку, но не удаляет историю очереди; при повторном включении старые информационные события не вываливаются лавиной. Критичные неотправленные события показываются в админской диагностике.

## Изменения контрактов и правил

- Новые server-only коллекции закрываются в `firestore.rules` от клиентской записи и чтения, кроме явно необходимой админской диагностики.
- Если Jarvis начинает читать новую коллекцию или поле, одновременно обновляются соответствующий fetcher, `jarvis_data_contract_guard.test.ts`, `all_departments_snapshot.ts` и `JF_DEPARTMENT_META` по правилам проекта.
- Изменение схемы `admin_config/alerts` версионируется и мигрирует старые настройки без молчаливого включения выключенных владельцем типов.
- Существующая инструкция вставлять bot token в URL `getUpdates` удаляется из UI. Chat ID определяется безопасной командой бота или серверным действием без попадания токена в историю браузера.
- App Check для админских функций остаётся выключенным согласно отдельному владельческому запрету.

## Этапы реализации

1. Основа: общий каталог, outbox, dispatcher, retry/recovery, privacy formatter, rules, диагностика, миграция девяти существующих типов и исправление конфиг-контракта.
2. Обязательный контур: новые пользователи, выбранные оценки, все выбранные репорты, рефералы, purchases/trials и остальные RevenueCat-события.
3. Контент и операции: inbox, support, UGC, surveys, admin audit, push, App Messages, cron, compliance и Jarvis.
4. Сводки и новые агрегаты: уроки, App Errors, revenue, surveys, reactions, Card Packs, activity, paywall и ежедневный owner digest.

Этап считается готовым только после независимой проверки его deterministic gates. Частичная готовность одного этапа не должна выдавать несуществующие источники за работающие переключатели.

## Проверки

- unit-тест каталога: UI и сервер принимают одинаковый набор типов;
- unit-тест privacy formatter на вложенные UID, email, activation code, transaction ID, stack и произвольный текст;
- idempotency-тест: повтор исходного события создаёт один outbox-документ;
- retry-тесты на network, 429 с `retry_after`, 5xx, постоянный 4xx и dead letter;
- тест обязательного нового пользователя и отсутствия второго `users/{uid}` trigger;
- тесты каждого RevenueCat lifecycle event, Web Checkout и Telegram Stars без PII и дублей;
- тесты выбранных `feedback_entries` и явное отсутствие MAX alert;
- тест корректной терминологии referral attribution против first launch;
- тесты digest window keys и защиты от лавины после master off/on;
- Firestore Rules тесты server-only outbox/receipts и запрета прямой записи alert config;
- Jarvis data-contract guard при добавлении читаемых контрактов;
- admin single-surface contract: изменения находятся только в `admin/v2/legacy.html`;
- DOM/accessibility тесты шести категорий, 47 выбранных пунктов, locked new user, keyboard focus и узкого экрана.

## Критерии приёмки

1. Новый пользователь всегда создаёт одно безопасное Telegram-уведомление в течение нормального времени Cloud Functions/Telegram и не может быть отключён отдельным toggle.
2. Все 47 выбранных событий имеют честно определённый источник, режим `instant` или `digest` и устойчивый ключ дедупликации.
3. Оценка звонка MAX и сохранения фразы дня не отправляются.
4. Повтор webhook/trigger не создаёт вторую запись события; временная ошибка доставки повторяется автоматически.
5. Ни один тестовый payload с email, полным UID, секретом, платёжным ID, activation code, stack или чувствительным текстом не попадает в Telegram formatter output.
6. Store, Web и Telegram Stars покупки приходят в одном формате и не дублируются старыми прямыми admin-сообщениями.
7. «Реферальный код применён» и «первый запуск подтверждён» являются разными событиями и не подменяют друг друга.
8. Все мгновенные типы и сводки можно настроить в единственной рабочей админке; сервер принимает ровно тот же каталог.
9. Прямое клиентское изменение `admin_config/alerts` запрещено, а callable остаётся доступен авторизованному администратору без включения App Check.
10. Админская диагностика показывает pending, retrying, sent и dead-letter состояния без раскрытия чувствительного payload.
11. Существующие функции приложения, пользовательские подтверждения покупок, репорты и админские действия сохраняются.
12. Фокусные тесты, Rules-тесты и контрактные сторожи проходят перед публикацией функций и Hosting.

## Не входит в этот дизайн

- уведомление об оценке звонка MAX;
- уведомление о сохранении фразы дня;
- отправка полного содержимого репортов, писем, идей или ошибок в Telegram;
- произвольные шаблоны или произвольные Firestore-пути, вводимые из админки;
- включение App Check для админских функций;
- обещание математически строгого exactly-once поверх Telegram Bot API.
