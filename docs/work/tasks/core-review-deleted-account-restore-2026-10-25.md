# Ядро · ревью безопасности: «передумать за 14 дней» для удалённых аккаунтов Apple/Google (25.10)

Governance-ID: TG-B316B26A779A

## Outcome
Поручение координатора: владелец решил чинить восстановление удалённых аккаунтов Apple/Google (разбор «5 · ВХОД», 3247cafa1).
Ядро делает ревью безопасности схемы «индекс по хэшу провайдерской личности» ДО коммита и оценивает альтернативу «не удалять
пользователя Auth до конца 14 дней». Код Ядро не пишет — только ревью и рекомендация.

## Scope
Только чтение: functions/src/account_delete.ts (enqueue → decideGuest → auth_release ~2470; воркер ~2063),
account_delete_restore.ts, account_delete_job.ts, auth_identity.ts (resolveStableUidForAuth, authEnsureStableLink).

## Architecture
Сейчас вход сопоставляется с записью только по uid Firebase. Задача удаления, метки и восстановление привязаны к authUid, а
пользователя Auth не-гостя снимают сразу при постановке задачи. Повторный вход Apple/Google создаёт нового пользователя
Firebase, и задача не находится никогда. Воркер в конце grace сам удаляет пользователя Auth повторно — для пустого входа это
`user-not-found` с логом.

### Рекомендация Ядра: альтернатива Б (не снимать пользователя Auth до конца grace) — проще и безопаснее
- Правка: в enqueue для НЕ-гостя вместо `deleteUser` → `revokeRefreshTokens(authUid)`. Гости (D189) — как сейчас, сразу.
  Воркер уже удаляет пользователя Auth в конце grace.
- Повторный вход Apple/Google возвращает ТОГО ЖЕ пользователя Firebase → существующие accountDeleteStatusMine /
  accountDeleteRestoreMine работают без изменений: задача, метки, tombstone ищутся по тому же authUid. Нового индекса,
  перепривязки auth_links и слияния записей нет — нет и нового класса «увели вход на чужую запись».
- Безопасность «удалить сейчас» сохраняется: revokeRefreshTokens выбивает все устройства (ID-токен живёт ≤ 1 ч), а доступ к
  данным уже закрыт метками и tombstone. Проверить: правила Firestore и ключевые callable режут authUid с меткой удаления на
  весь grace, не только при входе.
- Обещания: «14 дней на передумать» начинает работать для всех провайдеров. В политике и в тексте окна удаления проверить
  формулировку: «данные и учётная запись удаляются через 14 дней, до этого можно восстановить войдя снова». Apple 5.1.1(v)
  допускает отложенное удаление, если человеку это ясно сказано в момент удаления.
- Минус: тот, кто хочет «начать с чистого листа» тем же Apple/Google в течение 14 дней, попадёт в «Восстановить аккаунт?».
  Нужна вторая кнопка: «Нет, удалить навсегда сейчас» → немедленное удаление (как у гостя). Решение владельца по тексту.

### Если всё же индекс по хэшу (схема А) — обязательные условия
1. Личности брать ТОЛЬКО из проверенных данных: providerData пользователя Auth (`admin.auth().getUser(authUid)`) или
   `token.firebase.identities` — и только ключи из белого списка `apple.com`, `google.com`. НИКОГДА `email`/`phone`/`password`:
   в identities у Google есть ключ `email` — хэш по почте открывает захват через другой способ входа с той же почтой.
2. Хэш — HMAC-SHA256 с серверным секретом и пространством имён, а не голый sha256: индекс не должен подтверждать «этот Apple sub
   у нас удалялся» тому, кто его прочтёт. Коллекция индекса — `allow read, write: if false` в правилах.
3. Индекс и задача — в ОДНОЙ транзакции enqueue, ДО deleteUser (у владельца повторный вход был через 20 с).
4. Коллизии: один sub — несколько задач (удалил A, вошёл B, удалил B). Индекс хранит список jobId (ограниченный) или ведёт на
   последнюю; восстановление берёт только задачу в состоянии restorable и сверяет хэш вызывающего с хэшами В САМОЙ задаче.
5. Проверку делать только на пути «у этого authUid ещё нет связи» (новый пользователь Firebase) — иначе +1–2 чтения на каждый
   вход у всех 12 тыс. человек.
6. Во входе НЕ создавать новую запись users до ответа человека: есть живая задача → `deletion_pending` → окно «Восстановить?».
   Иначе запись B успевает получить прогресс.
7. Восстановление = перепривязка входа (auth_links/{новый uid}, users.firebaseAuthUid/linkedAuth, account_id_index) на старую
   запись + снятие задачи, tombstone, меток и постоянных отказов по ВСЕМ личностям closure — одной транзакцией, идемпотентно:
   второй вызов (два устройства, двойной тап) при уже перепривязанном входе — успех, а не ошибка.
8. Клиент после восстановления обязан сменить поколение аккаунта и выбросить локальное состояние нового входа: иначе облачная
   синхронизация зальёт пустой/новый прогресс B поверх восстановленного A — потеряем ровно то, что спасали.
9. Хэши — псевдонимные персональные данные: стирать индекс при завершении задачи (воркер) и при восстановлении; добавить в
   списки стирания account_delete; Джарвису не читать.

## Security and privacy
Ревью без записей в прод и без правки кода. Отдельная находка вне задачи: отзыва токена Sign in with Apple при удалении
аккаунта нет нигде в functions/src — требование Apple с 2022 г. для приложений с SIWA. Нужна отдельная задача (REST
appleid.apple.com/auth/revoke в воркере в конце grace).

## Technical debt
Пятерым в grace (пользователь Auth уже снят) ни схема А, ни Б автоматически не помогут: sub их Apple/Google в задачах не
сохранён. Им — только ручная админ-починка по решению владельца, до истечения сроков (у владельца ≈06.11).

прохождение существующих тестов восстановления (Б).
