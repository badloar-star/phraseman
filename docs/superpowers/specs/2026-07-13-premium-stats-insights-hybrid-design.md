# Гибридная персональная аналитика Premium

## Цель

Сделать раздел «Статистика» точным и действительно персональным: приложение само вычисляет проверяемые наблюдения из данных пользователя, а серверный ИИ только формулирует их естественно, разнообразно и без выдуманных фактов.

Функция остаётся Premium-only. Серверный вызов выполняется лениво при открытии экрана и сохраняет существующие ограничения расходов: серверный Premium-гейт, окно генерации не чаще одного раза в три дня, почасовой rate limit, дневной бюджет и административный kill switch.

## Текущее состояние и причины проблемы

1. `functions/src/stats_insights.ts` содержит серверный промпт и callable `statsInsightsGenerate`, однако `app/stats_insights_client.ts` его не вызывает. Клиент всегда строит пять локальных шаблонов через `buildLocalStatsInsights()`; это закреплено cost-контрактом в `tests/openai_runtime_cost_contract.test.ts`.
2. Генерация запускается после появления lifetime-статистики, но эффект не зависит от готовности перцентилей. Промежуточные `null` и нули могут попасть в заметки и кэш на три дня.
3. `null`-перцентиль смешивает разные состояния: загрузка, отсутствие глобальной выборки или сети, XP ниже порога выборки, отсутствующая метрика. Все они превращаются в одну неточную фразу про «больший объём».
4. Все основные перцентили принудительно скрываются при `user_total_xp < 5000`. Дополнительно UI скрывает рассчитанные значения ниже 50-го перцентиля.
5. `bestMonth` передаётся пустым, `weakCategories` всегда пуст, а заметка `rhythm` генерируется, но не отображается.
6. Текущие шаблоны повторяют одинаковые формулировки и иногда дублируют цифры, уже видимые в карточках.

## Архитектурный принцип

ИИ не решает, что произошло с пользователем. Он получает только готовые доказанные наблюдения и переформулирует их.

Поток данных:

1. Экран загружает локальную статистику, lifetime-итоги, 365-дневную активность и глобальные пороги перцентилей.
2. Детерминированный анализатор строит нормализованный snapshot и список наблюдений.
3. Анализатор ранжирует наблюдения по значимости и распределяет их между видимыми смысловыми блоками без повторов.
4. Клиент передаёт готовый briefing в `statsInsightsGenerate`.
5. Сервер повторно валидирует briefing, применяет лимиты и просит модель только написать короткие тексты по выданным наблюдениям.
6. Сервер проверяет JSON, язык, обязательные факты и запрет на выдуманные числа, затем сохраняет результат для идемпотентного replay.
7. Клиент кэширует результат. При недоступности callable показывает детерминированный локальный fallback из тех же наблюдений.

## Готовность данных

Генерация не начинается только по факту появления `lifetimeStats`. Для неё требуется единый статус готовности:

- основные локальные показатели загружены;
- lifetime-итоги загружены;
- 365-дневная активность завершила загрузку успешным результатом либо явным состоянием `unavailable`;
- запрос глобальной статистики завершён успешным результатом либо явным состоянием `unavailable`;
- язык интерфейса и изучаемый язык известны.

До завершения этих запросов значения не подменяются нулями. Ноль означает реальный измеренный ноль; отсутствие значения означает `null`/`unavailable`.

Входной snapshot получает стабильный fingerprint. Кэш можно повторно использовать только при совпадении изучаемого языка, языка интерфейса и релевантного fingerprint. Поздно пришедшие перцентили должны сформировать новый briefing, а не оставаться навсегда скрытыми старым локальным кэшем.

## Модель перцентилей

Для каждой сравнительной метрики передаётся не только число, но и явный статус:

- `loading` — запрос ещё не завершён; генерация запрещена;
- `unavailable` — глобальная статистика или сеть недоступна;
- `below_sample_floor` — общий XP пользователя ниже опубликованного порога выборки;
- `metric_empty` — конкретная метрика действительно равна нулю или неприменима;
- `available_but_hidden` — перцентиль рассчитан, но продуктовый UI не показывает значение ниже 50;
- `available` — значение разрешено показывать.

Briefing также содержит `sampleSize`, `sampleUpdatedAtMs`, `minimumSampleXp` и локальный `userTotalXp`. ИИ не получает права превращать `unavailable` или `available_but_hidden` в выдуманный ранг.

Локальный fallback использует честные тексты:

- при `unavailable` сообщает, что сравнение временно недоступно, не обвиняя пользователя в недостатке практики;
- при `below_sample_floor` показывает конкретный прогресс к опубликованному порогу;
- при `available_but_hidden` фокусируется на личной динамике без заявления, что данных мало;
- при `available` использует рассчитанный ранг и размер выборки.

Для устойчивости последний валидный кэш глобальных порогов может использоваться при временной сетевой ошибке с явной отметкой свежести. Устаревший кэш не должен выдаваться за свежую выборку.

## Детерминированные наблюдения

Анализатор использует только реально доступные данные и может сформировать следующие типы наблюдений:

- активные дни, минуты и XP за последние 7 дней;
- изменение практики относительно предыдущих 7 дней, если обе недели имеют данные;
- средняя и медианная длительность активного дня;
- равномерность практики и наличие одного чрезмерно доминирующего дня;
- лучший день недели и подтверждённый устойчивый паттерн;
- 30-дневное направление активности при достаточном числе измеренных дней;
- активные дни за год, текущая и лучшая серия;
- лучший месяц из `activity.bestMonth`;
- прогресс к годовой цели;
- накопленные слова, фразы, квизы, победы Арены и активные дни;
- подтверждённые слабые категории, если источник реально доступен;
- доступные сравнительные результаты с размером и свежестью выборки.

Каждое наблюдение имеет:

- стабильный `id`;
- категорию и период;
- машинно проверяемые факты;
- уровень уверенности;
- локализованный детерминированный fallback;
- разрешённое действие или отсутствие рекомендации.

Наблюдение не создаётся, если данных недостаточно для честной интерпретации.

## Выбор и неповторяемость

Перед генерацией анализатор ранжирует наблюдения по полезности:

1. значимое изменение относительно собственного прошлого;
2. устойчивый сильный или слабый паттерн;
3. новый milestone;
4. актуальное сравнение с выборкой;
5. нейтральное резюме периода.

Один факт нельзя использовать в двух соседних блоках. В кэше сохраняются идентификаторы наблюдений, использованных в предыдущем успешном разборе. При следующем допустимом обновлении анализатор предпочитает новый подтверждённый акцент, если он существует. Случайная замена прилагательных не считается разнообразием.

## Видимые смысловые блоки

Сохраняются четыре самостоятельных вывода:

1. **Текущая неделя** — ритм, объём и наиболее полезное ближайшее действие.
2. **Долгий ритм** — годовая активность, серии, лучший месяц и долгосрочное направление.
3. **Среди других** — только честно доступные сравнения и статус выборки.
4. **Весь путь** — накопленный результат и значимый milestone.

Существующие данные `balance` и `rhythm` объединяются в один видимый недельный вывод, чтобы не дублировать активные дни и минуты. Серверный и клиентский контракты должны использовать одинаковый набор видимых ключей либо иметь явное отображение старых ключей для совместимости кэша.

Скрытая карточка не должна оставлять отдельно висящую ИИ-заметку без контекста. Для закрытого блока «Весь путь» заметка появляется вместе с раскрытым содержимым.

## Серверный промпт

Промпт получает готовые observation packets, а не неструктурированный набор сырых чисел. Для каждого блока модель должна:

1. назвать один конкретный факт из разрешённого списка;
2. дать осторожную интерпретацию, не выдавая корреляцию за причину;
3. добавить одно действие только когда оно прямо разрешено наблюдением.

Правила промпта:

- использовать только значения и утверждения из briefing;
- не вычислять новые проценты, ранги, серии или тренды;
- не называть отсутствие данных недостатком пользователя без статуса `below_sample_floor`;
- не повторять один факт или совет в разных блоках;
- не пересказывать все цифры карточки;
- избегать пустых похвал, канцелярита и одинаковых вступлений;
- писать на языке интерфейса, обращаться неформально и уважительно;
- возвращать строгий JSON с обязательными ключами;
- сохранять `observationIds` рядом с текстами для серверной проверки.

Сервер отклоняет ответ, если модель сослалась на неизвестный observation id, добавила число, которого нет в разрешённых фактах, вернула неверный язык или пустые/дублирующиеся заметки. При отклонении клиент получает локальный fallback; невалидный текст не кэшируется как успешный.

## Расходы и безопасность

- Функция доступна только аутентифицированному Premium-пользователю; Premium проверяется на сервере.
- Клиентское `isPremium` не является источником права доступа.
- Одна успешная генерация на пользователя не чаще раза в три дня.
- Сохраняются существующие почасовой rate limit, глобальный дневной budget cap и kill switch.
- Идемпотентный повтор одинакового briefing возвращает сохранённый результат без нового платного вызова.
- Ошибка провайдера не сжигает трёхдневное окно.
- Локальная разработка и тесты не вызывают OpenAI API и не используют проектный `OPENAI_API_KEY`.
- Изменение production-функции не означает автоматический deploy; развёртывание выполняется отдельно и только в разрешённом объёме.

## Обратная совместимость

- Старый кэш `stats_insights_v1` читается через нормализатор, но не блокирует обновление, если в нём отсутствует fingerprint или используются устаревшие ключи.
- При миграции видимых блоков старые заметки отображаются только там, где их смысл однозначно соответствует новой карточке.
- При недоступности Firebase Functions статистика остаётся полезной благодаря локальному анализатору и fallback-текстам.
- Никакие существующие карточки, графики, показатели или Premium-блокировки не удаляются.

## Проверки и критерии приёмки

1. Пользователь с XP выше порога и доступной выборкой не получает фразу о недостаточном объёме.
2. Пользователь с XP ниже порога видит конкретное объяснение и прогресс к порогу.
3. Offline/недоступная выборка и низкий XP дают разные состояния и разные тексты.
4. Рассчитанный перцентиль ниже 50 не трактуется как отсутствие данных.
5. Перцентили, пришедшие после lifetime-данных, входят в финальный briefing до кэширования заметок.
6. Незагруженные значения не превращаются в фактические нули.
7. `activity.bestMonth` передаётся и может использоваться в долгосрочном выводе.
8. Слабая категория передаётся только при наличии реального источника и достаточной выборки.
9. Все видимые блоки получают соответствующий вывод; скрытые/удалённые из UI ключи не генерируют висящий текст.
10. Один observation id не повторяется в соседних блоках, а новый период предпочитает новый значимый акцент.
11. Сервер отклоняет неизвестные числа, observation ids, неверный язык, пустые и дублирующиеся ответы.
12. При callable-ошибке показывается локальный fallback из тех же доказанных наблюдений.
13. Premium, трёхдневное окно, rate limit, дневной cap, kill switch и идемпотентный replay покрыты тестами.
14. Все тесты используют моки; локального OpenAI-вызова нет.
15. Узкие проверки статистики, перцентилей, server prompt/parser, cost controls и TypeScript проходят без изменения несвязанных файлов.

## Вне объёма этой работы

- изменение визуального дизайна всего экрана «Статистика»;
- отмена или изменение продуктового порога 5000 XP без отдельного решения на основе реальной выборки;
- раскрытие перцентилей ниже 50 без отдельного продуктового решения;
- генерация статистики для бесплатных пользователей;
- автоматический deploy Cloud Functions;
- удаление существующих графиков, карточек или данных.
