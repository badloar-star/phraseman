## Итог исполнителя (2026-10-02)

### 1. Откат 7B — по коду гипотеза «снимок получает новые V2-значения» НЕ подтверждается; настоящая причина другая (логи поставлены, починка — решение координатора)

**Что делает код (doSyncToCloud):** при выключателе `data = omitAccountsV2LegacyDomains(storedData, …)` — V2-ключи вырезаются, а снимок `cloud_last_sync_snapshot_v1` строится из того же `data` → V2-ключей в снимке НЕТ (не «новые значения»). После выключения: `previousSnapshot` без `flashcards_v1` → значение не совпадает → `writeFlashcardPages(uid, 'en', актуальный список)` → страницы `flashcard_pages` получают `[a2,a3]` → ключ «выгружен», и ТОЛЬКО ТОГДА снимок получает `[a2,…]`. Это и видела квитанция (снимок = `[a2,…]`) — снимок отражает реально записанные страницы.

**Почему карточка «возвращается»:** список карточек давно живёт НЕ в документе, а в страницах `users/{id}/flashcard_pages` (с 2026-09-01). Поле `progress.flashcards_v1` в документе клиент больше не пишет (при успешной выгрузке ключ выкидывается из патча) и НЕ удаляет; удалял его только серверный скрипт `functions/scripts/migrate_flashcards_to_pages.js` (по `--only`/`--min-kb`). А restore (`applyRestoreFromUserDoc`) берёт **поле документа, если оно есть, и тогда страницы вообще не читает** («Документ главнее…»). В E2E сид положил карточки прямо в поле документа → оно навсегда «затеняет» свежие страницы → старый restore возвращает `[a1,a2,a3]`. Это не только 7B: так же у любого аккаунта, у которого в документе осталось старое поле и который правил карточки после выгрузки (масштаб неизвестен — зависит от того, по каким аккаунтам запускался скрипт).

**Сделано (правило «сперва логи»):**
- `[LEGACY-V2-SYNC] sync key=… decision=write|skip local_len=… snapshot=has|none equal=…` — на каждом V2-ключе в doSyncToCloud до записи страниц/патча (помощник `logAccountsV2LegacySyncKeys` в `app/accounts_v2_legacy_sync_switch.ts`, без uid и значений);
- `[LEGACY-V2-SYNC] restore key=… source=doc_field doc_len=… pages=not_read` / `source=pages|none pages_len=…` — в restore карточек.
- Тесты (в `tests/accounts_v2_legacy_sync_switch.test.ts`, раздел 8H): restore с полем в документе берёт документ и страницы не читает (зафиксировано как факт, лог `source=doc_field`); без поля — страницы; лог синхронизации — решение по ключу без значения; вызов лога стоит до записи страниц.

**Починку restore/записи НЕ делал — вопрос координатору (меняет общий прод-путь, есть риск правил):**
- (A) restore: при наличии страниц брать страницы, а поле документа — только если страниц нет. Риск: при сбое выгрузки клиент пишет список в документ (тогда документ новее страниц) — нужна отметка времени/источника; плюс «все карточки удалены» = 0 страниц → снова документ.
- (B) при успешной записи страниц ставить `progress.<ключ> = null` в документе (restore тогда читает страницы). Риск: правила `users/{id}` — если запись `null` в этот ключ запрещена, отвергнется ВЕСЬ set прогресса; нужна проверка правил на эмуляторе.
- (C) серверный разовый проход скрипта `migrate_flashcards_to_pages.js` по всем аккаунтам с полем (по команде владельца) + (A)/(B) для будущего.
Рекомендую (B) после проверки правил в эмуляторе + (C) для существующих данных.
