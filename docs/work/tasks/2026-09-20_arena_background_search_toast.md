# Task packet: поиск соперника в Арене продолжается вне экрана, находка приходит тостом с выбором

Governance-ID: TG-FAB2EEC600A5
Status: Implemented (аудит пройден 2026-09-20)
Owner: сессия Claude Opus 5 (2026-09-20), по заданию владельца
Related epic/enabler: none

## Outcome

Человек запускает поиск матча в Арене и уходит в любой другой раздел приложения —
поиск продолжается. Когда соперник найден, поверх текущего экрана приходит тост
с именем соперника и двумя действиями: **Принять** и **Отклонить**. Отклонил (или
промолчал до конца отсчёта) — поиск останавливается совсем, нового соперника не
ищут. Принял — открывается матч.

Энергия (25⚡) **проверяется на входе, а списывается при принятии матча**
(владелец 2026-09-20: «энергия должна списываться только после начала матча» +
«поиск не начинается если не хватает энергии»). Не хватает 25⚡ — поиск вообще не
стартует, человек сразу видит `NoEnergyModal` и не уходит ждать впустую. Хватает
— очередь создаётся бесплатно, а плата берётся на кнопке «Принять». Это
устраняет весь нынешний механизм возврата энергии: без списания на входе
возвращать нечего.

Успех: (1) уход с экрана поиска не обрывает очередь; (2) тост приходит на любом
экране; (3) «Отклонить» действительно гасит поиск — повторного тоста не будет;
(4) ни один сценарий не списывает энергию за несостоявшийся матч; (5) поиск
невозможно запустить с балансом меньше 25⚡.

## Scope

In scope:
- `app/arena_matchmaking.tsx` — экран поиска перестаёт быть владельцем очереди;
  становится одним из зрителей фонового поиска.
- Новый модуль состояния поиска вне экрана (рабочее имя
  `modules/arena/background_search.ts`) — единственный владелец очереди:
  heartbeat, запрос бота, срок жизни, пауза в фоне, остановка.
- Новый хост тоста (`components/arena/ArenaOpponentFoundHost.tsx`) +
  регистрация в `app/_layout.tsx` рядом с остальными хостами.
- `app/arena_entry_prefetch.ts` — авто-приём (`accept`) перестаёт быть
  безусловным: приём выполняется только после явного согласия человека.
- Энергия: точка списания переезжает из входа в очередь в приём матча

- Сторож: `tests/arena_background_search_contract.test.ts`.

Out of scope:
- Push-уведомления при полностью свёрнутом приложении. Владелец выбрал паузу в

- Серверные функции Арены. Механика согласия (`state: 'accepting'`,

- Экран матча, расчёт результата, рейтинг, лиги.
- Приглашения друзей (`arena_invite`) — у них свой поток согласия.

## Architecture

**Текущая граница.** Владелец очереди — экран `app/arena_matchmaking.tsx`.
Всё состояние поиска (requestId, момент подтверждения очереди, срок бота,
heartbeat, сдача) живёт в его `useRef`/`useState` и умирает вместе с экраном.
Уход с экрана = `arenaV2QueueCancel` + возврат энергии. Найденный матч
принимается **автоматически** в `arenaEntryPrefetchStart` → `accept`, то есть
серверное окно согласия проскакивается без участия человека.

**Целевая граница.** Владелец очереди — модуль вне дерева React
(`modules/arena/background_search.ts`), переживающий смену экранов:

```
background_search (singleton)
  ├─ ставит/продлевает очередь (arenaV2FindMatch, тот же requestId)
  ├─ heartbeat 15 с, ТОЛЬКО пока приложение на переднем плане
  ├─ запрашивает бота по серверному botDueAtMs
  ├─ pause()/resume() по AppState (background → таймеры глохнут)
  ├─ stop(reason) — единственная точка остановки
  └─ подписка: 'idle' | 'searching' | 'paused' | 'found' | 'stopped'
        ↓                                   ↓
  экран поиска (зритель)          ArenaOpponentFoundHost (тост)
```

**Поток управления при находке.** Сервер создаёт матч в состоянии `accepting`
со сроком `ARENA_V2_ACCEPT_MS`. Модуль переходит в `found`, хост показывает тост.
«Принять» → списание энергии → `arenaEntryPrefetchStart` (он же делает
`arenaV2MatchAccept`) → переход на матч. «Отклонить» или истёкший отсчёт →
`arenaV2MatchDecline` + `stop('declined')`.

**Инвариант 1 — окно согласия принадлежит серверу.** `ARENA_V2_ACCEPT_MS = 12 000`.
Владелец назвал 15 секунд; серверное окно короче, и обещать 15 нельзя — на 13-й
секунде `arenaV2MatchAccept` отобьёт `accept_timeout`, а человек будет смотреть
на живую кнопку. Отсчёт в тосте берётся из `match.stateDeadlineAtMs`, а не из
константы клиента: тост никогда не показывает время, которого у сервера нет.
Если владелец хочет ровно 15 — менять надо серверную константу, и тогда это
отдельная правка `functions/` с деплоем.

**Инвариант 2 — одна очередь на аккаунт.** Модуль — синглтон; повторный запуск
поиска при живом поиске возвращает существующий, а не создаёт второй requestId.

**Инвариант 3 — молчание равно отказу.** Истёкший отсчёт вызывает тот же путь,
что и кнопка «Отклонить», включая `arenaV2MatchDecline`. Живой соперник на том
конце не должен ждать дольше серверного окна.

**Инвариант 4 — энергия только за состоявшийся матч.** Единственная точка
списания — приём матча. Нет списания на входе → нет возврата → исчезает целый
класс багов «энергия сгорела за поиск» (по которому в истории уже правились
четыре точки Арены).

**Инвариант 5 — проверка на входе, плата на выходе.** Вход в очередь делает
чтение баланса (`energy + bonusEnergy >= ENERGY_COST.arena_match`), а не
списание. Недостаточно — поиск не создаётся вовсе, показывается `NoEnergyModal`.
Проверка обязана ждать `energyReady`: до первого чтения из хранилища контекст
отдаёт `MAX_ENERGY` по умолчанию, и решать по этому значению нельзя — ровно на
таком «поспешном суждении» в истории проекта уже ломался вход в Арену
(`'cancelled'` при живой энергии, 2026-08-28).

**Зазор между проверкой и платой (осознанный).** Проверка на входе и списание на
«Принять» разнесены во времени: за эти секунды баланс может упасть — параллельная
сессия на другом устройстве, истёкший временный бонус. Тогда `confirmSpendAmount`
вернёт `insufficient` уже в момент принятия. Это **не** ошибка проекта, а
неизбежная цена отложенной платы, и обработать её надо явно: матч отклоняется
(`arenaV2MatchDecline`), поиск останавливается, человек видит `NoEnergyModal`.
Молча проглотить этот отказ нельзя — получится «нажал Принять, и ничего не
произошло». Сценарий редкий, поэтому отдельного вида тоста он не получает:
переиспользуется существующая модалка нехватки энергии.

**Решение про срок поиска.** Владелец: «до нахождения соперника (бот всегда
находится)». Бот назначается сервером в пределах 20 с (quick) / 60 с (ranked),
поэтому отдельный предел ожидания не нужен: поиск всегда завершается находкой.
Нынешние `ARENA_QUICK_SEARCH_GIVE_UP_MS` / `ARENA_RANKED_SEARCH_GIVE_UP_MS`
остаются страховкой от молчащего сервера, но исход меняется: вместо «выбросить
на хаб и вернуть энергию» — тост «соперник не нашёлся» и остановка поиска.
Возвращать нечего, потому что не списывали.

## Security and privacy

- **Аутентификация/авторизация** — не меняются: все вызовы идут через уже
  существующие callable-функции Арены с обязательным авторизованным вызовом.
  App Check не вводится (пломба владельца 2026-08-17).
- **Новые данные не собираются.** В тосте показывается только то, что сервер уже
  отдаёт в `match.players` — отображаемое имя и аватар соперника, те же поля, что
  на экране матча. Ни стабильных id, ни почты, ни новых полей.
- **Privacy policy правки не требует**: нет нового поля профиля, нового стороннего
  сервиса, нового разрешения (push сознательно вне объёма), нет экспорта/удаления
  данных, нет детских данных.
- **Злоупотребление.** Отклонение матча в рейтинге уже обрабатывается сервером
  (ветка dodge на `arena_v2.ts:3520`). Новый путь пользуется тем же
  `arenaV2MatchDecline` и не создаёт способа уклоняться бесплатно.
- **Секреты** — не затрагиваются.

## Technical debt

- **Pay now.** Возврат энергии за несостоявшийся поиск (`refundUnstartedSearch`,
  `energyChargedRef`, ветки `opponent_not_found` / `cancelled_before_entry`)
  удаляется целиком вместе с причиной — списанием на входе. Это снимает долг, а
  не переносит его.
- **Pay now.** Безусловный авто-приём в `arena_entry_prefetch.ts` заменяется на
  приём по явному согласию. Сейчас это скрытая семантика: функция называется
  «prefetch», а на деле соглашается за человека.
- **Contain.** Расхождение «12 с у сервера ↔ 15 с в задании владельца»
  удерживается тем, что отсчёт читается из `stateDeadlineAtMs`. Сторож проверяет,
  что клиент нигде не хардкодит окно согласия. Выход из containment: владелец
  решает, менять ли серверную константу.
- **Accept temporarily.** Пауза поиска в фоне вместо push. Владелец: сессия
  2026-09-20. Потолок влияния: свернул надолго — вернулся к «поиск на паузе»,
  ничего не потеряно (энергия не списана). Пересмотр — когда/если появится
  задача на push-уведомления Арены.

## Verification

Детерминированные проверки (новый сторож
`tests/arena_background_search_contract.test.ts`):
1. Вход в очередь **не** списывает энергию; списание происходит ровно один раз и
   только на пути «Принять».
2. Уход с экрана поиска не вызывает `arenaV2QueueCancel` — состояние остаётся
   `searching`.
3. `stop('declined')` вызывает `arenaV2MatchDecline` и переводит модуль в
   `stopped`; повторный тост после этого не выдаётся.
4. Истёкший отсчёт и кнопка «Отклонить» проходят одним и тем же путём.
5. Переход `AppState` в `background` гасит heartbeat и таймер бота; возврат в
   `active` их восстанавливает без создания второго requestId.
6. Отсчёт в тосте вычисляется из `stateDeadlineAtMs`; окно согласия нигде не
   захардкожено на клиенте.
7. Двойной тап по «Принять» даёт одно списание и один переход.
8. Баланс меньше 25⚡ → поиск не создаётся: `arenaV2FindMatch` не вызывается
   вовсе, состояние остаётся `idle`, показана `NoEnergyModal`.
9. Проверка на входе ждёт `energyReady`: при неготовом контексте поиск не
   стартует и не отклоняется — ждёт реального баланса, а не значения по умолчанию.
10. Баланс упал между проверкой и принятием → `insufficient` на «Принять»
    отклоняет матч, останавливает поиск и показывает `NoEnergyModal`; тихого
    отказа без реакции интерфейса не существует.

## Rollback

Откат одним флагом: константа `ARENA_BACKGROUND_SEARCH_ENABLED` в модуле поиска.
При `false` экран поиска снова владеет очередью, хост тоста не монтируется,
списание энергии возвращается на вход. Серверная часть не меняется вовсе,
поэтому откат клиента не требует деплоя функций и не может рассинхронизировать
версии. Пользовательских данных правка не создаёт и не мигрирует — терять при
откате нечего. Уже выданные права (Plus/Pro) не затрагиваются.

## Аудит собственной работы (2026-09-20)

Проведён по прямой просьбе владельца, сразу после реализации. Искал
собственные ошибки, а не подтверждения. Найдено и исправлено четыре дефекта,
из них один прямо нарушал задание владельца.

### 1. Отказ не останавливал поиск, если человек стоял на экране Арены (🔴)

Эффект запуска в `app/arena_matchmaking.tsx` зависел от `search.phase`.
Цепочка: тост → «Отклонить» → фаза `stopped` → эффект видит «не
searching/paused/found», энергия есть → **запускает поиск заново**. То есть
главное требование владельца («если отклонить, то поиск должен остановиться»)
не выполнялось ровно в том случае, когда человек ждал на экране Арены.

Исправлено замком `startedOnceRef`: экран запускает поиск ОДИН раз за вход.
Плюс добавлен уход на хаб, когда поиск закончился при открытом экране —
показывать пульс после остановки было бы ложью.

Закреплено тестом «после отказа ядро не возвращается в поиск само».

### 2. Потерян `studyTarget` при переходе в матч (🔴)

`router.push('/arena_match')` уходил без контура обучения, хотя все остальные
переходы в проекте его передают. Экран матча ушёл бы в чужой языковой контур.
Добавлен `studyTarget`, а вместе с ним и `prepared: '1'` — без него экран
матча заново грузил бы уже загруженный план (лишний круг сети).

### 3. Потерян разбор причины отказа предзагрузки (🟡)

Старый экран различал виды сбоя через `arenaEntryFailure` (временный сбой —
не повод входить в сломанный матч). При переносе я эту защиту не перенёс.
Возвращена: причина теперь пишется в лог и влияет на диагностику. Переход на
экран матча происходит в любом случае — энергия уже списана за принятый матч,
и бросать его нельзя; экран матча умеет догрузить план сам.

### 4. Исключение при списании могло съесть энергию (🔴 по деньгам)

Если `confirmSpendAmount` падал исключением, поиск гасился, а плата
оставалась. Добавлен идемпотентный `refundActivityStart` по тому же
`operationId`: лишний безвредный возврат лучше молча съеденных 25⚡.

### Проверено и НЕ является дефектом

- Замок `decidedRef` корректно снимается при смене матча (разобрана
  последовательность A → null → B).
- Объект `found` не пересоздаётся без смены матча — ложных сбросов нет.
- Ожидание предзагрузки перед переходом оставлено НАМЕРЕННО: войти в матч без
  плана хуже, чем подождать секунду с погашенными кнопками.
