## Outcome

Жалоба №9 (разбор 29.10): buildInvoicePayload клал ник из приложения в данные счёта (base64url JSON, лимит Telegram 128 байт);
ник длиннее ~14 кириллических букв (или с эмодзи) → «invoice payload too long» → человек видит «Не удалось открыть оплату», повтор
не помогает (журнал 21.10 22:04). Владелец 29.10 ~08:15 через координатора: «Да, чинить + логи».
1. Ник в данные счёта не класть: данные постоянной длины {v:2, p, u, c, i:номер счёта, t} (~60–80 байт); ник — в
   telegram_premium_bot_sessions/{userId}.invoiceNicknames[i]. Старые счета (v1 с ником внутри) продолжают работать в pre_checkout и
   successful_payment (подписки продлеваются со старыми данными месяцами).
2. Логи [TG-PAY]: вход апдейта (тип, хэш id), выставление счёта (вид, тариф, байты данных, длина ника знаки/байты, причина отказа),
   pre_checkout (решение, причина, мс, итог answerPreCheckoutQuery), два немых catch — с причиной, ответ вебхука (код, мс).
3. getWebhookInfo при старте инстанса: только хост url, pending_update_count, last_error_date, last_error_message. Токен в лог не идёт.

## Architecture

Номер счёта — 8 знаков base36 (случайный). Ник: v1 — из данных счёта; v2 — сессия.invoiceNicknames[i], запас — сессия.appNickname.
Источник ника пишется в лог. Firestore: +1 запись (merge в уже существующий документ сессии) на выставление счёта, +1 чтение сессии на
успешную оплату — копейки, нагрузку не поднимает.

## Security and privacy

telegramUserId в логах заменён хэшем (sha256, 10 hex). Токен в логи не попадает (getWebhookInfo — только перечисленные поля, url — только
хост). Ник по-прежнему хранится там же, где и раньше (сессия бота и заказ) — новых данных и получателей нет, политика не меняется.
