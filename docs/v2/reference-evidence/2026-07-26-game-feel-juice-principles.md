# Game feel / juice — принципы UI-анимации из web research

Собрано: **2026-07-26**, метод сбора: **web-research** (WebSearch + WebFetch по
публичным статьям про геймдизайн-теорию «juice» и Disney 12 animation
principles применительно к играм/UI). Это **НЕ** first-hand capture конкретного
продукта — это теоретическая база принципов, не привязанная к скриншотам
живого приложения. Статус и правила приоритетов см.
`docs/v2/REFERENCE_EVIDENCE_LEDGER.md`.

Status: `web-corroboration` / теоретический справочник. Использовать как
словарь терминов и чек-лист приёмов при проектировании анимаций V2, не как
готовые тайминги — тайминги нужно откалибровать самим и проверить на
реальном устройстве (см. раздел «Что всё ещё требует first-hand capture»).

## Наблюдения

### Squash and Stretch (принцип №1, самый цитируемый)

- Классическое определение: деформация формы (сплющивание при ударе,
  растяжение при разгоне) при сохранении воспринимаемого объёма — глаз
  читает это как вес и энергию, а не как «предмет сломался».
  (totter87.medium.com; общий пересказ в нескольких источниках).
- Игровое ограничение по totter87.medium.com: экстремальный
  squash/stretch может ломать читаемость коллизии (хитбокс визуально не
  совпадает с формой). Рекомендованное решение из источника — держать
  squash/stretch на **нескольких кадрах непосредственно перед/после**
  столкновения, не растягивать эффект на весь путь движения.
- Для UI-элементов (не персонажей): тот же приём описан как «лёгкое
  сжатие-растяжение при тапе кнопки» — делает интерфейс тактильнее
  (thedesignlab.blog, без точных цифр деформации).

### Anticipation (принцип №2)

- Игровое ограничение по totter87.medium.com: анимация подготовки к
  действию (замах) воспринимается как **задержка отклика на ввод**, если
  сделана неаккуратно. Источник называет два обходных пути: (а) анимировать
  anticipation **прямо во время** самого действия, а не до него (пример из
  игры Little Nemo — сжатие происходит уже в момент отрыва от земли); (б)
  делать anticipation частью риск/награда-механики (тяжёлое оружие с
  видимым замахом — сознательный компромисс, не баг).
- Прямое следствие для UI-инструментов реального времени: любой visual
  anticipation перед подтверждением действия пользователя не должен
  добавлять воспринимаемую задержку — это же требование, что и Optimistic
  UI правило проекта (мгновенный локальный отклик).

### Screen shake / удар по экрану

- Исторически ассоциируется с Vlambeer и докладом «The Art of Screenshake»
  (2013) — работа с играми Nuclear Throne, Luftrausers, Ridiculous Fishing;
  вторичные источники описывают доклад как ~30 приёмов за 25 минут.
- Ключевой тезис (несколько источников сходятся): juice/screen shake — это
  то, что добавляется **поверх уже работающей механики**, а не то, что
  создаёт ощущение работоспособности само по себе. Если базовый фидбек не
  читается без шейка — проблема в механике, не в отсутствии эффекта.
- thedesignlab.blog формулирует применение: screen shake «добавляет вес
  ударным действиям вроде взрывов или попаданий» — то есть должен быть
  зарезервирован для событий с реальной значимостью, не для рутинных
  тапов.

### Particles / частицы

- Общий паттерн по нескольким источникам: частицы недороги по перформансу
  (thedesignlab.blog упоминает встроенные системы частиц в игровых движках
  как «минимальную цену за реализацию» — но это про игровые движки, не
  про React Native/Skia — прямой перенос стоимости не доказан).
- gameanalytics.com даёт конкретные примеры для казуальных мобильных игр:
  splash при приземлении, dust при движении, sparkle/stars при столкновении
  спрайтов, trails для подчёркивания быстрого движения по дуге.
- Важное правило пропорциональности из того же источника: интенсивность
  эффекта (в их примере — амплитуда wobble) должна зависеть от силы
  действия («wobble зависит от силы прыжка и удара приземления»), а не быть
  одинаковой всегда — иначе эффект перестаёт нести информацию и
  превращается в шум.

### Timing / тайминг

- totter87.medium.com отмечает игровое преимущество: скорость воспроизведения
  можно менять на уровне движка без переанимирования исходников; для 2D
  пиксель-арта с ограниченным числом кадров упоминается техника «смиров»
  (frame smearing — один кадр совмещает несколько промежуточных поз для
  иллюзии плавности при меньшем числе исходных кадров).
- Wildnetedge (мобильный UI-контекст, не игровой): для мобильных
  UI-анимаций диапазон 200-400 мс называется оптимальным для эффектов
  прямого фидбека на действие, а 600-800 мс — для переходов между
  контекстами (смена экрана/секции). Это качественная рекомендация из
  одного вторичного источника, не стандарт индустрии с эмпирической
  проверкой в этом наборе источников.

### Exaggeration (принцип №10)

- totter87.medium.com: в играх exaggeration нужно балансировать с
  ограничениями коллизии и отзывчивостью управления — слишком сильное
  преувеличение может визуально «соврать» о реальном положении хитбокса.
  При аккуратном применении усиливает именно то, что называется
  «game feel»/juice — субъективное ощущение отзывчивости.

### Haptics (тактильная обратная связь)

- Официальная документация Android (Tier B, платформенная, не
  геймдев-теория): частые/мелкие события (например, скролл) должны иметь
  очень слабый haptic-отклик; более значимые события (submit формы,
  refresh страницы) — более сильный. Прямое пересечение с уже принятым в
  проекте правилом «хаптик на управляющих кнопках, НЕ на плитках/буквах»
  (см. системный промпт пользователя, правило дизайна) — эта рекомендация
  из независимого источника совпадает по духу с уже действующим правилом
  проекта.
- thedesignlab.blog и wildnetedge оба называют многослойность (тач +
  haptic + звук одновременно) трендом 2025 года для мобильных
  микро-взаимодействий — без конкретных цифр интенсивности.

### «Juice эмоциональнее, чем UX» — методологическое предупреждение

- gameanalytics.com прямо противопоставляет juice и «UX-принципы»,
  называя juice «более личным и эмоциональным». Это полезная рамка для
  V2: часть анимационных решений не поддаётся A/B-обоснованию тем же
  способом, что и функциональный UX (время до конверсии и т.п.) — их
  ценность субъективна и требует вкусового ревью (что уже покрыто
  скиллами `impeccable` / `taste-skill` / `emil-design-eng` в правилах
  проекта), а не только метрик.

### Полный список 12 принципов Диснея и их игровая адаптация (кратко, по totter87.medium.com)

1. **Squash and Stretch** — см. выше.
2. **Anticipation** — см. выше.
3. **Staging** — читаемый силуэт и композиция; в играх сложнее, потому что
   камеру часто контролирует игрок — решение через левел-дизайн,
   направляющий внимание, и чёткие ключевые позы спрайта с разных углов.
4. **Straight Ahead vs Pose to Pose** — это рабочий процесс аниматора, не
   ограничение движка; pose-to-pose для стандартных движений, straight-ahead
   для эффектов и «свободных» элементов (волосы, ткань).
5. **Follow Through and Overlapping Action** — рекомендация источника:
   «минимизировать число кадров доработки движения, но делать их по-настоящему
   впечатляющими», либо строить на этом всю анимацию, либо выносить в
   отдельный «болтающийся» объект.
6. **Slow In / Slow Out** (замедление на входе/выходе движения) —
   принципиальных ограничений нет; для кадро-ограниченных контекстов
   (пиксель-арт) критичен точный подбор кадров.
7. **Arcs** — тела естественно двигаются по дугам, а не по прямым; правило
   применять последовательно ко всему движению, включая мелкие детали вроде
   мимики.
8. **Secondary Action** — второстепенное движение поверх основного
   (покачивание руки при беге, ёрзание в состоянии простоя) добавляет
   «визуальный интерес» без отвлечения от главного действия.
9. **Timing** — см. выше.
10. **Exaggeration** — см. выше.
11. **Solid Drawing** — базовый навык: анатомия, перспектива, избегание
    симметричных «зеркальных» поз («twinning»), создаёт убедительный
    трёхмерный объём.
12. **Appeal** — дизайн персонажа/элемента через доминирующие формы,
    палитру, выразительные «лица», динамичные позы, транслирующие
    характер.

## Выводы для Phraseman V2

Это НАШИ интерпретации, применение теории к проекту — не факты из
источников.

1. **Squash/stretch на кнопках и наградных иконках — дёшево и уместно.**
   Лёгкая деформация (не искажающая хитбокс, всего 1-3 кадра/десятки мс) на
   тапе — универсально рекомендованный, недорогой приём. Нужно убедиться,
   что деформация не съезжает с реального touch target (44pt iOS/48dp
   Android по правилу проекта) — сохраняем читаемость попадания при любой
   деформации формы.

2. **Anticipation не должен создавать воспринимаемую задержку ввода** — это
   прямое пересечение с уже действующим в проекте Optimistic UI правилом.
   Если где-то в V2 планируется «замах» перед подтверждением действия
   (например, анимация перед начислением осколков/жемчужин), она обязана
   идти ПОСЛЕ мгновенного локального обновления состояния, никогда вместо
   него или до него.

3. **Screen-shake-подобные эффекты (тряска, вспышка) резервировать для
   по-настоящему значимых событий** (идеальный урок, крупная награда,
   левел-ап), не размазывать на рутинные действия — иначе эффект теряет
   информативность и начинает раздражать при частом использовании
   (несколько источников сходятся на этом принципе пропорциональности).

4. **Частицы/count-up анимации — недорогой высокоотдачный приём**, но
   стоимость на React Native/Reanimated/Skia не доказана этими источниками
   (они говорят про игровые движки) — перед закладкой в план нужен
   отдельный perf-прогон на реальном устройстве (холодный старт, FPS при
   частицах поверх списка), это явно требует проверки, а не копирования
   цифр «дёшево» из геймдев-контекста.

5. **Пропорциональность эффекта силе действия** — прямое правило для
   дизайна анимаций комбо/наград V2: анимация за 3-в-ряд правильных ответов
   не должна визуально быть такой же мощной, как анимация за идеальный
   урок целиком. Нужна явная лестница интенсивности эффектов, привязанная к
   лестнице наград (комбо → урок → веха → редкое достижение).

6. **Тайминг 200-400 мс для прямого фидбека, 600-800 мс для смены
   контекста** — рабочая отправная точка для калибровки анимаций V2, но
   помечена как качественная рекомендация одного вторичного источника, не
   эмпирический стандарт — нужно тестировать субъективно на реальном
   устройстве и подстраивать под ощущение, не жёстко фиксировать в коде как
   «доказанное оптимальное число».

7. **Haptics только на значимых, не на частых событиях** — это уже
   действующее правило проекта («хаптик на управляющих кнопках, НЕ на
   плитках/буквах — там вибрация»), и независимый источник (официальная
   документация Android) подтверждает ту же логику с другой стороны
   (сильный haptic на значимых действиях типа submit, слабый или никакого —
   на частых типа скролла). Дополнительное основание держаться этого
   правила железно в V2.

8. **Juice — надстройка, не костыль.** Если базовый функциональный фидбек
   активности (правильно/неправильно, прогресс, награда) не читается без
   анимационного усиления — сначала чинить сам фидбек (иерархию, цвет,
   текст), потом добавлять juice поверх. Это прямое следствие тезиса
   Vlambeer-школы: эффект должен усиливать уже рабочую механику, не
   маскировать нерабочую.

9. **Секция «эмоциональное, не только метрическое» ревью для анимаций.**
   Раз один из источников прямо разделяет «UX-логику» и «juice-логику» как
   разные оси оценки — при ревью новых анимаций V2 стоит явно спрашивать не
   только «это ускоряет/облегчает действие», но и «это ощущается приятно
   тактильно» — что уже покрыто требованием проекта подключать
   `impeccable`/`taste-skill`/`emil-design-eng` при любой дизайн-правке, но
   стоит явно включить анимации в тот же контур ревью, а не считать их
   отдельной от «дизайна» категорией.

10. **Смиры (frame smearing) и straight-ahead workflow — нишевые приёмы для
    ограниченных по кадрам контекстов** (пиксель-арт, покадровая
    2D-анимация); для Rive/Lottie/Reanimated-based анимаций в V2 это
    менее актуально, чем принципы 1/2/9/10 выше — не стоит тратить время
    на адаптацию этой техники, если стек не покадровый.

## Что всё ещё требует first-hand capture

Web-источники **не доказывают**:

- Конкретные easing-кривые (bezier-параметры) для squash/stretch, screen
  shake или count-up — все источники говорят на уровне принципа
  («используй slow-in/slow-out»), не дают готовых кривых для копирования.
- Реальную стоимость частиц/screen-shake на целевых устройствах Phraseman
  (какие FPS-просадки при каких сценах) — источники говорят про игровые
  движки (Unity/Godot) или абстрактно про «UI», не про React Native/Expo
  стек проекта. Это отдельная perf-задача, не покрытая web-research.
- Диапазон 200-400 мс / 600-800 мс как эмпирически проверенный стандарт —
  единственный источник этой цифры (wildnetedge) не приводит первоисточник
  исследования, это нужно валидировать субъективным тестированием, не
  принимать как научный факт.
- Любые скриншоты/видео текущего рантайма Phraseman «до» и «после» —
  этот файл не содержит визуальной фиксации существующего состояния
  анимаций проекта; для сравнения нужен отдельный first-hand capture по
  правилам `REFERENCE_EVIDENCE_LEDGER.md`.
- Точную реализацию «смиров»/частиц в контексте специфичных библиотек
  проекта (Reanimated/Skia/Lottie/Rive-for-RN, если используется) — этот
  документ описывает только теорию геймдизайна, не даёт готового кода под
  стек Phraseman.
