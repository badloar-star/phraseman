## Outcome

Человек удалил аккаунт Google/Apple и в течение 14 дней снова вошёл ТЕМ ЖЕ Google/Apple → вместо новой пустой записи
приложение спрашивает «Восстановить аккаунт?» (существующий поток клиента на отказ входа `account_delete_pending`).
«Восстановить» → задача удаления снимается, новый uid Firebase привязывается к прежней записи users, повтор входа
открывает прежний прогресс. «Не восстанавливать» → повторный тап входа даёт новый аккаунт (не запираем человека на 14 дней),
старый удалится по сроку. Причина поломки (отчёт 3247cafa1): при удалении сервер сразу снимает пользователя Auth, а
статус/восстановление искали задачу по authUid вошедшего — у повторного входа uid новый.

## Scope

- functions/src/account_delete_provider_index.ts (новый): хэш личности, индекс, поиск, ворота входа, отметка «предложено».
- functions/src/account_delete_job.ts — при создании задачи (не гость) записать индекс в той же транзакции.
- functions/src/account_delete.ts — передать хэши личностей из проверенного токена в постановку.
- functions/src/account_delete_restore.ts — статус и восстановление: если задачи по uid нет — по индексу; восстановление
  перепривязывает новый uid к прежней записи (тот же формат полей, что пишет вход).
- functions/src/auth_identity.ts — authEnsureStableLink: ворота до привязки (только google.com/apple.com).
- тесты. Клиент не меняется (поток «Восстановить аккаунт?» уже есть).

## Architecture

- Ключ индекса: `sha256("pm-adel-provider-v1:" + providerId + ":" + sub)` из `request.auth.token.firebase.identities`
  (проверено Firebase). Только `apple.com` и `google.com`. Сырые sub не хранятся. Почта не участвует.
- `account_deletion_provider_index/{hash}` = { jobId, providerId, graceDeadlineMs, createdAtMs } — пишется в транзакции
  создания задачи; хэши дублируются в задаче (`providerIdentityHashes`) для уборки.
- Ворота входа: индекс → задача (queued, в grace, authUid задачи ≠ вызывающий) → нет отметки «предложено» для
  вызывающего → `failed-precondition account_delete_pending` (клиент показывает «Восстановить аккаунт?»).
- `accountDeleteStatusMine`: по индексу → pending/restorable/daysLeft + отметка «предложено»
  (`account_deletion_provider_offers/{callerUid}`). После отметки ворота пропускают (отказ = новый аккаунт).
- `accountDeleteRestoreMine` по индексу (одна транзакция): задача restorable, индекс указывает на неё, у вызывающего НЕТ
  привязки к другой записи (иначе отказ — не сиротим новый прогресс); снять задачу, tombstone, метки, отказы, индекс,
  отметку; записать `auth_links/{callerUid}` → прежняя запись и `users/{stable}.firebaseAuthUid/linkedAuth` = callerUid;
  аудит в `account_deletion_restores` (только хэши).
