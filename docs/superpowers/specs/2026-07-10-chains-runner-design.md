# Chains Runner: отдельный запускатель Chains для CapCut

**Статус:** согласованная архитектурная спецификация, 2026-07-10

## Цель

Сделать отдельное локальное Windows-приложение с окном, которое запускает существующий Chains-процесс без постоянных сессий Codex и без ручной перестройки скриптов под каждый проект.

Пользователь выбирает проект из списка CapCut, запускает анализ, получает понятный предпросмотр изменений и после подтверждения создаёт отдельную копию проекта. Исходный CapCut-проект не изменяется по умолчанию.

## Решение

Новый запускатель живёт отдельно от основного репозитория приложения:

```text
C:\appsprojects\chains-runner\
C:\Users\badlo\OneDrive\Desktop\CHAINS_RUNNER\
C:\Users\badlo\OneDrive\Desktop\CHAINS_RUNNER_DATA\
```

Окно будет написано на Python/Tkinter, потому что Tkinter уже доступен в локальном Python 3.14 и не требует отдельной установки тяжёлого desktop-фреймворка. Детерминированная часть будет читать CapCut JSON, строить fingerprint, хранить историю, клонировать проект и запускать проверки.

Для AI используется локально установленный Codex через `codex exec --json` с сохранённой авторизацией Codex. Прямой API-токен не записывается в проект, CapCut или папку истории. Интерфейс провайдера оставляет отдельную границу для будущего `codex app-server`, если понадобятся интерактивные подтверждения и постоянный поток событий.

Codex не получает право записывать CapCut-файлы. Он получает компактный манифест, правила и историю, а возвращает только JSON по утверждённой схеме. Запись выполняет Python-движок после проверки схемы и подтверждения пользователя.

## Пользовательский сценарий

1. Пользователь открывает ярлык `CHAINS_RUNNER\Run Chains Runner.cmd`.
2. Окно показывает проекты из `%LOCALAPPDATA%\CapCut\User Data\Projects\com.lveditor.draft`.
3. Пользователь выбирает проект и нажимает `Анализировать`.
4. Программа проверяет CapCut, читает только стабильный снимок проекта и сравнивает его с историей.
5. Если структура и правила не изменились, Codex повторно не вызывается. Показывается состояние `Без изменений`.
6. Если появились новые или изменённые элементы, Codex получает только нужные части манифеста и создаёт структурированный контент-план.
7. Окно показывает: известные элементы, новые элементы, пропущенные элементы, предлагаемые изменения, путь будущей копии и ожидаемые проверки.
8. Кнопка `Создать копию` требует отдельного подтверждения.
9. Программа закрывает CapCut, делает timestamped backup, клонирует исходную папку и применяет только разрешённые изменения к копии.
10. Программа синхронизирует корневой `draft_content.json`, `template-2.tmp` и `Timelines/<id>/draft_content.json`, регистрирует копию в CapCut и запускает quality gate.
11. При любой ошибке до записи приложение останавливается. При ошибке после клонирования исходная папка остаётся нетронутой, а путь копии и backup попадают в отчёт.

## Состав системы

### Окно

Окно содержит:

- список проектов CapCut с путём, датой изменения и последним статусом истории;
- кнопки `Обновить проекты`, `Анализировать`, `Показать изменения`, `Создать копию`, `Открыть отчёт`;
- переключатели `Использовать Codex`, `Только dry-run`, `Зарегистрировать копию в CapCut`;
- область лога с этапами и ошибками;
- сводку перед применением: источник, backup, будущая копия, количество известных/новых/пропущенных элементов и результат quality gate.

Окно не показывает API-токены и не пишет их в лог. Если Codex не авторизован, пользователь получает команду для отдельной авторизации, а операция останавливается до её завершения.

### Анализатор CapCut

Анализатор работает с Windows-форматом `draft_content.json` и связанными файлами. Он извлекает:

- id и имя draft;
- список дорожек, типы, имена и порядок;
- количество сегментов на дорожке;
- стабильные структурные признаки сегментов;
- материалы текста, аудио и видео без загрузки всего тяжёлого JSON в Codex;
- временные интервалы, длительности и пути ресурсов;
- наличие `template-2.tmp`, timeline mirror и метаданных.

Позиция дорожки сама по себе не считается стабильным идентификатором. Сопоставление использует комбинацию `track_role`, типа материала, имени дорожки, normalized source identity, диапазона времени и короткого structural hash. Индексы и CapCut UUID используются как дополнительные признаки.

### История

История хранится вне CapCut в `CHAINS_RUNNER_DATA`:

```text
CHAINS_RUNNER_DATA\
  projects\<project-key>\
    project.json
    last-manifest.json
    runs.jsonl
    codex-thread.json
    reports\
    backups\
```

`project-key` строится из нормализованного пути исходного draft и его timeline id. В истории сохраняются fingerprint, версия профиля, хэш правил, хэш входного манифеста, Codex thread id, результат запуска, backup, clone и quality gate.

Повторный запуск сначала делает лёгкую проверку fingerprint. Если fingerprint, версия профиля и хэш правил совпадают, глубокий анализ и вызов Codex пропускаются. Если появился новый элемент, он попадает в `new_elements`, получает статус `ignored_by_policy` и не изменяет известные элементы. Если известный элемент исчез или его роль неоднозначна, применение блокируется до ручного решения.

### Codex-провайдер

Первый релиз использует:

```text
codex exec --json --sandbox read-only --output-schema <schema> <prompt>
```

`codex exec` использует сохранённую авторизацию CLI по умолчанию и предназначен для запуска из скриптов. Идентификатор потока сохраняется для продолжения проектной истории через `codex exec resume`. В будущем поверх того же интерфейса можно добавить `codex app-server` для более глубоких интерактивных диалогов, подтверждений и стриминга.

Codex получает:

- профиль Chains;
- правила генерации;
- компактный project manifest;
- изменения относительно предыдущего запуска;
- список новых элементов, которые по умолчанию запрещено менять.

Codex возвращает только поля схемы: content rows, role bindings, requested asset jobs, rationale и warnings. Любое поле вне схемы, невалидный JSON, кракозябры, неизвестная роль или попытка адресовать ignored element блокируют применение.

### Детерминированный исполнитель

Исполнитель:

- повторно проверяет, что исходный путь находится внутри CapCut root;
- проверяет состояние процесса CapCut;
- делает полный backup исходной папки перед любым изменением;
- создаёт новый уникальный target, не используя имя исходника;
- копирует ресурсы и локализует абсолютные пути внутри клона;
- применяет только операции, разрешённые профилем и одобренные предпросмотром;
- зеркалит draft-файлы;
- по умолчанию запускает общий structural gate для клона; специализированный `capcut_chains_quality_gate.py` включается только профилем `chains-quality`;
- вызывает существующий `register_capcut_draft.py` только для клона и только после успешного gate;
- сохраняет итоговый отчёт.

Ни один путь к исходному draft не передаётся в операцию записи как target. Для target и backup используются отдельные проверенные абсолютные пути.

## Профили формата

Вместо нового одноразового скрипта на каждый проект используется профиль:

```json
{
  "profile_id": "chains-default-v1",
  "profile_version": 1,
  "track_roles": [
    {"role": "phrase_text", "type": "text", "name_patterns": ["english", "phrase"]},
    {"role": "translation_text", "type": "text", "name_patterns": ["russian", "translation"]},
    {"role": "phrase_audio", "type": "audio", "name_patterns": ["en", "ru", "voice"]}
  ],
  "unknown_element_policy": "ignore_and_report",
  "missing_known_element_policy": "fail_closed",
  "capcut_gate": "structural"
}
```

Профиль определяет роли и допустимые вариации. Он не содержит имя конкретного проекта. Новый проект можно добавить через окно и привязать к профилю после анализа, не переписывая код пайплайна.

## AI и генерация ассетов

Codex отвечает за текст, классификацию ролей и контент-план. Аудио, фоновые видео и другие ресурсы проходят через отдельные провайдеры. Каждый провайдер возвращает manifest с локальным путём, длительностью, source id и хэшем.

В Codex-сессии проекта не используется generic `OPENAI_API_KEY` из `.env.local`. Запускатель может иметь отдельный пользовательский провайдер для TTS или уже существующий генератор, но он запускается только явно, с отдельной конфигурацией и собственной проверкой расходов. В dry-run никакие платные генераторы не вызываются.

## Защита от поломки основного проекта

- исходник только читается до подтверждения;
- применение к исходнику отсутствует в интерфейсе первой версии;
- `--in-place` не добавляется;
- CapCut закрывается до клонирования и записи;
- backup делается до регистрации копии и до записи любых CapCut-метаданных;
- новый элемент никогда не используется автоматически;
- пропавший известный элемент останавливает применение;
- после записи проверяется равенство зеркальных draft-файлов;
- при провале gate приложение не открывает копию автоматически и сохраняет полный отчёт.

## Критерии приёмки

1. Окно запускается двойным кликом с рабочего стола.
2. Список проектов CapCut загружается без ручного ввода имени.
3. Анализ не меняет ни один CapCut-файл.
4. Повторный анализ неизменённого проекта не вызывает Codex.
5. Новый элемент отображается как `ignored_by_policy` и не попадает в operations.
6. Пропавший известный элемент блокирует создание копии.
7. Копия создаётся под новым именем и регистрируется отдельно.
8. Корневой draft и timeline mirror синхронны.
9. Исходный draft и его хэш после запуска совпадают с исходным снимком.
10. Отсутствующая авторизация Codex, невалидный ответ или провал quality gate приводят к понятной остановке, а не к частичной записи.
