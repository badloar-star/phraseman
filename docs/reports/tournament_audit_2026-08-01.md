## 💸 Стоимость Firestore — главная статья расходов

### C1. Ответ на ОДИН вопрос читает квитанции ВСЕХ игроков раунда

`functions/src/tournaments.ts:205-216`

```ts
function tournamentReceiptRefsForRound(roomRef, round, playerIds) {
  return playerIds.flatMap((playerId) => round.taskIds.map((taskId) => ({...})));
}
```

Это `players × tasksPerRound` ссылок, читаемых через `tx.getAll` в
`tournamentSubmitTaskAnswerTransaction` (`tournaments.ts:2638`).

| Параметр | Значение |
|---|---|
| Игроков в комнате | 16 |
| Заданий в раунде | 4 |
| Квитанций за один submit | 64 |
| + секреты, попытки, access | ~11 |
| **Чтений на один тап «ответить»** | **~75** |
| Ответов за турнир на игрока | 16 |
| Игроков | 16 |
| **Чтений на турнир (порядок)** | **~19 000** |

Это доминирующая статья расходов всей системы — на порядок дороже, чем
генерация пула заданий или создание комнаты.

**Причина:** место игрока пересчитывается по каждому заданию, а для этого
нужно видеть квитанции всех. Компромисс «честность против цены» сделан
осознанно, но цена растёт как O(игроки × задания).

### C2. Простановка TTL при закрытии комнаты — 100+ записей одной транзакцией

`functions/src/tournaments.ts:3507-3509` — `tx.set(secretRef, {expireAt},
{merge:true})` для КАЖДОГО документа подколлекции `taskSecrets` (задания +
квитанции + попытки speed-match).

### C3. Двойное чтение users/banned_users на каждый submit

`assertNotBanned` читает документы вне транзакции, затем
`assertTransactionalTournamentAccess` читает те же два документа внутри
транзакции. Два лишних чтения на каждый ответ каждого игрока.

### C4. Двойной пересчёт рангов внутри одной транзакции

`functions/src/tournaments.ts:2738` и `2780` — `canonicalTournamentReceiptRanks`
вызывается дважды за один submit. Удваивает O(игроки×задания) работу внутри
транзакции и увеличивает время её удержания (→ больше конфликтов, см. D1).

эмоциональная вершина режима — растянут почти на две секунды бездействия.

## ⚡️ Optimistic UI

### Что сделано хорошо (не трогать)

`tournament_round.tsx:617-681` `submitCurrentTaskAnswer` — образцовый паттерн:
локальная покраска до `await` через `answerFingerprint`, `activeTaskSubmissionRef`
как last-write-guard, идемпотентный ключ, ретрай того же payload, откат при
ошибке без ложного «неверно». Гонки и двойные тапы закрыты.

`tournament_season.tsx` — `peekSeasonStandings()` синхронно гидратирует первый
кадр.

### Где не хватает

**O1. `answerMatch` без fingerprint не красит карточку вообще**
`tournament_round.tsx:745-771` — когда `localAnswerVerdict` вернул `null`
(старые комнаты без `answerFingerprints`), ветка уходит в
`await waitForTournamentAnswerWindow(...)` → `await submitSpeedMatchAttempt(...)`
и красит `matchStatus` только после ответа сервера. Карточка остаётся `idle`
всё время сетевого round-trip.

**O2. Разбор раунда всегда грузится с нуля**
`tournament_review.tsx:62-69` — `loadRoundReview` без peek-гидратации: полный
скелетон при каждом заходе, даже повторном на тот же `roomId`. Контраст с
`tournament_season.tsx`, где приём уже применён.

**O3. Счётчик очков в таблице меняется скачком**
`tournament_table.tsx:347-352` — `<Animated.Text>{row.score}</Animated.Text>`
без пошаговой анимации, хотя на подиуме результатов готовый паттерн уже есть
(`shownGems`). Несогласованность внутри одного режима.

## 🟡 Ощущение игры

**F1. Реакции в лобби выключены флагом**
`app/tournament_client.ts:683` — `TOURNAMENT_REACTIONS_ENABLED = false`.
Живые эмодзи-реакции — единственное, что делало лобби «многопользовательским»
— отключены из-за фриза после нажатия. Проблема замаскирована, а не решена.

**F2. Выход из турнира — без тактильного отклика**
`tournament_round.tsx:950-958` — открытие модалки подтверждения выхода не
даёт haptic, тогда как аналогичное действие в лобби его имеет.

**F3. Edge-состояния анимированы беднее остального режима**
`components/tournament/TournamentEdgeState.tsx` — все состояния (offline,
cancelled, preseason, emptyPool) используют только `FadeIn.duration(200)`,
тогда как лобби использует `ZoomIn.springify()`, а результаты — `withSpring`.

**F4. Боты выдают себя формулой**
`functions/src/tournament_core.ts:2994` — скорость ответа бота жёстко
привязана к его винрейту. У людей скорость и точность так не коррелируют;
внимательный игрок со временем научится отличать ботов.

## ⚡ Ре-рендеры

**R1. Два независимых `setInterval(1000)` на экране раунда**
`tournament_client.ts:576` (общий countdown) + `tournament_round.tsx:530`
(таймер задания) — оба вызывают `setState` раз в секунду → минимум два
ре-рендера экрана в секунду вместо одного.

**R2. Немемоизированные вычисления в теле рендера**
`tournament_round.tsx:354-363` — `elapsedTaskIds` создаёт новый `Set` через
`.filter().map()` **на каждом рендере**, и от него зависит
`allQuestionsResolved` (`questions.every(...)`). Оба вне `useMemo`, при этом
экран перерисовывается раз в секунду по таймеру.

**R3. `makeStyles(P)` вызывается в каждом дочернем компоненте отдельно**
`tournament_round.tsx:1146, 1211, 1281, 1351` и `tournament_table.tsx:271` —
`StyleSheet.create` с сотнями полей выполняется по разу на каждый `OptionRow` /
`MatchCard` / `TableRow`. При 16 строках таблицы это 16 идентичных вызовов.
