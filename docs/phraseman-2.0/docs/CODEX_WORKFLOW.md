# Как работать в Codex без расхода лимита на весь проект сразу
Проверка официальной документации: 23.09.2026. [W1–W4]

## Модель для каждой задачи
`registries/models.json` и каждая `tasks/PM-NNN.md` содержат конкретные model/effort. L0: Luna/low — точная механическая правка. L1: Luna/high — ограниченный поиск, проверка, компоненты. S1: Sol/medium — обычный функциональный срез. S2: Sol/high — state, деньги, миграции, security и queue. A1: Astra/low — сложное межсистемное решение. Astra не назначена всем задачам и не нужна для смены отступа.

Это стартовая маршрутизация, а не доказанный минимум стоимости. Перед началом посмотреть фактический `/model` и доступность модели/effort; client/plan/rollout могут отличаться. В этом пакете нет данных о расходе недельного лимита владельца. Не использовать старые названия как гарантированно доступные. При отсутствии выбранной модели зафиксировать доступный аналог и причину, не переключать молча на самую дорогую.

## Ручной старт — надёжный основной путь
В интерактивном Codex выбрать `/model`, затем модель и effort. Дать постоянные правила + один task prompt. Для CLI пример из корня проекта (пути подставляются по фактическому размещению):
```sh
codex -m gpt-6-luna -c model_reasoning_effort='"high"'
```
На Windows PowerShell синтаксис передачи quoting может отличаться: интерактивный `/model` устраняет неоднозначность. Сверить `codex --help` своей версии. Указание модели в обычном тексте задачи не доказывает, что исполнитель реально переключился.

`tools/make_prompt.py PM-001` печатает конкретную задачу и модель. Сам скрипт не запускает Codex, не пишет в репозиторий и не вызывает API. Не запускает тысячу задач подряд.

## Сессии и агенты
Рекомендация: один write-исполнитель и до двух read-only reviewers в рамках сложного среза. Маленькая задача — исполнитель + один reviewer после локальных tests. Независимое чтение можно распараллелить; запись в одну рабочую копию последовательно. Требование одной канонической ветки не разрешает параллельным агентам затирать файлы друг друга.

В поддерживаемых локальных клиентах custom agents могут иметь model/effort. В `codex_examples/` предложены TOML-примеры по [W3–W4], они не установлены и не запускались. Сначала слить с существующей конфигурацией, проверить поддержку полей. Просить отдельную ревью-сессию можно вручную; автоматические отдельные видимые чаты в этой переписке не создавались.

Не грузить 76 КБ исходника и весь bundle задач в каждую маленькую сессию. Роль источников не исчезает: загрузить нужный фрагмент по source locator, при конфликте открыть полный исходник/решение. Бюджетный stop rule: после двух неудачных попыток устранить одну проблему остановиться, описать failure и поднять конкретную задачу на один уровень; не запускать бесконечные sweeps.

## Пакет задачи
BIBLE → CURRENT_STATE → DECISIONS → task → domain spec → actual files. Executor отдаёт impact до изменения, затем patch/tests/evidence. Reviewer получает тот же requirement и diff, но не пишет код. В конце tasks.json/worklog/handoff обновлены. `done` — только с доказательствами; `review` и `blocked` не маскируются процентом 100.

Шаблоны `prompts/` содержат старт, preflight, исполнение, ревью и handoff. Это управляющая документация, не заявление, что агенты уже поработали.
